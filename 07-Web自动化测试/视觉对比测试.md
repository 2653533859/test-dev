# 视觉对比测试（Visual Regression）

![[assets/visual-diff.svg]]
*图示：视觉对比的核心流程——首次生成 baseline 截图，之后每次截取当前图，做像素级对齐与差异计算，差异低于阈值则通过，超过则标记视觉回归并产出 diff 图供人工确认。*

> 功能测试能断言「按钮存在」，但断言不了「按钮歪了 5 像素、颜色从蓝变灰、被遮了半截」。视觉回归测试补的就是这最后 5% 的「看起来对不对」。

## 概念

### 视觉测试解决什么问题

功能断言（`assert el.is_visible()`、`assert text == "提交"`）验证的是**结构和逻辑**，验证不了**像素呈现**。以下这类问题功能测试完全看不见：

- 某次重构把 CSS 变量改了，全站主色从品牌蓝变成灰；
- 列表项高度写死，第 11 项被截断；
- 新组件把footer遮住了一半；
- 移动端某个断点下按钮溢出屏幕。

这些「看起来不对」的问题，靠 DOM 断言发现不了，只能靠**截图对比**。

### 三种对比粒度

| 粒度 | 方法 | 抗干扰能力 | 说明 |
|------|------|:---:|------|
| 像素级 | 逐像素比对 | 最敏感 | 1 个像素不同也会报，易误报 |
| 感知哈希 | 缩略图特征比对 | 中 | 抗轻微抗锯齿差异 |
| AI 感知 | 人眼相似度（Applitools） | 最强 | 忽略无关噪点，只报「人眼能看到的差异」 |

**纯像素级最易误报**——字体渲染、抗锯齿、时间戳、动画帧的微小差异都会触发。工业级方案都会加「动态区遮罩」和「感知阈值」来降噪。

### 动态内容是把双刃剑

页面上的日期、头像、广告、实时价格、随机推荐位，每次截图都不一样。直接全图 diff 会**永远失败**。解法：

1. **遮罩（mask）**：对比时把这些区域涂黑/裁剪掉不参与比对；
2. **固定随机源**：用 [[Playwright 网络拦截与 Mock]] 把动态接口返回固定值，让页面「可预期」；
3. **固定视口与字体**：无头模式下固定 `--window-size`、禁用动画。

## 用法

### 朴素方案：Playwright 截图 + 本地 diff

```python
from playwright.sync_api import sync_playwright
from pathlib import Path
import pytest

BASELINE = Path("snapshots/baseline_product.png")
CURRENT = Path("snapshots/current_product.png")

def test_visual_product():
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page(viewport={"width": 1280, "height": 800})
        page.goto("/product/A1")
        page.wait_for_load_state("networkidle")
        page.screenshot(path=str(CURRENT))

        if not BASELINE.exists():        # 首次运行：把当前图存为基线
            CURRENT.replace(BASELINE)
            return
        # 之后：用图像库做像素 diff
        diff = pixel_diff(BASELINE, CURRENT, threshold=0.01)
        assert diff.ratio < 0.01, f"视觉差异 {diff.ratio:.2%}，见 {diff.path}"
        browser.close()
```

`pixel_diff` 可以用 `Pillow` 自己写，或借助 `pytest-playwright` 自带的 `to_have_screenshot` 断言（它内部已处理基线生成与 diff）：

```python
def test_visual_product(page):
    page.goto("/product/A1")
    # 第一次自动生成基线，之后自动对比；可配 max_diff_pixels / threshold
    expect(page).to_have_screenshot("product.png", full_page=True)
```

### 遮罩动态区域

```python
# 把「价格/时间」这类动态区遮掉再截图
price = page.get_by_test_id("price")
price.screenshot(path="mask.png")         # 单独截小图无意义，演示定位
# 实际做法：对比前用 CSS 把动态区隐藏
page.add_style_tag(content="""
  [data-dynamic="clock"], .ad-banner { visibility: hidden !important; }
""")
page.screenshot(path="current.png")        # 动态区被隐藏，不参与比对
```

Playwright 的 `to_have_screenshot` 支持 `mask=[locator]` 参数，直接把指定元素在对比时涂掉，比手写 CSS 干净：

```python
expect(page).to_have_screenshot(
    "product.png",
    mask=[page.get_by_test_id("price"), page.locator(".ad-banner")],
)
```

### 云视觉平台（Percy / Applitools）

单机 diff 的痛点是：基线散落在本地、没有「人工确认」流程、跨机器基线管理乱。云方案解决这个：

```python
# Percy：截图上传，平台做 diff + 人工 review 工作流
from percy import snapshot
snapshot(page, name="product-page")
```

Applitools 用 AI 做「人眼感知」比对，能忽略无关噪点、只在「人眼真能看到差异」时报：

```python
from applitools.playwright import Eyes, Target
eyes = Eyes()
eyes.open(page, "MyApp", "Product page")
eyes.check("product", Target.window().ignore(page.get_by_test_id("price")))
eyes.close()
```

**云方案适合「有专职视觉 review 流程」的团队**；中小团队用 Playwright 自带的截图断言足够起步。

### CDP 截图的高级用法

视觉测试底层依赖浏览器的截图能力，Playwright 通过 CDP 实现。需要更精细控制时（如指定设备像素比、截取特定裁剪区），可直达 CDP：

```python
# 通过 CDP 设定设备像素比再截，保证不同机器截图一致
client = page.context.new_cdp_session(page)
client.send("Emulation.setDeviceMetricsOverride",
            {"width": 1280, "height": 800, "deviceScaleFactor": 1,
             "mobile": False})
```

固定 `deviceScaleFactor=1` 能避免高 DPI 机器和普通机器截图像素尺寸不一致导致的全量误报。

## 踩坑

1. **没固定视口和字体导致每次都飘**
   不同机器分辨率、系统字体不同，截图必然不同。无头模式固定 `--window-size`、用一致字体栈。

2. **动态内容没遮罩，全量误报**
   时间、头像、广告让截图永不重复。用 `mask` 或 Mock 接口固定动态区，见 [[Playwright 网络拦截与 Mock]]。

3. **deviceScaleFactor 不一致**
   高 DPI 屏截图尺寸翻倍，和基线对不上。CDP 固定 `deviceScaleFactor=1`。

4. **阈值设 0（要求 100% 一致）**
   抗锯齿、亚像素渲染的微小差异会触发误报。给合理阈值（如 0.1%~1%），或改用感知哈希/AI 比对。

5. **基线随意更新（「飘了就点接受」）**
   把 `git update` 基线当常规操作，会悄悄吞掉真实回归。基线更新必须走 review，且和代码改动一起提交。

6. **全页截图包含懒加载下方内容**
   `full_page=True` 会触发滚动，懒加载区域状态不稳定。对长页面要明确截图范围或用锚点定位。

7. **动画/过渡未停**
   截图瞬间元素在过渡中，位置不同。截图前 `wait_for_load_state("networkidle")` 并禁用 CSS 动画。

8. **把视觉测试当功能测试用**
   视觉测试只管「长相」，不验证交互逻辑。它应该和功能断言互补，而非替代。

## 面试怎么答

**Q：什么是视觉回归测试？什么时候用它？**
A：功能断言只能验证 DOM 结构和逻辑，验证不了像素呈现。视觉回归测试就是截图对比——首次跑生成 baseline 截图，之后每次截取当前图，做像素级对齐和差异计算，差异超过阈值就报「视觉回归」，并产出 diff 图供人工确认。它补的是功能测试看不见的那 5%：比如 CSS 变量改了导致全站变色、列表项被截断、新组件遮住 footer、某个断点下按钮溢出屏幕。但要注意它只管「长相」不验证交互，要和功能断言互补。

**Q：视觉测试最容易踩的坑是什么？**
A：首当其冲是动态内容——日期、头像、广告、实时价格每次都不一样，全图 diff 会永远失败。解法是遮罩动态区（Playwright 的 `mask` 参数），或者用网络 Mock 把动态接口返回固定值让页面可预期。其次是环境一致性：视口尺寸、系统字体、设备像素比（deviceScaleFactor）在不同机器上不一致，截图必然漂移，无头模式要固定窗口、CDP 固定 `deviceScaleFactor=1`。还有阈值不能设 0，抗锯齿的亚像素差异会误报，给合理阈值或改用 AI 感知比对。最后，基线更新必须走 review，不能「飘了就点接受」，否则会悄悄吞掉真实回归。

**Q：自己写 diff 和用云方案（Percy/Applitools）差在哪？**
A：单机 diff 的痛点是基线散落本地、没有人工确认流程、跨机器管理乱。云方案补的就是工作流：截图上传后平台做 diff，并带「人工 review / 接受基线」的流水线，适合有专职视觉 review 的团队。Applitools 更进一步用 AI 做「人眼感知」比对，能忽略无关噪点、只在人眼真能看到差异时报，大幅降低误报。中小团队用 Playwright 自带的 `to_have_screenshot` 断言起步就够，上规模再考虑云方案。
