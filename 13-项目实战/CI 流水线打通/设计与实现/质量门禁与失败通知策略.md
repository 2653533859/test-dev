# 质量门禁与失败通知策略

> 门禁要拦得住真问题又不能天天误伤，通知要让人一眼知道「是不是我的锅、该去哪看」。

## 概念

### 门禁的本质是「用自动化替代人工卡点」

没有门禁的 CI 只是个跑得勤快的定时任务——结果没人看，红了也能合。门禁把「测试结果」变成**合入的硬约束**。

但门禁最容易死于**误伤**。一条 flaky 用例拦住紧急修复，两三次之后团队的诉求就变成「把门禁关了」。所以设计门禁的顺序必须是：

```text
先治 flaky → 再上宽松门禁 → 数据稳定后收紧 → 按用例分级差异化
```

顺序反了，门禁一定活不过一个月。

### 门禁指标怎么选

| 指标 | 是否采用 | 理由 |
|------|----------|------|
| 用例通过率 | 采用（P0 100%，整体 ≥ 98%） | 最直接的质量信号 |
| P0 用例失败数 | 采用（> 0 直接阻断） | 核心链路不容妥协 |
| 新增代码覆盖率 | 采用（增量 ≥ 60%） | 只卡增量，存量欠债不追溯，否则永远达不了标 |
| 整体代码覆盖率 | **不采用** | 老项目基数低，卡了没人能过；且容易催生无断言的凑数用例 |
| flaky 数量 | 采用（告警不阻断） | 作为治理输入，不作为拦截条件 |

**只卡增量不卡存量**是让门禁能真正落地的关键设计。

### 通知的三个要求

1. **可定位**：说清哪个分支、哪个 commit、哪几条用例失败，而不是「构建失败」。
2. **可点击**：直达 Allure 报告，别让人自己去 Jenkins 里翻。
3. **可追责**：@ 到具体的人（触发者），群发等于没发。

还有一条反直觉的：**成功不要通知**。每天几十条绿色消息刷屏，结果就是整个群把机器人折叠，真失败时也没人看见。

## 用法

### 门禁脚本

```python
# scripts/gate.py
import argparse
import sys
import xml.etree.ElementTree as ET

def parse_junit(path: str) -> dict:
    root = ET.parse(path).getroot()
    suites = root.iter("testsuite") if root.tag == "testsuites" else [root]
    total = failures = errors = skipped = 0
    failed_cases = []
    for s in suites:
        total += int(s.get("tests", 0))
        failures += int(s.get("failures", 0))
        errors += int(s.get("errors", 0))
        skipped += int(s.get("skipped", 0))
        for case in s.iter("testcase"):
            node = case.find("failure") or case.find("error")
            if node is not None:
                failed_cases.append({
                    "name": f"{case.get('classname')}::{case.get('name')}",
                    "message": (node.get("message") or "")[:200],
                })
    executed = total - skipped
    pass_rate = (executed - failures - errors) / executed * 100 if executed else 0.0
    return {"total": total, "executed": executed, "pass_rate": pass_rate,
            "failed_cases": failed_cases}

def main():
    p = argparse.ArgumentParser()
    p.add_argument("--junit", required=True)
    p.add_argument("--min-pass-rate", type=float, default=100.0)
    p.add_argument("--max-p0-failures", type=int, default=0)
    args = p.parse_args()

    r = parse_junit(args.junit)
    p0_failed = [c for c in r["failed_cases"] if "p0" in c["name"].lower()]

    print(f"执行 {r['executed']} 条，通过率 {r['pass_rate']:.2f}%，P0 失败 {len(p0_failed)} 条")
    for c in r["failed_cases"][:10]:
        print(f"  FAIL {c['name']}: {c['message']}")

    blocked = False
    if r["pass_rate"] < args.min_pass_rate:
        print(f"::门禁不通过:: 通过率 {r['pass_rate']:.2f}% < {args.min_pass_rate}%")
        blocked = True
    if len(p0_failed) > args.max_p0_failures:
        print(f"::门禁不通过:: P0 失败 {len(p0_failed)} 条")
        blocked = True

    sys.exit(1 if blocked else 0)     # 退出码决定构建结论

if __name__ == "__main__":
    main()
```

**退出码是门禁的全部**。脚本打印得再漂亮，只要 `sys.exit(0)`，Jenkins 就认为通过。

### 通知卡片

```python
# scripts/notify.py
import os
import requests

TEMPLATE = """\
**{icon} {status}** · `{job}` #{build}
> 分支：{branch}　触发：{trigger}
> 用例：{executed} 条，通过率 **{pass_rate:.1f}%**，耗时 {duration}

{failed_block}
[查看 Allure 报告]({report_url})　[构建日志]({build_url})
"""

def build_failed_block(failed_cases: list[dict]) -> str:
    if not failed_cases:
        return ""
    lines = ["**失败用例（Top 3）**"]
    for c in failed_cases[:3]:
        lines.append(f"- `{c['name']}`\n  {c['message'][:80]}")
    if len(failed_cases) > 3:
        lines.append(f"- ……另有 {len(failed_cases) - 3} 条，详见报告")
    return "\n".join(lines) + "\n"

def notify(result: dict, status: str):
    if status == "SUCCESS" and os.getenv("BRANCH_NAME") != "main":
        return                                  # 成功不打扰，避免机器人被折叠
    content = TEMPLATE.format(
        icon="✅" if status == "SUCCESS" else "❌",
        status="构建通过" if status == "SUCCESS" else "构建失败",
        job=os.environ["JOB_NAME"], build=os.environ["BUILD_NUMBER"],
        branch=os.environ["BRANCH_NAME"], trigger=os.getenv("BUILD_USER", "webhook"),
        executed=result["executed"], pass_rate=result["pass_rate"],
        duration=result.get("duration", "-"),
        failed_block=build_failed_block(result["failed_cases"]),
        report_url=f"{os.environ['BUILD_URL']}allure/",
        build_url=f"{os.environ['BUILD_URL']}console",
    )
    requests.post(
        os.environ["WECOM_WEBHOOK"],            # webhook 走凭据注入，不写死
        json={"msgtype": "markdown",
              "markdown": {"content": content},
              "mentioned_list": [os.getenv("COMMIT_AUTHOR", "@all")]},
        timeout=10,
    )
```

### flaky 治理

```bash
# 从历史构建里统计不稳定用例，每周拉一次榜
pytest --reruns 1 --alluredir=allure-results
python scripts/flaky_report.py --allure allure-results --top 5
```

判定规则：**同一条用例在近 20 次构建中「重跑后转绿」达到 2 次以上**，即计入 flaky 榜单，当作 bug 单排期修。两个月后 flaky 率从 3.2% 降到 0.4%。

## 踩坑

1. **门禁上得太早，直接被要求关掉**：flaky 还有 3% 的时候就上了 100% 通过率门禁，开发天天被拦、查了又没问题。差点前功尽弃。**正确顺序**是先治稳定性、门禁先设成「只告警不阻断」跑两周看数据，再收紧。

2. **一刀切阈值**：所有用例一视同仁，一条边缘用例的抖动能拦住线上紧急修复。改成分级——P0 失败直接阻断，P2 失败只告警。**紧急发布还要留一个带审批记录的 skip 通道**，否则真出事时大家会绕过整个 CI 而不是绕过一条用例。

3. **重跑掩盖真 bug**：`--reruns 2` 之后一个真实的并发问题被「治好」了，上线才暴露。现在只重跑 1 次，且重跑成功的用例强制打 flaky 标记单独统计，不允许悄悄放过。

4. **通知只说「构建失败」**：没人点进去看，两周后集体折叠。加上失败用例名和错误摘要之后，响应速度明显变化——**信息密度决定了通知会不会被忽略**。

5. **成功也通知，机器人被折叠**：每天 30 多条绿色消息刷屏。改成成功静默（主干构建除外），失败才推。

6. **`mentioned_list` 用 `@all`**：等于没 @。要拿到 commit author 并映射到企微账号——这一步的映射表维护是个脏活，但值得做。

7. **Markdown 里的特殊字符炸掉卡片**：错误信息里带反引号或未闭合的 `**` 会让整条消息渲染错乱甚至发送失败。摘要统一截断并转义。

8. **webhook 地址硬编码**：泄露后被人拿去发垃圾消息。走 Jenkins 凭据注入。

9. **通知发送失败让整个构建变红**：`requests.post` 抛异常导致 post 步骤失败。通知逻辑必须包 try/except，通知挂了不该影响构建结论。

## 面试怎么答

**Q：你们的质量门禁是怎么设置的？**

A：分级设置。P0 核心用例失败直接阻断合入；整体通过率低于 98% 阻断；新增代码覆盖率低于 60% 告警。只卡增量不卡存量覆盖率——老项目基数低，卡整体谁都过不了，而且容易催生没有断言的凑数用例。门禁判定靠一个解析 JUnit XML 的脚本，用退出码决定构建结论。

**Q：门禁太严导致误伤怎么办？**

A：这个问题我们真踩过。第一版 100% 通过率门禁上得太早，当时 flaky 还有 3%，开发天天被拦又查不出问题，直接要求关掉。后来的做法是调整顺序：先花两个月治理 flaky，建立不稳定用例榜单当 bug 修，把 flaky 率压到 0.4%，同时门禁先设成只告警不阻断跑两周看数据，稳定后再收紧。另外做了分级和带审批的紧急通道。**门禁的阈值本质是管理问题不是技术问题**——定得再科学，只要天天误伤就一定会被关掉。

**Q：失败通知怎么设计才有效？**

A：三个要求：可定位（分支、commit、Top3 失败用例名和错误摘要）、可点击（直达 Allure 报告）、可追责（@ 到触发人而不是 @all）。还有一条反直觉的：成功不要通知。我们一开始成功也推，每天几十条绿色消息，两周后整个群把机器人折叠了，真失败也没人看见。

**Q：flaky 用例怎么治理？**

A：先量化再治理。规则是同一条用例近 20 次构建中「重跑后转绿」超过 2 次就进 flaky 榜单，每周拉 Top5 当 bug 单排期。根因大概三类：显式等待缺失或时序假设（占大头）、测试数据互相踩踏、依赖第三方沙箱不稳定。前两类必须修，第三类实在治不了的移出门禁放到夜间跑并人工看。关键是**不能用重跑掩盖**——我们吃过亏，一个真实的并发 bug 被重跑「治好」了，上线才暴露。
