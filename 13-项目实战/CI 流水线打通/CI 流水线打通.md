# CI 流水线打通

> 让自动化用例从「我本地跑了一下」变成「每次提交自动跑、失败自动 @ 到人、不修不许合」。

![[assets/ci-pipeline-stages.svg]]
*图示：流水线阶段编排与分层触发策略——PR 只跑冒烟保反馈速度，合入主干跑接口全量，夜间跑含 UI 的完整回归。*

![[assets/ci-trigger-notify-chain.svg]]
*图示：从 git push 到通知落地的完整链路与各段时延——成功静默打绿标，失败定向通知并阻断合入，形成闭环。*

## 背景与目标

### 改造前的状态

[[接口自动化框架落地]] 交付后，出现了一个很典型的尴尬局面：**框架有了，但没人跑**。

- 用例只在测试同学本地执行，跑一次要手动切环境、敲命令、等 22 分钟，实际频率是「提测前跑一次」。
- 开发提交代码后到测试发现问题，平均间隔**约半天**。等反馈回去，开发早已切到别的需求，捡回上下文的成本很高。
- 用例开始腐烂：后端改了字段没同步，两周后再跑，30 多条挂掉，没人知道是几号坏的，排查成本高到干脆放弃，形成「越不跑越坏、越坏越不敢跑」的死循环。

**结论**：自动化的价值不在于用例写了多少，而在于**执行频率**。不接 CI 的自动化，半衰期不超过一个月。

### 目标

| 目标项 | 改造前 | 目标值 |
|--------|--------|--------|
| 触发方式 | 人工手动 | 提交即触发，零人工介入 |
| PR 反馈时长 | 约半天 | ≤ 10 分钟 |
| 失败感知 | 靠人看 | 5 分钟内推送到责任人 |
| 用例腐烂 | 两周积累 30+ 失败 | 当天发现当天修，失败清零才允许合入 |
| 报告 | 本地 HTML，跑完就没 | 构建级归档，保留趋势 |

## 技术选型与架构

### Jenkins vs GitHub Actions

| 维度 | Jenkins（选定） | GitHub Actions |
|------|-----------------|----------------|
| 代码托管 | 公司内网 GitLab，可对接 | 代码不在 GitHub，用不了 |
| 内网访问 | agent 在内网，直连测试环境数据库 | 需自建 runner 打通内网，等于绕回 Jenkins |
| 生态 | Allure 插件、凭据管理、共享库成熟 | 生态更现代，但对本场景无优势 |
| 维护成本 | 要自己维护 master/agent | 托管，零运维 |

**决定性因素是内网**：测试环境和数据库都在内网，用例要连库做落库校验。GitHub Actions 的云端托管 runner 访问不了，自建 runner 又要解决同样的机器运维问题——那不如直接用团队已有的 Jenkins。

> 但 `code/` 里同时给了一份 GitHub Actions 配置。原因很实际：**开源项目和面试演示都用得上**，而且两者的编排思路是相通的，会 Jenkinsfile 迁 Actions 只是语法转换。

### 其他关键选型

- **Pipeline as Code（Jenkinsfile 进仓库）而非 GUI 配置**。GUI 配的 Job 改动无记录、无法 review、迁移靠截图。Jenkinsfile 跟着代码走，改流水线也要提 PR。
- **Docker 化执行环境**。改造初期最常见的失败原因不是用例问题，而是「agent 上 Python 版本不对 / 某个包没装 / 上个任务残留的浏览器进程」。用容器把环境固化，agent 只需要有 Docker。
- **企业微信机器人**而非邮件。邮件没人看，群消息能 @ 到人。
- **分层触发**（见流水线图）：PR 跑冒烟、合主干跑接口全量、夜间跑完整回归。这是让流水线活下来的核心设计，下面展开。

### 流水线阶段

```text
Checkout → Lint → 部署待测服务 → Test（并行分片） → Quality Gate → Report 归档
                                                              ↓
                                              post { always } 通知 + 清理
```

关键点是最后的 `post { always }`：**通知和清理必须无条件执行**。放在正常阶段里，一旦前面某步抛异常直接跳过，就会出现「构建挂了但群里没消息」——这种静默失败比不接 CI 更糟，因为大家以为没消息就是没问题。

## 关键实现与踩坑

### 难点一：PR 阶段跑全量，没人愿意用

第一版很朴素：任何提交都跑全部 320 个用例，40 分钟。上线一周后开发的反馈是「等不起」，开始在 commit message 里加 `[skip ci]`。**CI 被绕过，等于没有 CI**。

**解法**：按触发源分层，用 pytest 标记切分。

```python
# pytest.ini 注册标记，避免 PytestUnknownMarkWarning
# [pytest]
# markers =
#     smoke: 冒烟用例，PR 阶段执行
#     p0: 核心链路，失败直接判定构建失败

@pytest.mark.smoke
@pytest.mark.p0
def test_下单主流程(api_order, sku):
    ...
```

```groovy
// Jenkinsfile 片段：按触发源决定跑什么
script {
    def scope = env.CHANGE_ID ? "-m smoke"           // PR 构建
              : env.BRANCH_NAME == "main" ? "-m 'smoke or api'"
              : ""                                    // 定时构建：全量
    sh "pytest ${scope} -n 4 --alluredir=allure-results"
}
```

选冒烟用例的标准不是「随便挑 50 条」，而是**覆盖核心业务链路的最短路径**：登录、下单、支付、退款各一条主流程 + 各模块的健康检查。最终 48 条、4 分钟，PR 全链路 9 分钟，开发接受度立刻变了。

### 难点二：并发构建抢占同一套测试环境

**现象**：两个开发同时提 PR，两条流水线并行跑，双双失败。单独重跑又都过。

**根因**：两条流水线连的是同一套测试环境、同一个数据库。A 的用例造了商品又删掉，B 的用例正好在查它。

**试过的方案与取舍**：

| 方案 | 结论 |
|------|------|
| Jenkins `lock` 资源锁，串行排队 | 简单，但高峰期排队 30 分钟，退化成串行 |
| 每条流水线拉一套完整环境 | 最干净，但 6 个微服务 + 中间件，起一套要 8 分钟且吃内存，agent 扛不住 |
| **数据维度隔离**（选定） | 每次构建生成 `BUILD_TAG` 前缀，所有造的数据带上它，互不可见 |

数据隔离的落地方式：用例造数时统一拼构建标识，且查询类断言都带上这个前缀过滤。

```python
# conftest.py
@pytest.fixture(scope="session")
def data_prefix():
    """CI 里用构建号，本地用用户名+时间戳，保证任意两次执行的数据互不干扰。"""
    return os.getenv("BUILD_TAG", f"local-{getpass.getuser()}-{int(time.time())}")
```

这不是最完美的方案（共享环境的配置类改动仍会互相影响），但**是成本与收益平衡下的最优解**——面试讲这段时，讲清「为什么没选最干净的方案」比讲方案本身更有说服力。

### 难点三：flaky 用例把门禁变成「狼来了」

门禁定的是「通过率 100% 才允许合入」。上线两周后，平均每次构建有 1~3 条随机失败——网络抖动、第三方沙箱超时、异步任务延迟。开发被拦住又查不出问题，开始要求「把门禁关了」。

**解法是三步，不是简单加重跑**：

1. **区分真假失败**：`--reruns 1`，重跑成功的不算失败，但**打上 flaky 标记单独统计**，不允许悄悄放过。
2. **建立 flaky 榜单**：每周拉 Top5 不稳定用例，当作 bug 单排期修。两个月后 flaky 率从 3.2% 降到 0.4%。
3. **对确实无法稳定的用例（依赖第三方沙箱）单独标记 `xfail(strict=False)` 并移出门禁**，放到夜间跑，人工看。

```yaml
# 质量门禁判定（GitHub Actions 表达等价逻辑）
- name: 质量门禁
  run: |
    python scripts/gate.py \
      --junit reports/junit.xml \
      --min-pass-rate 100 \
      --allow-flaky 2
```

**关键认知**：门禁的阈值不是技术问题是管理问题。定 100% 但天天有假失败，结果一定是门禁被关掉；先治 flaky 再上严格门禁，顺序反了就前功尽弃。

### 其他踩过的坑

1. **Allure 趋势图每次构建都清零**：`allure generate` 需要把上次构建的 `history` 目录拷进本次 `allure-results`，否则没有历史趋势。Jenkins 的 Allure 插件会自动处理，但自建报告服务时要手动 `cp -r`。
2. **凭据硬编码进 Jenkinsfile**：早期把测试账号密码明文写在脚本里，提 PR 时被 review 拦下。改用 `withCredentials` 注入环境变量，且**注意 `sh "echo $PASSWORD"` 会把密码打进构建日志**（Jenkins 会做掩码，但拼接后可能漏），一律不打印。
3. **workspace 不清理导致磁盘打满**：`allure-results` 每次几十 MB，一个月后 agent 磁盘满了，报错却是莫名其妙的 `No space left on device` 出现在 pip 安装阶段。`post { always { cleanWs() } }` + 构建历史保留 30 次。
4. **Docker 容器时区是 UTC**：报告里时间全差 8 小时，且「断言创建时间是今天」的用例在北京时间早上 8 点前必挂。Dockerfile 里设 `ENV TZ=Asia/Shanghai`。
5. **pip 每次重装耗时 2 分钟**：把 `~/.cache/pip` 挂成 volume 或用 Actions 的 `cache` action，装依赖从 2 分钟降到 15 秒。
6. **定时任务用 `H 2 * * *` 而不是 `0 2 * * *`**：Jenkins 的 `H` 会把任务散列到时间窗内，避免几十个 Job 在整点同时启动把 master 压垮。
7. **构建失败但退出码是 0**：早期用 `sh "pytest ... || true"` 想让后面的报告步骤能执行，结果 Jenkins 认为构建成功，门禁完全失效。正确做法是保留退出码，把报告生成放在 `post` 里。

## 面试怎么讲

### 30 秒版本

> 我把团队的接口和 UI 自动化接进了 Jenkins，用 Pipeline as Code + Docker 化执行环境，做了分层触发：PR 跑 4 分钟冒烟、合主干跑接口全量、夜间跑完整回归，配质量门禁和企微定向通知。改造后开发拿到质量反馈的时间从平均半天降到 9 分钟，用例腐烂问题基本消失，自动化的实际执行频率从每周 1 次涨到每天 30 多次。

### 可量化收益

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 缺陷反馈时长（P50） | 约 4 小时（半个工作日） | 9 分钟（PR 冒烟全链路） |
| 自动化执行频率 | 约 1 次 / 周 | 32 次 / 天（含 PR、主干、定时） |
| 用例腐烂修复周期 | 两周积压 30+ 条 | 当天发现当天修，主干长期零失败 |
| 夜间全量回归 | 无 | 42 分钟，次日早会前出报告 |
| flaky 率 | —— | 3.2% → 0.4%（两个月治理） |
| 提测前人工回归 | 2 人天 / 版本 | 0.3 人天（只做探索性测试） |

### 最大的技术难点怎么讲

讲**并发构建的环境争抢**，因为它能体现工程权衡而不只是配置能力：

> 多条流水线并行跑同一套测试环境，数据互相踩踏，出现「单跑必过、并跑随机挂」。我评估了三个方案：Jenkins 资源锁串行排队，简单但高峰期排队 30 分钟，等于放弃了并行；每条流水线拉一套独立环境最干净，但 6 个微服务加中间件启动要 8 分钟、内存也扛不住；最后选了数据维度隔离——用构建号做数据前缀，各构建只能看到自己造的数据。这个方案不完美，配置类改动仍会互相影响，但它是在 agent 资源受限的前提下投入产出比最高的。后来资源扩容后，我们才把核心链路迁到了 Docker Compose 独立环境。

### 现在回头看的设计缺陷

1. **门禁阈值一刀切**。所有用例一视同仁地要求 100% 通过，导致一条边缘用例的 flaky 能拦住紧急修复。**更好的设计**：按用例分级设门禁——P0 失败直接阻断，P2 失败只告警不阻断。我们后来补了，但一开始就该这么设计。
2. **Jenkins 单点**。master 挂过一次，整个团队的 CI 停摆半天，且 Job 配置只在磁盘上没做备份。应该早点上 JCasC（Configuration as Code）把配置纳入版本管理，agent 也该多准备一台。
3. **只做了「测试的 CI」，没打通「构建的 CD」**。待测服务的镜像还是开发手动部署到测试环境，流水线里的「部署待测服务」其实是拉的固定 tag。真正的持续交付应该是「代码合入 → 构建镜像 → 部署 → 自动化验证」一条龙，我们只做了后半段。
4. **通知做了「失败必达」但没做「失败归因」**。机器人只推了失败用例名，开发还是要点进 Allure 一条条看。如果重做，会加一层错误聚类——把「连接超时」「断言不符」「元素找不到」自动分类，直接在卡片里告诉大家「这次 7 条失败里 6 条是环境问题」，能省掉大量无效排查。
5. **没有度量流水线本身**。流水线跑了多少次、平均耗时多少、哪个阶段最慢、失败构建里有多少是环境问题——这些数据当时全靠感觉。后来才知道应该把构建数据落到看板，否则「效能提升」这件事本身就不可度量。
