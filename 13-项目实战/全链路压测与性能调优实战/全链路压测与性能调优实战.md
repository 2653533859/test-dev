# 全链路压测与性能调优实战

> 针对大促秒杀与核心交易链路，搭建 TPS 目标 5000+ 的全链路压测模型，通过 Arthas、JVM 堆分析与 MySQL 执行计划定位并突破三大性能瓶颈，P99 响应耗时由 1200ms 优化至 180ms，吞吐量提升 4.2 倍。

## 背景与目标

### 业务背景与压测诉求

某电商核心交易平台即将迎来「双十一」大促狂欢活动，产品运营团队根据历史增长与投放预测，大促峰值每小时成交订单量将激增至 360 万单。历史大促中，系统曾出现过支付成功但未生成订单、商品秒杀时前台响应剧烈超时（HTTP 504 达到 8%）、数据库 CPU 满载（100%）报警等事故。

研发与测试团队必须在大促前完成全链路容量评估与压测调优，确保峰值流量下核心交易链路（浏览商品 -> 加入购物车 -> 结算页算费 -> 提交订单 -> 支付回调）系统稳定、资金不错账、限流熔断按预期生效。

### 性能指标与量化目标

根据「二八原则」与大促峰值预估模型推导：
- **峰值成交订单量**：360 万单 / 小时。
- **推导 TPS 公式**：峰值 80% 的订单在 20% 的集中时间内产生（约 720 秒）：
  $$\text{Peak TPS} = \frac{3,600,000 \times 0.8}{3,600 \times 0.2} = \frac{2,880,000}{720} = 4000\text{ TPS}$$
- 为预留系统安全余量（25% 突发洪峰 buffer），确定**下单链路峰值目标 TPS 为 5000**。

| 评估指标 | 压测调优前初测表现 | 考核目标基线 | 调优后终测成果 |
|---|---|---|---|
| **下单峰值 TPS** | 1,180 TPS（并发加不上去） | ≥ 5,000 TPS | **5,260 TPS**（达标） |
| **P95 响应时间 (RT)** | 850 ms | ≤ 200 ms | **95 ms** |
| **P99 响应时间 (RT)** | 1,280 ms（偶发超时） | ≤ 500 ms | **180 ms** |
| **错误率 (Error Rate)** | 6.8%（连接池满+超时） | < 0.1% | **0.002%**（无业务异常） |
| **服务端资源利用率** | CPU 98% 频繁抖动，频繁 Full GC | CPU < 75%, 内存平稳 | CPU 均值 68%，GC 停顿 < 35ms |

### 压测模型与流量配比

根据线上全链路监控埋点日志（SkyWalking / 日志清洗），还原真实用户行为链路模型：
1. **浏览商品详情（Read）**：占比 60%，预期 TPS 30,000。
2. **加入购物车（Write）**：占比 20%，预期 TPS 10,000。
3. **结算确认算费（Read+Compute）**：占比 10%，预期 TPS 5,000。
4. **提交订单并扣减库存（High-Write Transaction）**：占比 10%，**预期目标 TPS 5,000**。

采用 JMeter `Concurrency Thread Group` 配合 `Throughput Shaping Timer` 实现平滑阶梯加压，梯度为 500 -> 1500 -> 3000 -> 5000 TPS，每阶梯持续稳定保压 10 分钟。

## 关键瓶颈定位与调优实战

在逐步加压至 1500 并发线程时，系统 TPS 在 1180 左右出现瓶颈拐点，响应时间急剧陡增，通过自底向上的立体监控排查，揪出三大根本性瓶颈：

### 瓶颈一：JVM 频繁 Full GC 导致服务「世界冻结（STW）」

**现象**：
- TPS 出现周期性大幅下坠（从 1100 跌至 200，随后又恢复）；
- Grafana 看板监控到应用容器 JVM 老年代使用率在 3 分钟内迅速攀升至 98%，频繁触发 Full GC，单次 STW（Stop The World）停顿耗时高达 1.8 秒。

**定位过程**：
1. 通过 `jstat -gcutil <pid> 1000 10` 观察 GC 行为，发现老年代 `O` 持续高位不降，`FGC` 计数每隔 2 分钟增加 1 次。
2. 在压测期间使用 `jmap -dump:format=b,file=heap.hprof <pid>` 导出堆内存快照。
3. 通过 Eclipse MAT（Memory Analyzer Tool）分析 Dominator Tree，发现大对象占比最高的是一个自定义 `LocalCacheManager` 中的 `ConcurrentHashMap`，占用了近 1.4GB 内存。
4. 追查代码发现：促销券核销计算逻辑为了提速，研发写了一个本地内存缓存，缓存了用户领取的全量券明细，但该 Map **未设置过期驱逐策略与最大条目上限（LRU）**，在高并发压测期间，大量随机用户造数导致缓存无节制无限膨胀，迅速撑爆堆内存并不断溢出到老年代。

**调优方案**：
- 将无上限的 `ConcurrentHashMap` 重构为 Google Guava Cache（或 Caffeine Cache），显式限制 `maximumSize(20000)` 并配置基于访问时间的弱引用失效策略（`expireAfterWrite(5, TimeUnit.MINUTES)`）。
- 调整 JVM 启动参数，将默认垃圾收集器升级为 G1GC，分配足够大的堆空间与可控停顿目标：
  ```bash
  -Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=50 -XX:InitiatingHeapOccupancyPercent=45
  ```
- 优化后 Full GC 彻底归零，Young GC 耗时稳定在 20ms 以内，STW 抖动消除。

### 瓶颈二：大促优惠计算接口慢 SQL 与锁升级

**现象**：
- 数据库连接池（HikariCP）活跃连接数被打满（Active Connections = 100），后端日志大量报错 `ConnectionTimeoutException: App-HikariPool - Connection is not available, request timed out after 30000ms`。
- MySQL 实例 CPU 使用率直逼 99%，磁盘 IOPS 异常居高。

**定位过程**：
1. 开启 MySQL 慢查询日志（`long_query_time = 0.5`），在压测期间抓取到高频耗时 SQL：
   ```sql
   SELECT * FROM t_user_coupon WHERE user_id = 108284 AND status = 1 ORDER BY create_time DESC;
   ```
2. 单次查询耗时达 850ms。在测试库使用 `EXPLAIN` 分析执行计划：
   ```sql
   EXPLAIN SELECT * FROM t_user_coupon WHERE user_id = 108284 AND status = 1 ORDER BY create_time DESC;
   ```
   输出显示：`type = ALL`, `possible_keys = idx_status`, `key = NULL`, `rows = 1845000`, `Extra = Using where; Using filesort`。
3. 发现原因：该表数据量已达 800 万行，表上仅有一个单列索引 `idx_status`，MySQL 优化器评估过滤效率太低直接走全表扫描，并且还触发了内存与临时磁盘文件的排序（Using filesort）。

**调优方案**：
- 为该高频查询建立复合覆盖索引：
  ```sql
  ALTER TABLE t_user_coupon ADD INDEX idx_user_status_ctime(user_id, status, create_time);
  ```
- 再次执行 `EXPLAIN`，查询类型变为 `ref`，命中新建复合索引，扫描行数从 184 万行骤降为 3 行，去除了 filesort。
- 单条 SQL 查询耗时从 850ms 降至 1.2ms，HikariCP 连接池等待归零，数据库 CPU 使用率从 99% 回落至 42%。

### 瓶颈三：Redis 分布式锁粗粒度热点争抢

**现象**：
- 下单库存扣减接口吞吐量卡死在 2000 TPS 无法向上突破，应用线程池（Tomcat Worker Threads）大面积处于 `BLOCKED` 或 `TIMED_WAITING` 状态。

**定位过程**：
1. 压测中执行 `jstack -l <pid> > threads.tdump`，使用在线线程分析工具或 grep 分析，发现近 120 个线程阻塞在 `RedissonLock.tryLock()` 上。
2. 配合 Arthas `trace com.mall.order.service.impl.OrderServiceImpl扣减库存 '#cost > 200'` 动态追踪耗时：
   ```bash
   [arthas@1]$ trace com.mall.order.service.OrderServiceImpl deductStock '#cost > 100'
   ---ts=2026-09-28 14:32:01;thread_name=http-nio-8080-exec-45;id=8c;is_daemon=true;priority=5;TCCL=org.springframework.boot.loader.LaunchedURLClassLoader@5b6f74b1
       `---[245.89ms] com.mall.order.service.OrderServiceImpl:deductStock()
           +---[0.08ms] com.mall.order.util.ParamValidator:validate()
           +---[242.31ms] org.redisson.api.RLock:tryLock() # 严重阻塞点
           `---[3.12ms] com.mall.order.dao.StockDao:updateStock()
   ```
3. 根因分析：原本秒杀扣减库存逻辑采用了全表一把大锁：`lockKey = "mall:stock:lock"`。所有用户秒杀不同商品时，争抢同一个全局分布式锁，直接把多核并发执行串行化了。

**调优方案**：
- **锁粒度细化（Fine-grained Locking）**：将锁范围精确收敛至 SKU 级别，`lockKey = "mall:stock:lock:" + skuId`，不同商品的下单完全解耦互不影响。
- **结合 Redis Lua 脚本预扣库存**：对于超大流量秒杀爆款，避免直接加分布式锁落库，采用 Redis 单线程原子 Lua 脚本先在内存中校验并预扣库存（`stock = redis.call('get', KEYS[1]); if stock > 0 then redis.call('decr', KEYS[1]) ...`），异步再发送 RocketMQ 削峰落库。
- 调优后库存扣减接口耗时由 245ms 骤降至 6ms，成功冲上 5000+ TPS 目标。

## 面试怎么讲

### 30 秒版本

> 我在电商大促项目中主导了全链路压测与性能调优。针对大促峰值 360 万单/小时的需求，基于 2/8 原则推导出 5000 TPS 的下单链路考核基线。压测初期系统在 1180 TPS 时遇到严重瓶颈，我主导使用 JStack/JMap、MAT、Arthas 以及 MySQL 执行计划进行多维度深度排查，定位并彻底解决了本地缓存无界导致 Full GC STW、优惠券慢 SQL 拖垮连接池、以及分布式锁粗粒度串行争抢三大核心瓶颈。调优后系统平稳达成 5260 TPS，P99 耗时从 1280ms 缩短至 180ms，大促期间平稳零故障扛过峰值。

### 面试高频深度追问

1. **你们压测的数据是怎么造的？如何保证数据不污染生产或者测试环境？**
   - 采用「影子库/影子表（Shadow Table）」隔离机制：在测试压测环境（或类生产），通过在压测请求 Header 中打入标记 `t-stress: 1`。底层数据库中间件（如 ShardingSphere）自动识别标识，将压测产生的数据自动路由写入影子库（`t_order_shadow`），不影响基础表业务统计。
   - 压测造数利用 Python 造数脚本按线上画像构造了 50 万个白名单测试账号与 2 万个独立测试 SKU，避免缓存全穿透打偏。
2. **5000 TPS 是怎么算出来的？**
   - 结合大促预测核心峰值成交 360 万单，应用 80/20 原则（80% 交易发生在前 20% 时间，约 12 分钟内）：
     $$\text{TPS} = (3600000 \times 0.8) / (3600 \times 0.2) = 2880000 / 720 = 4000\text{ TPS}$$
   - 再额外考虑 25% 的突发安全缓冲区，因此基线定为 5000 TPS。
