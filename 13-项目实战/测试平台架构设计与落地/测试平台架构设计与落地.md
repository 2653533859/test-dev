# 测试平台架构设计与落地

> 从「分散在个人电脑里的脚本」走向「企业级协同质量效能中台」：基于 FastAPI + Vue3 + Celery + Docker 打造一站式自动化测试与资产管理平台，赋能业务测试无代码化编排，回归执行效率提升 65%。

## 背景与痛点

随着公司业务扩张至多条产品线，传统的「脚本化自动化测试」遇到了难以逾越的工程协同瓶颈：

1. **代码门槛阻碍业务测试赋能**：团队 80% 的业务测试人员不具备熟练的 Python/Java 编码能力，自动化框架成了少数测开的「自留地」，业务测试无法参与用例编写与维护；
2. **用例资产碎片化且难以共享**：用例散落在各个 Git 仓库甚至个人电脑中，存在大量重复造轮子（不同人写同一套登录鉴权与造数脚本），公共方法缺乏版本与权限治理；
3. **缺乏中心化调度与环境隔离**：每次发版需人工在本地终端或 Jenkins 手动触发执行，没有任务优先级排队与分布式并发调度能力，多任务同时跑时测试数据相互踩踏污染；
4. **质量度量缺失**：全量回归通过率、接口历史耗时趋势、Flaky 用例排行缺乏长期结构化存储，季度汇报无法向管理层量化呈现质量团队的投资回报率（ROI）。

## 架构设计与技术选型

### 技术选型对比

| 模块 | 选定方案 | 备选方案 | 选型权衡理由 |
| :--- | :--- | :--- | :--- |
| **后端框架** | **FastAPI** | Django / Flask | 原生异步 ASGI 高并发支持、基于 Pydantic 自动生成 OpenAPI 交互文档与强类型校验，相比 Django 更轻量现代 |
| **前端框架** | **Vue 3 + Element Plus** | React + AntD | 上手门槛低，Composition API 便于封装组件，团队全员可快速参与维护 |
| **任务调度** | **Celery + Redis** | APScheduler / Airflow | 成熟的分布式任务队列、原生支持任务优先级、ETA 延迟执行、广播与状态追踪，适配弹性 Worker 节点 |
| **执行沙箱** | **Docker 动态容器 Runner** | 本地多进程 | 环境彻底隔离，不同项目依赖的 Playwright/Chrome/Python 库版本互不冲突，单用例崩溃不影响宿主机 |
| **实时日志** | **WebSocket 双工通道** | HTTP 轮询 | 实现毫秒级测试控制台输出推流，大幅降低服务端并发轮询压力 |

### 系统四层分层架构

```text
       ┌────────────────────────────────────────────────────────┐
       │             展示与交互层 (Vue 3 + Pinia + Vite)           │
       │  • 用例树状编排  • 数据驱动参数池  • 实时日志控制台  • 质量看板 │
       └───────────────────────────┬────────────────────────────┘
                                   │ HTTP RESTful / WebSocket
                                   ▼
       ┌────────────────────────────────────────────────────────┐
       │             核心业务中台层 (FastAPI ASGI Engine)        │
       │  • 统一鉴权 (RBAC) • 项目空间隔离 • 用例版本快照 • 依赖拓扑解析 │
       └─────────────┬────────────────────────────┬─────────────┘
                     │ 发布调度指令               │ 异步结果与日志回写
                     ▼                            ▼
       ┌───────────────────────────┐  ┌─────────────────────────┐
       │  分布式任务调度 (Celery)   │  │   数据持久层            │
       │  • Priority 队列分发       │  │   • PostgreSQL (关系数据)│
       │  • 定时触发 (Beat)         │  │   • Redis (缓存与状态)   │
       │  • Worker 负载均衡         │  │   • MinIO (报告与附件)   │
       └─────────────┬─────────────┘  └─────────────────────────┘
                     │ 动态拉起容器
                     ▼
       ┌────────────────────────────────────────────────────────┐
       │          分布式执行 Runner 沙箱集群 (Docker Container)   │
       │  [Runner-01: pytest]  [Runner-02: playwright]  [Runner-N] │
       └────────────────────────────────────────────────────────┘
```

## 核心功能模块设计

### 1. 无代码化用例编排与多级数据驱动
- **用例资产树**：按「项目 $\rightarrow$ 模块 $\rightarrow$ 业务流 $\rightarrow$ 单步骤」四级结构组织。支持导入 Swagger/OpenAPI 规范一键生成接口用例；
- **前后置勾子链**：内置通用公共方法库（MD5/AES 加密、SQL 查询校验、全局变量提取、Redis 缓存预热），业务测试拖拽即可完成接口依赖拼装；
- **环境矩阵切换**：一套用例在测试（QA）、预发（Staging）、生产压测（Prod-Shadow）环境一键切换，动态映射对应的域名网关、DB 配置与账号密码。

### 2. 分布式任务分发与优先级队列
- 支持三种触发源：**手动单用例调试**、**定时任务轮询（Cron）**、**GitLab CI / 研发分支发布 Webhook 触发**；
- 采用 Celery Priority Queue，手动即时调试走高优先级 `debug_queue`，CI 批量回归走普通 `regression_queue`，实现高并发资源互不阻塞。

### 3. 实时测试控制台与断言现场留存
- Runner 执行期间，通过 Redis Pub/Sub 将标准输出与错误日志实时流式推送到 WebSocket 通道，前端终端组件（`xterm.js`）实时渲染高亮输出；
- 用例失败时，沙箱自动打包**前后上下文报文、数据库实际值快照、Playwright Trace 录像**上传至 MinIO 对象存储，并在平台用例详情页内嵌渲染。

## 量化收益与复盘

### 核心收益指标

| 评估维度 | 平台上线前 | 平台上线后 | 量化收益提升 |
| :--- | :--- | :--- | :--- |
| **自动化编写参与度** | 仅 3 名测开写代码 | 14 名业务测试全员参与 | 业务测试覆盖率提升 360% |
| **接口用例总规模** | 约 300 条本地脚本 | 2200+ 条平台受控用例 | 用例资产化率 100% |
| **发版回归耗时** | 手工点测 1.5 天 | 平台并发执行 18 分钟 | 发布效率提升 **97.5%** |
| **缺陷拦截成果** | 依赖线上发布后监控 | 平台准入门禁近半年拦截缺陷 127 个 | 拦截线上故障 14 起 |

### 踩坑与反思

1. **早期没有限制并发 Runner 导致测试环境服务被自身打崩**：
   - 早期多个项目同时触发回归，瞬间拉起 30 个并发进程，将测试环境 MySQL 连接池耗尽。
   - *优化*：引入全局并发令牌桶机制，限制单环境最大并行 Worker 数，超过限制进入排队状态；
2. **多租户数据混淆**：
   - 不同人员调试用例时共享了同一个测试账号，导致 token 被踢出。
   - *优化*：建立平台级「动态测试账号池」，Runner 执行前申请独占锁定账号，执行完毕自动释放。

## 面试怎么讲

**Q：你在项目中做过的测试平台，整体架构是怎样的？解决了团队什么核心问题？**
> 1. **背景痛点**：过去团队自动化脚本由测开独立编写，业务测试由于代码门槛无法参与，导致回归场景覆盖不足且脚本资产分散、调度缺乏统一治理。
> 2. **架构方案**：我主导搭建了基于 **FastAPI + Vue3 + Celery + Docker** 的分布式质量协同平台。架构上划分为展示层、业务中台层、分布式调度层与沙箱执行层。通过标准化组件库与前后置拖拽编排，让业务测试零代码完成复杂接口链组装。
> 3. **核心攻关点**：
>    - 采用 Celery + Redis 实现了基于优先级的任务调度与 Docker 隔离沙箱，解决了环境冲突；
>    - 引入 WebSocket 与 Redis Pub/Sub 实现了无延时的实时测试日志推流；
>    - 建立账号池独占锁定机制，破除了多任务并发执行时的数据互踩。
> 4. **业务产出**：平台上线后全团队 14 名业务测试全员接入，沉淀了 2200+ 核心接口用例，每次版本发布回归耗时从 1.5 天缩短至 18 分钟，半年内阻断了 120 余次严重缺陷流入生产。
