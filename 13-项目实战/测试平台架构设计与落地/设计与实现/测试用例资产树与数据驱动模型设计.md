# 测试用例资产树与数据驱动模型设计

> 解决测试平台用例管理的灵活性与扩展性难题：通过「多叉树结构」组织用例资产，结合「依赖拓扑排序」与「轻量表达式变量池」，实现零代码可视化编排与数据驱动无缝集成。

## 概念

### 传统平面用例结构的缺陷

初期的测试平台常将用例存储为平铺列表（如一张 `test_cases` 表），当用例规模达到数千条时暴露出严重缺陷：

1. **层级归属混乱**：缺乏模块化命名空间，无法反映大型业务系统的多级树状结构（系统 $\rightarrow$ 业务域 $\rightarrow$ 子模块 $\rightarrow$ 接口流）；
2. **前后置步骤无法复用**：如果 100 条用例都需要「登录获取 Token」和「查询商品 SKU」，传统的做法是在每条用例中重复复制这两步配置，一旦登录逻辑变动，需要人工修改 100 次；
3. **数据依赖硬编码**：缺乏统一的运行时数据总线，步骤与步骤之间无法动态传值。

### 资产树模型设计

平台采用「项目（Project） $\rightarrow$ 业务套件（TestSuite） $\rightarrow$ 场景用例（TestCase） $\rightarrow$ 测试步骤（Step）」四级资产模型：

```text
┌──────────────────────────────────────────────┐
│  项目空间: 电商中台业务线 (Project)           │
├──────────────────────────────────────────────┤
│  ├── 模块 A: 用户中心                        │
│  │   └── 套件: 登录鉴权链路 (TestSuite)      │
│  │       ├── 用例 1: 密码登录正常流程 (Case) │
│  │       └── 用例 2: 验证码登录异常边界      │
│  └── 模块 B: 交易中心                        │
│      └── 套件: 核心下单履约业务流            │
│          └── 用例: 领券下单支付全流程 (Case) │
│              ├── Step 1: 选品加入购物车      │
│              ├── Step 2: 领券并计算抵扣      │
│              ├── Step 3: 创建订单 (提取 ID)  │
│              └── Step 4: 模拟支付并断言状态   │
└──────────────────────────────────────────────┘
```

- **Step 为原子执行单元**：每个 Step 包含：请求协议（HTTP/gRPC）、URL/方法、Headers、Params/Body、前置脚本（Setup Hooks）、后置提取器（Extractors）、断言规则（Validators）；
- **参数池（Context Scope）分级继承**：全局环境变量 $\rightarrow$ 项目级配置 $\rightarrow$ 套件级入参 $\rightarrow$ 步骤局部变量（优先级逐层覆盖）。

## 用法

### 1. Pydantic 强类型用例执行模型

FastAPI 采用强类型 Pydantic Schema 进行用例结构定义与严格反序列化校验：

```python
from enum import Enum
from typing import Any, Dict, List, Optional
from pydantic import BaseModel, Field


class ComparatorEnum(str, Enum):
    EQUALS = "eq"
    NOT_EQUALS = "ne"
    CONTAINS = "contains"
    JSON_SCHEMA = "json_schema"


class ValidatorRule(BaseModel):
    """断言规则"""

    source: str = Field(
        ..., description="断言来源：status_code / body / headers"
    )
    selector: str = Field(..., description="JSONPath 或正则提取表达式")
    comparator: ComparatorEnum = Field(..., description="比对算子")
    expected: Any = Field(..., description="期望值（支持 ${var} 动态表达式）")


class ExtractorRule(BaseModel):
    """变量提取规则"""

    variable_name: str = Field(..., description="导出到上下文中的变量名")
    source: str = Field(..., description="提取来源：body / headers")
    expr: str = Field(..., description="JSONPath 表达式，如 $.data.order_id")


class TestStepSchema(BaseModel):
    """原子测试步骤"""

    step_id: int
    name: str
    method: str = "POST"
    url: str
    headers: Dict[str, str] = Field(default_factory=dict)
    body: Optional[Dict[str, Any]] = None
    extractors: List[ExtractorRule] = Field(default_factory=list)
    validators: List[ValidatorRule] = Field(default_factory=list)


class TestCaseSchema(BaseModel):
    """场景测试用例"""

    case_id: int
    name: str
    steps: List[TestStepSchema]
    dataset: List[Dict[str, Any]] = Field(
        default_factory=list, description="参数化数据驱动数据集"
    )
```

### 2. 动态依赖解析器（Dependency Resolver）

在步骤执行前，通过正则表达式扫描并解析上下文中的动态占位符（如 `${token}` 或 `${generate_random_phone()}`）：

```python
import re

VAR_PATTERN = re.compile(r"\$\{([a-zA-Z0-9_]+)\}")


def resolve_variables(target: Any, context: Dict[str, Any]) -> Any:
    """递归替换结构体中的动态变量占位符"""
    if isinstance(target, str):
        match = VAR_PATTERN.fullmatch(target.strip())
        if match:
            # 保持原始类型（如整型或布尔值）
            var_name = match.group(1)
            return context.get(var_name, target)
        # 字符串内嵌替换
        return VAR_PATTERN.sub(lambda m: str(context.get(m.group(1), "")), target)
    elif isinstance(target, dict):
        return {k: resolve_variables(v, context) for k, v in target.items()}
    elif isinstance(target, list):
        return [resolve_variables(item, context) for item in target]
    return target
```

## 踩坑

1. **循环依赖引发死锁崩溃**：
   - *案例*：步骤 A 的前置引用了套件 B，套件 B 内部又通过 Hook 引用了步骤 A，拓扑排序直接爆栈；
   - *解法*：在保存用例和执行前，建立依赖有向无环图（DAG），采用 **Kahn 算法进行拓扑检测**，一旦检测到环直接阻断保存并提示告警。
2. **大批量数据驱动时的 JSON 序列化性能瓶颈**：
   - *案例*：单用例挂载了 1000 行 CSV 参数化数据，读取和渲染 Pydantic 模型导致 API 响应长达 3 秒。
   - *解法*：分离「用例静态结构」与「参数化数据集」。数据集按分页流式加载，执行引擎在 Worker 节点侧就近读取数据文件，不在 Web API 主线程频繁全量序列化。

## 面试怎么答

**Q：在测试平台设计中，你们的测试用例模型是如何设计的？如何支持多步骤参数传递与数据驱动？**
> 1. **分层资产树设计**：我们采用了「项目 $\rightarrow$ 业务域 $\rightarrow$ 套件 $\rightarrow$ 步骤」的四级多叉树模型。将每个步骤设计为原子执行单元，包含独立的协议、前后置 Hook、变量提取器与断言列表。
> 2. **三级变量作用域与拓扑传参**：设计了全局环境、套件上下文与步骤局部三层数据总线。在步骤执行完成后，利用内置 JSONPath 提取器将动态值写回当前 Context；后续步骤在发送前通过递归占位符解析引擎，将 `${order_id}` 等表达式动态替换为上游提取值。
> 3. **数据驱动解耦**：用例结构与测试数据彻底分离。支持导入 Excel/YAML 格式的数据集挂载在用例节点上，执行引擎会自动根据数据集行数派生执行实例，实现低耦合的大规模数据驱动测试。
