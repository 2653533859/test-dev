# 三层断言与响应校验实现

> 断言写太松测不出问题，写太死后端加个字段就全线飘红——用「协议 / 结构 / 业务」三层把这两件事分开管。

## 概念

断言是接口用例的价值所在，但两种极端写法都很常见：

- **太松**：只 `assert resp.status_code == 200`。后端把金额算错了、状态返回错了，用例照样绿。这种用例的作用仅限于「证明服务没挂」。
- **太死**：`assert resp.json() == expected_full_body`。后端加一个 `traceId` 字段，200 多条用例集体变红，排查半天发现零个真 bug。**误报会摧毁团队对自动化的信任**，代价比漏报更大。

三层断言的思路是**按变化频率分层**，每层只管自己那段：

| 层级 | 校验对象 | 变化频率 | 失败意味着 |
|------|----------|----------|------------|
| 一层：协议 | HTTP 状态码、响应耗时 | 极低 | 服务挂了 / 路由错了 / 超时 |
| 二层：结构 | 字段是否存在、类型对不对（JSON Schema） | 低 | 接口契约被破坏（少字段、类型变了） |
| 三层：业务 | 具体字段值、数据库落库状态 | 高 | 业务逻辑算错了 |

**关键在于二层的宽严设定**：JSON Schema 默认 `additionalProperties: true`，即**允许新增字段但不允许缺字段或类型变更**。这一条就化解了「后端加字段导致全线飘红」的问题。

## 用法

### 统一断言入口

```python
# core/assertions.py
import jsonschema
from jsonpath_ng import parse as jsonpath_parse

def assert_status(resp, expected: int = 200):
    """一层：协议层。失败信息带上响应体，省一次复现。"""
    assert resp.status_code == expected, (
        f"状态码不符：期望 {expected}，实际 {resp.status_code}\n"
        f"URL: {resp.request.method} {resp.url}\n"
        f"响应: {resp.text[:500]}"
    )

def assert_schema(body: dict, schema_name: str):
    """二层：结构层。只校验必填字段与类型，允许新增字段。"""
    schema = load_schema(schema_name)
    try:
        jsonschema.validate(instance=body, schema=schema)
    except jsonschema.ValidationError as e:
        raise AssertionError(
            f"响应结构校验失败 [{schema_name}]\n"
            f"路径: {'.'.join(str(p) for p in e.absolute_path) or '<root>'}\n"
            f"原因: {e.message}"
        ) from None      # from None 屏蔽 jsonschema 冗长的内部栈

def assert_fields(body: dict, expected: dict):
    """三层：业务层。按 JSONPath 逐个字段比对，一次收集所有差异。"""
    errors = []
    for path, want in expected.items():
        expr = path if path.startswith("$") else f"$.{path}"
        matches = jsonpath_parse(expr).find(body)
        if not matches:
            errors.append(f"  {path}: 字段不存在")
            continue
        got = matches[0].value
        if not _equal(got, want):
            errors.append(f"  {path}: 期望 {want!r}，实际 {got!r}")
    if errors:
        raise AssertionError("业务字段校验失败：\n" + "\n".join(errors))
```

`assert_fields` **一次收集所有差异再抛**，而不是遇到第一个就失败。三个字段都错时，一次就能看全，不用改一个跑一次。

### 金额与浮点比较

```python
from decimal import Decimal

def _equal(got, want) -> bool:
    """金额类比较必须绕开浮点误差。"""
    if isinstance(want, float) or isinstance(got, float):
        return Decimal(str(got)) == Decimal(str(want))
    return got == want
```

`0.1 + 0.2 == 0.3` 是 `False`，`payAmount` 这种字段直接用 `==` 一定会偶发失败。转 `Decimal(str(x))`（注意必须经过 `str`，`Decimal(0.1)` 仍然带误差）。

### JSON Schema 示例

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["code", "data"],
  "additionalProperties": true,
  "properties": {
    "code": { "type": "integer" },
    "message": { "type": "string" },
    "data": {
      "type": "object",
      "required": ["orderId", "status", "payAmount"],
      "properties": {
        "orderId": { "type": "string", "minLength": 1 },
        "status": { "type": "string", "enum": ["WAIT_PAY", "PAID", "CANCELLED"] },
        "payAmount": { "type": "number", "minimum": 0 }
      }
    }
  }
}
```

`enum` 很有用：状态字段拼错或后端返回了未定义的新状态，这里就能拦住。

### 第四层：落库校验

接口返回成功不代表数据真写对了。异步下单、消息队列消费这类场景，必须查库确认。

```python
def test_下单后落库正确(api_order, db, sku):
    resp = api_order.create({"skuId": sku, "quantity": 2})
    assert_status(resp, 200)
    order_id = resp.json()["data"]["orderId"]

    # 异步写库：轮询而不是 sleep(3)
    row = wait_until(
        lambda: db.query_one("SELECT status, pay_amount FROM t_order WHERE order_no=%s", order_id),
        timeout=10, interval=0.5,
    )
    assert row["status"] == 0
    assert Decimal(str(row["pay_amount"])) == Decimal("198.00")
```

```python
def wait_until(fn, timeout=10, interval=0.5):
    """轮询直到 fn 返回真值，超时抛错。替代硬编码 sleep。"""
    deadline = time.time() + timeout
    last = None
    while time.time() < deadline:
        last = fn()
        if last:
            return last
        time.sleep(interval)
    raise AssertionError(f"等待超时（{timeout}s），最后一次结果：{last}")
```

`sleep(3)` 的问题是双向的：环境快时白等，环境慢时仍然失败。轮询才是正解。

## 踩坑

1. **全量比对响应体**：最初的写法，后端加 `traceId` 导致 200+ 用例集体飘红。改成分层校验后，新增字段不再误报。

2. **`assert resp.json()["data"]["orderId"]` 直接取值**：字段缺失时抛 `KeyError`，报错信息完全看不出是哪个接口哪条用例。统一走 JSONPath 并给出可读错误。

3. **断言失败信息里没有响应体**：只有 `AssertionError: assert 400 == 200`，还得手动复现一次才知道后端说了啥。所有断言函数都把 URL 和响应片段带上，本地和 CI 都直接可读。

4. **`pytest` 断言重写对自定义函数失效**：`assert_status` 里的 assert 语句在被 import 的模块中默认不会被重写，报错信息退化。在 `conftest.py` 顶部加 `pytest.register_assert_rewrite("core.assertions")`，且**必须在 import 该模块之前调用**。

5. **浮点金额偶发失败**：见上文 `Decimal` 处理。这个坑的隐蔽之处是它**偶发**——大多数金额没有精度问题，只有特定数值才触发。

6. **时间字段断言没考虑时区**：断言 `createTime` 是今天，在 UTC 的 Docker 容器里，北京时间早上 8 点前必挂。统一转成带时区的 `datetime` 再比，或者只断言「在最近 5 分钟内」这种相对区间。

7. **枚举值用中文描述断言**：`assert data["statusDesc"] == "待支付"`，产品改文案就挂。断言状态码 `status == "WAIT_PAY"` 而不是展示文案。

8. **Schema 写得太宽等于没写**：只写 `{"type": "object"}` 是自欺欺人。至少要有 `required` 和核心字段的 `type`。Schema 可以用工具从真实响应生成初稿再手工收紧，别从零手写。

9. **异步场景用 `sleep`**：见 `wait_until`。另外轮询的超时值要按环境最慢情况留余量，CI 上的容器通常比本地慢。

## 面试怎么答

**Q：接口自动化的断言你们怎么做？**

A：分三层，按变化频率分开管。第一层协议层，校验状态码和响应耗时；第二层结构层，用 JSON Schema 校验字段存在性和类型，关键是设成允许新增字段但不允许缺字段，这样后端加字段不会导致误报；第三层业务层，用 JSONPath 精确校验这条用例关心的具体字段值。涉及异步写库的场景还有第四层，轮询查数据库确认落库正确。

**Q：为什么不直接比对整个响应体？**

A：因为会产生大量误报。后端加一个 traceId 或者返回顺序变了，几百条用例集体飘红，实际零个 bug。误报比漏报更致命——它会消耗团队对自动化的信任，几次之后大家就默认「红的不用管」，自动化就废了。所以断言的原则是「只校验这条用例关心的东西」，通用的结构稳定性交给 Schema 兜底。

**Q：断言太松会怎样？怎么判断松紧合适？**

A：太松就是只测「服务活着」，金额算错、状态返回错都发现不了。判断标准我用的是**反向验证**：故意在被测服务里改一个字段值或状态，看用例能不能挂。挂不了说明这条断言是摆设。上线新用例时抽样做这个验证，比看覆盖率数字实在。

**Q：接口返回成功，但数据没写对，怎么发现？**

A：加落库校验。特别是涉及异步处理、消息队列的场景，接口立即返回成功只代表消息投递了。我们的做法是轮询查数据库，用 `wait_until` 这类工具而不是 `sleep`，因为 sleep 的时长永远不对——环境快时浪费时间，环境慢时照样失败。
