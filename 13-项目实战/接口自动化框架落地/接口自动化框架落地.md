# 接口自动化框架落地

> 把 320 个接口的手工回归，收敛成一条 22 分钟、可在 CI 里无人值守跑完的自动化回归。

![[assets/api-framework-layers.svg]]
*图示：框架五层架构与横切关注点——依赖只能自上而下，改接口字段只动接口对象层，换环境只动配置层，用例层不受影响。*

![[assets/api-datadriven-flow.svg]]
*图示：数据驱动执行流程——YAML 在收集期展开成 N 条独立用例，经变量渲染、发送、三层断言、提取回写形成串联闭环。*

## 背景与目标

### 改造前的状态

项目是一个电商后台服务，Java 微服务拆了 6 个模块，对外暴露约 320 个 HTTP 接口。测试团队 4 人，回归方式是 Postman collection 手点：

- 一轮完整回归 **2 人天**，其中大半时间花在「登录拿 token → 手动填订单号 → 复制粘贴到下一个请求」这类机械操作上。
- 发版频率从双周一次提升到**每周两次**后，回归时间根本排不进去，实际做法变成「只测本次改动相关的接口」，靠人脑判断影响范围。
- 结果就是漏测：半年内有 4 次线上问题，事后复盘都属于「改 A 模块，B 模块的老接口被连带改坏，但没人回归 B」。

### 目标

定的是可验收的量化目标，不是「提升测试效率」这种没法交差的说法：

| 目标项 | 改造前 | 目标值 |
|--------|--------|--------|
| 全量回归耗时 | 2 人天 | ≤ 30 分钟，且无人值守 |
| 核心接口覆盖 | 0 | ≥ 200 个（P0 + P1 全覆盖） |
| 冒烟反馈 | 无 | ≤ 5 分钟 |
| 新增一条用例成本 | 手工点 | ≤ 10 分钟，只写 YAML 不写代码 |
| 接入 CI | 无 | 提交即触发（详见 [[CI 流水线打通]]） |

最后一条最关键：**框架不接 CI 就是个玩具**。没人会每天手动敲 `pytest`，跑不起来的自动化三个月内必然腐烂。

## 技术选型与架构

### 选型对比与取舍

| 方案 | 优点 | 放弃原因 |
|------|------|----------|
| **pytest + requests**（选定） | 生态最全（xdist / allure / rerunfailures）、fixture 依赖注入优雅、断言原生可读 | —— |
| unittest | 标准库无依赖 | 参数化弱（要靠 `subTest` 或 ddt），无 fixture 作用域概念，插件生态几乎为零 |
| HttpRunner | YAML 即用例，上手快 | 复杂逻辑（加签、动态造数、落库校验）要写 debugtalk 插件，反而绕；框架黑盒，出问题难调 |
| Robot Framework | 关键字驱动，非技术同学能写 | 团队全是能写 Python 的，关键字层是纯负担；报告样式老旧；与 CI 集成不如 pytest 顺 |
| Postman + Newman | 零迁移成本 | 脚本用 JS 写在 GUI 里，无法有效 Code Review，无法复用 Python 侧的造数与数据库工具 |

**核心取舍**：放弃 HttpRunner 那种「纯配置化」的诱惑。配置化在简单 CRUD 场景确实爽，但这个项目有加签、有 token 双 token 刷新、有下单后要查库核对金额——这些用配置表达不了。最终选了「**代码为骨、数据为肉**」：结构用 Python 写死保证可调试，变化的部分（入参、期望值）放 YAML。

### 分层架构

见顶部架构图。五层职责：

```text
api-autotest/
├── tests/              ① 用例层：只调业务方法 + 断言
├── flows/              ② 业务流层：多接口串联（下单流程 = 登录→加购→结算→支付）
├── apis/               ③ 接口对象层：一个接口一个方法，收敛 url / method / 必填参数
├── core/               ④ 基础能力层：HttpClient、断言引擎、提取器、日志、加签、DB 工具
├── config/             ⑤ 配置层：env.yaml 多环境、敏感信息读环境变量
├── data/               ⑤ 数据层：YAML 用例数据、造数工厂
├── conftest.py         横切关注点注入（token、环境、清理、Allure 埋点）
└── pytest.ini          标记注册、日志格式、默认参数
```

**这个分层是抄 PO 模式的思路搬到接口侧**（参见 [[测试框架分层架构设计]]）：UI 自动化把「页面元素」封装成 Page Object，接口自动化就把「一个接口」封装成 API Object。

判断分层是否到位，只看一个标准：**接口新增一个必填字段时，要改几个文件**。分层前要改所有用到它的用例；分层后只改 `apis/` 里的一个方法。

### 关键技术点

- **数据驱动**：YAML → `pytest.mark.parametrize`，展开为 N 条独立 item。详见 [[YAML 用例结构与数据驱动实现]]。
- **鉴权**：session 级 fixture 拿 token，带过期自动刷新。详见 [[Token 鉴权与会话管理实现]]。
- **断言**：状态码 → JSON Schema → 业务字段/落库 三层递进。详见 [[三层断言与响应校验实现]]。
- **并行**：`pytest-xdist` 按用例分片，4 worker。
- **报告**：Allure，失败自动附请求体/响应体/耗时。

> 完整工程代码另开仓库维护，本目录 `code/` 只放能说明设计意图的最小示例。
> 仓库地址（占位）：`https://github.com/<your-name>/api-autotest`

## 关键实现与踩坑

### 难点一：并行执行下的 token 重复登录与竞态

**现象**：加上 `-n 4` 后，日志里出现 4 次登录，且偶发 401。

**定位**：`pytest-xdist` 的每个 worker 是**独立进程**，`scope="session"` 的 fixture 在**每个 worker 各执行一次**——这是最容易踩的 xdist 语义坑。4 个 worker 各自登录，而服务端登录接口是「**后登录的 token 会挤掉先前的 token**」（单点登录策略），于是先拿到 token 的 worker 全线 401。

**解法**：用文件锁 + 缓存，让 token 在整个测试会话中只生成一次、跨进程共享。

```python
# conftest.py（核心思路，完整版见 code/conftest.py）
import json, os, time
from pathlib import Path
from filelock import FileLock
import pytest

TOKEN_CACHE = Path(".pytest_cache/token.json")

@pytest.fixture(scope="session")
def token(env_conf):
    """跨 xdist worker 共享同一个 token，避免单点登录互相挤掉。"""
    TOKEN_CACHE.parent.mkdir(parents=True, exist_ok=True)
    with FileLock(str(TOKEN_CACHE) + ".lock"):     # 进程级互斥
        if TOKEN_CACHE.exists():
            cached = json.loads(TOKEN_CACHE.read_text(encoding="utf-8"))
            if cached["expire_at"] - time.time() > 300:   # 留 5 分钟余量
                return cached["token"]
        tk, ttl = do_login(env_conf["user"], os.environ["TEST_PASSWORD"])
        TOKEN_CACHE.write_text(
            json.dumps({"token": tk, "expire_at": time.time() + ttl}),
            encoding="utf-8",
        )
        return tk
```

**留 5 分钟余量**这一点是二次踩坑补的：一开始判断条件是 `expire_at > time.time()`，结果全量回归跑 22 分钟，中途 token 到期，后半段集体 401。

### 难点二：测试数据互相踩踏，失败「随机」出现

**现象**：单跑必过，全量跑随机挂 2~5 条，每次挂的还不一样。

**根因**：多条用例共用同一个「测试商品 SKU-1001」，一条用例把库存扣成 0，另一条断言「下单成功」就挂了。串行时按顺序执行看不出来，并行后彻底暴露。

**解法**：三条规则，缺一不可。

1. **用例自带数据**：每条用例在 fixture 里现造自己的商品/用户，不依赖环境里的存量数据。
2. **唯一化**：所有可能冲突的字段拼上 `worker_id + 时间戳 + 随机后缀`。
3. **后置清理**：`yield` 之后删掉造的数据，且清理逻辑必须能容忍「数据已被删」。

```python
@pytest.fixture
def sku(api_goods, worker_id):
    """每条用例独享一个商品，用完即删。"""
    code = f"SKU-{worker_id}-{int(time.time() * 1000)}"
    goods_id = api_goods.create(code=code, stock=999)["data"]["id"]
    yield goods_id
    try:
        api_goods.delete(goods_id)
    except Exception as e:            # 清理失败不能让用例结果变红
        logger.warning("清理商品 %s 失败：%s", goods_id, e)
```

清理放在 `yield` 后而不是用例末尾，**用例断言失败时清理照样执行**——这是 fixture 相比 setUp/tearDown 之外最实用的一点。

### 难点三：断言写太死，接口一改全线飘红

第一版断言是拿整个响应体和期望 JSON 做全量比对。后果：后端加了个 `traceId` 字段，200 多条用例全红，实际一个 bug 都没有。

**改法**：断言只校验「**这条用例关心的字段**」，结构稳定性交给 JSON Schema 兜底。

```python
# 差：全量比对，任何新增字段都误报
assert resp.json() == expected

# 好：分层校验，各管一段
assert_status(resp, 200)                       # 一层：协议
assert_schema(resp.json(), "order_create")     # 二层：结构（新增字段不报错，缺字段/类型变了才报）
assert_fields(resp.json(), {                   # 三层：业务
    "data.status": "WAIT_PAY",
    "data.payAmount": 99.00,
})
```

### 其他踩过的坑

1. **`requests` 默认不带超时**：某次测试环境 hang 住，一条用例卡了 40 分钟直到 CI 超时。所有请求统一在 `HttpClient` 里强制 `timeout=(5, 15)`（连接 5s、读取 15s）。
2. **金额断言用 `float` 相等**：`0.1 + 0.2 != 0.3`，改用 `Decimal(str(x))` 或 `pytest.approx`。
3. **`Session` 跨用例复用导致 Cookie 污染**：一条用例登录后的 Cookie 带进了「未登录访问应返回 401」的用例，导致该用例永远通过（假阳性）。改成鉴权态与游客态用两个独立 Session。
4. **`rerunfailures` 掩盖真问题**：为治 flaky 加了自动重跑 2 次，结果一个真实的并发 bug 被重跑「治好」了，上线才暴露。现在重跑只跑 1 次，且**重跑成功的用例会打 flaky 标记单独统计**，每周复盘 Top5。
5. **YAML 里 `on`、`yes`、`no` 被解析成布尔值**：`status: on` 读出来是 `True`。YAML 1.1 的历史包袱，字符串一律加引号。
6. **Allure 中文用例名乱码**：`parametrize` 的 `ids` 直接传中文在部分环境显示成 `\u4e0b\u5355`，需在 `pytest.ini` 里配 `disable_test_id_escaping_and_forfeit_all_rights_to_community_support = True`（名字很劝退但确实是官方选项）。
7. **测试环境和线上时区不一致**：断言「创建时间是今天」在 UTC 环境下凌晨必挂。所有时间断言统一转成带时区的 `datetime` 再比。

## 面试怎么讲

### 30 秒版本

> 我主导落地了一套接口自动化框架，pytest + requests + YAML 数据驱动 + Allure，五层分层架构。覆盖了 218 个核心接口，把原来 2 人天的手工回归压到 22 分钟无人值守，接进 Jenkins 做到提交即触发。上线半年拦截了 37 个回归缺陷，其中 3 个是 P0 级别的资损问题。

### 可量化收益

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 全量回归耗时 | 2 人天（约 16 人时） | 22 分钟（4 worker 并行，无人值守） |
| 冒烟耗时 | —— | 4 分钟（48 条 P0 用例） |
| 接口覆盖 | 0 | 218 / 320，P0 与 P1 全覆盖（68%） |
| 半年拦截缺陷 | —— | 37 个，其中 P0 3 个（含一个优惠券可叠加的资损问题） |
| 线上回归类事故 | 半年 4 次 | 半年 1 次（且属于未覆盖的第三方回调场景） |
| 新增用例成本 | —— | 存量接口加一组数据约 5 分钟，新接口约 20 分钟 |

> 数字要能自圆其说。面试官一定会追问「22 分钟怎么算的」「37 个缺陷怎么统计的」——答案是 CI 构建历史 + 缺陷单上打的 `发现阶段=自动化回归` 标签，讲得出来源才可信。

### 最大的技术难点怎么讲

讲**并行化**，因为它同时牵扯 fixture 作用域、进程模型、数据隔离三块知识，最能展开：

> 串行跑 80 分钟，压不进 CI，必须并行。上 `pytest-xdist` 之后暴露了两个问题：一是 session 级 fixture 在每个 worker 都会执行一次，4 个 worker 各自登录，而服务端是单点登录策略，后登录的把先前的 token 挤掉，导致大面积 401——用文件锁加缓存让 token 全局只生成一次解决；二是用例共用测试数据互相踩踏，出现「单跑必过、并跑随机挂」的假失败——改成每条用例用 fixture 现造数据、字段拼 worker_id 唯一化、yield 后置清理。治完这两个，并行通过率从 82% 回到 100%，耗时从 80 分钟降到 22 分钟。

### 现在回头看的设计缺陷

这一段千万别说「没有缺陷」，讲得出反思才显得是真做过：

1. **YAML 表达能力不够，后期出现了「配置里写逻辑」的坏味道**。有人为了表达「A 字段存在时才校验 B」，在 YAML 里塞了 `if` 表达式并用 `eval` 解析——既不安全也难调试。**正确做法**：复杂逻辑就该回到 Python 用例里写，配置只放纯数据。当初应该定一条硬规则：YAML 里出现任何表达式即视为设计信号，说明这条用例不适合数据驱动。
2. **没做契约测试，覆盖是「事后追赶」**。框架永远滞后于后端改接口，只能靠回归失败被动发现。如果重来会引入 Pact 或至少让后端产出 OpenAPI 并做 schema diff 门禁，在接口变更时就拦住（参见 [[独立 Mock 服务与契约测试]]）。
3. **用例与测试环境强绑定**，依赖了一个共享的测试环境。环境一挂全线红，噪音大。更好的做法是核心链路配一套 Docker Compose 拉起的独立环境，或对不稳定的第三方依赖做 Mock。
4. **只做了「结果对不对」，没做「性能会不会退化」**。框架里其实已经记录了每个请求的耗时，但没利用起来。低成本改进：把响应耗时也纳入断言（P95 超过阈值告警），相当于顺手拿到一套接口级性能基线。
5. **覆盖率统计口径偏乐观**。「218/320」算的是接口数，但一个接口只测了正常流也算「已覆盖」。更诚实的口径应该按「接口 × 关键场景」算，真实覆盖率大概只有 40%。这个数字自己心里要有底，面试被追问时主动说出来反而加分。
