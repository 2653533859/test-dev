# 移动端核心性能指标采集与基线度量

> 摆脱昂贵繁琐的商业性能 APM 依赖：基于 Android 原生 `dumpsys` 与 Linux 底层指标采集，构建自动化版本间流畅度（FPS）、内存泄漏（PSS）与冷启动耗时的性能基线对比看板。

## 概念

### 为什么性能专项必须纳入版本发布门禁

很多团队在功能测试通过后直接发版，结果上线后大量用户反馈「新版本滑动好卡」、「用 10 分钟手机发烫」：

1. **隐蔽性极高**：研发引入了一张未压缩的 4K 大图，或者在滑动列表事件回调里执行了复杂 JSON 解析，功能层面没有任何 Bug，但界面掉帧极其严重；
2. **渐进式内存泄漏**：单次手工点测看不到明显变化，但用户连续刷 20 分钟后，Java 堆内存持续单调暴增最终抛出 `OutOfMemoryError` 闪退；
3. **性能基线缺乏比对**：没有自动化记录每个版本的冷启动耗时曲线，性能劣化是逐渐累积的（从 800ms 慢慢滑坡到 2000ms），等到感知时已积重难返。

### 四大核心性能指标度量模型

```text
┌─────────────────┬───────────────────────┬────────────────────────────────────┐
│ 性能指标        │ 底层采集命令          │ 判定与质量红线标准                 │
├─────────────────┼───────────────────────┼────────────────────────────────────┤
│ 丢帧率 (Jank)   │ dumpsys gfxinfo       │ 渲染单帧耗时 > 16.6ms (60Hz) 算丢帧│
│                 │                       │ 要求核心列表 Jank Rate ≤ 2.5%      │
├─────────────────┼───────────────────────┼────────────────────────────────────┤
│ 内存泄漏 (PSS)  │ dumpsys meminfo       │ 记录初始 PSS 与循环 10 次业务后 PSS │
│                 │                       │ 回归基准线，若增量 > 30MB 告警     │
├─────────────────┼───────────────────────┼────────────────────────────────────┤
│ 冷启动耗时      │ am start -W           │ 测量 TotalTime (应用进程到界面首帧) │
│                 │                       │ 基准要求: 冷启动 ≤ 1200ms          │
├─────────────────┼───────────────────────┼────────────────────────────────────┤
│ CPU 与发热      │ top -n 1 / dumpsys    │ 静态闲置 CPU ≤ 2%，密集滑动 ≤ 35%  │
└─────────────────┴───────────────────────┴────────────────────────────────────┘
```

## 用法

### 1. 流畅度与掉帧率（Jank Rate）采集解析

```python
import subprocess


def measure_fps_jank(serial: str, package_name: str) -> dict:
    """采集 Android 渲染丢帧率与卡顿次数"""
    # 1. 先重置帧历史计数
    subprocess.run(
        f"adb -s {serial} shell dumpsys gfxinfo {package_name} reset",
        shell=True,
    )

    # ... 此时让 Appium 或自动化脚本在页面上匀速滑动 10 秒 ...

    # 2. 导出详细渲染帧耗时统计
    out = subprocess.check_output(
        f"adb -s {serial} shell dumpsys gfxinfo {package_name}",
        shell=True,
        text=True,
    )

    total_frames = 0
    jank_frames = 0

    for line in out.splitlines():
        if "Total frames rendered:" in line:
            total_frames = int(line.split(":")[1].strip())
        elif "Janky frames:" in line and "(" in line:
            # 提取形如: Janky frames: 12 (2.40%)
            jank_str = line.split(":")[1].split("(")[0].strip()
            jank_frames = int(jank_str)

    jank_rate = (jank_frames / total_frames * 100) if total_frames > 0 else 0.0
    return {
        "total_frames": total_frames,
        "jank_frames": jank_frames,
        "jank_rate": round(jank_rate, 2),
    }
```

### 2. 内存泄漏（PSS Slope）连续监测与斜率拟合

```python
import re
import subprocess
import time


def get_process_pss(serial: str, package_name: str) -> int:
    """获取当前进程实际物理占用内存 TOTAL PSS (单位: KB)"""
    out = subprocess.check_output(
        f"adb -s {serial} shell dumpsys meminfo {package_name}",
        shell=True,
        text=True,
    )
    for line in out.splitlines():
        if "TOTAL PSS:" in line:
            # 匹配行: TOTAL PSS: 145620 TOTAL RSS: ...
            match = re.search(r"TOTAL\s+PSS:\s+(\d+)", line)
            if match:
                return int(match.group(1))
    return 0


def detect_memory_leak(serial: str, package_name: str, rounds: int = 5) -> bool:
    """进入退出页面 5 次，探测内存是否单调递增不回落"""
    pss_records = []
    for _ in range(rounds):
        # 触发垃圾回收 GC
        subprocess.run(
            f"adb -s {serial} shell kill -10 $(adb -s {serial} shell pidof {package_name})",
            shell=True,
        )
        time.sleep(2)
        pss_records.append(get_process_pss(serial, package_name) / 1024.0)  # MB

    # 比较最终轮次与初始轮次的净增差值
    growth = pss_records[-1] - pss_records[0]
    print(f"内存连续监测轨迹: {pss_records} MB, 净增: {growth:.2f} MB")
    return growth > 30.0  # 净增超过 30MB 判定可能存在内存泄漏
```

## 踩坑

1. **机身发热降频导致性能测试失真**：
   - *案例*：跑了 30 分钟压测后机身很烫，此时测启动耗时和 FPS 暴跌 50%。测试人员提了性能 Bug，开发本地复现完全正常。
   - *解法*：手机高温会触发 SoC 严重温控降频（Thermal Throttling）。性能基线测试**必须在冷机状态下执行**（机身温度 $\le 36^\circ\text{C}$），各轮次测试之间强制冷却 5 分钟。
2. **`TotalTime` 与用户真实可交互时间（TTI）偏差**：
   - *案例*：`am start -W` 测出启动时间只有 600ms，但手机屏幕上此时才刚画出骨架屏，网络图片和接口数据还没出来，用户依然无法点击。
   - *解法*：以系统打出的 `ActivityTaskManager: Displayed` 日志作为冷启动基准，结合高速摄像机（或录屏逐帧拆解），以「界面出现首个首屏商品卡片且可点击」为最终 TTI 结束点。

## 面试怎么答

**Q：移动端 App 的性能指标（流畅度、内存、启动时间）你们是怎么自动采集与设立门禁的？**
> 1. **标准化无侵入采集工具链**：我们在真机流水线中，通过封装 Android 原生 `dumpsys` 命令进行静默采集。利用 `dumpsys gfxinfo` 提取每帧渲染毫秒数推算丢帧率（Jank Rate）；利用 `dumpsys meminfo` 提取物理内存占用（PSS）；利用 `am start -W` 测量冷热启动耗时。
> 2. **建立版本性能基线与趋势比对**：将性能数据统一打上 Git Commit Hash、构建号与机型标签落入 InfluxDB。在 Grafana 建立版本横向对比大盘，设定严格发布门禁：
>    - 核心商品列表页 Jank Rate 必须 $\le 2.5\%$；
>    - 连续 10 次进入退出核心页面并触发 GC 后，内存净增长不得超过 20MB；
>    - 旗舰机冷启动耗时阈值控制在 1000ms 以内，若出现明显劣化趋势则流水线阻断排查。
