# 水平越权与垂直越权测试

> OWASP 2021 排名第一的风险。扫描器扫不出来，因为工具不知道「谁该看什么数据」——这恰恰是测试人员最大的优势。

![[assets/broken-access-control.svg]]
*图示：水平越权改的是「资源标识」（同角色跨数据），垂直越权改的是「访问的接口」（低权限调高权限功能）；两者缺失的校验点不同，但根子都是「身份来自请求参数而不是服务端会话」。*

## 概念

### 两种越权的判别方法

一句话区分：**看你改的是什么**。

- 改**数据 id**（订单号、用户 id、文件 id）还能拿到 → **水平越权**，同一角色越到了别人的数据。
- 改**接口路径 / 功能入口**（普通接口换成管理接口）还能执行 → **垂直越权**，低权限角色越到了高权限功能。

还有一类容易被忽略的：

- **未授权访问**：连登录都不需要，直接访问接口就返回数据。本质是垂直越权的极端情况（从「游客」越到「用户」）。
- **越权改数据**：能读别人的数据危害是泄露，能改/删别人的数据危害就是篡改，定级要更高。测试时读和写要分别验证。

### IDOR 是什么

水平越权在英文语境里最常见的叫法是 **IDOR（Insecure Direct Object Reference，不安全的直接对象引用）**：接口直接把数据库主键之类的内部标识暴露给客户端，且没有校验调用者是否有权访问该对象。

面试里说出 IDOR 这个词是加分的，因为它更精确地指出了问题在「直接对象引用 + 缺访问校验」这两点上。

### 根本原因永远是同一条

**服务端把「身份」这个应该从会话推导的东西，从请求参数里取了。**

```python
# 危险：userId 来自请求参数，等于让客户端自己声明自己是谁
def get_orders():
    user_id = request.args.get("userId")
    return db.query("SELECT * FROM orders WHERE user_id = %s", (user_id,))

# 正确：身份来自服务端会话，参数只用于筛选，且查询条件带上归属
def get_orders():
    user_id = current_session.user_id          # 不可被客户端篡改
    order_id = request.args.get("orderId")
    return db.query(
        "SELECT * FROM orders WHERE id = %s AND user_id = %s",
        (order_id, user_id),                   # 归属校验直接下推到 SQL
    )
```

**把归属条件写进 SQL 的 WHERE 里**，比先查出来再用 `if` 判断更不容易漏（后者一旦忘了 if，数据就出去了）。

### 为什么扫描器扫不出来

扫描器能判断「这个响应是不是 200」，但判断不了「这条订单本来该不该给这个人看」。这需要业务语义：谁是所有者、什么角色能做什么操作、哪些数据是共享的。

这个信息只存在于两个地方：需求文档，和测试人员的脑子里。所以**越权测试是测试人员不可替代的部分**，也是简历上最能体现安全能力的一项。

### 常被忽略的越权入口

```text
批量接口       ids=[1001,1002]，只校验了第一个或一个都没校验
导出接口       导出条件里塞入别人的部门 id / 时间范围
搜索接口       搜索词能命中他人数据，或返回列表未按归属过滤
文件下载       /download?path=xxx 或 /file/{fileId}
消息/通知      通知 id 可遍历，能读到发给别人的内容
状态流转       直接调「审批通过」接口跳过前置节点
第三方回调     支付回调、Webhook 无签名校验，可伪造
移动端专用接口 因为「用户看不到」而漏了鉴权
GraphQL        单个入口下的字段级权限最容易漏
```

## 用法

### 测前准备：两套账号、一张权限矩阵

越权测试是**唯一一类必须提前准备账号的安全测试**。开工前先在测试环境里准备好：

```text
账号 A   普通用户，有一批自己的业务数据（订单、地址、附件）
账号 B   同角色普通用户，也有自己的数据 —— 用来测水平越权
账号 C   管理员/运营，能访问后台功能 —— 用来测垂直越权
游客     未登录状态（无痕窗口或清空 Cookie）—— 用来测未授权访问
```

再把接口按「谁能访问」列成一张矩阵，这张表本身就是测试用例集：

| 接口 | 游客 | 用户 A | 用户 B（他人数据） | 管理员 C |
|------|------|--------|-------------------|----------|
| `GET /api/orders/{id}`（A 的订单） | 401 | 200 | **403** | 200 |
| `POST /api/orders/{id}/cancel` | 401 | 200 | **403** | 200 |
| `GET /api/admin/users` | 401 | **403** | 403 | 200 |
| `POST /api/admin/user/{id}/disable` | 401 | **403** | 403 | 200 |

加粗的格子就是漏洞点：**期望 403，实际返回 200 就是越权**。

### 四步测法：换凭证不换请求

核心手法一句话：**保持请求内容不变，只换身份凭证；或保持凭证不变，只换资源标识**。用 Burp Repeater 操作最顺手（详见 [[Burp Suite 抓包改包工作流]]）。

```text
步骤 1  用账号 A 登录，正常操作一遍，抓到目标请求（含 A 的 Cookie / Token）
步骤 2  用账号 B 登录，记下 B 的凭证，并记下 B 名下某条数据的 id
步骤 3  把 A 的请求发到 Repeater，做两组替换：
        组① 凭证换成 B 的，id 保持 A 的 → 测「B 能否读 A 的数据」
        组② 凭证保持 A 的，id 换成 B 的 → 测「A 能否读 B 的数据」
步骤 4  比对响应：返回 200 且内容是他人数据 = 越权；返回 403/404 且无数据 = 通过
```

判定时**不要只看状态码**，有三种迷惑情况：

```text
返回 200 但 data 为 null        → 通过（服务端过滤了，只是没用 403）
返回 200 且 data 是自己的数据    → 通过（服务端忽略了参数，用会话身份查的）
返回 500 报错栈里带出他人字段    → 仍算问题（信息泄露），单独提一条
```

### 越权测试用例设计模板

写用例时按「资源类型 × 操作类型」铺开，别只测查询：

```text
读（Read）    查详情、列表、导出、下载附件、打印预览
写（Update）  改资料、改地址、改状态、改备注
删（Delete）  删除、批量删除、撤回
执（Execute） 审批、支付、退款、发起流程、重发通知
```

一条标准用例长这样：

```text
用例 ID    SEC-BAC-012
标题       用户 B 可越权取消用户 A 的订单（水平越权 · 写操作）
前置       测试环境；账号 A(uid=1001)、B(uid=1002) 均为普通用户；A 有订单 SO202607310001
步骤       1. 用 B 登录，抓取任意「取消订单」请求
           2. Repeater 中将订单号替换为 A 的 SO202607310001，其余不变，发送
预期       403，且 A 的订单状态不变
实际       200 {"code":0}，A 的订单状态变为「已取消」
影响       任意用户可取消他人订单，属数据篡改，定级高
```

**写操作的越权一定要回到 A 的账号里确认数据真的被改了**，只看响应码容易误判（有些接口返回成功但实际没生效）。

### 半自动化：用脚本批量遍历

矩阵格子多的时候手点不过来。测试环境里可以写个小脚本跑「同一批 id × 不同凭证」：

```python
import requests

BASE = "http://test-app.internal.com"          # 仅指向自有测试环境
TOKENS = {"A": "token-of-a", "B": "token-of-b", "guest": ""}
# A 名下的资源 id，从 A 的列表接口里取出来，不做无意义的全量遍历
A_ORDER_IDS = ["SO202607310001", "SO202607310002"]

def probe(role, token, order_id):
    headers = {"Authorization": f"Bearer {token}"} if token else {}
    r = requests.get(f"{BASE}/api/orders/{order_id}", headers=headers, timeout=5)
    leaked = r.status_code == 200 and '"orderNo"' in r.text
    return {"role": role, "id": order_id, "status": r.status_code, "leaked": leaked}

for oid in A_ORDER_IDS:
    for role, tk in TOKENS.items():
        if role == "A":
            continue                            # A 访问自己的资源是正常的，作基线
        res = probe(role, tk, oid)
        if res["leaked"]:
            print("疑似越权:", res)
```

两个纪律：**只遍历自己账号名下已知的 id**，不要写 `range(1, 100000)` 去撞库式扫描——那既超出授权范围，也会在测试环境里造出一堆脏数据和告警。跑之前和环境负责人打招呼。

### 修复方案：把校验做在唯一入口

```python
# 方案一：统一鉴权切面（推荐）——在框架层拦，业务代码不用各自记得写
def require_owner(resource_loader):
    def decorator(fn):
        def wrapper(*args, **kwargs):
            obj = resource_loader(kwargs["res_id"])
            if obj is None or obj.owner_id != current_session.user_id:
                abort(403)                       # 不存在与无权限返回同样的结果
            return fn(*args, **kwargs)
        return wrapper
    return decorator

@app.get("/api/orders/<res_id>")
@require_owner(lambda i: Order.get(i))
def get_order(res_id):
    ...

# 方案二：数据层强制带归属条件——查询本身就查不出别人的数据
def get_order(res_id):
    return db.query(
        "SELECT * FROM orders WHERE id = %s AND user_id = %s",
        (res_id, current_session.user_id),
    )
```

垂直越权则靠**「默认拒绝」的角色校验**：路由表里没显式声明允许角色的接口，一律拒绝，而不是「没声明就放行」。

补充一条常见但错误的做法：**用不可预测的 id（UUID / 雪花号）代替自增 id**。这只是把「遍历」变难了，属于纵深防御的加固项，**不能代替权限校验**——id 只要泄露一次（分享链接、日志、客服截图）就照样能越权。面试里说清这点很加分。

## 踩坑

1. **只测了「读」没测「写」**。列表和详情做了过滤，取消、修改、删除接口却漏了。写操作危害更大，必须单独覆盖。
2. **只看状态码不看响应体**。有的实现返回 200 + 空数据（其实是安全的），有的返回 200 + 他人数据（漏洞）。必须核对响应内容。
3. **忽略「不存在」与「无权限」的区分**。服务端对他人资源返回 403、对不存在资源返回 404，攻击者就能靠状态码差异枚举出「哪些 id 是存在的」。修复建议里应写明：**两种情况返回同样的结果**。
4. **只测了主流程接口**。批量接口 `ids=[...]` 常常只校验第一个元素；导出、搜索、消息通知这类接口最容易漏。
5. **前端隐藏了按钮就以为没问题**。后台菜单不显示 ≠ 接口不能调。垂直越权必须直接打接口，不能只在 UI 上点。
6. **多租户场景漏掉租户维度**。SaaS 系统要同时校验 `tenant_id` 和 `user_id`，只校验后者会出现跨租户读数据。
7. **改完只回归了发现问题的那个接口**。越权通常是「一类」问题而不是「一个」问题——同一个开发写的同批接口大概率都有。发现一处后要横向扫同模块所有接口。
8. **在生产环境验证**。越权测试必然要读/改他人数据，**只能在测试环境用自己准备的账号做**。生产上哪怕只读一条别人的数据，也已经构成违规。
9. **测完不清理数据**。写操作类用例改了 B 的数据要记得还原，否则后续用例会因为脏数据而误判。

## 面试怎么答

**Q：水平越权和垂直越权的区别是什么？怎么测？**

A：区别看你改的是什么。改数据 id 还能访问到，是水平越权，同一角色越到了别人的数据；改接口路径、用普通账号调管理接口还能执行，是垂直越权，低权限越到了高权限功能。测法是「保持请求不变，只换身份凭证；或保持凭证不变，只换资源 id」。具体我会准备两个同角色账号 A、B 和一个管理员账号，先列一张权限矩阵——行是接口、列是角色，格子里写期望状态码，然后用 Burp Repeater 逐格验证。判定时不只看状态码，还要看响应体里是不是真的返回了他人数据；如果是写操作，还要回到对方账号里确认数据真的被改了。所有验证都在测试环境用自己准备的账号做。

**Q：为什么扫描器扫不出越权漏洞？**

A：因为扫描器只能判断「这个响应是不是 200」，判断不了「这条数据本来该不该给这个人看」。这个判断需要业务语义——谁是所有者、什么角色能做什么操作、哪些数据是共享的，这些信息只存在于需求文档和测试人员脑子里，不在 HTTP 报文里。所以越权和支付逻辑这类漏洞是测试人员相比工具不可替代的部分，也是 OWASP 把「失效的访问控制」排到 2021 年第一位的原因之一——它太依赖人工，最容易漏。

**Q：越权漏洞怎么修？换成 UUID 当 id 行不行？**

A：根因永远是「服务端把身份从请求参数里取，而不是从会话推导」，所以修复的核心是身份只能来自服务端会话。落地上有两种做法：一是在框架层做统一鉴权切面，进业务逻辑之前先校验资源归属，避免依赖每个开发自觉写 if；二是把归属条件下推到 SQL 的 where 里，查询本身就查不出别人的数据，比先查出来再判断更不容易漏。垂直越权则要做成「默认拒绝」——路由没显式声明允许角色就一律拒绝。至于换 UUID，那只是让 id 猜不到，属于纵深防御的加固项，不能代替权限校验：id 一旦通过分享链接、日志或者客服截图泄露，照样能越权。

**Q：一个订单详情接口，你会设计哪些越权用例？**

A：我会按「资源 × 操作 × 身份」三个维度铺。身份维度是游客、同角色他人、低权限角色、管理员四种；操作维度是查详情、查列表、导出、修改、取消、删除、退款；资源维度除了自己的订单，还要覆盖已删除订单、其他租户的订单、其他门店的订单。重点关注几个容易漏的入口：批量接口只校验了第一个 id、导出接口的筛选条件里能塞别人的部门 id、搜索接口返回列表没按归属过滤、还有移动端专用接口——因为「用户看不到」经常整个漏了鉴权。另外「不存在」和「无权限」要返回同样的结果，否则能靠状态码差异枚举出有效 id。
