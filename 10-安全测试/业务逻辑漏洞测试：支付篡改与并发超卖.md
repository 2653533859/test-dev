# 业务逻辑漏洞测试：支付篡改与并发超卖

> 这类漏洞代码本身没有语法层面的错误，扫描器一条都扫不出来。它们只能靠「懂业务的人」发现——这正是测试开发相比安全工具最大的优势区。

![[assets/race-condition-order.svg]]
*图示：两个并发请求都读到 `stock=1` 并各自通过判断，造成超卖；根因是「检查」与「扣减」之间存在窗口期，右侧给出三类修复思路——数据库原子扣减、唯一索引兜底、分布式锁或幂等号。*

## 概念

### 逻辑漏洞为什么扫描器扫不出来

注入、XSS 这类漏洞有固定的**模式特征**：一个引号、一个尖括号就能触发异常响应，工具靠模式匹配就能发现。

逻辑漏洞没有模式。`price=0.01` 是一个语法完全合法的请求，返回 200 也完全正常——它是不是漏洞，取决于「这个商品原价是多少」「金额该不该由客户端传」。这些信息只存在于需求文档和测试人员脑子里。

一句话总结：**扫描器判断「响应对不对」，测试人员判断「业务对不对」**。

### 两条主线：参数篡改与并发时序

逻辑漏洞的花样很多，但归纳下来主要是两条线：

```text
参数篡改  客户端能改的东西，服务端信了
          金额、数量、折扣、积分、状态、收货地址、优惠券 id、用户 id

并发时序  服务端的「检查」与「执行」不是原子的
          超卖、重复领券、重复提交、余额扣两次、并发退款
```

第一条线的根因是**信任边界画错了**——凡是从客户端来的数据都是不可信输入，价格必须回后端查，权限必须从会话推导。

第二条线的根因是**「检查 - 执行」窗口期（TOCTOU，Time of Check to Time of Use）**——先 `SELECT` 判断库存够，再 `UPDATE` 扣减，两步之间任何并发请求都能挤进来。

### 下单链路上的信任边界

一条典型的电商下单链路，把「谁说了算」标出来就能看到所有风险点：

```text
选商品   商品 id            客户端传 → 服务端查价格            ← 价格绝不能由客户端传
填数量   quantity           客户端传 → 服务端校验上下限        ← 负数、0、超大值
用优惠券 couponId           客户端传 → 服务端校验归属+有效期+门槛
算总价   totalAmount        ★ 服务端算，客户端传的一律忽略
提交订单 orderId            服务端生成
调起支付 payAmount          ★ 从订单表读，不从请求取
支付回调 第三方通知          ★ 必须验签 + 核对金额 + 幂等
发货     状态流转            ★ 校验前置状态，不能跳步
```

标 ★ 的四个点是支付类漏洞的高发区，**「金额从哪来」和「回调可不可信」这两个问题能问倒很多开发**。

## 用法

### 一、金额与参数篡改测试

用 Burp Repeater 逐个参数改（工作流见 [[Burp Suite 抓包改包工作流]]），全程在测试环境用自己的测试账号和测试商品。

**用例组 A：金额直接篡改**

```text
A1  totalAmount 100.00 → 0.01      期望：服务端以自己算出的金额为准，或直接报错
A2  totalAmount → 0                期望：拒绝
A3  totalAmount → -1               期望：拒绝（负数可能变成「充值」）
A4  payAmount 与订单金额不一致       期望：支付网关或服务端校验拦截
A5  币种 currency CNY → USD         期望：拒绝或按正确汇率
```

**用例组 B：数量与边界**

```text
B1  quantity → 0                   期望：拒绝
B2  quantity → -1                  期望：拒绝（负数 × 单价 = 负总价 → 可能退钱）
B3  quantity → 99999999            期望：库存校验拦截
B4  quantity → 1.5（小数）          期望：类型校验拦截
B5  quantity → 2147483648（越界）   期望：拒绝，不能整型溢出变负数
```

**用例组 C：优惠券与积分**

```text
C1  用别人的优惠券 id                期望：403（这其实是水平越权）
C2  同一张券在两个订单里同时使用      期望：只有一单成功
C3  已使用/已过期的券再用            期望：拒绝
C4  不满门槛（满 100 减 20，只买 50）  期望：拒绝
C5  多张互斥券叠加                   期望：按规则拒绝
C6  积分抵扣数 > 账户积分余额         期望：拒绝
C7  取消订单后券是否正确退回          期望：退回且不能重复退
```

**用例组 D：状态流转跳步**

```text
D1  未支付直接调「发货」接口          期望：拒绝
D2  已完成订单再调「取消」接口         期望：拒绝
D3  已退款订单再调一次退款             期望：拒绝（重复退款是真金白银的损失）
D4  跳过审批中间节点直接调「审批通过」  期望：拒绝
```

状态流转类问题写用例时，把状态机画出来，**每条「不该存在的边」都是一条用例**。

**用例组 E：支付回调伪造（重点）**

```text
E1  不带签名直接调回调接口             期望：拒绝
E2  签名字段随意填                     期望：拒绝
E3  签名正确但金额改大                 期望：拒绝（应核对订单实付金额）
E4  同一条成功回调重放 5 次             期望：只生效一次，不重复发货/加余额
E5  用测试环境订单号 + 已知回调格式伪造   期望：拒绝
```

E4 的幂等性是最容易漏的：第三方支付平台**本来就会重发通知**，不做幂等在生产上迟早出事。

### 二、并发测试：怎么把偶发问题稳定复现

思路是**压缩窗口期的相对占比**：把库存/额度调到 1，然后让多个请求尽可能同时到达。

```python
import threading
import requests

BASE = "http://test-app.internal.com"          # 仅测试环境
TOKEN = "<自己账号的 token>"
ACTIVITY_ID = 9001                             # 测试活动，库存已由测试数据初始化为 1

barrier = threading.Barrier(10)                # 关键：让 10 个线程同时起跑
results = []
lock = threading.Lock()

def grab():
    s = requests.Session()
    barrier.wait()                             # 全部就位后一起发
    r = s.post(f"{BASE}/api/activity/grab",
               json={"activityId": ACTIVITY_ID},
               headers={"Authorization": f"Bearer {TOKEN}"}, timeout=10)
    with lock:
        results.append((r.status_code, r.json().get("code")))

ts = [threading.Thread(target=grab) for _ in range(10)]
for t in ts:
    t.start()
for t in ts:
    t.join()

success = sum(1 for _, code in results if code == 0)
print(f"成功数 = {success}，期望 = 1")
assert success == 1, "存在超卖 / 重复领取"
```

`threading.Barrier` 是这段脚本的关键——不用它，10 个线程会因为创建开销而错开几十毫秒，正好错过窗口期，测出来「没问题」。

**光看响应还不够，必须核对数据**：

```sql
-- 断言 1：库存不能为负
SELECT stock FROM activity_stock WHERE activity_id = 9001;

-- 断言 2：中奖/领取记录数不能超过库存
SELECT COUNT(*) FROM activity_record WHERE activity_id = 9001;

-- 断言 3：同一用户不能重复领取
SELECT user_id, COUNT(*) AS cnt
FROM activity_record
WHERE activity_id = 9001
GROUP BY user_id
HAVING cnt > 1;

-- 断言 4：账实一致（发出去的 = 扣掉的）
SELECT (SELECT COUNT(*) FROM activity_record WHERE activity_id = 9001) AS issued,
       (SELECT total - stock FROM activity_stock WHERE activity_id = 9001) AS deducted;
```

**这类缺陷是概率性的，跑一次通过不代表没问题。** 固定做法是同一场景跑 5～10 轮，每轮重置数据并核对上面四条断言。

### 三、其他高频并发场景

```text
重复提交    同一个订单请求快速点两次 → 生成两笔订单
并发退款    同时发两次退款 → 退两次钱
余额并发    余额 100，同时发两笔 80 的消费 → 余额变 -60
签到 / 打卡  同时发多次 → 一天签到多次拿多份奖励
关注 / 点赞  并发导致计数错乱（危害低但常见）
邀请奖励    同时用同一个邀请码 → 奖励超发
```

### 四、修复方案怎么写进报告

不要只写「建议加锁」，给出可选方案和适用场景：

```sql
-- 方案一：数据库原子扣减（最简单最可靠，单库场景首选）
UPDATE activity_stock
SET stock = stock - 1
WHERE activity_id = 9001 AND stock > 0;
-- 关键：判断影响行数，为 0 说明没抢到；把「检查」和「扣减」合并成一条语句
```

```sql
-- 方案二：唯一索引兜底（防「一人多领」最稳，数据库帮你保证）
ALTER TABLE activity_record
ADD UNIQUE KEY uk_user_activity (user_id, activity_id);
-- 重复插入直接冲突失败，业务层捕获唯一键异常即可
```

```python
# 方案三：幂等号 / 分布式锁（跨服务、跨库场景）
def submit_order(req):
    # 客户端生成 requestId，服务端用它去重；同一 requestId 只处理一次
    if not redis.set(f"idem:{req.request_id}", "1", nx=True, ex=300):
        return get_cached_result(req.request_id)      # 直接返回上次结果
    ...
```

三者可以叠加：**原子扣减防超卖 + 唯一索引防重复 + 幂等号防重复提交**，分别挡住不同层面的问题。

## 踩坑

1. **并发测试没让请求「同时」发出**。用简单的 for 循环起线程，创建开销让请求错开几十毫秒，正好避开窗口期，结论是「没问题」。必须用 `Barrier` 或信号量对齐起跑线。
2. **只看响应不查数据**。10 个请求返回了 9 个「已抢完」，看起来正常，但数据库里其实插了 2 条记录。**并发问题的判定标准永远在数据层**。
3. **跑一轮就下结论**。这类缺陷是概率性的，必须多轮重复。同理，开发说「修好了」之后也要多轮回归。
4. **在生产环境做并发测试**。会造成真实的超卖和资损。所有并发验证只在测试环境、用测试活动和测试库存做。
5. **测试数据没重置**。上一轮的库存被扣光，下一轮全部返回「已售罄」，测了个寂寞。每轮前重置库存和记录表。
6. **只测了金额没测数量**。`quantity = -1` 配上正常单价，总价变负数，有的系统会当成退款处理。负数和 0 是这类测试的必测值。
7. **忽略支付回调的幂等**。第三方支付平台本身就会重发通知，不做幂等在生产上必然出问题，不是「可能」。
8. **优惠券只测了「用一次」**。同一张券在两个订单里并发使用、取消订单后券重复退回，都是资损点。
9. **状态机没画出来就写用例**。只测了正向流程，「已完成再取消」「已退款再退款」这些反向边全漏了。
10. **发现问题只报单个接口**。逻辑漏洞往往是同一个开发的思维定式导致的，一个接口有，同模块其他接口大概率也有，要横向排查。

## 面试怎么答

**Q：一个下单接口，你会从哪些角度找安全问题？**

A：我会先把链路上的信任边界画出来，标清楚每个参数「谁说了算」。然后分四组测。第一组是金额：把 totalAmount 改成 0.01、0、负数，看服务端是不是以自己算的为准——金额绝对不能由客户端传。第二组是数量和边界：0、负数、超大值、小数、整型溢出值，负数尤其危险，负数乘单价可能变成退款。第三组是优惠券和积分：用别人的券、同一张券并发用两次、不满门槛用、已过期用、取消订单后券会不会重复退回。第四组是状态流转：把订单状态机画出来，每一条「不该存在的边」都是用例，比如未支付直接调发货、已退款再退一次。另外单独关注支付回调，要验签、要核对金额、要幂等，因为第三方本来就会重发通知。

**Q：什么是超卖？怎么测？怎么修？**

A：超卖的根因是「检查」和「扣减」不是原子操作，也就是 TOCTOU。先 select 判断库存大于 0，再 update 扣减，两步之间有一个窗口期，并发请求都读到同一个旧值、都通过判断、都去扣，结果库存 1 件卖出去 2 件。测法是把库存调成 1，用十几个线程配合 Barrier 让请求同时发出，然后断言「成功数等于 1」，而且一定要查数据库核对——库存不能为负、记录数不能超过库存、同一用户不能有多条。这类问题是概率性的，要跑五到十轮，每轮重置数据。修复有三条路：数据库原子扣减，把 where 条件写成 stock > 0 并看影响行数，把检查和扣减合并成一条语句；唯一索引兜底，用 user_id 加 activity_id 建唯一键防一人多领；跨服务场景用分布式锁或者客户端带 requestId 做幂等。三者可以叠加，分别挡不同层面的问题。

**Q：为什么逻辑漏洞扫描器扫不出来？**

A：因为注入、XSS 这类漏洞有固定的模式特征，一个引号一个尖括号就能触发异常响应，工具靠模式匹配就能识别。逻辑漏洞没有模式——`price=0.01` 是一个语法完全合法的请求，返回 200 也完全正常，它是不是漏洞取决于「这个商品原价多少」「金额该不该由客户端传」，这些属于业务语义，只存在于需求文档和测试人员脑子里，不在 HTTP 报文里。所以扫描器判断的是「响应对不对」，测试人员判断的是「业务对不对」。这也是为什么逻辑漏洞是测试开发最有价值的发力点。

**Q：支付回调怎么测？**

A：四个点。一是验签：不带签名、签名乱填都必须被拒绝，很多系统只解析参数不验签。二是金额核对：签名对但金额改大，服务端必须拿订单表里的实付金额去比，不能直接信通知里的值。三是幂等：同一条成功通知重放五次，只能生效一次，不能重复发货或重复加余额——这点特别重要，因为第三方平台本身就会重发通知，不是攻击者才会重放。四是订单状态校验：已完成的订单再来一次成功通知应该直接忽略。这些验证全部在测试环境用测试商户号和测试订单做。
