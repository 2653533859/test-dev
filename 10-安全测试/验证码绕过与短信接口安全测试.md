# 验证码绕过与短信接口安全测试

> 验证码是「区分人和机器」的关卡，短信接口是「会真实花钱」的接口。前者被绕过等于所有防爆破形同虚设，后者被滥用等于给业务直接烧钱。

## 概念

### 验证码到底在防什么

先明确目的，才知道该怎么测：

```text
图形验证码   防自动化脚本批量请求（爆破、刷接口、注册机）
短信/邮箱验证码  证明「你拥有这个手机号/邮箱」，用于注册、登录、找回密码、敏感操作确认
滑块/行为验证   在图形验证码基础上增加行为特征判断，防打码平台
二次密码/MFA   防「凭证泄露后被冒用」，用于转账、改绑这类高危操作
```

**短信验证码承担的是「所有权证明」，一旦能被绕过，任意用户密码重置、任意手机号注册就都成立了。** 相关链路见 [[任意用户密码重置漏洞测试]]。

### 一个正确的验证码必须满足的六条

这六条同时也是测试用例的来源，缺任何一条就是缺陷：

```text
① 服务端生成、服务端校验     —— 值绝不能出现在响应体或响应头里
② 与会话/手机号强绑定       —— A 的验证码不能用来验证 B
③ 一次性                   —— 校验成功后立即失效，不能重复使用
④ 有有效期                 —— 通常 5 分钟，过期即废
⑤ 校验失败有次数上限        —— 超过 5 次作废并要求重新获取
⑥ 足够随机且长度足够        —— 4 位纯数字只有 1 万种，配合无限重试等于没有
```

**③⑤ 两条是关键**：只要「一次性」和「失败次数上限」有一条没做，4～6 位的验证码就能被有限次尝试穷举。这也是为什么「短验证码 + 无限重试」比「长验证码」更危险。

### 短信接口的三类滥用

短信接口的特殊性在于**每一次调用都产生真实成本**，而且直接骚扰到真实用户：

```text
短信轰炸    对同一个手机号高频发送 → 骚扰用户、消耗短信费用
短信盗刷    遍历不同手机号批量发送 → 直接烧钱，严重时几小时耗尽额度
接口滥用    把企业短信通道当成免费发信工具（内容可控时更危险）
```

这类问题的定级通常按「资损 + 品牌影响」算，比很多技术漏洞更容易被业务方重视。

## 用法

### 测试纪律（这一类尤其重要）

```text
只对自己的测试手机号 / 虚拟号码发送，绝不对任意真实号码测试
频控验证只发到「触发限制」为止，不做真正的高频轰炸
不使用打码平台、不购买接码服务
所有测试在测试环境进行；若测试环境走真实短信通道，先与业务方确认额度和白名单
测完在报告里注明「已触发 N 次发送」，便于对账
```

### 一、验证码值泄露检查（最容易命中）

三个位置，抓包一看便知：

```bash
# 1. 响应体里直接返回验证码
curl -s -X POST http://test-app.internal.com/api/sms/send \
  -H 'Content-Type: application/json' \
  -d '{"phone":"13800000000"}' | python -m json.tool
# 危险示例：{"code":0,"data":{"smsCode":"482913"}}   ← 直接给了
```

```text
位置 1  响应体          常见于「方便前端调试」留下的字段，上线忘了删
位置 2  响应头          自定义头如 X-Debug-Code
位置 3  Set-Cookie      把验证码写进 Cookie 让前端自己比对
位置 4  前端 JS 校验     前端拿到值本地比对，服务端根本不校验 —— 最严重
```

位置 4 的判定方法：**直接用 curl 或 Repeater 跳过前端调接口，填任意验证码**，如果通过就说明校验只在前端。

### 二、验证码逻辑测试用例

用 Burp Repeater 逐条验（详见 [[Burp Suite 抓包改包工作流]]）：

```text
V1  验证码留空                        期望：拒绝
V2  验证码字段整个删掉                 期望：拒绝（有的实现「没传就不校验」）
V3  验证码传 null / "" / 0 / "%00"     期望：拒绝
V4  万能码试探（000000、123456）        期望：拒绝（开发留的后门是真实存在的）
V5  用正确验证码成功后，同一个码再用一次  期望：拒绝（一次性）
V6  等待超过有效期后再提交              期望：拒绝（有效期）
V7  连续输错 10 次                     期望：达到上限后作废，要求重新获取
V8  用手机号 A 收到的码去验证手机号 B     期望：拒绝（绑定关系）
V9  换一个 sessionId 再提交同一个码      期望：拒绝（会话绑定）
V10 只改手机号不重新获取验证码           期望：拒绝
V11 图形验证码不刷新时重复使用           期望：每次校验后强制刷新
V12 并发提交同一个验证码到两个业务接口     期望：只有一个成功
```

**V7 是命中率最高的一条**：很多实现只做了「发送频控」，忘了做「校验失败次数限制」，于是 6 位验证码可以用有限次尝试穷举。测的时候输错到系统开始拒绝为止即可，**不需要真的跑完一百万次**——能确认「没有次数限制」这个事实就够了，报告里写清楚「连续输错 N 次仍返回『验证码错误』而非『已失效』」。

V4 的万能码不是段子，开发为了联调方便留一个固定码、上线前忘了摘掉，是真实发生过的事故类型。

### 三、短信发送接口的频控测试

```python
import time
import requests

BASE = "http://test-app.internal.com"          # 测试环境
MY_TEST_PHONE = "13800000000"                  # 自己的测试号码 / 虚拟号

def send():
    r = requests.post(f"{BASE}/api/sms/send",
                      json={"phone": MY_TEST_PHONE}, timeout=5)
    return r.status_code, r.json().get("code"), r.json().get("msg")

# 只发到触发限制为止，一旦被拒绝立即停止，不做真实轰炸
for i in range(1, 11):
    status, code, msg = send()
    print(f"第 {i} 次: {status} {code} {msg}")
    if code != 0:
        print(f"→ 第 {i} 次被限制，频控生效")
        break
    time.sleep(1)
else:
    print("→ 连发 10 次均成功，缺少频控，存在短信轰炸风险")
```

频控应该是**多个维度叠加**的，只做一个维度容易被绕：

```text
维度 1  同一手机号   60 秒内 1 条、1 小时内 5 条、24 小时内 10 条
维度 2  同一 IP      1 小时内 20 条（防遍历不同号码盗刷）
维度 3  同一设备指纹  防换 IP 绕过
维度 4  全局阈值     整体发送量突增时告警并降级
维度 5  图形验证码前置 发短信之前先过一道图形/滑块验证 —— 最有效的一道
```

### 四、频控绕过手法验证

有频控不代表挡得住，这几个变形要专门测：

```text
B1  手机号加空格、加 +86、加 0086、加前导 0     → 是否被当成不同号码
B2  手机号后面加 %00、换行符、逗号分隔多个号码   → 是否绕过去重甚至群发
B3  修改 X-Forwarded-For 头                    → 若 IP 频控取这个头则可无限绕过
B4  更换 sessionId / 清 Cookie 重发             → 频控是否只做在会话维度
B5  同时并发发送 10 条                          → 频控是否有并发窗口期（计数不原子）
B6  在「注册」被限流后改用「找回密码」接口       → 多个短信接口是否共享频控额度
B7  参数里塞入自定义短信内容字段                 → 能否控制短信正文（危害极高）
```

**B3 和 B6 最容易命中**：`X-Forwarded-For` 是客户端可控的头，如果服务端直接拿它做频控 key 就等于没做；而多个业务接口各自独立计数、不共享额度，也让「换个接口继续发」变得可行。

### 五、修复方案

```python
# 发送侧：多维度频控 + 图形验证码前置
def send_sms(phone: str, scene: str, captcha_token: str):
    if not verify_captcha(captcha_token):          # 前置人机校验，最有效的一道
        raise BadRequest("请先完成验证")
    phone = normalize_phone(phone)                 # 归一化：去空格、去 +86，防 B1
    ip = get_real_ip()                             # 从可信代理链取，不直接信 XFF

    # 多维度计数，任一超限即拒绝；用 Redis 原子自增避免并发窗口
    for key, limit, ttl in [
        (f"sms:phone:{phone}:min", 1, 60),
        (f"sms:phone:{phone}:day", 10, 86400),
        (f"sms:ip:{ip}:hour", 20, 3600),
        (f"sms:global:{scene}:min", 500, 60),      # 全局熔断
    ]:
        if redis.incr(key) > limit:
            raise TooManyRequests("发送过于频繁，请稍后再试")
        redis.expire(key, ttl, nx=True)

    code = f"{secrets.randbelow(1000000):06d}"     # 6 位强随机，不用 random
    redis.setex(f"smscode:{scene}:{phone}", 300, json.dumps({"code": code, "tries": 0}))
    gateway.send(phone, render_template(scene, code))   # 模板固定，内容不可由参数控制

# 校验侧：一次性 + 次数上限 + 绑定关系
def verify_sms(phone: str, scene: str, input_code: str) -> bool:
    key = f"smscode:{scene}:{normalize_phone(phone)}"
    raw = redis.get(key)
    if not raw:
        return False                               # 不存在或已过期
    data = json.loads(raw)
    data["tries"] += 1
    if data["tries"] > 5:
        redis.delete(key)                          # 超过次数直接作废，防穷举
        return False
    if not secrets.compare_digest(data["code"], input_code):
        redis.set(key, json.dumps(data), keepttl=True)
        return False
    redis.delete(key)                              # 校验成功立即删除，保证一次性
    return True
```

四个要点：**图形验证码前置**、**手机号归一化**、**校验失败计数并在超限时作废**、**成功后立即删除**。

## 踩坑

1. **只测了「发送频控」没测「校验次数」**。绝大多数系统都做了 60 秒限一条，但校验侧可以无限次试错，6 位码就成了纸糊的。这两条是独立的，必须分开测。
2. **验证码校验成功后不删除**。同一个码能反复用，配合「找回密码」链路就是任意次数的账号接管。
3. **手机号没归一化**。`13800000000`、`+8613800000000`、`138 0000 0000` 被当成三个不同的 key，频控直接失效。
4. **频控 key 取自 `X-Forwarded-For`**。这个头客户端完全可控，等于没做 IP 维度频控。应从可信代理链的固定位置取。
5. **多个短信接口不共享额度**。注册被限流了就换找回密码接口继续发，同一个号码照样能收到几十条。频控 key 应包含手机号维度且跨场景累计。
6. **计数不原子**。用「先 get 再 set」实现计数器，并发下会漏计。必须用 Redis 的 `INCR` 这类原子操作。
7. **响应体里返回验证码**。为了方便前端联调加的字段，上线忘了删。这条虽然低级，但真实项目里出现频率高得惊人，是每次必查项。
8. **万能码没摘干净**。开发环境留的固定码 `888888` 跟着配置带到了生产。代码审计时专门搜一下硬编码的验证码常量。
9. **短信内容可由参数控制**。接口里有个 `content` 或 `template_param` 字段能塞任意文本，等于把企业短信通道变成了任意发信工具，会被用来发诈骗短信，直接影响通道资质。
10. **真的去轰炸测试**。测试目的只是确认「频控存不存在、在第几次生效」，发到被拒绝就停。真发几百条既是骚扰也会烧掉短信费用。
11. **对非本人号码测试**。哪怕是同事的号码也不行。只用自己的测试号或平台提供的虚拟号。

## 面试怎么答

**Q：验证码有哪些常见的绕过方式？**

A：我一般按六条正确性要求反着测。第一是值泄露：响应体、响应头、Cookie 里直接带了验证码，或者干脆只在前端校验，这种直接用 curl 跳过前端调接口就能确认。第二是校验缺失：验证码字段留空、传 null、整个删掉，有的实现是「没传就不校验」。第三是一次性没做：用成功的码再用一遍还能过。第四是没有有效期。第五是校验失败次数没限制，这条命中率最高——大部分系统做了发送频控，但校验侧能无限试错，6 位码就能被穷举。第六是绑定关系缺失：A 收到的码能用来验证 B 的手机号，或者换个 session 还能用。另外还有开发留的万能码，这不是段子，联调用的固定码带到线上是真实事故类型。

**Q：短信轰炸怎么测？怎么防？**

A：测的时候只对自己的测试号码发，连续调用发送接口，看第几次开始被拒绝，一旦触发限制就停，不做真实轰炸。然后重点测绕过：手机号加空格加 +86 看会不会被当成不同号码，改 X-Forwarded-For 看 IP 频控是不是取的这个头，换 session 重发看频控是不是只做在会话维度，并发发十条看计数是否原子，还有换一个短信接口继续发看多个场景是否共享额度。防御要多维度叠加：手机号维度、IP 维度、设备指纹维度、全局熔断，而且最有效的其实是在发短信之前先过一道图形或滑块验证，把自动化脚本挡在门外。实现上手机号要先归一化，计数要用 Redis 的原子自增。

**Q：短信接口除了轰炸还有什么风险？**

A：还有两个更严重的。一是盗刷：轰炸是针对一个号码，盗刷是遍历不同号码批量发，直接把短信额度烧掉，几个小时能烧掉几万块，而且没有任何一个真实用户在投诉，很晚才会被发现，所以全局阈值告警很重要。二是短信内容可控：如果接口里有个字段能影响短信正文，那这个企业通道就变成了任意发信工具，会被用来发诈骗短信，后果是通道被运营商封停、企业资质受影响。所以短信模板必须固定在服务端，参数只能填充预定义的占位符。

**Q：图形验证码和滑块验证有什么区别？**

A：图形验证码验的是「能不能识别扭曲字符」，现在 OCR 和打码平台的成本已经很低了，单纯的图形验证码防不住有组织的自动化。滑块和行为验证除了看结果，还采集鼠标轨迹、按压时长、设备指纹这些行为特征，用风控模型判断是不是机器，成本高很多。但从测试角度看，两者的测试要点是一样的：验证结果的 token 是不是服务端签发并绑定会话、能不能重复使用、有没有有效期、能不能跳过验证直接调后续接口。最容易出问题的其实是最后一条——人机验证做得很花哨，但后续业务接口不校验那个 token，直接调就绕过了。
