# 任意用户密码重置漏洞测试

> 密码找回是一条「绕过登录也能改密码」的合法通道。它天生绕开了认证，所以每一步都必须自己扛住校验——任何一步松了，就是直接的账号接管。

## 概念

### 为什么这条链路格外危险

正常业务接口的前提是「用户已登录」，而密码找回的前提恰恰相反：**用户就是因为进不去才来找回的**。这意味着整条链路上没有会话身份可以依赖，只能靠「所有权证明」（收到短信/邮件）来临时建立信任。

链路一旦有缺口，危害直接是**账号接管（Account Takeover, ATO）**——不是泄露数据，是把账号整个拿走。定级基本都是高危或严重。

### 标准的四步链路与四个校验点

```text
① 输入账号     用户提交手机号 / 邮箱 / 用户名
   校验点：不能因为「账号不存在」的不同提示而被用来枚举账号

② 身份验证     发送验证码 / 重置链接，用户提交凭证
   校验点：凭证必须与「第①步提交的账号」强绑定，且一次性、有时效、有次数上限

③ 换取通行证   验证通过后，服务端签发一个「允许改密」的临时凭证
   校验点：这个凭证必须是服务端签发的、绑定账号的、不可预测、一次性
   ★ 90% 的漏洞出在这一步——很多实现根本没有这一步，直接进第④步

④ 设置新密码   提交新密码
   校验点：必须校验通行证；账号从通行证里取，绝不从请求参数里取
```

**第③步是整条链路的核心**。没有通行证机制的实现，等于把「我验证过了」这个状态交给客户端保管，而客户端说的话不能信。

### 三类典型缺陷

```text
类型 A  身份绑定断裂
        第②步用自己的手机号收码，第④步把账号参数改成受害者
        —— 服务端在两步之间没有保持「同一个账号」的上下文

类型 B  验证被跳过
        直接请求第④步的接口/页面，不经过第②③步
        —— 服务端没有校验「是否已完成前置验证」

类型 C  凭证可预测 / 可复用
        重置 token 是时间戳、md5(手机号)、自增 id，或者永久有效、能重复用
        —— 攻击者不需要收到短信也能构造出有效凭证
```

## 用法

### 测试纪律

```text
只在测试环境，只用自己控制的两个测试账号（A = 攻击者视角，B = 受害者视角）
两个账号都由自己注册、手机号是自己的测试号码
绝不对真实用户账号做任何找回密码尝试（哪怕只是触发一条短信）
测完把两个账号的密码还原，避免影响后续用例
```

### 用例组 A：身份绑定断裂

这是最经典的一组，核心手法是**「用 A 的验证码，改 B 的密码」**。

```text
A1  第②步用 A 的手机号收码验证通过；第④步把 phone 参数改成 B
    期望：403 / 400，服务端应从服务端上下文取账号，不看请求参数
A2  第①步提交 A，第②步抓包把手机号改成 B（让码发给 B？）
    期望：以第①步为准，或直接拒绝
A3  请求体里同时传 phone=A&phone=B（参数污染）
    期望：拒绝或取第一个，不能出现「验证 A、改 B」
A4  JSON 里传 {"phone":"A","phone":"B"} 重复键
    期望：拒绝；实测中不同框架取值不同（有的取第一个有的取最后一个），
          若校验层和业务层取值不一致就会出现「校验 A、修改 B」
A5  用 A 的 token 配 B 的 userId 调最终的改密接口
    期望：403
A6  多步之间的 Cookie / session 换成另一个账号的
    期望：整个流程作废，要求重来
```

A1 的具体操作（在 Burp Repeater 里完成，详见 [[Burp Suite 抓包改包工作流]]）：

```bash
# 步骤 1：用自己的测试号 A 走正常流程，拿到验证码并验证通过，抓下最后一个「设置新密码」请求：
# POST /api/user/password/reset
# {"phone": "13800000001", "reset_token": "tk_a1b2c3d4", "new_password": "Password123!"}

# 步骤 2：把请求体中的 phone 字段改成受害者号码 B（13800000002），重放发送
# 步骤 3：若返回 200 且使用受害者 B + 新密码能够成功登录，则漏洞存在（身份绑定断裂）
```

### 用例组 B：验证步骤跳过

```text
B1  直接请求「设置新密码」接口，不带 reset_token
    期望：401 / 403 明确拒绝，禁止匿名访问
B2  带空的 reset_token="" 或 null 提交改密
    期望：拒绝，不能发生字符串弱类型比对成功
B3  利用前端 URL 跳转绕过：直接在浏览器输入 step4.html / #/reset-password
    期望：前端路由守卫拦截并跳回第一步；即便前端没拦，后端接口必须强校验凭证
B4  修改服务端返回的 HTTP 响应包（如把 {"code": 400, "msg": "验证码错误"} 改为 200）
    期望：页面可能误跳转，但最终提交新密码时后端拒绝执行
```

### 用例组 C：凭证与 Token 缺陷

```text
C1  验证码爆破：验证码为 4~6 位纯数字，无频率限制、无验证码错误上限锁定
    期望：单手机号最多尝试 5 次错误即失效；接口有 IP/图形验证码频控
C2  Token 预测性：reset_token 仅仅是 base64(phone) 或 md5(timestamp)
    期望：使用密码学安全的随机数生成器（如 /dev/urandom 或 Python secrets 模块）
C3  Token 时效与复用：使用过的 reset_token 在 10 分钟后或再次提交时依然生效
    期望：一旦使用立即在 Redis 中原子删除；过期时间不超过 15 分钟
```

## 踩坑

1. **只在前端做步骤控制，后端裸奔**：
   - 开发认为「用户不走第二步点不到第三步的页面」，因此第四步的 `reset_password` 接口只接收 `phone` 和 `new_password` 两个参数，完全没有校验 `reset_token`。黑客直接用 Postman/Burp 调最终接口直接重置全库密码。
2. **重置 Token 未与用户身份在服务端绑定**：
   - 验证通过后服务端把 `reset_token` 存到 Redis，但 key 是 `reset_token`，value 存了 `true`。改密接口只判断该 token 是否存在，没有核对该 token 到底属于哪个账号。攻击者用自己手机号收码生成的合法 token，去改受害者的账号密码。
3. **验证码校验成功后未立即作废**：
   - 用户输入验证码后，服务端判定正确但没有立即销毁，而是等最终设密成功才删。攻击者在此窗口期内可并发多次利用同一验证码派生多个重置通行证。

## 面试怎么答

**Q：在安全测试中，如何系统性地测试「密码找回/重置」链路的逻辑漏洞？**
> 密码找回是典型的未登录状态下敏感业务，我们通常将其拆解为「身份录入 -> 凭证验证 -> 签发临时通行证 -> 密码重设」四阶段，按以下三大类展开测试：
> 1. **身份一致性与绑定断裂（最核心）**：用攻击者账号 A 完成短信验证，抓包在最终提交改密请求时，把 `phone`、`userId` 或 `email` 替换为受害者 B，验证服务端是否强校验「凭证所有权与目标修改人的一致性」。
> 2. **前置步骤跳过与响应包伪造**：测试是否可以直接越过验证码步骤直接请求设密 API；测试通过 Burp 篡改验证码错误的响应体（如 400 改 200），看前端是否会跳转以及后端是否具备独立的防伪机制。
> 3. **凭证的安全性与防爆破**：测试短信验证码是否具备 5 次输错即锁死、60 秒发送频率限制；测试换取的 `reset_token` 是否具有不可伪造性（高熵随机）、严格单次使用（一次一密）以及短期失效机制（10-15 分钟）。
