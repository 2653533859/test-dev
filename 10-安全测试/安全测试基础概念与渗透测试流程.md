# 安全测试基础概念与渗透测试流程

> 把「漏洞 / 威胁 / 风险」这三个总被混用的词分清楚，并给出一条测试人员可执行的、以授权为前提的安全测试流程。

![[assets/pentest-process.svg]]
*图示：授权安全测试的八步闭环——授权与范围确认是前置红线，复测不通过则回到漏洞探测；下半部分是漏洞、威胁、风险三个术语的递进关系。*

## 概念

### 三个总被说混的词

面试里最容易被抓的一个点：把「发现了一个漏洞」直接说成「有很高的风险」。这三者是递进关系，不能划等号。

| 术语 | 英文 | 定义 | 例子 |
|------|------|------|------|
| 漏洞 | Vulnerability | 系统**自身**存在的缺陷 | 订单查询接口没校验归属人 |
| 威胁 | Threat | **有主体**有能力有动机去利用这个缺陷 | 有人写脚本遍历订单号 |
| 风险 | Risk | 威胁利用漏洞造成损失的**可能性 × 影响** | 全量用户订单信息泄露，触发合规处罚 |

推论很实用：

- 有漏洞不一定有风险。一个内网自动化工具的调试接口没鉴权，外网不可达、没有敏感数据，风险就低。
- 没漏洞也可能有风险。业务设计上允许无限次免费领券，代码毫无 bug，但风控缺失，一样赔钱——这属于 OWASP 里的「不安全设计」。
- 所以**报告里必须写清楚影响**，只写「存在 XSS」而不写「能打到管理员 Cookie 从而接管后台」，开发不会优先修。

配套的还有两个词：

- **攻击面（Attack Surface）**：所有外部可输入的点的总和——URL 参数、表单、Header、Cookie、文件上传、消息队列、第三方回调。新功能上线本质上就是在扩大攻击面。
- **纵深防御（Defense in Depth）**：不指望单点防住，每一层都设一道。参数化查询 + 最小权限数据库账号 + WAF + 审计日志，前面漏了后面还能兜。

### 黑盒、白盒、灰盒

| 类型 | 你拥有什么 | 典型手段 | 局限 |
|------|-----------|---------|------|
| 黑盒 | 只有 URL 和界面 | 抓包改包、扫描器 | 覆盖不全，隐藏接口测不到 |
| 灰盒 | 测试账号 + 接口文档 + 部分架构 | 逐接口权限矩阵验证 | 拿不到源码，看不到内部实现 |
| 白盒 | 能读源码与配置 | 代码审计、SAST | 只看代码会漏掉配置与环境问题 |

**测试人员绝大多数时候处在灰盒**，这其实是性价比最高的位置：既有账号能构造业务场景，又有接口文档能穷举参数。所以「用接口文档 + 多角色账号做权限矩阵」是测开做安全最该练的一手。

### 一条不能越的线

本模块所有验证方法都**只适用于**：

1. 自己所在团队负责的测试环境（有明确书面授权）；
2. 本地或云上自建的靶场（DVWA、Juice Shop、pikachu、upload-labs）；
3. 公开的 CTF 比赛环境。

对无授权目标做扫描、探测、爆破在国内属于违法行为，与技术水平无关。工作中拿到测试任务的第一步永远是**确认授权范围书面化**：域名/IP 清单、测试时间窗口、禁止动作（不允许 DoS、不允许删数据、不允许横向移动到其他系统）、出事联系人。

## 用法

### 步骤一：确认范围（别跳过）

范围确认清单，建议直接做成模板：

```text
[授权确认单]
- 授权方：XX 业务线负责人（签字/邮件确认）
- 目标范围：test-order.internal.com、test-pay.internal.com（仅这两个域名）
- 排除范围：任何 *.prod.* 域名、第三方支付网关沙箱之外的地址
- 时间窗口：2026-08-01 10:00 ~ 2026-08-05 18:00
- 禁止动作：压力测试 / 删除或篡改他人数据 / 修改线上配置 / 社工
- 数据要求：只用测试账号 A(1001)、B(1002)、admin(9001)
- 应急联系人：值班群 + 手机
```

### 步骤二：信息收集（被动优先）

先用**已授权范围内**的手段摸清系统边界。最省事的做法不是拿扫描器扫，而是「正常用一遍系统，让代理沉淀出接口清单」。

```bash
# 在授权测试环境中，查看目标解析与开放端口（范围内主机）
nslookup test-order.internal.com

# Nmap 只扫授权 IP，常用端口 + 服务版本；-T3 降低对测试环境的干扰
nmap -sV -T3 -p 80,443,8080,8443 10.20.30.40

# 看 HTTP 响应头能暴露多少技术栈信息
curl -sI https://test-order.internal.com | grep -iE 'server|x-powered-by|set-cookie'
```

关注点：

- 中间件与框架版本（对应 SCA / 已知 CVE）；
- `Set-Cookie` 有没有 `HttpOnly; Secure; SameSite`；
- 有没有 `/swagger-ui.html`、`/actuator`、`/.git/`、`/backup.zip` 这类不该暴露的路径。

### 步骤三：威胁建模（这一步决定测试质量）

拿到一个功能，画一遍数据流，然后逐个信任边界提问。用 STRIDE 做检查表：

| 字母 | 威胁 | 对下单功能的具体提问 |
|------|------|---------------------|
| S Spoofing | 身份伪造 | 能不能改 userId 冒充别人下单？ |
| T Tampering | 篡改 | 金额、数量、优惠券 ID 能不能改？负数呢？ |
| R Repudiation | 抵赖 | 下单有没有完整审计日志、能不能追溯？ |
| I Info Disclosure | 信息泄露 | 响应里有没有多返回身份证、手机号全量？ |
| D DoS | 拒绝服务 | 有没有频率限制？（授权范围内才验证） |
| E Elevation | 权限提升 | 普通用户能不能调管理端的改价接口？ |

输出物是一张**测试点清单**，不是「感觉试试看」。

### 步骤四到五：探测、人工验证与定级

工具跑一遍拿候选，**每一条都必须人工确认**，扫描器误报率非常高。判断标准是「能不能给出可复现的证据」。

定级建议用 CVSS 的思路简化成四问：

```text
1. 攻击者需要什么前提？（无需登录 > 需要普通账号 > 需要管理员）
2. 影响哪些数据？（全量用户 > 单个用户 > 无敏感数据）
3. 造成什么后果？（可接管账号/服务器 > 可读数据 > 仅信息暴露）
4. 利用难度？（改个 URL 参数 > 需要复杂条件竞争）
```

前提越低、影响面越大、后果越严重 → 等级越高。详细写法见 [[漏洞报告编写与风险定级]]。

### 步骤六到八：报告、修复、复测

安全测试的闭环不是「发现了」，而是「修好了并且不会再犯」。复测通过后，要把这个场景**沉淀成自动化用例**（比如接口自动化里加一条「用 A 的 token 查 B 的订单必须返回 403」），否则下次重构又会漏回去。

## 踩坑

1. **没有书面授权就开测**。口头说「你随便测」在出事的时候没有任何效力。一定要邮件/工单留痕，写明范围和时间。
2. **扫描器指着测试域名，实际打到了生产**。测试环境和生产共用一个网关、或者测试环境的配置里回调地址写的是生产，都会导致流量穿透。开测前用 `curl` 确认目标 IP，别只看域名。
3. **扫描把测试环境打挂了**。Intruder 或者 sqlmap 的线程一开高，测试库直接锁表，其他同学的功能测试全被阻塞。测试环境同样要限速、要提前在群里同步。
4. **只报现象不报影响**。「/api/user/1002 能访问」这种报告开发看不懂优先级，会一直挂着。要写成「用 A 的 token 可遍历任意 userId 获取姓名+手机号，接口无频率限制，可批量拉取全量用户信息」。
5. **误报没排除就发报告**。扫描器报的「疑似 SQL 注入」很多是页面本身有随机内容导致响应长度变化。发出去几条误报之后，开发就不再认真看你的安全报告了。
6. **测完没清理现场**。存储型 XSS 的探针留在测试环境的评论区，上传的测试文件留在服务器上，改过的账号权限没恢复——都会影响别人。测试结束要有清理清单。
7. **把「合规扫描通过」当成「安全」**。工具只覆盖有固定模式的问题，越权和业务逻辑漏洞永远扫不出来，这部分只能靠人。
8. **测试账号权限开太大**。为了方便给测试账号开了管理员，结果测越权时发现「什么都能访问」，根本判断不出是漏洞还是权限本来就有。测越权必须准备**最小权限的干净账号**。

## 面试怎么答

**Q：漏洞、威胁、风险有什么区别？**

A：漏洞是系统自身的缺陷，比如接口没做归属校验；威胁是有主体有动机去利用它；风险是威胁利用漏洞后造成损失的可能性乘以影响。三者是递进的——有漏洞不等于有高风险，要看它能不能被触达、数据敏不敏感。所以我写漏洞报告的时候，除了描述缺陷本身，一定会写清楚触发前提和影响面，这直接决定开发的修复优先级。反过来，也存在代码没 bug 但设计上有风险的情况，比如没有风控的免费领券，这属于不安全设计。

**Q：黑盒、白盒、灰盒你平时用哪种？**

A：日常是灰盒。我有测试账号、接口文档，也大致知道服务怎么划分，这个位置做安全测试性价比最高：能拿多角色账号做权限矩阵，能按接口文档穷举参数边界，比纯黑盒瞎猜效率高很多。白盒的部分我会借助 SAST 工具，看它报的 SQL 拼接、`shell=True` 这类危险模式，再回到接口上验证能不能真的触发——工具定位到行，我负责证明可利用性。

**Q：给你一个新上线的功能，你怎么开始做安全测试？**

A：分四步。第一步确认授权范围，明确哪些域名能测、什么时间测、哪些动作禁止。第二步画数据流，标出信任边界，用 STRIDE 逐项提问，输出测试点清单，而不是凭感觉试。第三步分两条线执行：工具跑一遍拿候选（SCA 看依赖、DAST 看常见注入），人工重点覆盖工具覆盖不了的越权和业务逻辑——这部分是我作为测试最有价值的地方，因为只有我知道这个业务里「谁该看什么」。第四步是验证与闭环，每条候选都人工确认排除误报，按可利用性和影响定级，报告写成可复现步骤，修完复测，并把这个场景沉淀成接口自动化用例防回归。

**Q：安全测试和功能测试的关系是什么？**

A：我的理解是安全测试就是「反向的功能测试」。功能测试验证的是「按预期用能不能跑通」，安全测试验证的是「不按预期用会不会出事」。同一个下单接口，功能测试关心金额算得对不对，安全测试关心金额能不能被改成负数、能不能用别人的优惠券、能不能并发下单超卖。所以这两件事最好由同一个人做，因为业务语义是测出越权和逻辑漏洞的前提，纯安全团队反而不清楚「这个字段本来该谁看」。
