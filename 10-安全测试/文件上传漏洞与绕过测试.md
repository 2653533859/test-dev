# 文件上传漏洞与绕过测试

> 范围约束：以下验证只在自有测试环境/靶场（DVWA、pikachu 等）进行，目的是确认服务端校验是否到位，不针对无授权目标。

## 概念

文件上传是高危功能：一旦攻击者能把「可执行文件」传上去并被当作代码执行，就等于拿到服务器落脚点和后续控制能力。核心风险点是**服务端是否真正校验了文件类型、内容、存储路径**，而不是只看前端后缀。

常见绕过思路（仅用于理解被测系统是否缺失防护）：
- **前端校验可绕过**：前端 JS 限制后缀，请求直接改包即可。
- **Content-Type 伪造**：表单里 `image/png` 是客户端填的，服务端若只信它就会被骗。
- **后缀黑名单不全**：漏掉 `.phtml`、`.php5` 等变体。
- **二次渲染/内容校验缺失**：只查扩展名不查真实文件头（magic number）。

## 用法

测试时按「服务端到底信什么」逐层验证（自有环境）：

```text
1. 传一个正常图片，确认功能正常（基线）
2. 把请求里的 Content-Type 从 image/png 改成 application/octet-stream，
   看服务端是否只认 Content-Type（若是，则存在伪造绕过）
3. 把 .png 改名为 .php 再传，看服务端是否只校验扩展名
4. 在图片尾部追加一句无害注释，验证服务端是否做内容（文件头）校验
5. 确认上传后的文件是否可被直接访问执行（路径是否暴露在 Web 目录）
```

注意：以上只验证「防护是否缺失」，绝不在无授权系统上上传可执行脚本。

## 踩坑

- **只看前端弹窗就以为安全**：前端限制一秒绕过，安全必须靠服务端。
- **只校验 Content-Type**：这是客户端可控字段，等于没校验。
- **黑名单思维**：黑名单永远追不全变体，应用**白名单 + 内容校验 + 重命名**三件套。
- **存到 Web 可执行的目录**：即使类型校验了，若上传文件能被 URL 直接访问并执行，风险仍在——应存到非执行目录或对象存储，并随机重命名。
- **忽略图片二次渲染**：有的系统会对图片重采样，但只对首字节校验，仍可被构造绕过。

## 面试怎么答

- **怎么测文件上传功能？** 分层验证服务端校验：扩展名白名单、Content-Type 是否可被伪造、文件内容（magic number）是否校验、存储路径是否可执行、是否随机重命名。
- **为什么白名单比黑名单好？** 黑名单永远有遗漏（变体后缀、大小写、空字节截断），白名单只放行已知安全的类型，攻击面最小。
- **上传功能最该避免什么？** 上传文件落在 Web 可执行目录且可被直接访问执行——这是从「上传」到「Getshell」的关键一步。
