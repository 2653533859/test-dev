# 漏洞报告编写与风险定级

> 范围约束：以下内容只用于在自己有权限的测试环境/靶场中验证漏洞并编写可复现报告，不针对无授权目标。

## 概念

发现漏洞只是第一步，**能被研发复现、被负责人定优先级**的报告才有价值。一份合格的安全测试报告至少回答四件事：**是什么、影响多大、怎么复现、怎么修**。风险定级则把「技术严重度」和「业务影响」结合，给出统一的处置优先级。

常用定级框架是 **CVSS**（通用漏洞评分系统），从「攻击向量、复杂度、权限、用户交互、影响范围、保密/完整/可用三性」算出一个 0–10 分，再落到等级：危急 / 高危 / 中危 / 低危。

## 用法

一份最小可用的漏洞报告结构：

```text
标题：    [高危] 订单详情接口水平越权，可遍历他人订单
等级：    高危（CVSS 8.1）
环境：    https://staging.example.com（自有测试环境）
影响：    任意登录用户可读取非本人订单，含收货地址/手机号
复现步骤：
  1. 用账号 A 登录，抓包拿到订单详情请求 GET /api/order/{id}
  2. 把 id 从 1001 改成 1002（他人订单）
  3. 响应仍返回 200，且返回了他人订单数据
证据：   附请求/响应截图与订单号
修复建议：服务端按当前登录用户过滤 orderId，禁止靠客户端传入的 id 直查
```

定级时不只看技术：同样一个越权，涉及「手机号/身份证」就是高危，涉及「公开昵称」可能只是低危——**业务敏感度决定等级上限**。

## 踩坑

- **只给现象不给复现**：研发无法复现就等于没提。必须附「环境 + 步骤 + 证据」，最好给最小请求。
- **定级唯技术论**：用了 `id` 遍历就说高危，但数据是公开信息，实际低危——要结合业务影响。
- **漏报「影响范围」**：一个越权能遍历多少数据、是否可写，决定处置紧急度，报告里要说清。
- **把靶场结论直接套生产**：靶场（DVWA/Juice Shop）验证的是「原理可复现」，生产是否受影响要看实际代码与配置，不能混为一谈。
- **不区分「已利用」与「可利用」**：理论存在但利用条件苛刻的，定级应下调并注明前置条件。

## 面试怎么答

- **你怎么给一个漏洞定级？** 先按 CVSS 技术维度打分，再叠加业务影响（数据敏感度、是否可写、利用前提），最后落到危急/高/中/低。
- **研发不认可你的定级怎么办？** 用复现证据 + 业务影响说话，必要时拉安全团队或产品一起评估，避免主观争论。
- **报告和功能缺陷报告的区别？** 安全报告必须含「影响面、复现证据、修复建议」，且要标注测试环境与授权范围，不能把靶场结论当生产结论。
