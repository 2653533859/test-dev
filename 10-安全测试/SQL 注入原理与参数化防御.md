# SQL 注入原理与参数化防御

> 讲透一件事：为什么参数化查询能根治 SQL 注入，而转义和过滤不能——区别在于「语法树在什么时候定型」。

![[assets/sql-injection.svg]]
*图示：左侧拼接路径先拼字符串后解析，用户数据参与了语法树构建；右侧参数化先编译定型再绑定值，参数永远只是叶子节点上的数据。下方三格说明为什么单纯转义挡不住。*

## 概念

### 漏洞是怎么产生的

SQL 注入的唯一根因是：**把用户输入当作 SQL 语句文本的一部分拼接起来**，导致数据越界成了代码。

```python
# 有漏洞的写法（仅用于说明原理，任何项目里都不要这么写）
user_id = request.args.get("id")
sql = "SELECT * FROM users WHERE id = " + user_id
cursor.execute(sql)
```

正常情况 `id=1`，拼出 `SELECT * FROM users WHERE id = 1`。
如果输入变成 `1 OR 1=1`，拼出的语句里 `OR` 是一个合法的逻辑运算符，条件恒真，于是返回全表。

数据库没做错什么，它只是**忠实地解析了收到的语句**。错的是应用把用户可控的字符串放进了「会被当作语法解析」的位置。

### 参数化查询为什么有效

参数化（Prepared Statement）把一次查询拆成两个阶段：

1. **Prepare**：把带占位符的模板发给数据库，数据库完成词法分析、语法分析，生成执行计划。**此时语法树已经定型**，占位符是树上一个明确的「参数槽」。
2. **Bind + Execute**：参数值走独立通道单独发过去，填进那个槽里。

关键点：**参数在语法分析之后才到达**。无论值是 `1`、`1 OR 1=1` 还是一段完整的 SQL 片段，它都只是槽里的字面量，不可能改变树的形状。

类比：拼接是「把用户写的字直接插进合同正文再签字」，参数化是「合同正文先定稿签字，用户只能在预留的横线上填内容」。

```python
# 正确写法：占位符 + 参数序列，值永远不参与 SQL 文本
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
```

第二个参数必须是**序列**。写成 `cursor.execute("... id = %s" % user_id)` 本质仍是拼接，等于没防——这是最常见的伪参数化。

### 为什么转义不够

图示下半部分的三种情况，是「靠转义防注入」经常翻车的地方：

1. **数字型注入没有引号可转**。`WHERE id = 1 OR 1=1` 里根本没出现引号，转义引号的函数完全不起作用。
2. **字符集不一致**。当连接字符集与库表字符集不匹配时（典型是宽字节场景），转义添加的反斜杠可能被吃进多字节字符里，引号重新逃逸出来。统一使用 `utf8mb4` 能规避大部分此类问题。
3. **标识符位置无法参数化**。表名、列名、`ORDER BY` 的字段、`ASC/DESC` 都不能用占位符绑定，只能白名单枚举。这是实际项目里最常见的残留注入点。

结论：**转义是补丁，参数化是设计**。

### 注入的几种表现形态

判断严重程度和选择验证手法都靠它。

| 类型 | 特征 | 测试中的观察点 |
|------|------|---------------|
| 回显型 | 结果直接展示在页面上 | 返回了不该返回的记录 |
| 报错型 | 数据库错误信息回显到前端 | 页面出现 SQL 语法错误、表名列名 |
| 布尔盲注 | 无回显，但条件真假会改变页面 | 同一接口两次请求响应长度不同 |
| 时间盲注 | 无任何回显差异 | 构造延时后响应时间明显变长 |
| 堆叠 / 二阶 | 多语句执行；或先入库后在别处被拼接 | 危害最大，常规扫描器易漏 |

**二阶注入**值得单独记：用户注册时把特殊字符串存进数据库（此处入口是参数化的，安全），但后台某个统计功能把这个字段拼进了另一条 SQL。测试上的启示是——**不能只测输入点，还要测「这个数据后续会在哪里被使用」**。

## 用法

### 各语言/框架的正确写法

```python
# 1. Python DB-API（pymysql / psycopg2）
cursor.execute(
    "SELECT id, name FROM users WHERE dept = %s AND status = %s",
    (dept, status),
)

# 2. IN 列表：占位符个数动态生成，但值仍然走绑定
ids = [1, 2, 3]
placeholders = ", ".join(["%s"] * len(ids))
cursor.execute(f"SELECT * FROM users WHERE id IN ({placeholders})", ids)

# 3. LIKE 模糊查询：通配符拼在「参数值」里，不拼在 SQL 文本里
keyword = request.args.get("kw", "")
cursor.execute("SELECT * FROM users WHERE name LIKE %s", (f"%{keyword}%",))

# 4. 排序字段无法绑参 → 白名单映射，绝不直接使用用户输入
ALLOWED_SORT = {"created": "created_at", "name": "user_name"}
ALLOWED_ORDER = {"asc": "ASC", "desc": "DESC"}
sort = ALLOWED_SORT.get(request.args.get("sort"), "created_at")
order = ALLOWED_ORDER.get(request.args.get("order", "").lower(), "ASC")
cursor.execute(f"SELECT * FROM users ORDER BY {sort} {order} LIMIT %s", (limit,))
```

ORM 默认走参数化，但都留了裸 SQL 的口子，这些口子是代码审计的重点：

```python
# SQLAlchemy —— 危险：text() 里 f-string 拼接等同手写拼接
session.execute(text(f"SELECT * FROM users WHERE name = '{name}'"))

# SQLAlchemy —— 安全：命名参数绑定
session.execute(text("SELECT * FROM users WHERE name = :name"), {"name": name})

# Django —— 安全
User.objects.raw("SELECT * FROM users WHERE id = %s", [uid])
# Django —— 危险：extra 的 where 是原样拼接
User.objects.extra(where=[f"id = {uid}"])
```

MyBatis 的经典区别，Java 侧面试必问：

```text
#{}  → 编译成 PreparedStatement 的 ?，走参数绑定，安全
${}  → 直接字符串替换，等价于拼接，只允许用于白名单校验过的标识符
```

### 在授权靶场里怎么验证

以本地 Docker 起的 **DVWA（Security Level: low）** 或 **sqli-labs** 为例，验证按「探测 → 定性 → 取证」三步走，不追求扩大战果。

```bash
# 本地起靶场，只绑定回环地址，不对外暴露
docker run -d --rm -p 127.0.0.1:8080:80 --name dvwa vulnerables/web-dvwa
# 测完立即销毁
docker stop dvwa
```

**第一步：判断参数是否进入了 SQL 上下文。**

输入一个单引号，观察响应是否发生「与业务无关的异常」：

```sql
-- 在靶场的输入框里只输入这一个字符
'
```

- 页面报出 SQL 语法错误 → 参数确实被拼进了语句，且错误信息还外泄了（这本身是第二个问题）；
- 页面返回「查询无结果」但不报错 → 可能被参数化了，也可能只是关掉了错误回显，需要继续判断。

**第二步：用逻辑等价对照，确认可控性。**

这一步是关键，用「真条件」和「假条件」两组请求做对照，看响应是否有差异：

```sql
-- A 组：恒真条件
1' AND '1'='1
-- B 组：恒假条件
1' AND '1'='2
```

- A 有数据、B 没数据 → 说明拼进去的布尔条件真的影响了查询结果，注入点成立（布尔盲注也靠这个原理）；
- A、B 结果一致 → 参数没进入条件逻辑，此点大概率安全。

**第三步：无回显时用时间盲注定性（点到为止）。**

如果页面既不报错、真假条件也看不出差异，用可控延时证明「后端确实执行了我注入的逻辑」：

```sql
-- 条件成立才 sleep 3 秒；对比正常请求的响应时间即可定性
1' AND IF(1=1, SLEEP(3), 0) -- 
```

正常请求秒回、这条明显延迟 3 秒左右，就足以证明存在注入。**到此为止**——测试目标是「证明漏洞存在并可复现」，不是把数据拖出来。需要证明影响面时，用无害的元数据即可，例如：

```sql
-- 仅取当前数据库名/版本作为影响佐证，不去 dump 业务数据
1' UNION SELECT database(), version() -- 
```

### 用 sqlmap 辅助（仅授权靶场）

人工确认注入点后，可用 sqlmap 提高效率，但务必限定在授权靶场：

```bash
# 只对本地靶场；--batch 用默认选项；仅识别，不做危险操作
sqlmap -u "http://127.0.0.1:8080/vulnerabilities/sqli/?id=1&Submit=Submit" \
       --cookie="PHPSESSID=xxx; security=low" \
       --batch --dbs

# 报告里只需写明「可枚举数据库」，无需真的导出业务表
```

sqlmap 很强，也正因为强，**绝不能指向未授权目标**，它默认会尝试多种注入与提权手法。

## 踩坑

1. **伪参数化**。`cursor.execute("... = %s" % value)` 用的是 Python 的字符串格式化先把值拼进去了，再交给驱动，等于没防。参数必须作为 `execute` 的第二个参数传入。
2. **只测输入不测二阶**。注册接口用了参数化，以为安全，但昵称字段被后台报表功能拼进了另一条 SQL。测试要跟着数据流走，覆盖「存进去的东西后面在哪被用」。
3. **排序、动态表名成漏网之鱼**。开发知道值要绑参，但 `ORDER BY ${col}`、`FROM ${table}` 绑不了，就直接拼了。这些位置必须白名单，是代码审计要重点看的。
4. **关了错误回显就以为修好了**。把数据库报错藏起来只是让「报错型」变成了「盲注型」，注入点还在。修复必须是参数化，不是隐藏错误。
5. **宽字节注入**。GBK 等字符集下，转义的反斜杠被吃进多字节字符，引号逃逸。根治是统一 `utf8mb4` + 参数化，不要依赖 `addslashes`。
6. **WAF 当成修复**。WAF 能挡掉一部分带特征的 payload，但绕过手法层出不穷（大小写、注释、编码、内联注释）。WAF 是缓解不是修复，代码层面必须参数化。
7. **测试把库搞坏**。手抖执行了带 `DELETE`/`UPDATE`/`DROP` 的注入语句，把测试库数据删了。靶场用完即弃、用 Docker `--rm`，重要测试库先备份。
8. **报告里贴了能直接打的完整链条**。给开发的报告应聚焦「哪个参数、什么上下文、如何复现、如何修」，而不是提供一份可直接复用的攻击脚本。

## 面试怎么答

**Q：SQL 注入的原理是什么？参数化查询为什么能防住？**

A：根因是应用把用户输入当成 SQL 语句文本拼接了，导致本该是数据的东西越界成了代码，被数据库当作语法解析执行。参数化查询的关键在于把查询拆成两步：先把带占位符的模板发给数据库做语法分析、生成执行计划，这时语法树已经定型了；然后参数值走一条独立通道单独发过去，只能填进树上预留的参数槽里。因为参数是在语法分析之后才到达的，无论它写成什么样，都改变不了已经定好的树结构，所以注入不可能成立。一句话总结：拼接是先拼字符串后解析，参数化是先解析定型后填值。

**Q：那用转义、过滤特殊字符行不行？**

A：不够可靠，有三个典型翻车点。第一，数字型注入根本没有引号，转义引号的函数完全不起作用，比如 `id=1 OR 1=1`。第二，字符集不一致时，比如宽字节场景，转义加的反斜杠会被多字节字符吃掉，引号重新逃逸出来。第三，表名、列名、ORDER BY 这些标识符位置压根不能用占位符绑定，转义也解决不了，只能白名单枚举。所以转义是打补丁，参数化才是从设计上根治。实际项目里我会把参数化作为默认，只有标识符这种绑不了参的地方用白名单兜。

**Q：ORM 是不是就绝对安全了？**

A：不是。主流 ORM 默认走参数化没错，但都留了裸 SQL 的口子，比如 SQLAlchemy 的 `text()`、Django 的 `raw()` 和 `extra()`、MyBatis 的 `${}`。开发一旦在这些地方用字符串拼接，注入就回来了。所以我做代码审计时会专门搜这些关键字，看它们里面有没有出现用户输入的拼接。MyBatis 那个 `#{}` 和 `${}` 的区别是 Java 岗必问的，`#{}` 是预编译参数绑定安全，`${}` 是字符串替换等于拼接。

**Q：无回显的注入你怎么测？**

A：分两种。一种是布尔盲注，页面不直接回显数据，但真假条件会让页面表现不同，我就构造一组恒真、一组恒假的条件做对照，比如 `AND 1=1` 和 `AND 1=2`，看两次响应有没有差异，有差异就说明我注入的逻辑生效了。另一种是完全没有任何差异的，用时间盲注，注入一个条件成立才 `SLEEP(3)` 的语句，正常请求秒回、这条延迟三秒，就能定性。我强调一点，测试的目标是证明漏洞存在并可复现，定性到这一步就够了，需要说明影响时取个数据库名或版本号做佐证即可，不会去把业务数据整表拖出来，那既没必要也容易违规。
