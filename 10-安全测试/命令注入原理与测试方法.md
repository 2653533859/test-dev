# 命令注入原理与测试方法

> 只要代码里出现「把用户输入拼进 shell 命令」，就存在命令注入。测试重点是找出那些「后端需要调外部程序」的功能。

## 概念

### 危害为什么比 SQL 注入更严重

SQL 注入拿到的是数据库权限；命令注入直接拿到的是**运行 Web 进程的操作系统权限**。一旦成立，读任意文件、起外连、横向移动都可能发生，定级基本是 Critical。

根因与 SQL 注入完全同构：**数据被当成了代码**。区别只在于解释器从数据库换成了 shell。

### shell 元字符：注入之所以可能的原因

当程序把命令字符串交给 shell 执行时，shell 会先做一轮解析。以下字符对 shell 有特殊含义，不是普通文本：

| 字符 | 含义 |
|------|------|
| `;` | 顺序执行下一条命令 |
| `&&` / `\|\|` | 前一条成功 / 失败时执行下一条 |
| `\|` | 管道，把输出接给下一条命令 |
| `` ` `` 或 `$( )` | 命令替换，先执行里面的再把结果代入 |
| `&` | 后台执行 |
| 换行符 | 等价于命令分隔 |

所以只要用户输入里能带进这些字符，并且这段字符串最终交给了 shell，命令就会被拆成多条。

```python
# 有漏洞的写法：ping 一个用户给的地址
import os
host = request.args.get("host")
os.system("ping -c 1 " + host)     # shell=True 语义，host 里的 ; 会生效
```

用户传 `127.0.0.1; id`，实际执行的是两条命令。

### 两条根治路线

**路线一：不要 shell（首选）。**

```python
import subprocess
# shell=False（默认），参数以列表传入，操作系统直接 execve
# 此时 "127.0.0.1; id" 整体就是一个参数，ping 会报「无法解析主机名」而不是执行 id
subprocess.run(["ping", "-c", "1", host], capture_output=True, timeout=5, check=False)
```

这与 SQL 参数化是同一个思路：**把命令和参数分开传，而不是拼成一个字符串再让别人解析**。参数列表形式下，`;` 只是主机名里的一个普通字符。

**路线二：如果必须用 shell，就做严格白名单。**

```python
import re, ipaddress

def safe_host(raw: str) -> str:
    # 只接受合法 IPv4，任何其他内容直接拒绝（白名单，不是过滤黑名单）
    return str(ipaddress.IPv4Address(raw))   # 非法会抛 AddressValueError

# 域名场景用严格正则限定字符集
DOMAIN = re.compile(r"^[a-zA-Z0-9.-]{1,253}$")
```

注意顺序：**先校验合法性，不通过就拒绝**；而不是「把危险字符删掉再用」——删除式过滤永远会有遗漏（比如删了 `;` 还有换行符、`$()`、`|`）。

### Python 里的高危调用点

代码审计时直接搜这些：

```text
os.system(...)                    # 永远走 shell
os.popen(...)                     # 永远走 shell
subprocess.*(..., shell=True)     # 显式开 shell，最常见的坑
commands.getoutput(...)           # Python 2 遗留
eval(...) / exec(...)             # 不是命令注入但同类问题：代码注入
pickle.loads(不可信数据)           # 反序列化即代码执行
```

其他语言对应：Java 的 `Runtime.exec("sh -c ...")`、Node 的 `child_process.exec`（`execFile`/`spawn` 才是安全版）、PHP 的 `system`/`exec`/`shell_exec`/`passthru`。

## 用法

### 第一步：找出可能调外部程序的功能

命令注入的入口有很强的特征，见到这些功能就要重点排查：

```text
网络工具类：ping / traceroute / nslookup / 端口连通性检测（运维平台高发）
文件处理类：图片压缩（ImageMagick）、视频转码（ffmpeg）、PDF 转换、Office 转换
压缩解压类：zip / tar / unrar 调用
运维平台类：日志查询（拼 grep）、备份还原（拼 mysqldump）、批量执行
第三方集成：调用 curl / wget 拉取远程资源
DNS/证书类：openssl 命令行调用
```

一个经验：**凡是「后端做了一件 Python/Java 自己不擅长的事」，多半是在调外部命令**。

### 第二步：在授权靶场里定性

以 DVWA 的 Command Injection 模块（low 级别）为例，按无害探针逐级验证。

```bash
# 本地起靶场，仅绑定回环
docker run -d --rm -p 127.0.0.1:8080:80 --name dvwa vulnerables/web-dvwa
```

**探针 1：分隔符 + 无害命令，看输出是否多出内容。**

```bash
# 在靶场的 IP 输入框里填入（whoami 无副作用，仅用于证明命令被执行）
127.0.0.1; whoami
```

如果响应里除了 ping 结果，还多出一个用户名，说明第二条命令被执行了——注入成立，且能看到回显。

**探针 2：无回显时用时延做判定。**

很多真实场景下命令输出不会返回给前端，这时用可控延时证明「命令确实跑了」：

```bash
# 正常请求秒回；这一条如果慢约 5 秒，说明 sleep 被执行
127.0.0.1 && sleep 5
```

配合 `curl` 计时更客观：

```bash
# -o /dev/null 丢弃响应体，只看总耗时
curl -s -o /dev/null -w "耗时: %{time_total}s\n" \
  "http://127.0.0.1:8080/vulnerabilities/exec/?ip=127.0.0.1"
```

**探针 3：确认过滤强度（用于写修复建议）。**

如果 `;` 被拦了，换其他分隔符看是否也被拦，用来判断开发用的是黑名单还是白名单：

```text
127.0.0.1 && whoami        逻辑与
127.0.0.1 | whoami         管道
127.0.0.1 %0a whoami       换行符（URL 编码）
127.0.0.1 `whoami`         命令替换
```

如果只拦了 `;` 却放过了 `|`、`&&`、换行符，就说明是黑名单过滤，报告里应明确建议改为「参数列表调用 + 输入白名单」。

**到此为止**：证明命令被执行（多出回显 / 出现时延 / 触发外连），就足以定性提报。不需要真的去读系统文件或建立交互式访问，那既超出验证目的，也可能超出授权范围。

### 第三步：修复验证

修复后回归，逐个确认之前成立的探针都失效：

```python
# 修复前
os.system(f"ping -c 1 {host}")

# 修复后：参数列表 + 校验 + 超时
import subprocess, ipaddress
def do_ping(raw_host: str):
    host = str(ipaddress.IPv4Address(raw_host))     # 非法直接抛异常拒绝
    return subprocess.run(
        ["ping", "-c", "1", host],
        shell=False, capture_output=True, timeout=5, check=False,
    )
```

回归用例：把之前能注入的所有 payload 再打一遍，断言全部被拒绝或当成无效主机名处理。

## 踩坑

1. **只拦 `;` 就以为修好了**。分隔符不止一个：`|`、`&&`、`||`、换行符 `%0a`、命令替换 `` ` `` 和 `$()`。黑名单永远列不全，正确做法是参数列表 + 白名单校验。
2. **`shell=True` 是万恶之源**。很多人为了「方便传一整条命令」用了 `shell=True`，只要参数里有用户输入就中招。默认就应该用 `shell=False` + 列表。
3. **参数列表里塞了整条命令**。`subprocess.run(["sh", "-c", user_cmd])` 表面用了列表，实际又开了 shell，等于没防。列表的每个元素应该是「一个参数」，而不是「一整条命令」。
4. **过滤用删除而非拒绝**。`host.replace(";", "")` 这种「删危险字符」的写法，遇到 `a;;b`（删一次还剩一个）或组合字符就绕过了。要么校验通过、要么拒绝，不要试图「清洗」。
5. **无回显就以为没漏洞**。命令注入常常没有回显，必须用时间盲注（`sleep`）或带外检测（DNS/HTTP 外连到自己的服务器）来确认，不能只看页面有没有变化。
6. **测试时执行了破坏性命令**。手贱试了 `rm`、`shutdown`、`:(){ :|:& };:`（fork 炸弹）把测试机搞挂。定性只用 `whoami`、`id`、`sleep` 这类无副作用命令。
7. **忽略间接命令注入**。参数没直接进命令，但被写进一个配置文件 / 文件名，后续被某个脚本 `source` 或作为参数展开。要跟着数据流走。
8. **文件名也是注入面**。上传文件名 `a.jpg; rm -rf /`，如果后端把文件名拼进了转码命令，一样中招。文件名要做白名单重命名。

## 面试怎么答

**Q：命令注入和 SQL 注入有什么异同？**

A：原理完全一样，都是「数据被当成代码解释执行」，区别在于解释器不同——SQL 注入的解释器是数据库，命令注入的解释器是操作系统 shell。危害上命令注入更严重，因为它直接拿到的是运行 Web 进程的系统权限，能读文件、起外连、横向移动，基本都是 Critical。防御思路也同构：SQL 用参数化把数据和语句分开，命令注入用参数列表调用（`shell=False` 加 args 列表）把命令和参数分开，让用户输入永远只是一个参数，不参与 shell 解析。

**Q：怎么找命令注入？怎么在无回显时确认？**

A：先按功能特征找入口，凡是后端要调外部程序的地方都是嫌疑点，比如 ping、traceroute 这类网络工具，图片/视频/文档转换（背后是 ImageMagick、ffmpeg），还有运维平台里拼 grep、拼 mysqldump 的功能。定性上，有回显时直接用 `; whoami` 看输出里有没有多出用户名；没有回显时用时间盲注，注入 `&& sleep 5`，正常请求秒回而这条慢五秒就能确认；再隐蔽的场景用带外检测，让被测服务去请求我自己的一个地址，看有没有收到回连。我会强调，定性到「命令确实执行了」就停，全程只用 whoami、id、sleep 这类无副作用的命令，不会去读系统文件或建立交互访问。

**Q：`subprocess` 怎么用才安全？**

A：三个要点。第一，用默认的 `shell=False`，参数以列表传入，这样操作系统直接 execve，不经过 shell，元字符不会被解析。第二，绝对不要为了图方便写成 `subprocess.run(["sh", "-c", 用户输入])`，那又把 shell 引回来了，等于没防。第三，即便用了列表，涉及主机名、文件名这类参数，我还是会加一层白名单校验，比如 IP 就用 `ipaddress.IPv4Address` 去解析，非法直接抛异常拒绝，而不是试图删掉危险字符——删除式过滤总有绕过。另外顺手加 `timeout` 防止命令挂死拖垮服务。
