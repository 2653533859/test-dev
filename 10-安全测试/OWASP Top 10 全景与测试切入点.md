# OWASP Top 10 全景与测试切入点

> Top 10 不是「十个漏洞」，而是「十类风险」。这篇按「测试人员怎么下手」重新组织，每一项给出提问方式、验证方法和防御要点。

![[assets/owasp-top10-map.svg]]
*图示：把 Top 10 (2021) 归成三类——业务语义类（扫描器扫不出、测试人员价值最高）、输入输出处理类（有固定模式、工具+人工都能覆盖）、配置运维类（适合做成流水线检查）。*

## 概念

### Top 10 是什么、不是什么

OWASP Top 10 是基于真实漏洞数据统计出的**十大风险类别**，2021 版是当前主流（2025 版仍在推进中，面试按 2021 答即可）。

它**不是**：

- 漏洞清单（每一类下面有几十种具体漏洞）；
- 检查表（照着过一遍不等于安全）；
- 编码规范（它讲风险，不讲怎么写代码）。

它**是**：拿到任意一个功能时，脑子里的一套提问框架。

### 2021 版十项与相较 2017 的变化

| 编号 | 名称 | 2017 排名变化 | 一句话 |
|------|------|--------------|--------|
| A01 | 失效的访问控制 | 5 → **1** | 越权，最普遍也最容易被漏 |
| A02 | 加密失败 | 3 → 2 | 原「敏感数据泄露」，改为强调**根因是加密用错** |
| A03 | 注入 | 1 → 3 | XSS 被合并进注入 |
| A04 | 不安全设计 | **新增** | 强调威胁建模缺失，不是代码 bug |
| A05 | 安全配置错误 | 6 → 5 | XXE 被合并进来 |
| A06 | 脆弱与过时的组件 | 9 → 6 | 依赖漏洞，SCA 的地盘 |
| A07 | 身份认证失败 | 2 → 7 | 原「失效的身份认证」，框架成熟后排名下降 |
| A08 | 软件与数据完整性失效 | **新增** | 含不安全反序列化、CI/CD 供应链 |
| A09 | 安全日志与监控失效 | 10 → 9 | 出事查不出来 |
| A10 | SSRF | **新增** | 社区投票进榜 |

**面试高频**：为什么访问控制从第 5 升到第 1？因为框架把注入、认证这类「有标准解法」的问题基本解决了（ORM 默认参数化、Spring Security 开箱即用），而访问控制没有通用解法——「谁能看哪条数据」是纯业务逻辑，只能一处处写、一处处测，所以漏得最多。

## 用法

下面按图示的三类分组，每项给出**测试人员的提问 → 怎么验 → 怎么防**。

### A 类：业务语义类（人工为主）

#### A01 失效的访问控制

- **提问**：这个接口的数据属于谁？服务端拿什么判断我是不是有权访问？
- **验证**：用 A 的凭证访问 B 的资源 id；用普通账号直调管理接口。详见 [[水平越权与垂直越权测试]]。
- **防御**：默认拒绝；权限判断放服务端且基于会话身份，不信任任何请求参数。

#### A04 不安全设计

代码写得再对也挡不住设计上就没考虑风险。典型：

- 找回密码只验手机号不验证码有效期，可无限尝试；
- 优惠券没有「每人限领一张」的约束；
- 转账没有额度和二次确认。

- **提问**：这个流程最坏情况下会被怎么滥用？有没有次数、额度、频率的兜底？
- **验证**：在测试环境把业务规则推到极限——领 100 次券、下 0 元单、退款退两次。
- **防御**：需求评审阶段就做威胁建模，把风控规则写进验收标准。

#### A07 身份认证失败

- **提问**：口令策略、失败锁定、会话生命周期、Token 失效机制是怎么做的？
- **验证**：见 [[认证与会话安全测试]]、[[JWT 常见安全问题与校验测试]]。
- **防御**：慢哈希存密码、失败限流、登录后重建会话、登出与改密使旧凭证失效。

#### A10 SSRF（服务端请求伪造）

用户提供一个 URL，**服务端**替你去访问它。危险在于服务端在内网，能访问到你访问不到的地方。

```text
典型功能：图片 URL 转存、Webhook 回调配置、PDF 生成（抓远程资源）、
         富文本编辑器的「从 URL 导入」、导入 Excel 时的远程文件地址
```

- **提问**：这个功能里有没有「我填地址、后端去拉」的环节？
- **验证**（授权环境）：把 URL 换成自己搭的一个 HTTP 服务，看服务端是否真的发起了请求（看自建服务的访问日志）。这一步只证明「服务端会去访问我给的地址」，就足以定性了，不需要真的去探内网。

```python
# 在自己的测试机上起一个记录访问的服务，验证服务端是否会主动请求
from http.server import BaseHTTPRequestHandler, HTTPServer

class Probe(BaseHTTPRequestHandler):
    def do_GET(self):
        # 服务端真的来访问了 → 说明该功能存在 SSRF 风险面
        print("收到回连:", self.client_address, self.path, self.headers.get("User-Agent"))
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"ok")

HTTPServer(("0.0.0.0", 9001), Probe).serve_forever()
```

- **防御**：URL 白名单（只允许指定域名）；解析后校验 IP 不在内网段并防 DNS Rebinding；禁用 302 跟随；出网走独立的代理并限制目标。

### B 类：输入与输出处理类

#### A03 注入

包含 SQL 注入、命令注入、XSS、LDAP/NoSQL/模板注入。共同点：**用户数据被当成了代码解释执行**。

- **提问**：这个参数最后进了哪个解释器？SQL？shell？HTML？模板引擎？
- **验证**：见 [[SQL 注入原理与参数化防御]]、[[命令注入原理与测试方法]]、[[XSS 三种类型与输出编码防御]]。
- **防御**：数据与代码分离（参数化 / 参数数组 / 输出编码），不要指望过滤和转义。

#### A02 加密失败

- **提问**：敏感数据在传输中、存储中、日志中分别是什么形态？
- **验证**：

```bash
# 抓包看登录接口是不是 HTTP 明文（授权测试环境）
curl -v http://test-app.internal.com/api/login -d '{"user":"a","pwd":"b"}'

# 看是否强制跳转 HTTPS、是否下发 HSTS
curl -sI http://test-app.internal.com | grep -iE 'location|strict-transport-security'
```

  再查数据库里密码字段是不是明文或 MD5，看日志里有没有打印完整身份证/手机号。

- **防御**：全站 HTTPS + HSTS；密码用 bcrypt/Argon2 加盐慢哈希（不是 MD5/SHA1）；敏感字段落库加密、展示脱敏、日志脱敏。详见 [[敏感信息泄露与传输配置测试]]。

#### A08 软件与数据完整性失效

- **提问**：代码和依赖从哪来？有没有校验来源？有没有反序列化不可信数据？
- **验证**：检查依赖是否锁定版本与哈希（`requirements.txt` 有没有 `==` 和 `--hash`）；检查有没有 `pickle.loads`、`yaml.load`（非 safe_load）处理外部输入；检查 CI 的凭据是否可被 PR 触发窃取。
- **防御**：锁版本、校验签名、只用 `yaml.safe_load`、绝不反序列化不可信数据、CI 权限最小化。

### C 类：配置与运维类（适合自动化）

#### A05 安全配置错误

最常见也最容易修的一类，建议直接做成基线检查表：

```text
[ ] 生产/测试环境关闭 debug 模式（Django DEBUG=False、Spring 关 actuator 敏感端点）
[ ] 中间件默认账号密码已修改（Tomcat manager、Redis 无密码、Nacos nacos/nacos）
[ ] 目录列表关闭（访问 /static/ 不应列出文件）
[ ] 错误页不返回堆栈与 SQL 语句
[ ] 不该暴露的路径已封：/swagger-ui.html、/actuator/env、/.git/、/.env、/backup.sql
[ ] 安全响应头齐全：CSP、X-Content-Type-Options、X-Frame-Options、HSTS
[ ] CORS 不是 Access-Control-Allow-Origin: * 且不反射任意 Origin
```

#### A06 脆弱与过时的组件

- **验证**：

```bash
# Python 依赖漏洞
pip-audit -r requirements.txt

# 镜像与文件系统漏洞（含 OS 包和应用依赖）
trivy image myapp:1.0.0

# 生成 SBOM 便于后续追溯（比如爆 Log4j 时快速定位受影响服务）
trivy image --format cyclonedx --output sbom.json myapp:1.0.0
```

- **防御**：接入 SCA 到 CI（见 [[SAST、DAST 与 SCA 接入 CI 流水线]]）；定期升级；建立 SBOM。

#### A09 安全日志与监控失效

这一项最容易被测试忽略，但很好测：**做一次异常行为，然后去看有没有记录和告警**。

```text
测试步骤：
1. 用错误密码连续登录 20 次
2. 用 A 的账号尝试访问 B 的资源 10 次
3. 去日志平台搜：这些行为有没有记录？记了哪些字段？
4. 去告警平台看：有没有触发任何告警？
5. 反向检查：日志里有没有把密码、token、身份证明文打出来
```

- **防御**：登录、鉴权失败、权限变更、敏感数据导出必须记审计日志；日志集中存储且不可篡改；关键行为配告警；日志本身要脱敏。

## 踩坑

1. **背编号不理解分类**。面试被问「A04 是什么」答不上很正常，但被问「访问控制为什么排第一」答不上就露馅了。记分类逻辑比记编号有用。
2. **以为 XSS 不在 Top 10 里了**。2021 把 XSS 并进了 A03 注入，不是删除。答题时说清楚「XSS 在 2021 版归入 A03」反而是加分项。
3. **A02 只答「用 HTTPS」**。加密失败的重灾区其实是存储和日志：密码用 MD5、身份证明文入库、日志打印完整 token。传输层反而是最容易做到的。
4. **把 A05 配置问题丢给运维就不管了**。测试环境的配置基线和生产不一致，测的时候一切正常，上线炸。配置检查要跨环境对比。
5. **SSRF 验证时真的去探内网**。授权范围通常只覆盖应用本身，探内网可能越界。验证到「服务端会主动访问我给的外部地址」即可定性，再进一步要重新确认授权。
6. **A09 完全不测**。日志和监控没人报 bug，因为它不影响功能。但出安全事件时它决定了「能不能查清楚」，属于典型的「平时没人看，出事全靠它」。
7. **拿 Top 10 当验收标准**。Top 10 覆盖的是通用风险，业务特有的风险（比如金融的额度绕过、电商的薅羊毛）不在里面，需要按业务另建清单。

## 面试怎么答

**Q：说一下 OWASP Top 10。**

A：不建议背编号，我一般按「谁来测」分三类讲。第一类是业务语义类，包括失效的访问控制、不安全设计、身份认证失败和 SSRF，这类扫描器扫不出来，因为工具不知道「谁该看什么数据」，只能靠人工设计多角色用例，这也是测试人员价值最高的地方。第二类是输入输出处理类，包括注入、加密失败、完整性失效，有固定模式，工具能扫个七八成，人工再补边界。第三类是配置与运维类，包括配置错误、脆弱组件、日志监控不足，最适合做成流水线的自动检查项。这样分完，拿到一个新功能我就有了固定的四个问题：谁能访问它、输入去了哪里、输出给了谁、出事能不能查到。

**Q：2021 版有什么变化？为什么访问控制排到第一？**

A：三个新增项——不安全设计、软件与数据完整性失效、SSRF；XSS 被并进注入，XXE 并进配置错误；访问控制从第 5 升到第 1，注入从第 1 降到第 3。变化的逻辑是：注入和认证这类问题有标准解法，ORM 默认参数化、安全框架开箱即用，所以工程上基本被压下去了；而访问控制没有通用解法，「这条订单属于谁」是纯业务语义，每个接口都要单独写、单独测，一个新接口忘了加校验就是一个洞，所以它的实际发生率最高。新增「不安全设计」也是同一个思路——很多风险不是代码写错，而是需求阶段就没考虑，强调要把威胁建模左移到设计评审。

**Q：SSRF 是什么？你怎么测？**

A：SSRF 是用户提供一个 URL，服务端替你去访问。危险在于服务端往往在内网，能访问到外部访问不到的地址，比如内部管理后台或者云元数据服务。测试上我先找功能面——所有「我填地址、后端去拉」的地方，比如图片 URL 转存、Webhook 配置、远程文件导入、PDF 生成。验证方法是把地址换成我自己搭的一个 HTTP 服务，看它的访问日志里有没有收到回连，收到就说明服务端确实会请求任意地址，这就足以定性并提报了，我不会进一步去探内网，因为那通常超出授权范围。防御上主要是域名白名单、解析后校验 IP 不落在内网段并防 DNS Rebinding、禁止跟随 302 重定向。

**Q：Top 10 里哪几项是你日常最容易发现的？**

A：访问控制和不安全设计，因为我做功能测试时天然就有多个角色的账号和对业务规则的理解。比如测订单模块，我会顺手拿 A 的 token 去查 B 的订单、拿普通用户去调运营的改价接口、把优惠券领取接口并发打几次看会不会超领。这些用例的成本极低，就是在已有功能用例上多加一步，但发现的都是扫描器完全覆盖不到的高危问题。相对地，加密和组件漏洞我更多是靠工具，比如 CI 里的 pip-audit 和 Trivy，我负责的是确认它报的东西在我们的场景里是否真的可利用。
