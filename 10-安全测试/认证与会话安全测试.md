# 认证与会话安全测试

> 认证解决「你是谁」，会话解决「后面这些请求还是不是你」。测试人员最该盯的不是登录页本身，而是**登录之后那张凭证的生命周期**。

![[assets/session-lifecycle.svg]]
*图示：会话从发放、绑定身份、携带访问到过期与登出的完整链路，以及挂在链路上的四个必测风险点——会话固定、登出后仍可用、有效期过长、Cookie 属性缺失。*

## 概念

### 认证 vs 授权：别把两个词混着用

面试里问烂了但仍然经常答错的一对概念：

| | 认证 Authentication | 授权 Authorization |
|---|---|---|
| 回答的问题 | 你是谁 | 你能做什么 |
| 发生时机 | 登录时（一次） | 每次请求（持续） |
| 失败状态码 | 401 Unauthorized | 403 Forbidden |
| 典型漏洞 | 弱口令、爆破、验证码绕过 | 水平/垂直越权 |

一句话记忆：**401 是「我不知道你是谁」，403 是「我知道你是谁，但你不配」**。授权部分详见 [[水平越权与垂直越权测试]]，本篇只管认证与会话。

### HTTP 无状态带来的核心矛盾

HTTP 本身不记事，服务端要认出「这次请求和上次是同一个人」，只能靠客户端每次带一张凭证。凭证一旦签发，就产生三个必须回答的问题：

1. **这张凭证会不会被别人拿到？**（传输、存储、XSS 窃取）
2. **拿到之后能用多久？**（有效期、能否作废）
3. **换了人之后旧的还能不能用？**（登出、改密、会话固定）

绝大多数会话漏洞都能归到这三条里的一条。

### 两种会话实现的差别

```text
服务端会话（Session）
  客户端只拿一个 sessionId，数据全在服务端（内存 / Redis）
  优点：随时能作废（删掉服务端记录即可）
  缺点：分布式下要共享存储

无状态令牌（JWT / Token）
  数据编码在令牌里，服务端不存
  优点：水平扩展省事
  缺点：签出去就收不回来 —— 登出、改密后怎么让它失效是个专门问题
```

**「能不能立刻作废」是这两者最本质的差别**，也是测试时的关注重点。JWT 特有的坑见 [[JWT 常见安全问题与校验测试]]。

### 会话固定（Session Fixation）为什么是漏洞

正常流程里，用户没登录时服务端也会发一个匿名 sessionId（用来存购物车之类的东西）。如果**登录成功后服务端沿用了这个旧的 sessionId**，就出问题了：

```text
1. 攻击者自己访问站点，拿到一个匿名 sessionId = ABC
2. 想办法让受害者的浏览器也用上 ABC（旧浏览器的 URL 重写、子域 Cookie 注入等）
3. 受害者用 ABC 登录成功，服务端把 ABC 绑定到受害者账号
4. 攻击者手里的 ABC 现在也是受害者的登录态了
```

修复只有一句话：**登录成功时重新生成会话标识**（`session.regenerate()`），把旧的作废。测法极简单——记录登录前后的 Cookie 值，**必须不一样**。

## 用法

### 会话安全六项基础检查

这六项是每个项目都该跑一遍的固定动作，全部在测试环境用自己的账号完成。

**检查 1：Set-Cookie 三属性**

```bash
# 只看登录响应的 Set-Cookie 头
curl -i -s -X POST http://test-app.internal.com/api/login \
  -d 'username=test01&password=Test@123' | grep -i '^set-cookie'
```

```text
期望：Set-Cookie: SESSION=xxx; Path=/; HttpOnly; Secure; SameSite=Lax
缺 HttpOnly  → XSS 可以直接 document.cookie 读走会话
缺 Secure    → 明文 HTTP 信道上会被截获
缺 SameSite  → 更容易被 CSRF 利用（详见 [[CSRF 原理与 Token 防护]]）
```

**检查 2：登录前后 sessionId 是否变化（会话固定）**

```bash
# 第一步：未登录访问首页，拿到匿名会话
curl -i -s -c cookie.txt http://test-app.internal.com/ | grep -i '^set-cookie'
# 第二步：带着这个 cookie 去登录
curl -i -s -b cookie.txt -c cookie.txt -X POST \
  http://test-app.internal.com/api/login \
  -d 'username=test01&password=Test@123' | grep -i '^set-cookie'
# 对比两次的 SESSION 值：必须不同，相同即为会话固定漏洞
```

**检查 3：登出后旧凭证是否真的失效**

这是实际项目里命中率最高的一条。很多前端只是清了 localStorage 就跳转登录页，服务端根本没作废。

```bash
# 1. 登录拿到 token（在测试环境用自己的账号）
TOKEN=$(curl -s -X POST http://test-app.internal.com/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"test01","password":"Test@123"}' | jq -r .data.token)

# 2. 正常调一个业务接口，确认能用
curl -s -o /dev/null -w '登出前: %{http_code}\n' \
  -H "Authorization: Bearer $TOKEN" http://test-app.internal.com/api/profile

# 3. 调登出接口
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://test-app.internal.com/api/logout > /dev/null

# 4. 拿同一个 token 再调一次 —— 期望 401，返回 200 就是漏洞
curl -s -o /dev/null -w '登出后: %{http_code}\n' \
  -H "Authorization: Bearer $TOKEN" http://test-app.internal.com/api/profile
```

**检查 4：改密码 / 改绑手机后，其他设备的会话是否被踢**

场景是「账号被盗后用户改密码自救」。如果改密后旧会话还活着，攻击者就没被踢下线，改密码这个动作就失去了意义。

```text
步骤  设备 1 登录 → 设备 2 登录 → 设备 1 修改密码 → 设备 2 继续调业务接口
预期  设备 2 返回 401，被强制下线
```

**检查 5：有效期与超时策略**

```text
空闲超时   30 分钟无操作应失效（金融类可缩到 15 分钟）
绝对超时   不管有没有操作，8 小时 / 24 小时后必须重新登录
测法       改本地时间不算数（服务端判定），用 sleep 或让运维临时调小配置来验
速查       解开 token 看 exp 字段；Cookie 看 Max-Age / Expires
```

**检查 6：登录接口的防爆破**

```text
连续错误密码 5 次      → 应触发验证码或锁定
锁定是锁账号还是锁 IP  → 只锁账号会被用来恶意锁定他人（拒绝服务），应结合 IP + 设备指纹
错误提示是否泄露信息   → 「用户名不存在」vs「密码错误」会被用来枚举账号，应统一为
                        「用户名或密码错误」
返回时间是否有差异     → 用户存在时走哈希校验更慢，可被时间侧信道枚举
```

验证防爆破**只用自己的测试账号、只发几次请求确认策略生效即可**，不要真的跑字典——那是压测服务端，也超出了测试的范围。

### 弱口令怎么测才算合规

测的是**策略**，不是去撞别人的密码：

```text
① 注册 / 改密时输入 123456、password、与用户名相同、8 位纯数字
   → 应被密码复杂度策略拒绝
② 查系统是否存在默认账号（admin/admin、test/test、guest/guest）
   → 这类账号常见于中间件后台、监控面板，属于配置错误
③ 检查密码存储方式（需要开发配合或代码审计）
   → 明文 / MD5 / SHA1 都不合格，应为 bcrypt、scrypt、Argon2 这类加盐慢哈希
```

**明确不做的事**：不对他人账号做任何口令尝试，不使用泄露密码库撞库，不在生产环境做任何登录尝试。

### 多因素与凭证下发的补充检查

```text
短信 / 邮箱验证码     见 [[验证码绕过与短信接口安全测试]]
「记住我」功能         记住我的 token 是否长期有效、是否也随改密失效
第三方登录回调        state 参数是否校验（防 CSRF）、code 是否一次性
密码找回              见 [[任意用户密码重置漏洞测试]]
接口 token / AK-SK    是否能在前端源码或移动端包里翻到（属敏感信息泄露）
```

### 修复参考实现

```python
# 登录成功：重新生成会话标识 + 记录会话版本
def login(username, password):
    user = auth(username, password)
    if not user:
        # 统一错误文案，避免账号枚举
        raise Unauthorized("用户名或密码错误")
    session.regenerate()                      # 关键：作废登录前的匿名会话
    session["uid"] = user.id
    session["ver"] = user.token_version       # 与用户表的版本号绑定
    return ok()

# 每次请求校验：版本号不一致直接拒绝
def current_user():
    uid, ver = session.get("uid"), session.get("ver")
    user = User.get(uid)
    if not user or user.token_version != ver:
        raise Unauthorized()                  # 改密后 token_version 自增，旧会话全废
    return user

# 改密 / 改绑 / 主动登出全部设备：只需自增版本号
def change_password(user, new_pwd):
    user.password_hash = bcrypt_hash(new_pwd)
    user.token_version += 1                   # 一行搞定「踢掉所有旧会话」
    user.save()
```

`token_version` 这个模式对**无状态 JWT 同样适用**：把版本号写进 payload，校验时和数据库比对一次。代价是失去了「完全不查库」的优势，但换来了可撤销性，绝大多数业务系统都值这个代价。

## 踩坑

1. **只测登录不测登出**。登出接口经常是纯前端行为，服务端压根没实现作废。这条用例成本极低、命中率极高，务必固定加进回归集。
2. **把 401 和 403 用混**。凭证过期返回 403 会让前端不知道该跳登录页；无权限返回 401 又会导致前端反复弹登录框。这不只是规范问题，也会影响安全逻辑的判断。
3. **登录前后 Cookie 名字变了但没重新生成**。有的实现登录后换了一个 Cookie 名，旧的匿名 Cookie 还留着且仍被服务端认，等于没修会话固定。要看的是「服务端认哪个」，不是「浏览器里有几个」。
4. **只锁账号不锁 IP**。攻击者可以用错误密码持续锁定他人账号，把防爆破变成拒绝服务。应结合 IP、设备、渐进式延迟。
5. **错误提示区分「用户名不存在」和「密码错误」**。等于送了一个账号枚举接口。注册和找回密码页面也有同样问题（「该手机号未注册」）。
6. **忽略响应时间差异**。用户存在时走完整哈希校验耗时几百毫秒，不存在时立刻返回——这个差异足以枚举账号。修复是「不存在时也执行一次假哈希」。
7. **改密后不踢会话**。用户以为改了密码就安全了，实际攻击者的会话还活着。这是「用户预期」和「系统行为」不一致造成的真实风险。
8. **测试账号用弱口令并带到线上**。测试环境留的 `admin/123456` 随环境同步到预发甚至生产，是相当常见的事故来源。
9. **在生产环境验证登出 / 踢会话逻辑**。会踢掉真实用户，属于影响生产的行为。全部在测试环境完成。
10. **「记住我」的长期 token 被遗忘**。改密、登出都处理了，唯独漏了记住我的 token，30 天内仍可免密登录。

## 面试怎么答

**Q：认证和授权的区别？对应哪些状态码？**

A：认证解决「你是谁」，发生在登录时，失败返回 401；授权解决「你能做什么」，每次请求都要判，失败返回 403。一句话记：401 是我不知道你是谁，403 是我知道你是谁但你不配。对应的漏洞类型也不同——认证侧是弱口令、爆破、验证码绕过、会话管理问题；授权侧是水平越权和垂直越权。

**Q：什么是会话固定？怎么测怎么修？**

A：服务端在用户未登录时也会发一个匿名 sessionId，如果登录成功后仍然沿用这个旧 id，攻击者就可以预先让受害者的浏览器用上一个自己已知的 id，等受害者登录后，这个 id 就被绑定到了受害者账号，攻击者手里的同一个 id 也就成了登录态。测法非常简单：抓登录前和登录后的 Cookie，值必须变化，一样就是漏洞。修法是登录成功时调用 session regenerate，重新生成标识并作废旧的。

**Q：一个登录功能，你会设计哪些安全用例？**

A：我会分四层。第一层是凭证下发：看 Set-Cookie 有没有 HttpOnly、Secure、SameSite 三个属性，登录前后 sessionId 有没有变化。第二层是生命周期：登出后拿旧 token 重放业务接口应返回 401，改密码后其他设备应被踢下线，空闲超时和绝对超时是否生效，「记住我」的长期 token 是否也跟着失效。第三层是登录接口本身：连续错误是否触发验证码或锁定，锁定策略会不会被用来恶意锁定他人，错误提示是不是统一文案，响应时间有没有差异导致账号枚举。第四层是口令策略：注册和改密时能不能设 123456，系统有没有 admin/admin 这类默认账号，密码存储是不是加盐慢哈希。这里面命中率最高的是「登出后 token 仍可用」，因为很多前端只清了本地存储。

**Q：JWT 登出怎么做？无状态和可撤销矛盾吗？**

A：确实矛盾，JWT 签出去服务端就收不回来了，所以纯无状态方案下「登出」只能靠前端删本地存储，token 在有效期内仍然有效。工程上有三种折中：一是 access token 做得很短，15 分钟以内，靠 refresh token 续期，登出时只作废 refresh token，最多留 15 分钟窗口；二是维护一个黑名单，把主动登出的 token id 放进 Redis 并设置到 token 原本的过期时间，校验时查一次；三是在用户表里存一个 token_version，写进 payload，登出或改密时自增，校验时比对一次。后两种都要查库，等于放弃了完全无状态，但换来可撤销性，大多数业务系统都该这么做。

**Q：密码应该怎么存？为什么不能用 MD5 加盐？**

A：应该用 bcrypt、scrypt 或 Argon2 这类专门的密码哈希算法。MD5、SHA1、SHA256 的问题不是「不安全」而是「太快」——它们被设计成高吞吐，现代 GPU 一秒能算几十亿次，加了盐只是让彩虹表失效，挡不住针对单个用户的暴力破解。bcrypt 这类算法带可调的代价因子，可以让单次计算稳定在几十到几百毫秒，正常登录感知不到，但暴力破解的成本被放大了几个数量级。Argon2 还额外增加了内存消耗，进一步压制了 GPU 和专用硬件的优势。
