# 数据库测试数据构造与清理策略

## 概念

测开在数据库层的核心动作就两件：**造数据**（让被测功能有可校验的输入）和**清数据**（测试后不留垃圾，不污染别人、不影响下次执行）。数据构造不是「随便插几条」，而是要**贴合业务约束**——否则外键、唯一索引、`NOT NULL`、枚举值校验会直接把你的插入语句打回来。

构造方式大致分三类：

| 方式 | 适用 | 说明 |
| --- | --- | --- |
| SQL 直插 | 基础数据、少量精准数据 | `INSERT` 写死值，最可控 |
| 脚本/程序生成 | 大数据量、随机组合 | Python 批量造，模拟真实分布 |
| 生产脱敏克隆 | 回归真实场景 | 导出生产 → 脱敏 → 导入测试库 |

## 用法

### 造数据：先建表再插符合约束的数据

```sql
CREATE TABLE orders (
  id        INT PRIMARY KEY AUTO_INCREMENT,
  user_id   INT NOT NULL,
  status    TINYINT NOT NULL DEFAULT 0,   -- 0待支付 1已支付 2已取消
  amount    DECIMAL(10,2) NOT NULL,
  created_at DATETIME NOT NULL
);

-- 按业务约束精准造
INSERT INTO orders (user_id, status, amount, created_at) VALUES
  (1001, 1, 99.00,  '2026-07-30 10:00:00'),
  (1001, 2, 50.00,  '2026-07-30 11:00:00'),
  (1002, 0, 199.50, '2026-07-30 12:00:00');
```

### 造数据：用 Python 批量生成

```python
import pymysql, random
conn = pymysql.connect(host='testdb', user='tester', password='x', db='shop')
cur = conn.cursor()
for i in range(1000):
    uid = random.randint(1000, 2000)
    status = random.choice([0, 1, 2])
    amount = round(random.uniform(1, 500), 2)
    cur.execute(
        "INSERT INTO orders (user_id, status, amount, created_at) VALUES (%s,%s,%s,NOW())",
        (uid, status, amount))
conn.commit(); cur.close(); conn.close()
```

### 清数据：三档策略

```sql
-- 档1：清自己的测试数据（最安全，按条件删）
DELETE FROM orders WHERE user_id BETWEEN 1000 AND 2000;

-- 档2：整表清空且重置自增（不可回滚风险大，仅测试表）
TRUNCATE TABLE orders;

-- 档3：连同结构一起删（极少用，慎之又慎）
-- DROP TABLE orders;
```

更稳妥的做法：测试前把数据范围用「标记字段」圈定，例如所有测试数据 `source='auto_test'`，清理时只 `DELETE FROM orders WHERE source='auto_test'`，绝不动他人数据。

## 踩坑

1. **造数据忽略约束导致插不进**：外键、唯一索引、`NOT NULL`、枚举范围任意一条不满足就整批失败。造数前先 `SHOW CREATE TABLE` 看清约束。
2. **清理用 `DELETE` 不带 `WHERE`**：在事务外执行会真删且难恢复，瞬间清空整张表。生产/共享库严禁。
3. **`TRUNCATE` 隐式提交、没法回滚**：它本质是 DDL，会立即生效且绕过事务，误执行无法 `ROLLBACK`。清理务必优先 `DELETE`。
4. **测试间数据互相污染**：A 用例造的数据没清，B 用例断言时读到脏数据导致偶发失败。每个用例「自给自足」造数 + 收尾清理，或用事务回滚兜底。
5. **自增主键跨用例冲突**：`TRUNCATE` 会重置 `AUTO_INCREMENT`，但 `DELETE` 不会，导致用例间 ID 不连续、依赖固定 ID 的断言时灵时不灵。别让断言强依赖自增 ID。
6. **并发跑用例抢同一条数据**：多个用例用同一批 `user_id` 造数据会相互干扰。用动态唯一标识（时间戳+进程号）隔离。
7. **只清业务表不清关联表**：订单清了，订单明细还留着，外键或后续统计对不上。清理要按依赖顺序（子表先清，父表后清）。
8. **生产脱敏不彻底**：克隆生产数据时手机号、身份证、密码哈希没脱敏就进测试库，造成隐私泄露。脱敏是硬要求。
9. **大数据量造数不提交/一次 commit 太大**：几千条一次性 `executemany` + 单次 `commit` 可能锁表或超时，分批提交更稳。

## 面试怎么答

**Q：你怎么保证自动化测试后数据库是干净的？**
A：三层保障——①每条用例「自建自清」，开头造所需数据、结尾按标识字段（`source='auto_test'`）精准 `DELETE`；②能包在事务里的用例用事务，结束 `ROLLBACK` 整体回退；③共享测试库禁止 `TRUNCATE`/`DROP`，清理必须带 `WHERE` 且只动自己标记的数据。

**Q：造数据和清数据的先后顺序有什么讲究？**
A：按外键依赖反向操作。清理时先删子表（如订单明细）再删父表（订单）；造数据时先插父表再插子表。否则外键约束会拒绝写入/删除。

**Q：TRUNCATE 和 DELETE 清空表，测试上怎么选？**
A：测试清理优先 `DELETE ... WHERE`，可回滚、安全；只有确认是隔离的测试专用表、且需要重置自增时才用 `TRUNCATE`，且清楚它无法回滚。
