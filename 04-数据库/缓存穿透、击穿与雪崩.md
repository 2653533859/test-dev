# 缓存穿透、击穿与雪崩

![[assets/cache-issues.svg]]

*图示：穿透/击穿/雪崩三者的触发条件、区别与对应解法。*

## 概念

缓存的目的是挡在数据库前面、扛住大部分读流量。当「缓存没挡住、请求直接打到 DB」时，会出现三类经典问题。测开必须能区分三者，因为**压测和故障演练的设计点完全不同**：

| 问题 | 触发条件 | 本质 |
| --- | --- | --- |
| **穿透** | 请求的数据**根本不存在**（Redis 无、DB 也无） | 非法/误用 key 持续打 DB |
| **击穿** | 某个**热点 key 突然过期**，瞬时大量请求并发回源 | 单点失效的并发冲击 |
| **雪崩** | **大量 key 同一时刻失效**或 Redis 宕机 | 规模性失效压垮 DB |

注意三者共同前提：都是「缓存未命中 → 回源 DB」。区别在 key 是否存在、是单点还是批量。

## 用法

### 复现穿透：查一个永远不存在的 id

```bash
# 反复查不存在的 key
for i in $(seq 1 10000); do
  redis-cli get "product:-1"        # 永远 miss
  curl "http://api/product/-1"      # 每次都打到 DB
done
```

解法 1 —— 缓存空值（短期）：

```bash
SET product:-1 "NULL" EX 60    # 查 DB 没有也记一下，1 分钟内不再查 DB
```

解法 2 —— 布隆过滤器拦非法 key（伪代码）：

```python
if not bloom_filter.might_contain(key):
    return  # 直接拒绝，根本不进 Redis/DB
```

### 复现击穿：热点 key 过期瞬间并发

```bash
SET hot:detail "..." EX 5     # 设个超短过期
# 5 秒后大量并发同时 GET miss，全部去查 DB
```

解法 —— 互斥单飞（只放一个请求回源）：

```python
val = redis.get(key)
if val is None:
    if redis.set("lock:"+key, 1, ex=3, nx=True):   # 抢到锁的才回源（set + nx + ex 原子）
        val = db.query(key)
        redis.set(key, val, ex=300)
        redis.delete("lock:"+key)
    else:
        time.sleep(0.05)                     # 没抢到，稍等重试读缓存
        val = redis.get(key)
```

### 复现雪崩：批量 key 同时失效

```bash
# 初始化时给所有 key 设相同过期 → 到点集体失效
for k in keys: redis.set(k, v, ex=3600)
```

解法 —— 过期时间加随机抖动：

```python
import random
redis.set(k, v, ex=3600 + random.randint(0, 600))   # 1h±10min 分散失效
```

## 踩坑

1. **把三者混为一谈**：穿透是「key 不存在」、击穿是「单热点失效」、雪崩是「批量失效」。故障归因错了，演练和修复方向就全错。
2. **缓存空值不设短过期**：缓存 `NULL` 却给了和正常数据一样长（甚至不过期）的 TTL，若之后数据真补上了，会长期读到空值。空值必须短过期。
3. **布隆过滤器误判处理不当**：布隆有「假阳性」（说存在可能不存在），不能因为它说「存在」就放行到 DB 而不做 DB 兜底；但它「说不存在」一定不存在，用来拦截最合适。
4. **互斥锁没设过期导致死锁**：`SETNX` 抢锁后进程崩了、锁不过期，其他请求永远拿不到。锁必须带 `EX` 过期。
5. **单飞锁内回源失败未释放锁**：回源 DB 抛异常，锁没删，后续请求全卡住。务必 `try/finally` 释放。
6. **雪崩只加随机过期，忘了 Redis 宕机**：批量过期只是雪崩的一半，Redis 集群挂了同样雪崩。还要做高可用（哨兵/集群）+ 多级缓存（本地缓存兜底）。
7. **热点 key 用「逻辑过期」却没真正兜底**：逻辑过期（value 里带过期时间，由业务判断异步刷新）能避免阻塞，但若异步刷新失败，旧数据会一直被用。要有降级返回旧值还是报错的策略。
8. **压测只测正常命中**：缓存问题只有在「miss 场景」才暴露。压测必须刻意构造 miss / 过期 / 不存在 key 的流量，否则上线就被打挂。
9. **认为加锁就万事大吉**：击穿用单飞锁只对「同一个 key」有效；雪崩是大量不同 key 同时失效，锁解决不了，得靠分散过期 + 限流 + 降级。

## 面试怎么答

**Q：穿透和击穿有什么区别？**
A：穿透是请求的数据根本不存在（Redis 和 DB 都没有），靠缓存空值或布隆过滤器解决；击穿是某个热点 key 突然过期，瞬时大量并发回源，靠互斥单飞/热点不过期解决。一个针对「不存在的 key」，一个针对「存在但失效的热 key」。

**Q：怎么防止缓存雪崩？**
A：三点——①过期时间加随机抖动，避免集体失效；②Redis 高可用（集群/哨兵）+ 本地多级缓存兜底宕机；③DB 侧限流、降级、熔断，即使缓存失效也不被压垮。

**Q：缓存空值会有什么问题？**
A：如果空值 TTL 太长，期间真实数据补上了也会读到空（数据不一致），所以空值要设很短的过期；另外大量不同非法 key 都缓存空值也会占内存，这种场景更适合布隆过滤器前置拦截。
