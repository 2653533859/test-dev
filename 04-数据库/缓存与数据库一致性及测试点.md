# 缓存与数据库一致性及测试点

![[assets/cache-db-consistency.svg]]

*图示：Cache-Aside 读写流程，以及「先更新 DB、再删缓存」下的典型脏数据窗口。*

## 概念

缓存是 DB 的**副本**，DB 才是真相源。只要有两份数据，就存在「它们暂时不一致」的窗口。一致性问题不是「能不能 100% 实时一致」（代价极高），而是「如何在可接受的延迟内收敛到一致」。

最常见的读写模式是 **Cache-Aside（旁路缓存）**：

- **读**：先查 Redis → 命中返回；未命中查 DB → 写入 Redis 再返回。
- **写**：先更新 DB → 再**删除**缓存（不是更新缓存）。下次读自然回源重建，避免「双写」两份都写的复杂度。

为什么「删缓存」而不是「更新缓存」：直接更新缓存如果失败，缓存就比 DB 旧；而删缓存把不一致收敛成「下一次读自动重建」，配合 TTL 兜底更稳。

## 用法

### 标准实现：先 DB 后删缓存

```python
def update_product(pid, price):
    db.execute("UPDATE product SET price=%s WHERE id=%s", (price, pid))  # 1. 更 DB
    redis.delete(f"product:{pid}")                                       # 2. 删缓存

def get_product(pid):
    val = redis.get(f"product:{pid}")
    if val is None:
        val = db.query("SELECT * FROM product WHERE id=%s", (pid,))      # 3. 回源
        redis.set(f"product:{pid}", val, ex=3600)                        # 4. 重建
    return val
```

### 延迟双删（降低脏窗口概率）

```python
def update_product(pid, price):
    redis.delete(f"product:{pid}")                  # 1. 先删
    db.execute("UPDATE product SET price=%s ...", ...)# 2. 更 DB
    time.sleep(0.5)                                 # 3. 等读请求窗口过去
    redis.delete(f"product:{pid}")                  # 4. 再删，清掉可能写入的旧值
```

## 踩坑

1. **「先更缓存再更 DB」导致脏数据**：若更新缓存成功、写 DB 失败（事务回滚），缓存是新值、DB 是旧值，后续读一直错。所以推荐「先 DB 后删缓存」。
2. **忽略并发读写的小概率脏窗口**：即便「先 DB 后删」，也有极小窗口——A 读 miss 查到旧 DB 值，B 更新 DB 并删缓存，A 又把旧值写回缓存（见上图）。窗口极短但存在，靠「删缓存 + TTL 兜底」收敛，而非追求绝对一致。
3. **删缓存失败不重试**：DB 提交后 `redis.delete` 因网络失败，缓存仍是旧值。要加重试（消息队列/定时补偿）或订阅 binlog（Canal）异步删。
4. **用「更新缓存」代替「删缓存」**：更新缓存若并发乱序（B 先更、A 后更）会写反。删缓存把正确性转移给「下次读重建」，更不容易错。
5. **TTL 太长，脏数据存活久**：缓存过期时间设几小时，一旦不一致要等很久才自愈。热点数据 TTL 适当短，或依赖删缓存主动失效。
6. **测试只验「正常读写」不验「并发不一致」**：一致性的 bug 只在并发读写、删缓存失败、宕机恢复时才暴露。压测要刻意构造这些场景。
7. **把缓存当 DB 用，丢数据**：Redis 宕机或淘汰策略（LRU）会丢 key，若业务依赖缓存里的「订单状态」做判断会出错。关键状态以 DB 为准，缓存只加速。
8. **大 key / 热 key 让删缓存变慢**：删一个巨型 key 阻塞，影响一致性的及时性。大 key 拆分 + `UNLINK` 异步删。
9. **认为延迟双删能彻底解决**：延迟双删只是降低概率，不是银弹；且 `sleep` 在请求线程里会拖慢响应。生产更常用「binlog 订阅异步删」替代睡眠双删。
10. **没校验「最终一致」**：测试只在写完后立刻读，没等 TTL/补偿生效验证最终一致。应增加「延迟校验」用例确认数据最终收敛。

## 面试怎么答

**Q：缓存和 DB 如何保证一致性？**
A：没有银弹，追求「最终一致」。主流用 Cache-Aside：写时先更新 DB、再删缓存（而非更新缓存），下次读回源重建；配合缓存 TTL 兜底。为降低并发脏窗口可加延迟双删，删缓存失败用消息队列/订阅 binlog 补偿。强一致需求（如余额）则直接读 DB 或加分布式锁，不依赖缓存。

**Q：为什么是删缓存而不是更新缓存？**
A：更新缓存有并发写乱序风险（后发的旧值覆盖先发的新值），且缓存更新失败会留下脏值。删缓存把「正确性」交给下一次读重建，逻辑更简单、出错面更小，TTL 还能兜底。

**Q：怎么测试缓存一致性？**
A：三层面——①功能：写后读验证命中最新值；②并发：多线程读写 + 删缓存失败注入，验证最终一致；③容灾：Redis 宕机/逐出后业务降级读 DB 仍正确，恢复后缓存能重建。关键要有「延迟校验」确认最终收敛。
