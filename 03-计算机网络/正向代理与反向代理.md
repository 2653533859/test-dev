# 正向代理与反向代理

> 听到「代理」先别急着混。正向代理是「客户端借着代理去够不到的地方」，反向代理是「服务端躲在代理后面接客」。一个是**用户视角的出口**，一个是**服务视角的入口**。

![[assets/proxy-forward-reverse.svg]]
*图示：左为员工通过正向代理访问外网；右为用户的请求经反向代理落到多台后端。*

## 概念

### 正向代理：你得先「翻」过去

正向代理里，**代理服务器代替客户端去发起请求**。典型场景：公司内网要访问公网、测试环境要访问生产依赖、或本地要调一个只有特定出口 IP 才能达的服务。

```text
你的浏览器 ──► 正向代理(公司出口/IP 白名单) ──► 目标服务器
```

特征是：**客户端知道自己在用代理**，且代理「对服务端隐藏了真实客户端」。

### 反向代理：服务端躲在后面

反向代理里，**代理服务器代替服务端接收请求，再转发给后端**。典型场景：Nginx 挡在应用前做 TLS 终止、负载均衡、缓存。

```text
用户 ──► 反向代理(Nginx) ──► 后端 A / 后端 B / 后端 C
```

特征是：**客户端不知道背后有几台后端**，代理「对客户端隐藏了真实服务端」。

### 为什么测试必须分清两者

- 抓 HTTPS 包时，mitmproxy 是一种**正向代理**（你主动把流量导给它）。
- 压测时，你打的是 Nginx 这个**反向代理**，再由它分发。
- 定位「连的是哪台机器」时：正向代理决定了「你的请求从哪个 IP 出去」，反向代理决定了「请求最终落到哪台后端」。

## 用法

### 用 SSH 动态端口搭一个正向代理（SOCKS）

```bash
# 你有一台跳板机 jump.example.com，本地 1080 变成 SOCKS5 代理
ssh -D 1080 user@jump.example.com

# 之后浏览器 / curl 走这个代理：
curl --proxy socks5://127.0.0.1:1080 https://api.internal/health
# （注意：--proxy 接 socks5，不是 http）
```

### Nginx 反向代理 + 负载均衡最简配置

```nginx
# /etc/nginx/conf.d/app.conf
upstream backend {
    server 10.0.2.11:8080 weight=3;   # 权重越高分到的流量越多
    server 10.0.2.12:8080 weight=3;
    server 10.0.2.13:8080 weight=4;
}

server {
    listen 443 ssl;
    server_name app.example.com;
    ssl_certificate     /etc/nginx/ssl/app.crt;
    ssl_certificate_key /etc/nginx/ssl/app.key;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;     # 后端拿到的「真实客户端 IP」
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

### 本地用 mitmproxy 做反向代理（调试 API）

```bash
# mitmproxy 既可以是正向（抓客户端），也能用 reverse 模式当反向代理
mitmproxy --mode reverse:https://api.internal:443 -p 8080
# 浏览器配代理 127.0.0.1:8080，所有去 api.internal 的流量被解密 + 转发
```

### 验证「请求最终落到哪台后端」

```bash
# 连续打多次，看 X-Forwarded-For / 后端 IP 是否轮询
for i in $(seq 1 6); do
  curl -s https://app.example.com/which-backend | grep "10.0.2"
done
# 输出应当大致按 weight 比例出现 11 / 12 / 13
```

## 踩坑

1. **`X-Forwarded-For` 没传，后端拿到的全是代理 IP**。反向代理如果不显式 `proxy_set_header X-Real-IP`，后端日志里所有请求都来自 Nginx 的 IP，限流、风控、审计全失效。正确做法：Nginx 必须带上 `X-Real-IP` 和 `X-Forwarded-For`。

2. **正向代理和反向代理的端口搞混**。本地 `ssh -D 1080` 起的是 SOCKS 代理（要走 `socks5://127.0.0.1:1080`），不是 HTTP 代理；而 `mitmproxy -p 8080` 起的是 HTTP 代理（走 `http://127.0.0.1:8080`）。把 `socks5` 写成 `http` 会直接连不上。

3. **`proxy_pass` 后面带不带斜杠差别巨大**。Nginx 里 `proxy_pass http://backend/;` 末尾斜杠会把 `location /api/` 的 `/api` 路径**剥掉**再转发；而不带斜杠则会把完整 `/api/xxx` 原样转发。配错会导致「前端路径对、后端路径不对」的经典错位。

4. **CDN 其实是一种全球分布的反向代理**。你以为直连源站，其实先经过 CDN 边缘——所以测源站健康必须绕开 CDN（用 `Host` 头直连源站 IP，或临时把 CNAME 切回源站），否则 CDN 缓存会掩盖源站故障。

5. **反向代理做 TLS 终止后，后端收到的永远是 HTTP**。后端若据此判断「是内网来的就免鉴权」，等于开了个后门——因为反向代理转发时带的是自己的 IP，后端看到的是「来自内网」而被信任。这是内网横向移动的高危入口，必须显式校验来源。

6. **抓包时 mitmproxy 是正向代理，但你的代码可能绕过了它**。如果代码里写死了 `proxy=None` 或系统环境变量 `NO_PROXY=api.internal`，流量会直连真实服务端而不经过 mitmproxy——你以为在解密，其实看的是另一份流量。

## 面试怎么答

**Q：正向代理和反向代理的根本区别？**

A：看**代理替谁说话**。**正向代理替客户端**（客户端显式配置、服务端看到的是代理 IP）；**反向代理替服务端**（客户端无感知、客户端看到的是代理域名）。一句话记忆法：正向是「我借代理去够不到的地方」，反向是「服务躲在代理后面接客」。

**Q：为什么反向代理能做负载均衡，正向代理不行？**

A：反向代理**处在服务端侧**，它「认识」背后所有后端，自然能把请求分发出去；正向代理处在客户端侧，它只管「把我的请求送出去」，并不知道目标服务端后面有几台机器——负载均衡是服务端视角的活，正向代理插不上手。

**Q：测试环境怎么用反向代理隔离流量？**

A：典型做法：给测试域名单独配一层反向代理（如 `test.example.com` → 测试后端），和生产（`example.com` → 生产后端）物理隔离。配合 `Host` 头或独立子域，让「测试流量」和「生产流量」在代理层就分开，互不串扰。这也是为什么测 CDN 影响时，要用独立子域而非复用生产域名。
