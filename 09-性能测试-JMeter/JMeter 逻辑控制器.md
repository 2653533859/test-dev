# JMeter 逻辑控制器

## 概念

逻辑控制器（Logic Controller）本身**不发送任何请求**，它只决定「下面的子采样器/子控制器以什么顺序、什么条件、执行多少次」。你可以把它理解成脚本里的流程控制语句：`if`、`while`、`for`、事务块、开关分支。

它解决的问题是：现实的业务流不是一条直线。比如「登录只在每个用户第一次跑」「下单之后按概率走优惠券或走原价」「把『加入购物车→结算→支付』算作一笔完整事务」。这些都需要逻辑控制器来编排，否则脚本只能写死一条线性路径，既不像真实用户，也无法做混合场景比例分配。

作用域上，逻辑控制器和 [[JMeter 组件执行顺序与作用域]] 里讲的作用域规则一致：它只影响「自己子树内」的采样器，对同级其它分支没有控制力。

## 用法

### 简单控制器：纯分组

最简单，没有逻辑，只是把一组采样器打包命名，方便在结果树里折叠、在聚合报告里合并成一个 Label。常用来给业务步骤分区（如「下单流程」）。

### 循环控制器（Loop Controller）

指定子节点循环 N 次。注意它控制的是「该分支重复次数」，和外层线程组的循环次数是**相乘**关系：线程组循环 3 次 × 循环控制器 2 次 = 该分支执行 6 次。

### 仅一次控制器（Once Only Controller）

**每个线程（虚拟用户）只执行一次**，常用于「登录」。一个虚拟用户通常只登录一次，之后所有迭代复用会话。示例：

```xml
<OnceOnlyController guiclass="OnceOnlyControllerGui" testclass="OnceOnlyController" testname="仅一次-登录"/>
```

踩坑重点：它看的是「线程的迭代」而不是「控制器的迭代」。如果把它放进循环控制器里，它依然只对「线程级」生效，不会每个循环都跑——想每个循环都跑就不要用它。

### 如果（If）控制器

按条件决定是否执行子树。推荐写法：勾选「Interpret Condition as Variable Expression?」，条件用 `${__jexl3(...)}` 或 `${__groovy(...)}` 表达式，而不是老旧的 JavaScript。

```text
# 勾选 interpret condition as variable expression 后填：
${__jexl3("${userType}" == "vip",)}
```

不要写 `${userType} == "vip"`（那是字符串拼接，永远为真），也不要用 `${__javaScript(...)}`（已废弃、慢、有安全限制）。

### While 控制器

条件为真就一直循环。条件推荐用 `${__groovy(...)}`，避免废弃的 JavaScript。务必设计退出条件，否则死循环：

```text
# 当变量 done 不等于 "true" 时循环
${__groovy(vars.get("done") != "true",)}
```

### ForEach 控制器

遍历一组带序号后缀的变量（如 `item_1`、`item_2`…），把当前值注入到指定变量名。典型配合 [[JMeter 关联：正则表达式提取器与 JSON 提取器]] 的正则/JSON 多值提取：

```text
# Input variable prefix = item
# 输出变量 = curr
# 勾 Add "_" before number
# 循环内用 ${curr} 引用第 i 个值
```

### 事务控制器（Transaction Controller）

把多个子采样器「打包」成一笔事务，在聚合报告里显示为一个 Label，聚合它们的 RT 与 TPS。两个关键选项：

- **Generate parent sample**：勾上后，子采样器不再单独出现在结果里，只保留合并后的父样本。优点是结果干净、内存省；缺点是不会聚合思考时间（定时器不算进事务 RT，除非你显式加在事务内）。
- 不勾：父子都记录，能看明细但样本数翻倍。

下单一笔事务通常这么组织：`打开商品页 → 加入购物车 → 结算 → 支付`，四个采样器包进一个事务控制器，报告里直接看「下单成功一笔」的 RT 和 TPS。

### 吞吐量控制器（Throughput Controller）

按「百分比」或「总次数」控制子树执行的占比，**注意它控制的是执行次数比例，不是真实 TPS 限速**。混合场景用它分配流量：

```text
# 模式 = Percent
# Throughput = 30  → 该分支约占 30% 的迭代
# Per User 勾上 = 每个线程各自算 30%，不勾 = 全局合计 30%
```

想真正限制 TPS，要用 [[JMeter 定时器与同步定时器集合点]] 里的 Constant Throughput Timer，而不是这个控制器。

### 其它常用

- **Switch 控制器**：按变量值选一个子节点执行，像 switch-case。
- **随机/随机顺序/交替控制器**：做随机业务路径，更像真实用户。
- **模块控制器 / 包含控制器**：引用「测试片段（Test Fragment）」，实现脚本复用，避免重复粘贴。

## 踩坑

1. **If 控制器用 JavaScript 已废弃且慢**：一律改用 `${__jexl3(...)}` 或 `${__groovy(...)}`，并勾选「interpret condition as variable expression」。
2. **If 条件里变量未定义会变 null 报错**：用 `${__groovy(...)}` 时在表达式里判空（`vars.get("x") != null`），别直接拿未初始化变量比较。
3. **Once Only 在循环控制器里照样只跑一次**：它只对「线程迭代」生效，不是「控制器迭代」。想每轮循环都执行的逻辑别套它。
4. **事务控制器勾了 Generate parent sample 后看不到子明细**：聚合报告只显示父样本，调试时先不勾，确认无误再勾。
5. **事务控制器不自动算思考时间**：子采样器之间的定时器不在事务 RT 内，想要「含思考时间的事务耗时」要把定时器挪进事务控制器内部。
6. **吞吐量控制器控制的是比例不是 TPS**：它分配「执行次数占比」，无法把系统限制在某 TPS；限速用 Constant Throughput Timer。
7. **控制器嵌套作用域**：前置/后置处理器、定时器只作用于「同子树」的采样器，跨控制器不生效，别误以为放在线程组根就全局管。
8. **ForEach 的变量前缀要对齐**：提取器必须产出 `prefix_1`、`prefix_2`… 且 ForEach 要勾「Add _」，前缀名要和提取器命名一致，否则遍历为空。
9. **While 条件恒真会死循环**：必须有明确退出变量，且循环体内要能改变该变量，否则压测永不结束。
10. **逻辑控制器不发请求，只编排**：别指望它在报告里产生自己的 TPS，它只是改变子采样器的执行路径。
11. **分布式下 Once Only 在每个 slave 的线程里独立生效**：跨机的「全局只一次」它做不到，需要跨线程组/跨机一次性逻辑要用 [[JMeter 跨线程组传值]] + 文件/Redis 锁。
12. **交替/随机控制器会让聚合报告 Label 分散**：混合场景比例分析时要回到吞吐量控制器的配置核对，不能被零散 Label 误导。

## 面试怎么答

**Q：事务控制器有什么用？Generate parent sample 勾不勾有什么区别？**

答：事务控制器把多个子请求打包成一笔业务事务，比如「下单」= 浏览+加购+结算+支付，这样报告里直接看到一笔下单的 RT 和 TPS，而不是四个零散请求。勾选 Generate parent sample 后，只保留合并后的父样本，结果干净、内存省，但看不到子请求明细，调试时不方便；不勾则父子都记录，能看明细但样本数翻倍、报告更乱。我的习惯是调试阶段不勾、跑正式压测时勾上。另外要注意事务控制器默认不含子采样器之间的思考时间，需要的话要把定时器放进事务内部。

**Q：想让 30% 的用户走 A 流程、70% 走 B 流程，用吞吐量控制器限速到 100 TPS，对吗？**

答：不对，这里混了两个概念。吞吐量控制器（Throughput Controller）控制的是「执行次数占比」，可以做到 30%/70% 的流量分配，但它**限制不了 TPS**。要限制到 100 TPS 得用常量吞吐量定时器（Constant Throughput Timer），而且它只能「向下限速」——目标超过线程实际处理能力时达不到。两者经常配合使用：吞吐量控制器分比例，常量吞吐量定时器控总速。

**Q：If 控制器为什么推荐用 groovy/jexl3 而不是 JavaScript？**

答：JavaScript 解释器在 JMeter 里早就标记为废弃，执行慢、有安全限制，而且写法容易出错（字符串拼接导致条件永远为真）。groovy/jexl3 是 JMeter 官方推荐的表达式引擎，配合「interpret condition as variable expression」选项，既快又清晰。另外条件里引用的变量如果没初始化会变成 null 触发异常，所以复杂条件我习惯用 `${__groovy(vars.get("x") != null && vars.get("x").equals("y"))}` 显式判空。
