# 压测模型推算：目标 TPS 与二八原则

![[assets/load-model.svg]]
*图示：从日业务量到并发线程数的完整推算链路——二八原则折算峰值 TPS，再用 Little's Law 换算活跃并发，最后按思考时间占比放大成虚拟用户数。*

> 「压多少并发」不是拍脑袋定的。**压测模型是性能测试里唯一需要动脑的部分，工具操作只占三成。** 模型错了，后面所有数据都是自嗨。

## 概念

### 为什么需要压测模型

新手做性能测试的典型流程：打开 JMeter → 线程数填 100 → 跑 → 出报告。

问题在于：**为什么是 100？** 答不上来，那这份报告就没有业务意义——业务方问「双十一能扛住吗」，你说「100 并发下 P95 是 300ms」，这两句话之间没有任何逻辑连接。

压测模型要解决的就是这个连接：**把业务语言（日订单 100 万）翻译成压测语言（200 线程、目标 TPS 140）**，并且这个翻译过程是可解释、可复核的。

### 二八原则：从日量到峰值

现实中的流量从不是均匀的。电商、支付、社交的流量都呈现明显的波峰波谷：白天高晚上低，午高峰晚高峰突出。

**二八原则**是业界常用的粗估法则：**80% 的业务量集中在 20% 的时间内发生。**

```text
峰值 TPS = 日总业务量 × 80% ÷ (24 × 3600 × 20%)
        = 日总业务量 × 0.8 ÷ 17280
```

代入日订单 100 万：

```text
峰值 TPS = 1,000,000 × 0.8 ÷ 17280 ≈ 46 TPS
```

**注意这只是粗估。** 二八原则的适用前提是「流量有波峰但不极端」。以下场景必须用真实数据修正：

| 场景 | 特征 | 修正方式 |
|------|------|----------|
| 常规业务系统 | 波峰平缓 | 二八原则够用 |
| 电商大促 | 秒级洪峰 | 用历史大促监控峰值，二八原则严重低估 |
| 秒杀 | 全部量在 10 秒内 | 二八完全不适用，直接用 `总量 ÷ 秒杀时长` |
| 定时任务触发 | 整点尖刺 | 按单次触发量 ÷ 处理窗口 |
| 内部 OA | 上班时段均匀 | 可用「二八」甚至「三七」 |

**有生产监控数据时，永远优先用真实峰值**。二八原则是「没有数据时的兜底估算」，不是首选。

### 安全系数：为什么要留余量

推算出峰值 46 TPS，压测目标不能就设 46。要乘一个**安全系数**：

```text
压测目标 TPS = 峰值 TPS × 安全系数
```

| 系数 | 适用场景 | 理由 |
|------|----------|------|
| 1.5～2 | 成熟稳定业务，流量可预测 | 覆盖日常波动 |
| 2～3 | 常规业务，有增长预期 | 覆盖一年业务增长 |
| 3～5 | 大促、新业务、营销活动 | 覆盖不可预测的爆发 |
| 5～10 | 秒杀、明星带货 | 洪峰是常态峰值的数量级差异 |

取 3 倍：`46 × 3 ≈ 140 TPS`，这就是压测目标。

### Little's Law：从 TPS 到并发数

```text
并发数 = TPS × 响应时间
```

已知目标 TPS = 140，SLA 要求响应时间 ≤ 500ms：

```text
活跃并发数 = 140 × 0.5 = 70
```

**这 70 是「同一时刻真正在服务端被处理的请求数」，不是 JMeter 线程数。**

### 思考时间：从活跃并发到虚拟用户数

真实用户不会收到响应后立刻发下一个请求，中间会看页面、填表单——这段时间叫**思考时间（think time）**。

带思考时间时，一个虚拟用户的一轮循环耗时是 `RT + think time`，其中只有 `RT` 这段时间它是「活跃」的。所以：

```text
虚拟用户数（JMeter 线程数）= TPS × (RT + think time)
```

代入 think time = 3s：

```text
线程数 = 140 × (0.5 + 3) = 490
```

**同样是 140 TPS，不加 think time 只需 70 线程，加了 3 秒 think time 需要 490 线程。**

这引出一个关键决策：**要不要加思考时间？**

| 加 think time | 不加 think time |
|---------------|-----------------|
| 模拟真实用户行为，流量分布更接近生产 | 用最少线程打出最大压力 |
| 需要大量线程，压力机成本高 | 压力机资源省 |
| 适合：容量规划、模拟真实场景 | 适合：找系统极限、接口级压测 |
| TPS 波动更真实（有节奏） | TPS 平直，是「机关枪式」压力 |

实践上的折中：**接口级压测不加 think time（省资源、快速定位接口瓶颈），全链路场景压测必须加（否则流量模型失真，缓存命中率、数据库连接复用率都和生产对不上）。**

### 场景配比

真实业务不是只有一个接口在跑。全链路压测要按**生产实际比例**配置各接口的流量占比。

数据来源（按可靠性排序）：

1. **网关访问日志统计**（最准）
2. **APM 系统调用量**（Skywalking / 听云 / Pinpoint）
3. **数据库业务表增量**（如订单表日增量）
4. **产品经理估算**（最不可靠，但有时只有这个）

从 Nginx 日志统计接口占比（把路径里的数字 ID 归一化后再聚合）：

```bash
#!/bin/bash
# api-ratio.sh：统计接口调用占比
LOG=/var/log/nginx/access.log
TOTAL=$(wc -l < "$LOG")
awk '{print $7}' "$LOG" \
  | sed 's/?.*//' \
  | sed -E 's#/[0-9]+#/{id}#g' \
  | sort | uniq -c | sort -rn | head -10 \
  | while read -r cnt path; do
      printf "%-40s %8d  %5.2f%%\n" "$path" "$cnt" "$(echo "$cnt * 100 / $TOTAL" | bc -l)"
    done
```

## 用法

### 完整推算脚本

把整个模型固化成脚本，换业务只改输入参数：

```python
"""压测模型推算器：从业务量算到 JMeter 线程数。"""


def load_model(
    daily_volume: int,
    peak_ratio: float = 0.8,
    peak_hours_ratio: float = 0.2,
    safety_factor: float = 3.0,
    target_rt: float = 0.5,
    think_time: float = 0.0,
):
    """
    daily_volume     日业务总量（笔）
    peak_ratio       峰值时段承载的业务量占比（二八原则取 0.8）
    peak_hours_ratio 峰值时段占全天的比例（二八原则取 0.2）
    safety_factor    安全系数
    target_rt        目标响应时间（秒），取 SLA 里的 P95
    think_time       思考时间（秒），0 表示不加
    """
    peak_seconds = 24 * 3600 * peak_hours_ratio
    peak_tps = daily_volume * peak_ratio / peak_seconds
    target_tps = peak_tps * safety_factor
    active_concurrency = target_tps * target_rt
    threads = target_tps * (target_rt + think_time)

    print(f"日业务量        : {daily_volume:,} 笔")
    print(f"峰值时段        : {peak_seconds / 3600:.1f} 小时")
    print(f"峰值 TPS        : {peak_tps:.1f}")
    print(f"压测目标 TPS    : {target_tps:.1f}  (×{safety_factor} 安全系数)")
    print(f"活跃并发数      : {active_concurrency:.0f}")
    print(f"JMeter 线程数   : {threads:.0f}  (think time={think_time}s)")
    return {"target_tps": target_tps, "threads": round(threads)}


if __name__ == "__main__":
    print("=== 接口级压测（无 think time）===")
    load_model(daily_volume=1_000_000, think_time=0)
    print()
    print("=== 全链路场景压测（think time=3s）===")
    load_model(daily_volume=1_000_000, think_time=3)
```

输出：

```text
=== 接口级压测（无 think time）===
日业务量        : 1,000,000 笔
峰值时段        : 4.8 小时
峰值 TPS        : 46.3
压测目标 TPS    : 138.9  (×3.0 安全系数)
活跃并发数      : 69
JMeter 线程数   : 69  (think time=0s)

=== 全链路场景压测（think time=3s）===
...
JMeter 线程数   : 486  (think time=3s)
```

### 场景配比在 JMeter 里怎么落地

假设统计出的接口占比是：首页 50%、搜索 30%、下单 20%。有两种实现方式。

**方式一：吞吐量控制器（Throughput Controller）** —— 按百分比分流

```xml
<!-- 线程组下挂 3 个吞吐量控制器，percentExecutions 模式 -->
<ThroughputController guiclass="ThroughputControllerGui" testname="首页-50%">
  <intProp name="ThroughputController.style">1</intProp>
  <!-- style=1 表示按百分比 -->
  <boolProp name="ThroughputController.perThread">false</boolProp>
  <stringProp name="ThroughputController.percentThroughput">50.0</stringProp>
</ThroughputController>
```

三个控制器分别填 50 / 30 / 20，JMeter 会按概率把每次循环分配给其中一个。

**方式二：多线程组按线程数配比**（更可控，推荐）

```text
线程组-首页 ：245 线程
线程组-搜索 ：146 线程
线程组-下单 ： 97 线程
```

方式二的优势：每个业务可以设**不同的 think time 和不同的 SLA**，报告里也天然分开统计，不需要额外拆分。方式一的优势是只有一个线程组，共享 CSV 数据更方便。

### 定速压测：用 TPS 而不是线程数控制压力

有时候需求是「稳定压 140 TPS」而不是「压 200 线程」。这时用**常数吞吐量定时器（Constant Throughput Timer）**：

```xml
<ConstantThroughputTimer guiclass="TestBeanGUI" testname="定速 140 TPS">
  <!-- 注意单位是「每分钟」，140 TPS = 8400/min -->
  <doubleProp>
    <name>throughput</name>
    <value>8400.0</value>
  </doubleProp>
  <!-- calcMode=2: all active threads 共享这个吞吐量 -->
  <intProp name="calcMode">2</intProp>
</ConstantThroughputTimer>
```

**这是定速压测最容易错的地方：单位是「每分钟」不是「每秒」。** 想压 140 TPS 却填了 140，实际只压出 2.3 TPS。

更现代的做法是用 `jpgc-casutg` 插件的 **Throughput Shaping Timer**，可以定义 TPS 随时间变化的曲线：

```bash
# 安装插件管理器后
./PluginsManagerCMD.sh install jpgc-casutg,jpgc-tst
```

## 踩坑

1. **把在线用户数直接当线程数**。产品说「峰值 5 万人在线」，就开 5 万线程。压力机瞬间 OOM。在线用户 ≠ 并发用户，绝大多数在线用户在任意瞬间都处于 think time 里。**必须走 Little's Law 反推**，5 万在线通常对应几百到一两千的活跃并发。

2. **二八原则套用在秒杀场景**。秒杀的全部流量在 10 秒内，用二八原则算出「峰值 46 TPS」，实际是 10 万 TPS，差了三个数量级。**秒杀要用 `参与人数 ÷ 秒杀持续时间`**，而且要额外考虑「同一秒内的瞬时洪峰」。

3. **有生产数据却用估算模型**。二八原则是没数据时的兜底。有 APM、有网关日志的情况下坚持用公式估算，等于放着精确数据不用。**优先级：生产监控峰值 > 日志统计 > 二八原则 > 产品估算。**

4. **忘了乘安全系数**。压测正好压到峰值 46 TPS，报告「达标」。结果上线赶上一次运营活动，流量翻倍直接挂了。压测目标必须留余量，**至少 2 倍**。

5. **Little's Law 里用平均响应时间**。用 Average 算出来的并发数会偏小，因为长尾请求占用资源的时间被平均掉了。**应该用 P95 或目标 SLA 值**，算出来的并发才有安全边界。

6. **think time 加在了错误的位置**。把定时器放在采样器之后，以为「先请求再等待」。实际上 JMeter 的定时器**对同作用域内所有采样器生效，且永远在采样器之前执行**——放在最后一个请求下面，它会在下一轮的第一个请求前生效，节奏就乱了。想精确控制某个请求前的等待，要把定时器作为**该采样器的子节点**。

7. **常数吞吐量定时器单位填错**。填 100 以为是 100 TPS，实际是 100/min ≈ 1.7 TPS。压了半天 TPS 上不去，以为系统性能差。

8. **场景配比用产品经理的感觉**。「首页应该占一半吧」——实际日志统计出来首页只占 15%，某个前端轮询的接口占了 60%。**配比错了，压出来的瓶颈也是错的**：你以为在压首页渲染，实际生产的压力全在那个轮询接口上。

9. **模型算完就不校准**。模型只是起点。实际阶梯加压后发现拐点在 90 TPS（低于目标 140），这时要么优化系统，要么回头质疑模型输入（是不是响应时间目标定得太乐观）。**模型和实测要形成闭环**，只推算不校准的模型是废纸。

10. **忽略数据量对模型的影响**。压测库里只有 1 万条订单，生产有 5000 万条。同样的 SQL，压测环境走索引很快，生产环境因为数据量大、索引层级深而慢得多。**模型算出的目标 TPS 在数据量失真的环境里压出来毫无参考价值。**

## 面试怎么答

**Q：你们的压测并发数是怎么定的？**

A：不是拍脑袋定的，走一条完整的推算链路：

**第一步，确定峰值业务量。** 优先从生产 APM 或网关日志里取历史真实峰值 TPS；没有生产数据时用二八原则粗估——`峰值 TPS = 日业务量 × 80% ÷ (24h × 20%)`。比如日订单 100 万，算出峰值约 46 TPS。

**第二步，乘安全系数。** 常规业务取 2～3 倍覆盖业务增长，大促场景取 3～5 倍。46 × 3 ≈ 140 TPS，这是压测目标。

**第三步，用 Little's Law 换算并发。** `并发数 = TPS × 响应时间`，响应时间取 SLA 的 P95 值（比如 500ms），得到活跃并发 70。

**第四步，按思考时间放大成线程数。** 全链路场景要加 think time 模拟真实用户，`线程数 = TPS × (RT + think time)`，think time 取 3 秒的话就是 490 线程；接口级压测不加 think time，70 线程就够。

**第五步，配置场景比例。** 从网关日志统计各接口真实调用占比，用多线程组按比例分配线程数。

最后一点很重要：**模型只是起点，必须和实测形成闭环**。阶梯加压跑出真实拐点后，如果拐点远低于目标，要么优化系统，要么回头检查模型输入是否合理——比如响应时间目标是不是定得过于乐观。

**Q：二八原则是什么，什么情况下不适用？**

A：二八原则假设 80% 的业务量集中在 20% 的时间内发生，用来把「日总量」折算成「峰值 TPS」。它的价值在于**没有生产监控数据时提供一个有依据的估算**。

不适用的场景主要有三类：

一是**秒杀、抢购**。全部流量在几秒到几十秒内爆发，用二八算会低估两三个数量级，应该直接用 `参与人数 ÷ 秒杀窗口`，甚至要单独考虑第一秒的瞬时洪峰。

二是**大促**。双十一零点的流量可能是日常峰值的几十倍，二八原则基于「日总量」的平滑假设完全失效，必须用历史大促的真实监控峰值。

三是**定时任务驱动的系统**。比如每天凌晨 2 点批量对账，流量是一根尖刺，应该按「单次触发量 ÷ 处理窗口」算。

反过来，常规的 OA、后台管理、内容浏览类业务，流量波峰平缓，二八原则甚至可以放宽到三七，估算精度是够用的。

**核心原则是：有真实数据就永远不要用估算公式。** 二八原则是兜底手段，不是首选方案。

**Q：并发用户数和在线用户数有什么区别？**

A：在线用户数是「当前连着系统的用户总数」，并发用户数是「同一时刻正在发请求并等待响应的用户数」。两者能差一到两个数量级。

原因是真实用户绝大部分时间处于 think time——打开页面看内容、填写表单、犹豫要不要下单，这段时间他在线但不占服务端资源。

换算关系还是 Little's Law：`并发数 = TPS × RT`，而 `TPS = 在线用户数 ÷ (RT + think time)`。假设 5 万在线，平均每人每 30 秒操作一次，RT 是 0.5 秒，那么 `TPS = 50000 / 30 ≈ 1667`，`活跃并发 = 1667 × 0.5 ≈ 833`——5 万在线只对应 833 个真正的并发。

面试里这个问题的陷阱在于：如果直接按在线数开线程，压力机根本撑不住，而且压出来的是完全失真的压力模型。

**Q：压测要不要加思考时间？**

A：看压测目的。

**接口级压测不加**。目的是找单接口的性能极限，加 think time 只会让线程在那里空转，浪费压力机资源，还要开成倍的线程才能打出同样的 TPS。

**全链路场景压测必须加**。因为 think time 直接影响流量的时间分布，进而影响缓存命中率、连接池复用率、数据库的并发事务数。不加 think time 的「机关枪式」压力和生产的真实流量形态差很远，压出来的瓶颈可能根本不是生产会遇到的。

举个具体差异：不加 think time 时，同一个连接被高频复用，连接池只需要很少的连接；加了 3 秒 think time 后，同样 TPS 下需要的线程数是 7 倍，如果服务端是 BIO 模型或者每个连接占一个线程，暴露出的连接数瓶颈完全不同。

think time 的取值也要有依据：从生产埋点统计用户两次操作的真实间隔，或者用高斯随机定时器让它在一个区间内波动（比如 3s ± 1s），而不是所有用户整齐划一地等 3 秒——那样会造成人为的请求同步，制造出周期性的 TPS 尖刺。
