# 全链路压测流量染色与压测标透传机制

> 解决微服务架构下在真实生产环境进行大规模压测时，如何精确区分压测流量与业务流量，实现数据物理隔离、不污染生产数据的核心机制。

## 概念

全链路压测（Full-Link Stress Testing）是指在**生产环境**上模拟双十一或秒杀级海量真实用户请求，对涵盖网关、微服务、中间件、数据库及第三方依赖在内的全套链路进行的大规模真实压力验证。

在生产环境压测面临的最大难题是：**如何确保压测产生的千万级数据绝不污染真实业务报表与生产数据库，且外部接口（如真实短信、扣款）绝不误触发？**

### 核心要素

1. **流量染色（Traffic Coloring）**：
   - 在请求进入系统最外层网关（API Gateway / Nginx）时，由压测平台注入全局唯一的压测标记（例如 HTTP Header `x-pressure-test: true` 或携带特定压测租户 ID）。
2. **压测标全链路透传（Context Propagation）**：
   - 依赖微服务链路追踪上下文（如 TraceContext、ThreadLocal、MDC、SkyWalking 探针），确保请求在跨线程异步执行、RPC 调用（gRPC/Dubbo）、消息队列（Kafka/RocketMQ）投递时，压测标始终紧随流量向下游传播。
3. **数据隔离（影子存储体系）**：
   - **影子库 / 影子表（Shadow DB / Shadow Table）**：数据库中间件（如 ShardingSphere）拦截 SQL，若当前上下文带有压测标，则自动路由至 `shadow_db` 或 `t_order_shadow`，保持表结构一致但数据物理隔离；
   - **影子缓存（Shadow Redis）**：Redis Key 自动增加特定前缀（如 `pt_key`）；
   - **影子队列（Shadow Queue / Topic）**：MQ 消息体带标，压测消费者消费影子消息，避免触发实际业务外部回调；
   - **外部服务挡板（Mock Server）**：针对第三方支付通道（微信/支付宝）、短信运营商等，由网关或服务切面识别压测标后自动打桩拦截，返回预设成功报文。

## 用法

### 1. 全链路压测标透传与路由架构

```text
               ┌────────────────────────────────────────────────────────┐
               │              压测流量发起端 (JMeter / 压力机)             │
               │         Header: x-pressure-test: true, trace_id        │
               └───────────────────────────┬────────────────────────────┘
                                           │
                                           ▼
               ┌────────────────────────────────────────────────────────┐
               │           API 网关 (Spring Cloud Gateway / Nginx)       │
               │   鉴权白名单校验，校验并注入统一 Distributed Context 标记   │
               └───────────────┬────────────────────────┬───────────────┘
                               │ RPC (传递标)            │ HTTP (透传标)
                               ▼                        ▼
        ┌─────────────────────────────┐        ┌─────────────────────────────┐
        │       用户/订单微服务 A      │        │       履约/支付微服务 B      │
        │ ThreadLocal 上下文传递压测标  │        │   识别压测标，切断外部支付  │
        └──────────────┬──────────────┘        └──────────────┬──────────────┘
                       │                                      │
            ┌──────────┴──────────┐                ┌──────────┴──────────┐
            ▼                     ▼                ▼                     ▼
     [ 生产 DB / Redis ]   [ 影子 DB / Redis ]  [ 生产短信/支付 ]     [ Mock 挡板服务 ]
     (非压测正常流量落盘)   (带有压测标的流量落库) (禁止调用外部API)     (返回预设成功凭证)
```

### 2. Python / FastAPI 微服务中压测标提取与动态数据源路由示例

在微服务层中，通过中间件提取 Header 放入上下文，并驱动数据库驱动动态路由：

```python
import contextvars
from fastapi import FastAPI, Request
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

# 1. 定义协程安全的全局上下文变量
is_pressure_test_ctx: contextvars.ContextVar[bool] = contextvars.ContextVar(
    "is_pressure_test", default=False
)

# 2. 生产库与影子库连接池
PROD_DB_URL = "mysql+pymysql://user:pass@10.0.0.1:3306/shop_prod"
SHADOW_DB_URL = "mysql+pymysql://user:pass@10.0.0.2:3306/shop_shadow"

prod_engine = create_engine(PROD_DB_URL, pool_size=20)
shadow_engine = create_engine(SHADOW_DB_URL, pool_size=50)

ProdSession = sessionmaker(bind=prod_engine)
ShadowSession = sessionmaker(bind=shadow_engine)

app = FastAPI()

@app.middleware("http")
async def pressure_test_middleware(request: Request, call_next):
    # 提取压测染色标
    pt_header = request.headers.get("x-pressure-test", "false").lower()
    is_pt = pt_header in ("true", "1")
    
    # 注入当前异步上下文
    token = is_pressure_test_ctx.set(is_pt)
    try:
        response = await call_next(request)
        if is_pt:
            response.headers["x-pressure-test-echo"] = "pass"
        return response
    finally:
        is_pressure_test_ctx.reset(token)

def get_db_session():
    """动态数据源提供者：根据压测标自动路由到影子库"""
    if is_pressure_test_ctx.get():
        return ShadowSession()
    return ProdSession()

@app.post("/api/v1/order")
async def create_order(item_id: int, amount: float):
    session = get_db_session()
    try:
        # 如果是压测请求，SQL 将直接落入 shop_shadow 库，绝不触碰生产表
        # session.add(...)
        # session.commit()
        return {"code": 0, "msg": "success", "is_shadow": is_pressure_test_ctx.get()}
    finally:
        session.close()
```

## 踩坑

1. **异步多线程导致压测标丢失（致命隐患）**：
   - 业务代码中若使用了原生多线程（如 `ThreadPoolExecutor` 或异步事件循环 `asyncio.create_task`），如果不显式传递上下文（或 Java 中未包装 `InheritableThreadLocal` / `TransmittableThreadLocal`），下游子任务的压测标会直接丢失，导致压测数据写入真实的生产库！
   - **解法**：在代码层强制使用链路增强库（如阿里的 TTL，或框架级 ContextCopyingDecorator）包装所有线程池。
2. **第三方外部通道漏拦，造成实际扣费或客诉**：
   - 压测订单未经过 Mock 挡板直接调用了真实的银联或短信通道，导致公司资金池真实扣费或数万条短信轰炸真实客户手机号。
   - **解法**：外部 HTTP Client 必须集成熔断网卡拦截器，对于带有压测标的请求，只要域名是外网白名单以外的地址，拦截器直接抛错或转向内网 Mock 桩，严禁任何生产压测请求流向公网。
3. **影子库与生产库 DDL 结构漂移**：
   - 生产库升级了表结构并新增了非空字段，但运维未同步更新影子库，导致正式全链路压测时由于影子库缺失字段全线崩盘。
   - **解法**：CI/CD 数据库迁移工具（如 Flyway / Alembic）执行 DDL 时，必须通过自动化脚本联动同步变更影子库。

## 面试怎么答

> **面试官会怎么问**：
> 你们公司的全链路压测是怎么做的？压测数据打到生产环境，怎么保证不污染正常用户的真实数据？

**30 秒回答骨架**：
> “我们采用的是**全链路流量染色 + 影子存储隔离**方案。首先在压测发起端（JMeter/压测引擎）统一注入特定的 HTTP Header（如 `x-pressure-test: true`）。网关层校验后，基于微服务链路追踪组件（如 SkyWalking/TraceContext）在跨进程 RPC、线程池与 MQ 中做标的无缝透传。在数据层，通过分库分表与动态数据源组件拦截 SQL，凡带压测标的全部路由到预先准备好的影子库与影子 Redis 中；同时，针对支付、短信等外部渠道做服务挡板 Mock，以此做到千万级高并发真实压测下，生产业务数据零污染、零客诉。”

**容易被追问的点**：
- **追问 1**：压测产生的垃圾数据在影子库里后续怎么清理？
  - *回答要点*：影子库由于与生产物理分离，通常在压测窗口结束后，直接走定时脚本对影子库执行 `TRUNCATE TABLE` 或重建数据库快速重置；对于 Redis 影子 Key（统一加 `pt:` 前缀），设置短暂的过期时间（TTL）或批量扫描删除。
- **追问 2**：如何验证全链路压测标没有在某个隐蔽的微服务节点断掉？
  - *回答要点*：压测前必须执行**低并发全链路探针巡检**。用 1 个并发向所有涉及的核心接口打入带标流量，结合日志监控系统（ELK）和 APM 分布式追踪系统检查各节点的 Span Tags，校验每个下游组件落库是否均落在影子库，确认无断标节点后才允许开启大规模阶梯加压。
