# 性能测试类型：负载、压力、稳定性与容量测试

> 这几个词天天混用，但它们的**压测目标、加压方式、通过标准完全不同**。分不清就会出现「我做了压力测试」但实际只是跑了一轮负载测试的尴尬。

## 概念

### 为什么要分类型

性能测试不是「跑一轮 JMeter 看看 TPS」。**不同类型回答的是不同的业务问题**：

- 老板问「双十一能扛住吗」→ 容量测试
- 运维问「服务能连续跑一周不重启吗」→ 稳定性测试
- 架构师问「打挂了之后能自己恢复吗」→ 压力测试
- 产品问「日常流量下用户体验够快吗」→ 负载测试

**问题不同，加压曲线就不同，通过标准也不同。** 用一套脚本一个配置去回答四个问题，等于四个都没答。

### 五种类型的核心差异

| 类型 | 压多大 | 压多久 | 关注什么 | 通过标准 |
|------|--------|--------|----------|----------|
| 基准测试 | 1 个用户 | 5～10 min | 单次请求的纯净耗时 | 无并发时响应时间达标 |
| 负载测试 | 预期峰值（如 100 并发） | 15～30 min | 目标负载下是否达标 | TPS ≥ 目标，P95 ≤ SLA，错误率 < 0.1% |
| 压力测试 | 远超峰值，一直加到崩 | 加到崩为止 | 崩溃点在哪、怎么崩、能否恢复 | 崩溃后降压能自动恢复，不丢数据 |
| 容量测试 | 阶梯递增找拐点 | 每级 hold 5～10 min | 系统最大处理能力 | 找到拐点并给出容量结论 |
| 稳定性测试 | 峰值的 60%～80% | 7×24 h 或至少 8 h | 内存泄漏、连接泄漏、GC 退化 | 长时间指标无劣化趋势 |

### 最容易混的两组

**负载测试 vs 压力测试**

- **负载测试是「验证」**：我已经有一个目标（100 并发下 P95 < 500ms），压上去看达不达标。**结论是 是/否**。
- **压力测试是「探索」**：我不知道极限在哪，一直加压直到系统扛不住，观察它**怎么死的**——是优雅降级还是雪崩、错误信息是不是人话、降压后能不能自愈。**结论是 一个数字 + 一段崩溃行为描述**。

一句话：**负载测试证明「能行」，压力测试搞清楚「不行的时候会怎样」。**

**压力测试 vs 容量测试**

两者都往上加压，但：

- 压力测试**关心崩溃后的行为**（韧性），会一直压到 5xx 满屏。
- 容量测试**关心崩溃前的最大值**（容量），在拐点处就停下来做结论，不追求把系统压死。

### 稳定性测试为什么必须单独做

短时压测跑 20 分钟一切正常，上线三天后 OOM——这是最典型的线上事故来源。因为下面这些问题**只在时间维度上暴露**：

1. **内存泄漏**：每个请求泄漏 1KB，20 分钟无感，7 天累积几个 G。
2. **连接泄漏**：某个异常分支忘了 `close()`，连接池被慢慢耗光。
3. **磁盘写满**：日志无轮转，压几天把盘写满。
4. **缓存击穿周期**：缓存 TTL 是 24h，短压根本碰不到集中失效。
5. **GC 退化**：老年代碎片化后 Full GC 停顿从 50ms 涨到 3s。

所以稳定性测试**故意不压满**（用 60%～80% 峰值），因为目的不是找极限，而是**在合理负载下观察指标随时间的斜率**。斜率不为零，就是有泄漏。

## 用法

### 五种类型对应的 JMeter 配置

**基准测试**——1 个线程，摸清纯净耗时基线：

```xml
<!-- 线程组：num_threads=1, ramp_time=1, 循环 100 次 -->
<ThreadGroup testname="基准-单用户">
  <stringProp name="ThreadGroup.num_threads">1</stringProp>
  <stringProp name="ThreadGroup.ramp_time">1</stringProp>
  <elementProp name="ThreadGroup.main_controller" elementType="LoopController">
    <stringProp name="LoopController.loops">100</stringProp>
  </elementProp>
</ThreadGroup>
```

基准值是后续所有分析的锚点：**如果单用户就要 800ms，那 100 并发下 P95 是 3s 一点都不奇怪，问题出在代码本身而不是并发。**

**负载测试**——固定并发压固定时长：

```bash
# 100 并发、ramp-up 100s（每秒起 1 个）、持续 30 分钟
jmeter -n -t load.jmx -l load.jtl -e -o report-load/ \
  -Jthreads=100 -Jrampup=100 -Jduration=1800
```

对应脚本里用 `${__P(threads)}` 引用，实现一套脚本多种压法：

```xml
<stringProp name="ThreadGroup.num_threads">${__P(threads,10)}</stringProp>
<stringProp name="ThreadGroup.ramp_time">${__P(rampup,10)}</stringProp>
<boolProp name="ThreadGroup.scheduler">true</boolProp>
<stringProp name="ThreadGroup.duration">${__P(duration,300)}</stringProp>
```

> `${__P(threads,10)}` 表示读 JVM 属性 `threads`，取不到就用默认值 10。这是让脚本可配置化的标准做法，避免为每种压法复制一份 jmx。

**容量测试**——用 Concurrency Thread Group 阶梯加压：

```bash
# 需先装 jpgc-casutg 插件（Custom Thread Groups）
# 50 → 100 → 150 → 200，每级 hold 300s
jmeter -n -t capacity.jmx -l capacity.jtl -e -o report-capacity/
```

**压力测试**——一路加到崩，重点是崩溃后的恢复观察：

```bash
# 阶段一：加压到崩
jmeter -n -t stress.jmx -l stress.jtl -Jthreads=1000 -Jrampup=60

# 阶段二：立刻降压到正常水位，观察能否自愈
jmeter -n -t stress.jmx -l recover.jtl -Jthreads=50 -Jduration=600
```

判断恢复能力的关键：降压后 **错误率是否在 1～2 分钟内回到 0**。如果一直 5xx，说明有资源没释放（连接池耗尽、线程池死锁），这是很严重的架构缺陷。

**稳定性测试**——低压长跑，配合定时采样：

```bash
# 60 并发跑 8 小时，结果文件会很大，务必只写必要字段
nohup jmeter -n -t stability.jmx -l stability.jtl \
  -Jthreads=60 -Jduration=28800 > jmeter.log 2>&1 &
```

同步起一个采样脚本记录服务端指标趋势：

```bash
#!/bin/bash
# gc-watch.sh：每 60s 采一次 JVM GC 与内存，跑满 8 小时
PID=$(pgrep -f 'app.jar')
for i in $(seq 1 480); do
  echo "$(date '+%F %T') $(jstat -gcutil "$PID" | tail -1)" >> gc-trend.log
  sleep 60
done
```

分析时看的**不是绝对值，而是斜率**：

```bash
# 看 Full GC 次数是否单调增长（第 8 列是 FGC）
awk '{print $1, $2, $10}' gc-trend.log | tail -20
```

### 结果文件瘦身（长跑必做）

稳定性测试跑 8 小时，默认配置的 jtl 能到几个 G，还会拖慢压力机。在 `bin/user.properties` 里裁剪字段：

```text
# 只保留分析必需的列
jmeter.save.saveservice.output_format=csv
jmeter.save.saveservice.response_data=false
jmeter.save.saveservice.samplerData=false
jmeter.save.saveservice.requestHeaders=false
jmeter.save.saveservice.responseHeaders=false
jmeter.save.saveservice.assertion_results_failure_message=true
jmeter.save.saveservice.bytes=true
jmeter.save.saveservice.thread_counts=true
```

`response_data=false` 是最关键的一条——它决定了要不要把每个响应体写进磁盘。开着它压 8 小时基本必炸盘。

## 踩坑

1. **把「跑了一轮 JMeter」当成压力测试**。只压了预期峰值就交报告，报告里写「压力测试通过」。面试官一追问「那系统极限是多少」就答不上来——你压根没做压力测试，只做了负载测试。

2. **稳定性测试压满 100%**。有人觉得「长跑当然要压最大」。错。压满时系统本身就在临界状态，任何抖动都会导致错误，你分不清是泄漏还是本来就到极限了。**稳定性测试要在系统「明显吃得消」的水位跑**，这样任何指标劣化都能干净地归因到时间因素。

3. **压力测试压崩了就收工，不看恢复**。崩溃本身信息量很小（任何系统压到极限都会崩），有价值的是崩溃**方式**和**恢复能力**。我遇到过一次：压到 800 并发时服务 5xx，降压到 50 并发后**错误率一直是 100%**，查下来是 HikariCP 连接池在超时后没归还连接，泄漏到耗尽，必须重启才能恢复。这个缺陷比「极限是 800」重要得多。

4. **容量测试每级 hold 时间太短**。有人 30 秒一级，结果读到的是加压瞬间的抖动值而不是稳态值。**至少 hold 3～5 分钟**，让 JIT 编译完成、缓存预热、连接池达到平衡，再取后半段的均值。

5. **没做基准测试就上并发**。100 并发 P95 是 2s，团队开始怀疑数据库、怀疑网络，折腾两天后做了基准测试发现——**单用户就要 1.8s**，纯粹是代码里有个 N+1 查询。基准测试 10 分钟就能省掉这两天。

6. **稳定性测试的 jtl 写爆磁盘**。前面提过，默认配置保存响应数据。8 小时压测在凌晨 3 点因为 `No space left on device` 中断，早上来看什么都没有。

7. **多种类型共用一份 jmx 但没参数化**。复制出 `load.jmx`、`stress.jmx`、`stability.jmx` 三份文件，改了业务逻辑后只同步了其中一份，后面的测试结果全是错的。**用 `${__P()}` 参数化，永远只维护一份脚本。**

8. **稳定性测试用了会耗尽的测试数据**。CSV 里 1000 个账号，`recycle=false`，跑到第 40 分钟数据用完，线程全部停止，剩下 7 小时压了个寂寞。长跑必须 `recycle=true` 或用函数动态生成数据。

## 面试怎么答

**Q：负载测试和压力测试有什么区别？**

A：目标不同。负载测试是**验证性**的——已知目标（比如 100 并发下 P95 < 500ms），压上去验证达不达标，结论是「通过 / 不通过」。压力测试是**探索性**的——不预设目标，持续加压直到系统崩溃，目的是找到崩溃点、观察崩溃形态（是优雅降级还是雪崩）、以及降压后能否自动恢复，结论是一个极限数字加一段崩溃行为的描述。

实际项目里两个都要做：负载测试给业务方一个「能不能上线」的答复，压力测试给架构组一个「容量水位和限流阈值该设多少」的依据——通常限流阈值就设在压测拐点的 70%～80%。

**Q：稳定性测试要压多久，观察什么指标？**

A：业内一般至少 8 小时，重要系统跑 7×24。压力水位取峰值的 60%～80%，**故意不压满**，因为目的不是找极限而是观察指标随时间的变化趋势——压满的话系统本来就在临界状态，抖动会掩盖泄漏信号。

观察三类指标的**斜率**而非绝对值：

1. **内存**：JVM 老年代占用在每次 Full GC 后是否回落到同一水位。如果基线单调抬升，就是内存泄漏。
2. **连接与句柄**：数据库连接池活跃数、`lsof -p PID | wc -l` 文件句柄数，只涨不降就是泄漏。
3. **响应时间与 TPS**：同样的压力下 TPS 逐渐下滑、P99 逐渐抬高，说明系统在退化（GC 变频繁、表数据量涨了导致 SQL 变慢、日志文件变大导致写变慢）。

我实际做过一次 8 小时稳定性测试，前 6 小时一切正常，第 7 小时 TPS 从 300 掉到 180，`jstat` 看到 Full GC 从每小时 2 次涨到每分钟 3 次，堆 dump 后用 MAT 分析发现是一个 `static Map` 做本地缓存但没设上限，一直往里塞。这个问题短压完全测不出来。

**Q：怎么确定系统的最大容量？**

A：用容量测试，阶梯加压。比如 50 → 100 → 150 → 200 → 250 并发，每级稳定压 5 分钟，记录每级的稳态 TPS 和 P95。画出 TPS-并发曲线，**TPS 不再随并发上升的那个点就是拐点**，拐点对应的 TPS 就是系统最大处理能力。

要注意两点：一是必须同时看响应时间，有时候 TPS 还在涨但 P95 已经超出 SLA 了，这时候**以 SLA 为准**而不是以 TPS 峰值为准，得到的是「可用容量」而非「理论容量」；二是拐点处一定要定位出**是哪个资源先打满**（CPU、连接池、还是数据库），否则「容量是 500 TPS」这个结论无法指导扩容——你不知道该加应用机器还是加数据库配置。

**Q：为什么要先做基准测试？**

A：基准测试是单用户、无并发压力下测出的纯净响应时间，它是所有后续分析的锚点。有了它才能区分两类问题：如果基准就慢，那是**代码/SQL 本身的问题**，加机器没用；如果基准很快但并发上去就慢，那是**并发争用问题**（锁、连接池、线程池），才需要往架构层面查。跳过基准测试直接压并发，很容易把「代码本身就慢」误判成「并发能力不足」，方向一开始就错了。
