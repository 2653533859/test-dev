# 性能瓶颈定位顺序与调优对策

![[assets/bottleneck-chain.svg]]
*图示：瓶颈定位是「由外到内、逐层下钻」的链路——先排除压测机自身，再依次过网络、网关/中间件、应用进程、JVM/GC，最后到数据库。每一层都有对应的监控指标和对策，定位不到内层前不要盲目改代码。*

## 概念

压测跑出 TPS 不达标、RT 超标、错误率上涨，只说明「系统有问题」，但问题在哪一层不清楚。瓶颈定位（Bottleneck Analysis）是一套**由外到内、逐层排除**的方法论：从最外层（压测机、网络）一路下钻到最内层（数据库、慢 SQL），哪一层指标先「触顶」或「异常」，哪一层就是瓶颈。

之所以强调「按顺序」，是因为如果不先排除外层就直接改应用代码，经常是白改——比如其实是压测机 CPU 跑满了，你却去优化应用算法，毫无效果。正确顺序是：

**压测机 → 网络 → 网关/中间件 → 应用进程 → JVM/GC → 数据库**

每一层都有标志性指标和对应调优对策。下面逐层展开。详细监控手段见 [[服务端资源监控与 JVM、GC、慢 SQL 定位]]，实时监控通道见 [[JMeter 监控：InfluxDB + Grafana]]。

## 用法

### 第 1 层：压测机（施压端）

- **看什么**：压测机 CPU、内存、端口、网卡。CLI 模式（`[[JMeter 命令行压测与 HTML 报告]]`）下压测机 CPU 若 100%，说明发压端到顶。
- **对策**：减线程数、或上分布式（`[[JMeter 分布式压测]]`）。这是最常见被误判的「假瓶颈」——系统还很闲，是 JMeter 自己发不动了。

### 第 2 层：网络

- **看什么**：网卡吞吐是否打满、`ss -s` 看 TIME_WAIT/连接数是否堆积、是否有丢包。
- **对策**：万兆网卡替换、调大端口范围/`tcp_tw_reuse`、减少大响应体。网络满会让 TPS 卡住但 CPU 内存正常。

### 第 3 层：网关 / 中间件（Nginx、LB、MQ、缓存）

- **看什么**：网关连接数、 upstream 响应时间、MQ 堆积、Redis 命中率。
- **对策**：扩网关节点、调 upstream 超时与连接池、MQ 增加消费者、缓存预热/扩容。常见现象是应用本身快，但被网关或缓存拖慢。

### 第 4 层：应用进程

- **看什么**：应用 CPU/`top` 负载、`jstack` 线程状态（大量 BLOCKED=锁竞争，RUNNABLE 高 CPU=计算重）、连接池活跃数。
- **对策**：优化算法/减少序列化开销、消除锁竞争（减小锁粒度、用无锁结构）、扩大线程池/连接池、异步化。

### 第 5 层：JVM / GC

- **看什么**：`jstat -gcutil` 看老年代占用与 Full GC 耗时（`FGCT`）；老年代只涨不落=`内存泄漏`。
- **对策**：调堆大小（`-Xmx`/`-Xms`）、换/调 GC 算法（G1、ZGC）、修内存泄漏（`jmap -histo` 抓大对象）。FGC 长停顿直接拉高 RT。

### 第 6 层：数据库

- **看什么**：慢查询日志 + `EXPLAIN`、活跃连接数、锁等待、缓冲命中率。
- **对策**：加索引、改写慢 SQL、读写分离、分库分表、升级实例规格。数据库是性能问题最高发的「终局瓶颈」。

### 一张对照表

| 层级 | 触顶信号 | 首选对策 |
| --- | --- | --- |
| 压测机 | CLI 下 CPU 100% | 减线程 / 分布式 |
| 网络 | 网卡满 / TIME_WAIT 堆 | 万兆网卡 / 调内核参数 |
| 网关/中间件 | upstream 慢 / MQ 堆积 | 扩节点 / 加消费者 |
| 应用 | 锁竞争 / 线程池满 | 优化代码 / 扩池 |
| JVM | FGC 频繁 / 老年代不落 | 调堆 / 换 GC / 修泄漏 |
| 数据库 | 慢 SQL / 连接打满 | 加索引 / 拆库 |

## 踩坑

1. **没排除压测机就改应用代码**：最常见浪费——其实是 JMeter 发不动，优化应用毫无效果。定位顺序第一步永远是压测机。
2. **只看客户端 TPS 不对照服务端**：必须同屏看（[[JMeter 监控：InfluxDB + Grafana]]），否则不知道哪层异常。
3. **把 iowait 高当成 CPU 瓶颈**：`%wa` 高是磁盘/IO 慢，方向反了会白优化 CPU。
4. **GC 只看次数不看耗时**：YGC 多但短无害，FGC 耗时占比高才是真问题。
5. **数据库连池满误判为库慢**：可能是连接泄漏（没 close）或池配太小，先查连接是否释放。
6. **慢 SQL 只看 type 不看 Extra**：`Using filesort`/`Using temporary` 才是隐藏杀手，rows 大也要警惕回表。
7. **内存泄漏当普通 GC 调优**：老年代只涨不落必须 `jmap` 抓对象，调堆只是拖延。
8. **瓶颈没定位就加机器**：扩应用节点可能只是把压力转嫁给数据库，要先确认应用层真瓶颈。
9. **容器里看宿主机 CPU 误判**：容器内 `top` 显示宿主机核数，要用 cgroup 指标，否则 CPU 数据失真。
10. **只在平稳期抓线程栈**：要在 TPS 掉/RT 涨瞬间抓 `jstack`，才能看到高峰时的锁竞争。
11. **网络 TIME_WAIT 堆积被忽略**：CPU 内存都正常但 TPS 上不去，常是端口耗尽，看 `ss -s`。
12. **调优后不复测对照**：改完必须回到同一压测脚本复跑，用同一份目标值（[[压测模型推算：目标 TPS 与二八原则]]）验证是否真的改善。

## 面试怎么答

**Q：压测 TPS 不达标，你怎么定位瓶颈？**

答：按「由外到内」顺序逐层排除，不能跳层。第一步先确认不是压测机自身瓶颈——CLI 模式下如果压测机 CPU 满了，是 JMeter 发不动，要减线程或上分布式。排除了外层，再看网络（网卡满、TIME_WAIT 堆积），再看网关/中间件（upstream 慢、MQ 堆积），再看应用进程（jstack 查锁竞争、线程池满），再看 JVM（jstat 看 FGC 耗时和老年代回收），最后看数据库（慢 SQL、连接池）。每一层用对应监控指标判断，定位不到内层前绝不盲目改代码。我习惯把客户端 TPS 曲线和服务端各层指标放同一屏（[[JMeter 监控：InfluxDB + Grafana]]），RT 尖刺那一刻哪个指标异常就是瓶颈。

**Q：应用 RT 高，你怀疑是 GC 还是数据库，怎么区分？**

答：两个监控对照看。GC 侧用 `jstat -gcutil` 看 Full GC 次数和总耗时 `FGCT`、以及老年代 `O` 区是否回收后不回落；如果 FGC 频繁且耗时占比高，RT 尖刺会和 FGC 时间点重合，那就是 GC 停顿。数据库侧开慢查询日志 + 看连接池活跃数，如果连接池打满、且有超过 1 秒的 SQL，RT 尖刺对应慢 SQL 执行时段。两者时间对齐到 TPS/RT 曲线上一看就知道：GC 导致的尖刺更「规律整齐」，慢 SQL 导致的尖刺和具体请求分布相关。详细见 [[服务端资源监控与 JVM、GC、慢 SQL 定位]]。

**Q：定位到瓶颈后怎么验证调优有效？**

答：三个原则。一是「对照复测」：用完全相同的压测脚本和目标值（[[压测模型推算：目标 TPS 与二八原则]]）重跑，看 TPS/RT/错误率是否达到目标，而不是凭感觉。二是「单变量改动」：一次只改一个参数（比如只加索引、只调堆），否则不知道哪个改动生效、是否引入新瓶颈。三是「看稳态区间」：排除 ramp-up 爬坡段，取稳定区间的平均值对比，别被起步抖动误导。调优是迭代过程，一层通了可能暴露下一层瓶颈，要按定位顺序继续下钻。
