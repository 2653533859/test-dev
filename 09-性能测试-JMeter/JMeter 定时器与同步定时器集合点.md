# JMeter 定时器与同步定时器集合点

## 概念

定时器（Timer）用来在采样器**执行之前**插入等待，模拟真实用户的「思考时间（Think Time）」和控制请求节奏。它的核心作用有两个：一是让压测流量更像真人（真人不会请求完立刻下一个），二是通过控制节奏来间接控制 TPS、模拟瞬时并发。

一个关键的机制细节：**定时器在采样器之前执行，它等待的时间会算进该采样器的响应时间里**。也就是说，你在某个请求前加 1 秒固定定时器，这个请求的 RT 报告里就会多 1 秒。这点常被忽略，导致「明明接口很快，报告 RT 却很高」。

作用域规则（见 [[JMeter 组件执行顺序与作用域]]）：定时器作用于「同子树的所有采样器之前」。多个定时器会**叠加求和**，不是取最大。

同步定时器（Synchronizing Timer）又叫「集合点」，是定时器的特例：它不按时间等待，而是**等攒够 N 个线程到达后再一起放行**，用来模拟「瞬间齐发」的并发，比如秒杀、抢红包那种脉冲式负载。

## 用法

### 固定定时器（Constant Timer）——思考时间

```xml
<ConstantTimer guiclass="ConstantTimerGui" testclass="ConstantTimer" testname="思考时间">
  <stringProp name="ConstantTimer.delay">1000</stringProp>
</ConstantTimer>
```

加在某个采样器下，该采样器每次执行前等 1 秒。注意作用域：放在采样器下只对该采样器生效；放在线程组根下会对**每一个**采样器都加等，严重拉低 TPS。

### 随机定时器

- **高斯随机定时器（Gaussian Random Timer）**：延迟 = 固定偏移 + 高斯分布随机值，多数请求集中在均值附近，适合模拟自然抖动。
- **均匀随机定时器（Uniform Random Timer）**：延迟在 `[0, 随机值]` 均匀分布。
- **泊松随机定时器（Poisson Random Timer）**：按泊松到达过程生成间隔，最贴近「随机到达」的真实业务。

### 常量吞吐量定时器（Constant Throughput Timer）——真正限速

这是唯一能「控制 TPS」的定时器，按「每分钟目标」设置：

```text
# Target throughput = 6000 → 即 100 请求/秒
# Calculate Throughput based on = all active threads in current thread group
```

作用逻辑：JMeter 在每个线程执行后动态计算「要不要等一会儿」来逼近目标吞吐。重要限制：

- **只能向下限速**：目标 TPS 超过线程组实际处理能力时，永远到不了目标，因为线程已经全力在跑了。
- 基于「计算周期」调节，有滞后，**短测试不准，长测试才稳**。
- 作用域默认整个线程组；放在控制器下只对该控制器限速。

### 同步定时器（Synchronizing Timer）——集合点

```xml
<SynchronizingTimer guiclass="SynchronizingTimerGui" testclass="SynchronizingTimer" testname="集合点">
  <stringProp name="groupSize">200</stringProp>
  <stringProp name="timeoutInMs">5000</stringProp>
</SynchronizingTimer>
```

- **Number of Simulated Users to Group by**：攒够多少个线程一起放行，即模拟多少「瞬间并发」。
- **Timeout in milliseconds**：超时时间。到了超时还没攒够 N 个，也放行已到的线程，避免死等。

集合点常放在「下单」「抢购」这种关键采样器之前，模拟千人在同一秒点击。

## 踩坑

1. **定时器等待时间计入采样器 RT**：固定定时器加在请求前，该请求报告 RT 会包含这段等待。建模思考时间时会「虚高」RT，分析时要心中有数，或把思考时间放在事务控制器外单独看。
2. **固定定时器放线程组根 = 每个请求前都等**：会成倍拉低 TPS，思考时间应精确挂在具体请求之间，而不是一把梭挂在根。
3. **集合点 groupSize 不能超过线程数**：比如线程组只有 100 个线程，却设 groupSize=200，永远凑不齐，线程全卡死——必须设 Timeout 兜底，或保证线程数 ≥ groupSize。
4. **集合点制造脉冲负载，不适合稳态测试**：真实业务极少「同一毫秒齐发」，集合点只适合秒杀类场景；日常负载/压力测试用它反而会得出失真的拐点。
5. **集合点超时太小失去意义、太大拖慢**：太小（如 100ms）线程没到齐就放，集合效果没了；太大（如 30s）卡住整体节奏。通常设 3~5 秒。
6. **常量吞吐量定时器只能限速不能提速**：目标 TPS 高于系统/线程实际能力时达不到，要先把线程数和 ramp-up 配够（见 [[JMeter 加压策略：递增加压、阶梯加压与思考时间]]）。
7. **短测试吞吐不准**：它靠周期调节逼近目标，前几十秒会过冲或欠冲，测够时长才有参考价值。
8. **多个定时器叠加而非取最大**：同一个采样器前挂两个定时器，延迟是两者之和，不是挑大的，别重复挂导致等待翻倍。
9. **作用域误配**：定时器只对同子树采样器生效，想全局限速/思考要挂在能覆盖到所有目标采样器的层级。
10. **高斯/泊松偏差**：高斯集中在均值、泊松更散，模拟不同业务要选对；别用固定定时器硬凑，真人节奏是有抖动的。
11. **思考时间会放大并发需求**：按 Little's Law，并发 = TPS × RT（含思考时间），思考时间越长，要达到同一 TPS 需要的虚拟用户越多，建模时见 [[压测模型推算：目标 TPS 与二八原则]]。
12. **集合点放在事务控制器内会影响事务 RT 统计**：集合等待时间可能算进事务耗时，导致「瞬间并发」场景下事务 RT 异常，定位时要剔除。

## 面试怎么答

**Q：定时器加的等待时间，算不算进响应时间报告里？**

答：算。JMeter 的定时器在采样器执行**之前**运行，它等待的时间会被计入该采样器的经过时间（Elapsed Time），所以聚合报告里那个请求的 RT 会包含这段思考时间。这是个常见坑：接口本身 50ms，你加了 1 秒思考时间，报告 RT 就变成 ~1050ms。建模时要清楚这一点——如果你的 SLA 看的是「纯接口 RT」，思考时间应该放在事务控制器之外单独评估，或者用监控端（服务端日志）的耗时来交叉验证，而不是只看 JMeter 客户端 RT。

**Q：想模拟 1000 人同时秒杀，用集合点要注意什么？**

答：用同步定时器（Synchronizing Timer），groupSize 设 1000、并设一个 3~5 秒超时兜底。三个注意点：一是线程组的线程数必须 ≥ 1000，否则永远凑不齐会卡死；二是集合点制造的是脉冲式负载，只适合秒杀这类场景，日常负载测试用它失真；三是超时不能太小，太小没凑齐就放，集合效果没了，太大又拖节奏。另外集合等待可能算进事务 RT，分析拐点时要剔除这部分。

**Q：怎么把压测稳定限制在 100 TPS？**

答：用常量吞吐量定时器（Constant Throughput Timer），目标设 6000/分钟（即 100/秒）。但要理解它的边界：它只能「向下限速」，如果线程数不够或系统太慢，实际到不了 100；它是靠周期调节逼近目标的，前几十秒不准，测试要跑够时长；作用域默认整线程组，也能缩到单个控制器。配合上我还会用 [[JMeter 加压策略：递增加压、阶梯加压与思考时间]] 的阶梯加压先探顶，再用这个定时器把稳态锁在目标 TPS 上跑稳定性测试。
