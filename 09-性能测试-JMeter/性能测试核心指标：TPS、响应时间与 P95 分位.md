# 性能测试核心指标：TPS、响应时间与 P95 分位

![[assets/tps-rt-curve.svg]]
*图示：并发数、TPS、响应时间三者的关系曲线——轻压区 TPS 线性增长，拐点处 TPS 触顶，饱和区 TPS 不涨反跌且响应时间线性膨胀，崩溃区错误率飙升。*

> 报告里只写「平均响应时间 200ms」是没有价值的。**看懂 TPS 与响应时间的耦合关系、看懂为什么必须用 P95 而不是平均值**，才算入门性能分析。

## 概念

### 三个核心指标的定义

- **并发用户数（Concurrency）**：同一时刻**正在向服务端发请求并等待响应**的虚拟用户数。注意：不是在线用户数，不是注册用户数。10 万人挂在 App 上，同一秒真正在发请求的可能只有 200 个。
- **TPS（Transactions Per Second）**：服务端每秒完成的**事务**数。事务的粒度由你定义——可以是一个 HTTP 请求，也可以是「登录 + 查询 + 下单」整个业务链路。
- **响应时间（RT / Response Time）**：从客户端发出请求的第一个字节，到收到响应的最后一个字节的耗时。

**QPS 与 TPS 的区别**：QPS 是每秒查询数，粒度是单个请求；TPS 是每秒事务数，粒度是业务事务。一个「下单」事务可能包含 5 个 HTTP 请求，那么 TPS=100 时 QPS=500。**报告里必须写清楚你的「事务」是怎么定义的**，否则数字没法横向对比。

### 三者的数学关系：Little's Law

```text
并发数 = TPS × 响应时间
```

这是性能测试里唯一一个必须背下来的公式。它的含义非常直观：

- 如果系统每秒完成 100 个事务（TPS=100），每个事务平均耗时 0.5 秒（RT=0.5s）
- 那么任意时刻，系统内部**正在处理**的事务数 = 100 × 0.5 = 50 个

推论一（最重要）：**在系统未到瓶颈时，加并发 → TPS 线性增长，RT 基本不变。到达瓶颈后，加并发 → TPS 不再增长，RT 线性膨胀。**

因为 TPS 到顶后成了常数 C，那么 `RT = 并发数 / C`——并发数翻倍，响应时间就翻倍。**这就是为什么饱和区的响应时间会「起飞」**：新增的请求全在排队，排队时间被算进了响应时间。

推论二：**如果压测时 TPS 上不去而响应时间在涨，说明已经过了拐点，继续加并发只会让数据更难看，应该降压回到拐点附近做分析。**

### 为什么平均响应时间不可靠

假设 100 次请求：

- 95 次耗时 100ms
- 5 次耗时 5000ms（超时重试、GC 停顿、慢 SQL）

```text
平均值 = (95 × 100 + 5 × 5000) / 100 = 345ms
```

报告写「平均响应时间 345ms，达标」。但真实情况是**每 20 个用户里就有 1 个等了 5 秒**——这 5% 的用户体验极差，而且往往是最活跃的用户（请求多的人更容易命中长尾）。

平均值的问题在于**它被少数极端值稀释了，掩盖了长尾**。而性能问题恰恰主要发生在长尾。

### 分位值（Percentile）

**P95 = 把所有请求按耗时从小到大排序，第 95% 位置上的那个值。** 含义是「95% 的请求都比这个值快」。

同样的数据：

```text
排序后：100ms × 95 个，5000ms × 5 个
P50（中位数）= 100ms
P90 = 100ms
P95 = 100ms（第 95 个还是 100ms）
P99 = 5000ms  ← 长尾在这里暴露
Max = 5000ms
```

**分位值的正确读法**：

| 指标 | 意义 | 用途 |
|------|------|------|
| P50 / 中位数 | 典型用户体验 | 反映「大多数人多快」 |
| P90 | 常规体验下限 | 一般 SLA 底线 |
| P95 | 较差体验的边界 | **最常用的 SLA 指标** |
| P99 | 长尾体验 | 暴露 GC、慢 SQL、锁等待 |
| P99.9 | 极端长尾 | 大流量系统才有统计意义 |
| Max | 最坏情况 | 参考，单次抖动就能污染 |

**为什么是 P95 而不是 P99 或 Max**：

- Max 只需要一次网络抖动、一次 Full GC 就会变得极难看，**没有统计稳定性**，不适合做 SLA。
- P99 在样本量小时不稳定（1000 个样本里 P99 只由 10 个点决定），但对大流量系统很有价值。
- P95 兼顾了**统计稳定性**和**长尾敏感度**，是工业界最通用的选择。

一个实用的判读技巧：**看 P99/P50 的比值**。

- 比值 < 3：响应时间分布集中，系统行为稳定。
- 比值 3～10：存在明显长尾，通常是 GC、缓存未命中、慢 SQL 造成。
- 比值 > 10：系统有严重的偶发阻塞，必须查。

### 其他必看指标

- **错误率**：失败请求 / 总请求。压测里**错误率 > 0.1% 时所有性能数据都要打问号**——失败的请求通常返回极快（连接被拒绝只要 1ms），会把响应时间数据拉低，制造「性能很好」的假象。
- **吞吐量（Throughput，KB/s）**：网络字节数。用来判断带宽是否是瓶颈。
- **资源利用率**：CPU、内存、磁盘 IO、网络。用来定位瓶颈在哪一层。

## 用法

### 在 JMeter 里读聚合报告

命令行压测后生成 HTML 报告：

```bash
jmeter -n -t order.jmx -l result.jtl -e -o report/
```

聚合报告（Aggregate Report）的每一列：

| 列名 | 含义 | 怎么用 |
|------|------|--------|
| # Samples | 总请求数 | 样本量太小（< 1000）时分位值不可信 |
| Average | 平均响应时间 | **只做参考，不做结论** |
| Median | P50 | 典型用户体验 |
| 90% Line | P90 | |
| 95% Line | P95 | **主要 SLA 依据** |
| 99% Line | P99 | 长尾诊断 |
| Min / Max | 最快 / 最慢 | Max 用来发现极端阻塞 |
| Error % | 错误率 | **先看这一列**，超 0.1% 其余数据作废 |
| Throughput | TPS | 注意单位可能是 /sec 或 /min |
| Received KB/sec | 接收带宽 | 判断带宽瓶颈 |

**读报告的固定顺序**：

1. 先看 **Error %**。不为 0 就先查错误原因，别急着看性能数字。
2. 再看 **Throughput（TPS）**。有没有达到目标 TPS。
3. 再看 **95% Line**。达没达到 SLA。
4. 最后对比 **Average vs 95% vs 99%**，判断长尾严重程度。

### 用 jtl 文件自己算分位值

HTML 报告的粒度不够时，直接分析原始 jtl（CSV 格式）：

```bash
# jtl 表头：timeStamp,elapsed,label,responseCode,responseMessage,...,success,...
head -1 result.jtl
```

用 awk 快速算某个接口的分位值：

```bash
# 提取「下单」接口的耗时列（第 2 列 elapsed），排序后取分位
awk -F',' '$3=="下单" {print $2}' result.jtl | sort -n > order_rt.txt
TOTAL=$(wc -l < order_rt.txt)
echo "P50: $(sed -n "$((TOTAL*50/100))p" order_rt.txt) ms"
echo "P95: $(sed -n "$((TOTAL*95/100))p" order_rt.txt) ms"
echo "P99: $(sed -n "$((TOTAL*99/100))p" order_rt.txt) ms"
echo "Max: $(tail -1 order_rt.txt) ms"
```

用 Python 做更细的分布分析（比如找出长尾请求集中在哪个时间段）：

```python
import csv
from collections import defaultdict

rows = []
with open("result.jtl", newline="", encoding="utf-8") as f:
    for r in csv.DictReader(f):
        if r["label"] != "下单":
            continue
        rows.append({
            "ts": int(r["timeStamp"]) // 1000,   # 转成秒级时间戳
            "rt": int(r["elapsed"]),
            "ok": r["success"] == "true",
        })

rts = sorted(x["rt"] for x in rows)
n = len(rts)


def pct(p: float) -> int:
    """取第 p 分位（向上取整索引，越界时夹到最后一个）。"""
    idx = min(int(n * p / 100), n - 1)
    return rts[idx]


print(f"样本 {n}  错误率 {sum(not x['ok'] for x in rows) / n:.2%}")
print(f"P50={pct(50)}  P95={pct(95)}  P99={pct(99)}  Max={rts[-1]}")
print(f"P99/P50 = {pct(99) / max(pct(50), 1):.1f}  （>10 说明有严重长尾）")

# 按秒聚合，找出长尾集中的时间点
slow_by_sec = defaultdict(int)
for x in rows:
    if x["rt"] > pct(99):
        slow_by_sec[x["ts"]] += 1
worst = sorted(slow_by_sec.items(), key=lambda kv: -kv[1])[:5]
print("长尾最集中的 5 秒：", worst)
```

**「长尾最集中的 5 秒」这个输出极其有用**——如果长尾均匀分布，多半是某类请求本身慢；如果集中在几个时间点，多半是 Full GC 或定时任务抢资源，拿这几个时间戳去比对 GC 日志能直接定位。

### 验证 Little's Law 判断是否过了拐点

```python
# 从聚合报告读三个数，验证是否自洽
concurrency = 200      # 线程数
tps = 180              # 实测 TPS
avg_rt = 0.95          # 实测平均响应时间（秒）

theoretical = tps * avg_rt
print(f"理论并发 = {theoretical:.0f}，实际线程 = {concurrency}")
# 理论并发 ≈ 171，接近 200 → 线程基本都在忙，说明已接近饱和
# 若理论并发远小于线程数 → 大量线程在 think time 里空转，压力没打满
```

## 踩坑

1. **把在线用户数当并发数压**。产品说「峰值 5 万在线」，直接开 5 万线程——压力机先崩。在线用户绝大部分时间在看页面（think time），真正的并发数要用 Little's Law 从 TPS 反推，通常只有在线数的 1%～5%。

2. **错误率没归零就看性能数字**。压测报告显示「TPS 800，P95 120ms，性能优异」，一看 Error% 是 45%——因为一半请求秒级返回 503，把响应时间拉得极低。**失败请求必须从统计里剔除，或者先把错误率压到 0 再重测。**

3. **用平均响应时间做 SLA**。前面算过，平均值会被稀释。真实案例：某接口平均 180ms「达标」，上线后客诉不断，查监控 P99 是 8 秒——每 100 个用户就有 1 个等 8 秒，而这个接口是首页接口。

4. **样本量太小就算 P99**。跑了 500 个请求就报 P99，这个值由最慢的 5 个请求决定，换个时间跑结果可能差 3 倍。**至少 1 万样本，P99 才有统计意义；P99.9 至少要 10 万。**

5. **忽略 Throughput 的单位**。JMeter 聚合报告在 TPS 很低时会自动切成 `/min` 甚至 `/hour`。看到「Throughput 1200」以为是 1200 TPS，实际是 1200/min = 20 TPS。

6. **拿聚合了所有接口的 TPS 当业务 TPS**。脚本里有登录、查询、下单三个请求，聚合报告最后一行「TOTAL」的 TPS 是 300，就报告「下单 TPS 300」。实际下单只占 1/3，真实业务 TPS 是 100。**必须用事务控制器（Transaction Controller）把业务事务圈起来单独统计。**

7. **响应时间只看服务端，不看客户端排队**。JMeter 报的 RT 包含了「请求在压力机线程里等待发出的时间」吗？不包含——但如果压力机 CPU 打满，线程调度延迟会体现在 RT 里，让你以为服务端慢。**服务端埋点耗时 vs JMeter RT 的差值**，就是网络 + 排队开销，差得太大就要怀疑压力机。

8. **Connect Time 和 Latency 分不清**。JMeter 里有三个时间：
   - `Connect Time`：建立 TCP（含 TLS 握手）耗时
   - `Latency`：从发出请求到收到**第一个字节**（TTFB）
   - `Elapsed`：从发出请求到收到**最后一个字节**（这才是通常说的 RT）

   `Elapsed - Latency` 大 = 响应体传输慢（body 太大或带宽不足）；`Connect Time` 大 = 建连慢（TLS 握手、DNS、或服务端 accept 队列满）。这三个数拆开看能少查半天。

## 面试怎么答

**Q：并发用户数、TPS、响应时间三者是什么关系？**

A：用 Little's Law 描述：**并发数 = TPS × 响应时间**。

分两个阶段看：

系统**未到瓶颈**时，服务端资源有富余，增加并发相当于增加了并行处理的请求数，TPS 随并发线性增长，而单个请求的处理时间不变，所以响应时间基本平稳。

系统**到达瓶颈**后，TPS 被某个资源卡死成常数 C，此时由公式变形得 `RT = 并发数 / C`——**并发数翻倍，响应时间就翻倍**。因为新增的请求根本没有资源处理，全在队列里排着，排队时间被计入响应时间。

所以在压测曲线上，**TPS 曲线的拐点和响应时间曲线的抬头点是同一个位置**，那就是系统容量拐点。实际做容量测试就是靠阶梯加压找这个点。

再补一句实战判据：如果你发现加并发 TPS 不涨了，就别再加了，继续加只会让报告数字更难看，且掩盖真正的瓶颈信号——正确做法是退回拐点附近，去分析当时哪个资源先打满。

**Q：为什么要看 P95 / P99 而不是平均响应时间？**

A：因为**平均值会被长尾稀释，而性能问题主要就发生在长尾**。

举个具体例子：100 个请求里 95 个 100ms、5 个 5000ms，平均值是 345ms，看起来达标；但真实情况是每 20 个用户就有 1 个等了 5 秒。平均值把这个严重问题藏起来了。

P95 的定义是「95% 的请求都比它快」，它直接回答「较差的那部分用户体验有多差」，这才是 SLA 该关心的。

为什么选 P95 而不是 Max 或 P99：Max 只需要一次 GC 或网络抖动就会变得极难看，**没有统计稳定性**，不能作为验收标准；P99 在样本量不足时波动大；P95 是稳定性和长尾敏感度的平衡点，所以成了工业界通用选择。大流量系统会同时看 P99 甚至 P99.9。

实际分析时我还会看 **P99/P50 的比值**：比值小于 3 说明响应时间分布集中、系统稳定；超过 10 说明有严重的偶发阻塞，通常是 Full GC、缓存击穿或者锁等待，拿 P99 那批慢请求的时间戳去比对 GC 日志和慢查询日志，一般能直接定位。

**Q：TPS 和 QPS 有什么区别？**

A：QPS 是每秒查询数，统计粒度是单个请求；TPS 是每秒事务数，粒度是业务事务，一个事务可以包含多个请求。比如「下单」事务包含查库存、创建订单、扣减库存三个 HTTP 请求，那么 TPS=100 时 QPS=300。

实际工作中最容易出的问题是**口径不统一**：测试报的 TPS 是聚合了所有请求的总吞吐，开发理解成业务 TPS，两边数字差三倍还都以为对方看错了。所以报告里必须明确写出事务定义，JMeter 里要用**事务控制器**把业务链路圈起来，让报告输出的是业务级 TPS 而不是请求级 QPS。

**Q：压测时错误率 5%，性能数据还能用吗？**

A：不能用，必须先解决错误。原因是**失败请求会污染响应时间统计**——大部分失败是快速失败（连接拒绝 1ms、限流直接返回 3ms），它们混在样本里会把平均值和分位值都拉低，制造性能很好的假象。我见过错误率 40% 的报告显示 P95 只有 80ms，把失败样本剔掉后 P95 是 2.6 秒。

正确做法是先看错误明细：如果是脚本问题（比如参数化数据用完、断言写错）就修脚本重测；如果是服务端真的扛不住（503、超时），说明已经超过系统容量，应该降低并发回到错误率 0 的水位，那个水位对应的 TPS 才是有效容量。
