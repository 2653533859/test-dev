# 混沌工程故障注入测试实战

> 在受控的实验环境下对分布式系统主动注入硬件、网络与服务级故障，验证系统容错弹性、熔断降级与自愈能力的测试方法。

## 概念

随着微服务与 Kubernetes 云原生架构的普及，单个节点崩溃、网络抖动、机房断网成为常态。传统的测试方法往往只能验证在“所有依赖均正常运行”时的功能；而**混沌工程（Chaos Engineering）**的核心思想是：**“通过在分布式系统中主动制造不可预知的混乱，提前发现脆弱点并在故障发生前建立容灾信心”**。

### 混沌工程四大实验原则

1. **建立稳态假设（Steady State Hypothesis）**：明确系统在正常状态下的可度量行为（例如：业务核心接口成功率 $\ge 99.99\%$，P95 响应时间 $\le 200\text{ms}$）；
2. **多样化现实故障假设（Realistic Faults）**：模拟服务器掉电、交换机丢包、下游服务超时、磁盘读写夯死等真实极端事故；
3. **在真实或高仿真生产环境中运行**：离生产越近，实验发现深层隐患的价值越大；
4. **自动化持续注入并最小化爆炸半径（Blast Radius）**：先从单台 Canary 容器注入，并设置一键中止（Stop-The-World）机制。

### 1. 混沌工程实验流程

```text
               ┌────────────────────────────────────────────────────────┐
               │              第 1 步：定义稳态指标与监控基线              │
               │         业务接口成功率 > 99.9%，P95 RT < 200ms          │
               └───────────────────────────┬────────────────────────────┘
                                           │
                                           ▼
               ┌────────────────────────────────────────────────────────┐
               │          第 2 步：控制爆炸半径，启动 Chaos Mesh 注入       │
               │   注入场景：下游支付服务 50% 丢包 + 网络延迟 2000ms    │
               └───────────────────────────┬────────────────────────────┘
                                           │
                                           ▼
               ┌────────────────────────────────────────────────────────┐
               │          第 3 步：验证防御机制（熔断 / 降级 / 告警）     │
               │   断路器（Sentinel / Resilience4j）是否在 3 秒内开启？  │
               │   网关是否自动切换降级兜底文案？是否触发 P1 级别告警？   │

                                           │
                                           ▼
               ┌────────────────────────────────────────────────────────┐
               │          第 4 步：恢复环境，复盘并推动研发架构加固        │

               └────────────────────────────────────────────────────────┘
```

### 2. 使用云原生混沌工具 Chaos Mesh 注入网络延迟与丢包

在 Kubernetes 集群中部署 Chaos Mesh 后，通过 CRD（Custom Resource Definition）声明式定义故障实验：

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: payment-delay-and-loss
  namespace: test-mesh
spec:
  action: delay # 动作：模拟网络延迟与丢包
  mode: fixed   # 作用范围：注入到固定的 Pod
  value: '1'
  selector:
    namespaces:
      - production-staging
    labelSelectors:
      "app": "payment-service" # 注入目标：支付核心服务
  delay:
    latency: '1500ms'          # 增加 1.5 秒网络延迟
    jitter: '200ms'            # 抖动范围 +/- 200ms
    correlation: '50'
  loss:
    loss: '20'                 # 随机丢弃 20% 数据包
  duration: '5m'               # 持续 5 分钟后自动恢复
  scheduler:
    cron: '@every 10m'
```

### 3. 混沌自动化测试断言脚本（Python + Prometheus）

自动化检验注入故障后，网关断路器熔断是否在规定时间生效：

```python
import time
import requests
import pytest

PROMETHEUS_URL = "http://prometheus.internal:9090/api/v1/query"

def query_circuit_breaker_status(service_name: str) -> str:
    """查询 Sentinel / Resilience4j 当前断路器状态"""
    query = f'circuit_breaker_state{{service="{service_name}"}}'
    resp = requests.get(PROMETHEUS_URL, params={"query": query}).json()
    try:
        # 1 代表 OPEN (熔断), 0 代表 CLOSED (闭合)
        state_val = resp["data"]["result"][0]["value"][1]
        return "OPEN" if state_val == "1" else "CLOSED"
    except (IndexError, KeyError):
        return "UNKNOWN"

def test_payment_circuit_breaker_under_network_chaos():
    """验证当下游遭遇严重网络延迟时，系统是否如期触发降级断路"""
    # 1. 验证实验前稳态
    assert query_circuit_breaker_status("payment") == "CLOSED"
    
    # 2. 模拟触发业务流量加压
    # (此时后台 Chaos 注入已使 payment-service 延迟 1500ms)
    time.sleep(5)  # 等待错误率累积跨过熔断阈值 (例如 5 秒内错误率 > 50%)
    
    # 3. 自动化断言：熔断机制必须被成功触发
    current_state = query_circuit_breaker_status("payment")
    assert current_state == "OPEN", f"期望进入熔断保护，但断路器状态为: {current_state}"
    
    # 4. 验证对外返回降级托底数据，而不是原生 504 Gateway Timeout
    resp = requests.post("http://gateway.test/api/order/pay", json={"order_id": "123"})
    assert resp.status_code == 200
    assert resp.json()["code"] == 8001  # 降级返回排队中文案
```

## 踩坑

1. **缺少一键紧急恢复开关导致生产事故放大**：
   - 某次在预发/生产做 CPU 满载注入时，由于 Pod 探针没有正确响应，K8s 持续重启 Pod 并将流量切给未挂节点，导致连锁雪崩，而现场工程师没有留存快速卸载 Chaos CRD 的权限。
   - **解法**：任何混沌实验必须配备**全局死人开关（Dead-Man Switch）**。实验脚本若与控制台心跳断开 30 秒，本地 DaemonSet 必须自动清除 `iptables` 规则并释放资源。
2. **只测“注入后”，忽视“恢复后”的系统自愈与死锁**：
   - 实验重点常放在“注入后能不能报警、能不能熔断”，却忽略了故障解除后，由于瞬时积压请求涌入，连接池耗尽导致服务永久 hang 死。
   - **解法**：稳态验证必须分为三段：注入前基线、注入中降级、恢复后 15 分钟平稳自愈度量。

## 面试怎么答

> **面试官会怎么问**：
> 你们团队做过混沌工程（故障注入）吗？如何通过混沌工程验证系统的高可用性？

**30 秒回答骨架**：
> “做过。我们基于云原生的 **Chaos Mesh** 建立了常态化故障注入机制。核心策略遵循**‘假设稳态 → 注入故障 → 验证弹性 → 自动自愈’**四部曲。通常在压测或日常演练中，向目标节点注入网络延迟、丢包、磁盘 IO 耗尽或容器强杀。重点不是让服务挂掉，而是检验：**第一，监控与告警是否在 1 分钟内准确发出；第二，熔断与降级策略（如 Sentinel）是否生效并返回托底数据；第三，当故障取消后，服务连接池与资源能否在 3 分钟内平滑自愈**。”

**容易被追问的点**：
- **追问**：混沌工程和普通的负向异常测试有什么区别？
  - *回答要点*：传统负向测试大多是针对单个接口传非法入参、或者 Mock 某个方法抛出 Exception；而混沌工程是在**真实的底层基础设施与网络层**（如利用 Linux 内核 TC / iptables 注入丢包，或在 Cgroup 层面压爆 CPU/内存），验证的是分布式系统在未知级联失效时的整体弹性和自愈闭环。
