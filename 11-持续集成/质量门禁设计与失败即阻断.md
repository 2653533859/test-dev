# 质量门禁设计与失败即阻断

![[assets/quality-gate.svg]]
*图示：四道门禁依次检查（单测/覆盖率、静态扫描、自动化通过率、部署门禁）；任一不过 → 流水线标红阻断 → 配合代码平台 required check 阻止合入主干。*

## 概念

### 什么是质量门禁

「持续集成」不只是「自动跑测试」，更是「**不达标就拦下来**」。质量门禁（Quality Gate）是一组在流水线中设置的检查点，每项检查有明确的阈值，不达标就**失败即阻断**——流水线变红，且（配合代码平台）阻止代码合入主干。

没有门禁的 CI 只是「跑一跑看个热闹」：测试挂了一大片，PR 照样能合并，因为没人强制拦。门禁才让 CI 真正「守门」。

### 为什么「失败即阻断」要硬

测试团队常犯的错是「门禁失败只告警不阻断」——结果没人理，门禁形同虚设。门禁的本质是**准入控制**，必须硬阻断，且要和代码平台的 **required status check** 联动：CI 红 → 平台禁止合并。否则门禁只是装饰。

### 门禁的四类常见维度

1. **单元测试通过率 / 覆盖率**：单测不过、覆盖率低于阈值直接拦
2. **静态代码扫描**：SonarQube 等发现严重 bug / 安全漏洞 / 坏味道超阈值（见 [[SonarQube 静态扫描接入]]）
3. **自动化测试通过率**：接口/UI 自动化通过率低于阈值（如 95%）阻断
4. **部署门禁**：生产发布前的人工审批或自动化冒烟

## 用法

### 一、用 pytest 退出码做最基础的门禁

```groovy
// 单测 + 覆盖率门禁（见 [[Jenkinsfile Pipeline 语法]]）
stage('单测与覆盖率') {
    steps {
        sh '''
            . .venv/bin/activate
            pytest tests/unit --cov=app --cov-report=xml --cov-fail-under=80
        '''
    }
}
```

`--cov-fail-under=80`：覆盖率不足 80%，pytest 退出码非 0 → 流水线红。这是最朴素的门禁。

### 二、解析 JUnit 算自动化通过率门禁

```groovy
stage('质量门禁：通过率') {
    steps {
        script {
            def pass = sh(
                script: '''python3 - <<'PY'
import xml.etree.ElementTree as ET
r = ET.parse("junit.xml").getroot()
total = int(r.get("tests", 0)); fail = int(r.get("failures", 0)) + int(r.get("errors", 0))
print(round((total - fail) / total * 100, 2) if total else 0)
PY''',
                returnStdout: true
            ).trim() as Double
            echo "本次通过率：${pass}%"
            if (pass < 95) {
                error("通过率 ${pass}% 低于门禁阈值 95%")   // 硬阻断
            }
        }
    }
}
```

### 三、门禁失败即阻断 + 平台联动

```text
Jenkins/GitHub Actions 门禁失败
  → 流水线状态 = FAILURE / red
    → 代码平台（GitLab/GitHub）把该 CI 设为 required status check
      → 状态非绿 → 禁止 Merge / 禁止合入主干
```

在 GitLab 的「Protected Branches / Merge checks」或 GitHub 的「Branch protection → Require status checks」里把 CI job 勾选为必需。这一步是门禁真正生效的关键——光流水线红没用，必须拦住合并。

### 四、门禁过严或过松的取舍

```groovy
// 推荐：分级门禁
stage('门禁') {
    steps {
        script {
            def cov = currentCoverage()         // 假设从报告解析
            def rate = currentPassRate()
            if (cov < 80)  error("覆盖率 ${cov}% 低于 80%")      // 硬阻断
            if (rate < 95) unstable("通过率 ${rate}% 偏低，关注但不阻断")
            // 注意：unstable 不阻断，仅告警；error 才阻断
        }
    }
}
```

实践上：**覆盖率和单测是硬门禁**；**自动化通过率初期设为告警（unstable），待用例稳定后再转硬门禁**，避免一上来把团队全员卡死、引发反弹。

## 踩坑

1. **门禁只告警不阻断等于没有**。设成 `unstable`/`warn` 但没 `error`，PR 照样合。硬门禁必须用非零退出 / `error()`，并配合平台 required check。

2. **忘了在代码平台勾 required status check**。流水线红了，但 GitLab/GitHub 没把它设成必需，代码照样能合并。门禁生效的最后一公里在平台配置。

3. **阈值一拍脑袋定太高**。覆盖率一上来定 90%，存量代码根本够不到，全员被卡、纷纷绕过 CI。阈值应渐进：先 60 → 70 → 80，配合「新增代码覆盖率」而非「全量覆盖率」更合理。

4. **把 flaky 用例算进门禁导致误阻断**。偶发失败的用例让通过率门禁时红时绿，团队对门禁失去信任。先治理 flaky（见 [[持续集成、持续交付与持续部署]] 的测试金字塔与 flaky 管理），再上硬门禁。

5. **`piped` 命令吞掉失败**。`pytest | tee` 让退出码变成 tee 的 0，门禁永远绿。务必 `set -o pipefail` 或单独拿退出码（见 [[Jenkinsfile Pipeline 语法]]）。

6. **门禁失败没有「谁来看」的机制**。红了但没人负责修，门禁名存实亡。要配失败通知（见 [[Jenkins Allure 报告与构建后通知]]）和「红必须有人认领」的团队规则。

7. **门禁脚本本身出错被当成「未达标」**。解析 JUnit 的 Python 脚本若因字段缺失抛异常（退出码非 0），会被误判为门禁失败。门禁脚本自身要健壮，区分「检查失败」和「检查器故障」。

8. **覆盖率只看行覆盖忽略分支覆盖**。行覆盖 80% 但关键 if/else 分支没覆盖，漏洞仍在。重要模块看分支覆盖率。

9. **门禁把「跳过用例」也算通过**。有人用 `@pytest.mark.skip` 把失败用例跳过，通过率虚高。门禁应统计 skipped 并单独告警，或直接计入失败。

10. **本地能绕过门禁**。开发者本地 `--no-cov` 跳过覆盖率直接推，门禁只在 CI 跑等于摆设。门禁必须只在 CI 强制，且 PR 合入前必过 CI。

## 面试怎么答

**Q：什么是质量门禁，为什么需要失败即阻断？**

A：质量门禁是在流水线上设的一组检查点，每项有明确阈值，比如单测覆盖率不低于 80%、自动化通过率不低于 95%、SonarQube 严重问题数为 0。不达标就阻断流水线变红。光「跑测试」不够，必须「不达标就拦」，否则测试挂一片 PR 照样能合并，CI 就成了摆设。但光流水线红也没用，必须配合代码平台把该 CI 设为 required status check，状态非绿就禁止合并，这才是门禁真正生效的最后一公里。

**Q：门禁怎么设计才不会被团队抵制？**

A：两点。一是阈值渐进，别一上来定 90% 覆盖率，存量代码够不到全员被卡，大家就会想办法绕过。我一般从 60 提到 80，且优先看「新增代码覆盖率」而非全量。二是分级，单测和覆盖率这种确定性的设硬门禁，自动化通过率初期我只设告警 unstable，等用例稳定、flaky 治理好之后再转硬门禁，避免一上来把所有人卡死引发反弹。另外门禁红的必须有通知和认领机制，否则没人修就形同虚设。

**Q：门禁经常因为偶发失败误拦怎么办？**

A：这是 flaky 用例的问题，不是门禁的问题。门禁本身要硬，但前提是先治理 flaky：给偶发失败加重试标记、隔离依赖外部环境的用例、用 `--reruns` 区分「稳定失败」和「偶发失败」。我会在门禁脚本里区分「检查失败」（真不达标，error 阻断）和「检查器自身故障」（脚本异常），不能把解析脚本报错误判成不达标。等通过率稳定在阈值之上，门禁才可信。
