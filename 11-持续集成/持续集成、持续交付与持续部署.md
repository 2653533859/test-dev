# 持续集成、持续交付与持续部署

> 三个词都缩写成 CI/CD，但边界很清楚：CI 管「合不合得进主干」，持续交付管「随时能不能发」，持续部署管「发不发要不要人点」。

![[assets/ci-cd-pipeline.svg]]
*图示：同一条流水线上的三段作用域——CI 到「测试通过」为止，持续交付延伸到「产物随时可发布」，持续部署再去掉最后那个人工审批闸门。*

## 概念

### 持续集成 CI：解决「集成地狱」

CI 是 1990 年代末从极限编程（XP）里提出的实践，针对的是一个具体痛点——**集成地狱（integration hell）**。

传统模式下，五个人各写各的模块，两个月后合并。合并那周所有人加班：接口签名对不上、同名函数冲突、共享工具类被三个人各改了一遍、谁也说不清哪个版本是对的。**集成成本随隔离时间超线性增长。**

CI 的解法很朴素：**既然集成迟早要痛，那就每天痛一点点。** Martin Fowler 给的定义包含几条硬要求：

1. 维护单一代码仓库
2. 构建自动化
3. **构建要自测试**（build is self-testing）——这条最关键，没有自动化测试的构建叫「自动编译」，不叫 CI
4. 每人每天至少提交一次到主干
5. 每次提交都触发构建
6. **快速反馈**（10 分钟内出结果）
7. 修复失败的构建是最高优先级

注意第 4 条：**每天至少往主干提交一次**。这意味着长命 feature 分支跟 CI 的理念天然冲突——分支上跑的 CI 只是「分支自己的集成」，真正的集成风险被推迟了（见 [[Git 分支模型：Git Flow 与 trunk-based]]）。

### 持续交付 CD（Continuous Delivery）：解决「发布是个大工程」

CI 保证「代码是好的」，但从「代码是好的」到「能上线」之间还隔着一堆手工活：打包、配置、数据库迁移、灰度、回滚预案。很多团队 CI 绿了，发布还要两天。

持续交付的目标是：**任何一次通过 CI 的提交，都处于「随时可以部署到生产」的状态**，部署本身是一个按钮的事。

它要求把部署流程也自动化并反复演练：

- 制品（artifact）**构建一次，到处部署**——测试环境、预发、生产用的是同一个二进制/镜像，只换配置
- 环境用代码定义（IaC / Dockerfile / Compose），不靠人肉配机器
- 数据库变更脚本化、可回滚
- 部署脚本本身在测试环境跑过成百上千次

**最后一步上线由人决定**，这是持续交付的定义性特征。人决定的往往不是技术问题，而是业务问题：要不要赶在大促前发、要不要等运营文案。

### 持续部署 CD（Continuous Deployment）：去掉最后那个人

持续部署 = 持续交付 + 去掉人工审批。测试全绿就自动上生产，一天可能发布几十次。

**它不是「更高级的持续交付」，而是一个业务决策。** 能不能做，取决于：

- 是否有完善的**灰度/金丝雀发布**能力（先放 1% 流量）
- 是否有**自动回滚**（监控指标异常自动切回上个版本）
- 是否有**可观测性**（发上去之后能不能立刻知道坏没坏）
- 业务是否允许（金融交易、医疗系统通常有合规要求必须人工审批）

没有这些配套就上持续部署，等于把「事故」也自动化了。

### 一张对照表

| | 持续集成 CI | 持续交付 CD | 持续部署 CD |
|---|---|---|---|
| 终点 | 测试通过、可合入主干 | 产物随时可发布 | 已发布到生产 |
| 人工介入 | 修复失败 | **点击发布** | 无 |
| 核心能力 | 自动构建 + 自动测试 | 自动化部署 + 环境一致性 | 灰度 + 自动回滚 + 监控 |
| 反馈周期 | 分钟级 | 小时级 | 分钟级 |
| 谁都能做 | 是 | 需要工程投入 | 需要业务允许 |

### CI 对测试团队的真正意义

不是「跑脚本的地方」，而是三件事：

**1. 把测试从「阶段」变成「能力」。** 传统模式下测试是开发完成之后的一个阶段，被压缩、被跳过。接进 CI 之后，测试变成每次提交都执行的**质量约束**，是流水线的一部分而不是下游。

**2. 测试的价值第一次被量化。** CI 上能看到：拦截了多少次问题、平均反馈时长、用例稳定性（flaky rate）、覆盖率趋势。这些数据是测试团队最有说服力的产出。

**3. 倒逼自动化质量。** 只在本地手动跑的脚本，环境依赖、硬编码路径、随机失败都能靠人绕过去。接进 CI 之后，任何不稳定都会变成红灯打扰所有人，逼着你把用例写扎实（见 [[质量门禁设计与失败即阻断]]）。

### 测试金字塔在流水线上的分层

CI 要求「10 分钟出结果」，全量回归跑一小时显然不行。解法是**按阶段分层**：

```text
提交时（PR 门禁，目标 < 10 分钟）
  └─ 静态检查（秒级） → 单元测试（1-2 分钟） → 接口冒烟（3-5 分钟）

合入主干后（目标 < 30 分钟）
  └─ 全量接口回归 → 关键路径 UI 自动化

每日定时（夜间）
  └─ 全量 UI 回归 → 兼容性矩阵 → 性能基线

发版前
  └─ 全链路 + 探索性测试 + 安全扫描
```

原则：**越靠前的阶段跑得越快、越稳定**。把 20 分钟的 UI 回归塞进 PR 门禁，只会导致大家绕过门禁。

## 用法

### 一、最小可用的 CI（GitHub Actions）

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  ci:
    runs-on: ubuntu-latest
    timeout-minutes: 10          # CI 必须有超时，卡住比失败更糟
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip

      - name: 安装依赖
        run: pip install -r requirements.txt

      - name: 静态检查（最快，先跑）
        run: |
          ruff check .
          ruff format --check .

      - name: 单元测试 + 覆盖率门禁
        run: pytest tests/unit --cov=src --cov-fail-under=80

      - name: 接口冒烟
        run: pytest tests/api -m smoke --maxfail=1
```

`--cov-fail-under=80` 和 `--maxfail=1` 是「失败即阻断」的具体落地：不达标直接非零退出，流水线红灯。

### 二、加上持续交付（构建一次，多处部署）

```yaml
# .github/workflows/cd.yml
name: CD

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.meta.outputs.image }}
    steps:
      - uses: actions/checkout@v4

      - id: meta
        # 用 commit SHA 做 tag，保证「代码 ↔ 镜像」一一对应，可追溯可回滚
        run: echo "image=registry.example.com/app:${GITHUB_SHA::7}" >> $GITHUB_OUTPUT

      - name: 构建并推送镜像（全流程只构建这一次）
        run: |
          docker build -t "${{ steps.meta.outputs.image }}" .
          echo "${{ secrets.REGISTRY_PWD }}" | docker login registry.example.com -u ci --password-stdin
          docker push "${{ steps.meta.outputs.image }}"

  deploy-test:
    needs: build
    runs-on: ubuntu-latest
    environment: test
    steps:
      - name: 部署测试环境（同一镜像，只换配置）
        run: ./deploy.sh test "${{ needs.build.outputs.image }}"

  e2e:
    needs: deploy-test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: pytest tests/e2e --base-url=https://test.example.com

  deploy-prod:
    needs: e2e
    runs-on: ubuntu-latest
    environment:
      name: production       # 在仓库设置里给这个 environment 配 required reviewers
      url: https://example.com
    steps:
      # 这一步会挂起等待人工审批 → 这就是「持续交付」而非「持续部署」
      - name: 发布生产
        run: ./deploy.sh prod "${{ needs.build.outputs.image }}"
```

把 `environment: production` 的 required reviewers 去掉，这条流水线就从持续交付变成了持续部署——**区别就是配置里的一个开关**。

### 三、Jenkins 里的等价表达

```groovy
pipeline {
    agent { label 'linux' }
    options { timeout(time: 30, unit: 'MINUTES') }

    stages {
        stage('CI: 构建与自测') {
            steps {
                sh 'pip install -r requirements.txt'
                sh 'ruff check .'
                sh 'pytest tests/unit --cov=src --cov-fail-under=80'
            }
        }
        stage('CD: 打镜像') {
            steps {
                script {
                    env.IMAGE = "registry.example.com/app:${env.GIT_COMMIT.take(7)}"
                }
                sh 'docker build -t $IMAGE . && docker push $IMAGE'
            }
        }
        stage('CD: 部署测试环境 + 回归') {
            steps {
                sh './deploy.sh test $IMAGE'
                sh 'pytest tests/api --base-url=https://test.example.com --alluredir=allure-results'
            }
        }
        stage('人工审批') {
            // 有这一段 = 持续交付；删掉它 = 持续部署
            steps {
                timeout(time: 4, unit: 'HOURS') {
                    input message: '确认发布到生产？', ok: '发布', submitter: 'release-manager'
                }
            }
        }
        stage('CD: 发布生产') {
            steps { sh './deploy.sh prod $IMAGE' }
        }
    }
    post {
        always  { allure results: [[path: 'allure-results']] }
        failure { echo '通知责任人' }
    }
}
```

完整语法见 [[Jenkinsfile Pipeline 语法]]。

### 四、衡量 CI 是否真的在起作用

光搭起来不算数，看四个指标（DORA 四大指标的简化版）：

```text
1. 流水线时长          目标 PR 门禁 < 10 min，主干 < 30 min
2. 主干红灯时长        从变红到修复的平均时间，目标 < 30 min
3. 用例不稳定率        flaky rate = 重跑就过的失败次数 / 总失败次数，目标 < 1%
4. 缺陷逃逸率          线上缺陷数 / (线上 + CI 拦截) ，反映门禁有效性
```

第 3 条对测试团队最要命：**flaky 用例是 CI 最大的敌人**。一旦大家习惯了「红了先重跑一次」，门禁就名存实亡了。治理办法是给用例打稳定性标签，把不稳定的用例移出门禁套件、限期修复，而不是加重试掩盖。

## 踩坑

1. **有 CI 工具 ≠ 做了 CI**。装了 Jenkins、配了个 job 每天定时跑一次全量回归——这是「定时任务」，不是持续集成。CI 的定义要求「每次提交都触发」且「快速反馈」，没有这两点就没有 CI 的价值。

2. **流水线跑 40 分钟**。开发提交后去干别的了，40 分钟后红灯回来，上下文早就切走了，修复成本翻倍。这直接违背 CI 的核心——快速反馈。解法：按阶段分层、并行执行、缓存依赖、把慢用例挪到夜间。

3. **红灯常态化**。主干红了三天没人管，大家习惯了「反正一直是红的」，CI 彻底失效。这是 CI 死亡最常见的方式。要立规矩：**红灯修复优先级高于一切新需求**，并且通知精确到提交人（见 [[Jenkins Allure 报告与构建后通知]]）。

4. **用重试掩盖 flaky**。`pytest --reruns 3` 一加，红灯变绿了，皆大欢喜——然后真实的偶发 bug 也被掩盖了。重试可以用，但必须**统计并上报重试次数**，把 flaky 当缺陷管理。

5. **CI 上跑得过，本地跑不过（或反之）**。根因是环境不一致：Python 版本、依赖版本、时区、locale、依赖服务的数据。解法是把环境固化成镜像，本地和 CI 用同一个（见 [[Docker 镜像与容器核心概念]]）。

6. **每个环境重新构建一次**。测试环境构建一个包，生产又构建一个包——两次构建的产物可能不同（依赖漂移、构建机差异），等于**测试环境测的东西根本没上线**。持续交付的铁律是 build once, deploy everywhere，配置通过环境变量注入。

7. **把「持续部署」当 KPI 硬推**。没有灰度、没有自动回滚、没有监控告警就自动上生产，第一次事故就会让团队彻底放弃 CI/CD。应该按能力逐级演进：CI → 持续交付 → 灰度 → 自动回滚 → 持续部署。

8. **测试数据污染导致用例互相影响**。CI 上并发跑多条流水线，共用一套测试库，A 的用例删了 B 的数据。解法：每条流水线起独立容器化环境（见 [[docker compose 编排测试环境]]），或者用例级数据隔离（每个用例造自己的数据、用完清理）。

9. **门禁只在 CI 里，代码平台上没设 required check**。CI 报红但 Merge 按钮照样能点，大家习惯性无视。**真正的阻断来自分支保护规则**，CI 只是产生信号。

## 面试怎么答

**Q：持续集成、持续交付、持续部署的区别？**

A：持续集成的终点是「代码能不能安全合进主干」——每次提交都自动构建、跑自动化测试，快速反馈，失败即阻断，核心目的是消除集成地狱。持续交付在它之上，保证每一个通过 CI 的版本都处于「随时可以上生产」的状态，部署流程完全自动化并反复演练过，但**最后上线那一下由人点**。持续部署则是把这个人工审批也去掉，测试全绿就自动发到生产。三者是递进的，区别点很好记：CI 看「合不合得进主干」，Delivery 看「随时能不能发」，Deployment 看「发不发要不要人点」。落到实现上，持续交付和持续部署的差别可能就是流水线里有没有一个 `input` 步骤。

**Q：CI 对测试团队意味着什么？**

A：三层。第一，测试从「开发完成后的一个阶段」变成「每次提交都执行的质量约束」，不再是被压缩的下游。第二，测试的价值第一次可量化——CI 上能看到拦截了多少问题、平均反馈时长、用例稳定率、覆盖率趋势，这是测试团队最有说服力的产出。第三，倒逼自动化质量，本地手动跑的脚本可以靠人绕过环境问题，进了 CI 任何不稳定都会变成打扰所有人的红灯，逼着你把用例写扎实。具体工作上，我要负责用例的分层编排——PR 门禁只放静态检查、单测和接口冒烟，控制在 10 分钟内；全量回归放合入后；UI 全量和兼容性放夜间。

**Q：你们的流水线跑一次要多久，怎么优化的？**

A：PR 门禁控制在 8 分钟以内。优化做了四件事：一是分层，把 30 分钟的 UI 全量回归从门禁挪到夜间，门禁只留冒烟；二是并行，接口用例按模块拆成多个 job 并行跑，用 pytest-xdist 再做进程级并行；三是缓存，pip 依赖和 Docker 层缓存，装依赖从 2 分钟降到 15 秒；四是治理 flaky 用例，之前有几个用例偶发失败导致大家重跑，重跑一次就多 8 分钟，我们把不稳定用例识别出来限期修复、暂时移出门禁，而不是加 `--reruns` 掩盖。另外流水线一定要设 timeout，卡住比失败更浪费时间。

**Q：CI 上跑失败但本地跑得过，怎么排查？**

A：先看是不是真失败——重跑一次，如果时好时坏就是 flaky，方向是用例本身（硬编码等待、用例间依赖、共享数据）。如果稳定失败，那基本是环境差异，我会按几个维度对：Python 和依赖版本（CI 装的是不是锁文件里的版本）、环境变量与配置（CI 上少配了什么）、时区和 locale（时间断言最容易踩）、依赖服务的数据（本地库有历史数据，CI 是干净库，用例其实依赖了脏数据）、文件路径大小写（本地 Windows 不敏感，CI Linux 敏感）、浅克隆导致的 git 信息缺失。定位手段是在 CI 里加诊断步骤打印环境信息，或者直接用 CI 同款镜像在本地起容器复现。根治办法是把环境用 Docker 固化，本地和 CI 跑同一个镜像，让这类问题从源头消失。
