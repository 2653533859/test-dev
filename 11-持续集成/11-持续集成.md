# 11-持续集成

把自动化用例接进流水线，让测试真正产生持续价值。自动化脚本只有跑在 CI 上、有人看结果，才算落地。

## 学习目标

- 熟练使用 Git 协作，能处理冲突、回退、分支合并
- 能配好一条完整流水线：代码提交 → 构建 → 部署测试环境 → 跑自动化 → 出报告 → 通知
- 会用 Docker 解决环境不一致，把测试环境固化成镜像
- 能设计质量门禁，让不达标的代码进不了主干

## 计划覆盖的知识点

- Git：常用命令、分支模型（Git Flow / trunk based）、`merge` 与 `rebase`、冲突解决、`stash`、`cherry-pick`、`reset` 与 `revert` 的区别、`.gitignore`
- 概念：持续集成 / 持续交付 / 持续部署的区别，CI 对测试团队的意义
- Jenkins：安装与插件、Freestyle 与 Pipeline、Jenkinsfile 语法（stage / agent / post）、参数化构建、定时与 Webhook 触发、凭据管理、Allure 报告插件、节点与分布式构建、构建后通知（邮件 / 钉钉 / 企业微信）
- GitHub Actions：workflow 结构、触发事件、job 与 step、matrix 多环境、缓存、artifact 上传、secrets
- Docker：镜像与容器、常用命令、Dockerfile 编写、数据卷与网络、docker compose 编排测试环境、把自动化框架打成镜像
- 质量门禁：单测覆盖率、SonarQube 静态扫描、自动化通过率阈值、失败即阻断
- 实践串联：提交代码自动触发接口自动化 + Allure 报告 + 钉钉通知

## 常考点

- `git merge` 与 `git rebase` 的区别，团队里该用哪个
- `git reset --hard` 与 `git revert` 的区别，已推送的提交怎么撤销
- 持续集成、持续交付、持续部署的区别
- 你的自动化用例在 CI 上怎么触发，失败了谁看、怎么通知
- CI 上跑得起来但本地跑不起来（或反之），怎么排查
- Docker 解决了测试中的什么问题，镜像与容器的区别
