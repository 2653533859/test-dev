# 移动端自动化弹窗动态拦截与巡检机制

> 移动端自动化夜间无人值守回归的「头号杀手」：不可预知的运营大促弹窗、系统权限提示、版本灰度更新与低电量警告。通过「异常驱动的黑名单消除」与「系统级 Watcher 守护监听」，实现弹窗静默化解。

## 概念

### 移动端弹窗为何比 Web 更致命

在 Web 端自动化中，页面跳转相对清晰，弹窗也大多是 DOM 树上的简单浮层；而在移动端（Android / iOS）：

```text
       用例正常执行流: 首页 ──> 分类 ──> 商品详情 ──> 下单购买
                                  │
                                  ▼ 突然弹出浮层！
                         ┌─────────────────┐
                         │   新人专享大礼包   │ (非预期运营弹窗，全屏半透明遮罩)
                         │   [残忍拒绝] [领取] │
                         └─────────────────┘
                                  │
       后续所有坐标点击/元素查找 ──┴──> 全部失败 (报错 ElementNotInteractableException)
```

1. **出现时机高度不确定**：可能在启动阶段，也可能在进入特定 Tab、触发网络回调或停留 5 秒后异步弹出；
2. **来源极其复杂**：
   - **系统级弹窗**：通知权限、定位授权、低电量提示、网络断开；
   - **业务常态弹窗**：用户协议隐私政策（首次冷启动）；
   - **不可预知运营弹窗**：大促活动红包、强制/建议升级、满意度评分、连续签到。
3. **传统线性处理的破产**：如果在每一步操作前都去检查一次「有没有弹窗」，用例执行速度会变慢 3~5 倍；如果不检查，一旦出现弹窗，整套测试套件后面数十条用例全部连锁雪崩失败。

## 用法

### 1. 异常驱动的弹窗黑名单扫描（推荐通用解法）

**核心原则：绝不在正常交互前主动轮询弹窗；只在捕获 `NoSuchElementException` 或超时异常时，才激活弹窗消除流程。**

```python
import logging
from typing import List, Tuple
from appium.webdriver.common.appiumby import AppiumBy
from selenium.common.exceptions import (
    NoSuchElementException,
    TimeoutException,
    StaleElementReferenceException,
)


class BasePage:

    def __init__(self, driver):
        self.driver = driver
        # 弹窗关闭按钮的特征黑名单（支持 ID、XPath、文本、AccessibilityId）
        self._popup_blacklist: List[Tuple[str, str]] = [
            (AppiumBy.ID, "com.mall.app:id/iv_close_dialog"),  # 运营活动关闭叉
            (
                AppiumBy.ID,
                "com.mall.app:id/btn_cancel_update",
            ),  # 灰度升级稍后提醒
            (
                AppiumBy.XPATH,
                "//*[@text='我知道了' or @text='残忍拒绝' or @text='暂不开启']",
            ),
            (
                AppiumBy.XPATH,
                "//*[@resource-id='android:id/button2' and @text='取消']",
            ),
        ]
        self._max_retry_times = 3

    def find(self, by: str, value: str):
        """带弹窗自愈能力的稳健查找方法"""
        for retry in range(self._max_retry_times):
            try:
                # 正常查找（如果元素存在且可操作，零额外开销直接返回）
                return self.driver.find_element(by, value)
            except (NoSuchElementException, TimeoutException) as err:
                logging.warning(
                    f"查找元素失败 [{by}={value}]，第 {retry+1} 次尝试触发弹窗检测自愈..."
                )
                if not self._handle_popup():
                    # 如果没有命中任何黑名单弹窗，说明是真正的元素不存在，抛出异常
                    raise err
        raise NoSuchElementException(
            f"经历多次弹窗消除后，依然未找到元素: [{by}={value}]"
        )

    def _handle_popup(self) -> bool:
        """遍历黑名单消除弹窗，返回是否成功消除了弹窗"""
        # 临时将隐式等待调为 0，防止扫描黑名单时产生阻塞
        self.driver.implicitly_wait(0)
        handled = False
        try:
            for by, value in self._popup_blacklist:
                elements = self.driver.find_elements(by, value)
                if elements and elements[0].is_displayed():
                    logging.info(f"✨ 命中并拦截弹窗: [{by}={value}]，自动执行点击关闭")
                    elements[0].click()
                    handled = True
                    break  # 关闭一个弹窗后返回，交给外层重新尝试找目标元素
        except StaleElementReferenceException:
            pass
        finally:
            self.driver.implicitly_wait(5)  # 还原隐式等待
        return handled
```

### 2. Android 平台原生 UiWatcher 守护线程机制

如果是基于 `uiautomator2` Python 库或具备底层权限，可以注册系统级 Watcher：当 Android 底层判定界面无响应或出现目标关键字时，由系统 Accessibility 线程在毫秒级内自动点击，完全不阻塞 Python 测试主线程：

```python
import uiautomator2 as u2

d = u2.connect()

# 注册系统守护 Watcher：只要屏幕出现「我知道了」或「残忍拒绝」，底层自动点击
d.watcher("PROMO_POPUP").when("我知道了").click()
d.watcher("UPDATE_POPUP").when("以后再说").click()
d.watcher("SYS_PERM").when("仅在使用中允许").click()

# 启动后台守护监听（每隔一段时间由 C++ 底层轮询）
d.watcher.start(interval=1.0)

# ... 运行正常业务自动化用例，全程无需关心弹窗 ...

# 测试结束停止监听
d.watcher.stop()
```

## 踩坑

1. **黑名单匹配规则过于宽泛导致「误杀」核心业务弹窗**：
   - *案例*：黑名单里写了一条 `//*[@text='确认' or @text='取消']`。在测试「确认提交订单」用例时，用例等待订单结果时由于卡顿触发了弹窗扫描，直接把弹出的「是否支付 100 元」业务弹窗给点了「取消」，导致用例失败。
   - *解法*：黑名单定位器**必须限定在关闭/跳过场景**（如 `跳过`、`残忍拒绝`、`稍后再说`），严禁包含 `确定`、`确认` 等极具业务语义的词汇。
2. **多层嵌套弹窗消除不彻底**：
   - *案例*：某些 APP 启动时，先弹活动弹窗，关掉后又弹签到弹窗，签到后又弹版本升级。
   - *解法*：`_handle_popup()` 使用循环检测，设定上限最多消除 3 层，消除一层后休眠 500ms 继续探测，直到无遮罩为止。
3. **弹窗处于 WebView / H5 内部**：
   - *案例*：活动弹窗是通过前端抽屉组件以 HTML5 形式嵌入 Native 页面中的，Native 控件树上根本找不到关闭按钮的文字，只有一层白板 `android.webkit.WebView`。
   - *解法*：针对此类弹窗，要么在测试环境通过账号配置或服务端 Mock 接口直接下发关闭该活动的开关，要么通过执行注入 JavaScript 进行 DOM 移除。

## 面试怎么答

**Q：移动端夜间无人值守执行自动化回归测试时，经常被随机弹出的运营活动弹窗打断，你们是如何解决的？**
> 1. **事前防御（环境与服务端治理）**：在自动化执行环境，首先通过配置专项测试账号（标记为免灰度、免大促活动白名单），或者通过代理工具（mitmproxy）对启动配置接口进行 Mock，从数据源头关闭不必要的活动与升级推送。
> 2. **事中异常驱动的黑名单自愈（框架核心机制）**：
>    - 避免在正常步骤中无脑轮询（那会导致用例耗时剧增）；
>    - 在 BasePage 核心操作（点击、查找）上封装装饰器，**只有在捕获到元素无法交互或超时异常时，才触发弹窗黑名单扫描**；
>    - 维护常见系统权限（允许）、升级（稍后）与运营活动（跳过/关闭）特征定位器，命中后自动消除并回退重新尝试原步骤；
> 3. **底层 Watcher 守护（特定平台提效）**：在 Android 平台利用 UiAutomator2 原生 Watcher 机制挂载后台守护监听，实现毫秒级自动关闭弹窗，确保无人值守回归的稳定性达到 98% 以上。
