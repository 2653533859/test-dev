# 函数默认参数的可变对象陷阱

> “默认参数在函数定义时只求值一次”——这句话背后是“函数是一等对象、def 时创建函数对象并固定其 `__defaults__`”。理解这个机制，就明白为什么可变默认值会跨调用串味，也明白它其实是个特性而非 bug。

## 概念

### 1. 默认参数在 `def` 执行时求值并绑定

Python 中函数是**一等对象**。`def f(...)` 执行时，会创建一个函数对象，并把默认参数**作为该对象的属性**固定下来（可通过 `f.__defaults__` 查看）。因此默认参数**只在定义时计算一次**，不是每次调用都新建。

```python
def f(items=[]):
    items.append(1)
    return items

print(f.__defaults__)        # ([],)  —— 默认参数对象在函数创建时就绑定了
```

### 2. 为什么可变默认值会“串味”

如果默认值是 `list`/`dict`/`set` 这类**可变对象**，那么所有不传该参数的调用，拿到的都是**同一个对象引用**（见 [[Python 可变对象与不可变对象]]）。第一次调用往里 `append`，第二次调用看到的就是被改过的同一个列表。

```python
f()        # [1]
f()        # [1, 1]   ← 共享同一个 list！
```

### 3. 正确写法：用 `None` 哨兵

不传参时，在函数体内**新建**对象：

```python
def f(items=None):
    if items is None:
        items = []
    items.append(1)
    return items

f()        # [1]
f()        # [1]    ← 各自独立
```

### 4. 为什么这其实是“特性”

默认参数在 def 时求值是**有意为之**：它允许默认参数引用模块级的可变对象作为“跨调用缓存”（如默认 `cache={}` 当记忆化）。问题不在机制，在于“把可变默认值当成每次新建的局部变量”这个误解。想显式共享状态，把它提到模块级更清晰。

## 用法

```python
# 错误：所有调用共享同一个 list
def add_bad(x, items=[]):
    items.append(x)
    return items

# 正确：None 哨兵，函数内新建
def add_good(x, items=None):
    if items is None:
        items = []
    items.append(x)
    return items

# 想故意保留跨调用状态，提到模块级更清晰
_ACCUM = []
def add_global(x):
    _ACCUM.append(x)
    return _ACCUM
```

## 踩坑

- **测试框架里最隐蔽**：一个 helper/fixture 用 `items=[]` 默认参数，第一个用例加了数据，后续用例“凭空”多数据，表现为偶发失败。
- **`__defaults__` 可查当前默认对象**：调试时 `func.__defaults__` 看到的就是那个被共享的列表。
- **默认参数还能是其他可变对象**：dict/set 同样坑，任何可变类型都别直接当默认值。
- **想重置共享状态**：调用方传入新 `[]` 或显式 `del`，否则拿到的还是累积后的对象。
- **PEP 8 明确推荐**：可变默认值用 `None` 哨兵，函数体初始化。

## 面试怎么答

一句话：Python 默认参数是在**函数定义时求值一次**并绑定到函数对象的 `__defaults__`，可变对象默认值会被所有调用共享，导致状态串味。正确写法是用 `None` 作哨兵，函数体内再初始化。

延伸：这其实是有意设计（允许默认参数当跨调用缓存），坑源于“把可变默认值当每次新建的局部变量”的误解。测试里尤其隐蔽（用例间数据污染）。查看 `func.__defaults__` 能看到那个共享对象。PEP 8 推荐可变默认值用 `None` 哨兵。
