# 测试框架日志与断言封装

> 框架好不好用，很大程度看「失败了能不能一眼看出为什么」。日志和断言封装就是要让每一次失败都自带上下文：请求是什么、实际返回是什么、差异在哪。

## 概念

### 为什么要封装断言

裸 `assert resp.status == "CREATED"` 失败时，pytest 只告诉你 `assert "REJECTED" == "CREATED"`，**没有请求上下文**——你还得去翻日志才知道是哪笔单子、用的哪个账号。封装断言的目标是：

1. **失败时自带上下文**：把请求体、响应、用例名一起打出来；
2. **统一断言入口**：全项目断言风格一致，便于加日志/截图；
3. **支持软断言**：收集所有失败而不是遇到第一个就停。

### 为什么要封装日志

默认 `print` 在 pytest 捕获下要加 `-s` 才看得到，且没用例维度。封装日志要能：自动带上用例名/用例 ID、区分级别、失败时落盘便于 CI 排查。

### 和 pytest assert 重写的配合

注意：pytest 的 **assert 重写只重写测试模块里的顶层 `assert`**（见 [[pytest 断言重写机制]]）。如果你把断言包进一个普通函数 `my_assert()`，函数内部的 `assert` 不被重写，失败信息会退化为「None != None」这种无价值内容。封装断言时要手动把差异信息通过异常参数带上。

## 用法

### 带上下文的断言封装

```python
# core/assert_util.py
import json


class AssertionErrorWithContext(Exception):
    pass


def assert_status(resp, expect, ctx=None):
    actual = resp.status
    if actual != expect:
        msg = (
            f"断言失败：状态不符\n"
            f"  期望: {expect}\n"
            f"  实际: {actual}\n"
            f"  上下文: {ctx}\n"
            f"  响应: {json.dumps(resp.body, ensure_ascii=False)[:500]}"
        )
        raise AssertionErrorWithContext(msg)
```

这样失败信息里直接带了响应体和上下文，不用再去翻日志。

### 软断言（收集多个失败）

```python
import pytest


@pytest.fixture
def soft_assert():
    errors = []

    def _check(cond, msg):
        if not cond:
            errors.append(msg)

    yield _check
    if errors:
        raise AssertionError("软断言失败:\n" + "\n".join(errors))


def test_order_fields(soft_assert):
    soft_assert(order.id is not None, "order.id 为空")
    soft_assert(order.amount > 0, "amount 非正")
    # 两个失败都会收集，最后一起报
```

### 日志封装

```python
# utils/logger.py
import logging
import sys


def get_logger(name="test"):
    log = logging.getLogger(name)
    if not log.handlers:
        h = logging.StreamHandler(sys.stdout)
        h.setFormatter(logging.Formatter(
            "%(asctime)s [%(levelname)s] %(name)s: %(message)s"))
        log.addHandler(h)
        log.setLevel(logging.INFO)
    return log
```

结合 conftest，在每条用例开始时用 `logging.LoggerAdapter` 注入用例名，使每条日志自带 `case=xxx` 维度。

## 踩坑

1. **封装函数里的 assert 信息丢失**：`def check(x): assert x` 内部 assert 不被重写，失败只报 `assert None`。必须自己 `raise AssertionError(带上下文消息)`，或确保差异信息写进异常参数。
2. **裸 `assert False` 无信息**：`assert resp.ok` 失败只说 `assert False`，看不到响应。封装时把响应体塞进异常 message。
3. **软断言导致用例误报通过**：`soft_assert` 收集了错误但忘了在 fixture 的 yield 之后 `raise`，用例会被记为 PASSED。务必在 yield 后统一抛出。
4. **软断言吞掉真正的异常**：用例体里抛了真异常，被软断言的 try 包住当成一个失败项，掩盖了根因。软断言只应包「断言检查」，业务调用该抛就抛。
5. **日志没上下文刷屏**：所有用例日志都是一个格式，CI 上一千行分不清哪条用例。要用 LoggerAdapter 或 filter 把 `case_id` 带进每条日志。
6. **日志级别全 DEBUG 淹没重点**：默认 DEBUG 把请求重试细节全打出来，真正失败被埋。CI 默认 INFO，排查时再开 DEBUG。
7. **print 在 pytest 捕获下看不到**：直接 `print` 要加 `-s`，且不受日志级别控制。框架应统一走 `logging`，别混用 print。
8. **断言封装过度做成 DSL**：为了「好看」造一套 `expect(resp).to.have.status(200)`，学习成本高、报错栈深。除非团队规模大，否则简单函数式封装更可控。

## 面试怎么答

- **问：为什么要封装断言？怎么封装？**
  答：裸 assert 失败没上下文，排查要翻日志。封装成带上下文的断言函数，失败时把请求、响应、用例信息一起抛出；同时统一全项目断言入口，便于挂日志和截图。
- **问：软断言怎么实现？有什么坑？**
  答：用一个 fixture 提供 `_check(cond, msg)`，把失败消息收集到列表，`yield` 之后统一 `raise`。坑是忘了在 yield 后抛出会导致用例误报通过，以及不能把业务真异常也吞进去。
- **追问：pytest 的 assert 重写对封装断言有影响吗？**
  答：有影响。重写只作用于测试模块顶层的 assert，封装在函数内部的 assert 不被重写，失败信息会退化。所以封装断言时不能依赖重写，要自己把差异信息写进异常。
