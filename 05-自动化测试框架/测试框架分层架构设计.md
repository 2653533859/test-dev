# 测试框架分层架构设计

![[assets/framework-layers.svg]]
*图示：依赖只能自上而下——用例层 → 业务层 → 接口/页面层 → 核心层，配置层与数据层横向支撑，utils 工具层不依赖任何上层；conftest.py 是唯一被允许「往上看」的横切入口。*

> 框架设计能力是测开和手工测试的分界线。分层的本质不是「多建几个目录」，而是**把一次需求变更的改动范围限制在一层之内**。

## 概念

### 为什么要分层

不分层时，一条用例里可能同时出现：拼 URL、建 session、调接口、解析响应、写断言、读配置、打日志。后果是：

- 接口路径变了 → 几百条用例全要改；
- 换个环境跑 → 每条用例改 host；
- 新人加用例 → 得先懂请求封装、断言、配置全部细节。

分层后，**每一层只认识它的下一层**，依赖方向严格单向：

| 层 | 职责 | 允许 import |
|----|------|------------|
| ① 用例层 testcases/ | 给数据 → 调业务 → 断言 | 业务层、数据层 |
| ② 业务层 flows/ | 编排业务动作（下单=登录+加购+结算） | 接口/页面层、core |
| ③ 接口层 api/ · 页面层 pages/ | 一个接口/页面一个类，一次交互一方法 | core、config |
| ④ 核心层 core/ | 请求封装（重试/鉴权）、driver 工厂、断言封装 | utils、config |
| ⑤ 配置层 config/ | 多环境 yaml、`--env` 切换 | utils |
| ⑥ 数据层 data/ | yaml/excel 用例数据、造数工具 | utils |
| ⑦ 工具层 utils/ | 日志、加解密、DB/Redis 客户端 | 无（最底层） |

### conftest 是横切，不是某一层

`conftest.py` 是唯一被允许「往上看」的地方：它挂 `--env` 命令行参数、提供 session 级登录态 fixture、挂失败截图 hook、注册自定义 marker。其它层之间严禁反向依赖，否则就成环形引用，`utils` 里一旦 `import api` 迟早炸。

## 用法

### 目录骨架

```text
project/
├── conftest.py            # 横切：env、session fixture、hook
├── testcases/
│   └── test_order.py     # 只写数据-业务-断言
├── flows/
│   └── order_flow.py     # 下单业务编排
├── api/
│   └── order_api.py      # 订单接口封装
├── core/
│   ├── http.py           # 请求封装（重试/鉴权/日志）
│   └── assert_util.py    # 断言封装
├── config/
│   └── settings.py       # 多环境加载
├── data/
│   └── order_cases.yaml  # 数据驱动
└── utils/
    └── logger.py
```

### 用例层长什么样（不该出现 requests）

```python
# testcases/test_order.py —— 不 import requests，不碰 driver
from flows.order_flow import create_and_cancel
from data.order_cases import load_cases


def test_cancel_order():
    order = create_and_cancel(sku_id="SKU_001")
    assert order.status == "CANCELLED"
```

用例层只回答「给什么数据、调哪个业务、断言什么」，接口细节下沉到 `api/`，请求细节下沉到 `core/http.py`。

## 踩坑

1. **反向依赖环形引用**：`utils/logger.py` 里为了打印请求 URL 去 `import api`，而 `api` 又依赖 `core` → `core` 依赖 `utils`，启动即循环 import 报错。铁律：utils 不依赖任何业务层。
2. **业务层泄漏到用例层**：用例里直接调 `api.order.create()` 并手写 `assert resp["code"]==0`，等于把业务层架空，接口一变用例全改。业务动作应收口到 `flows/`。
3. **配置硬编码在用例里**：`BASE_URL = "https://test.xxx.com"` 写死，换环境只能全局替换。配置必须进 `config/`，靠 `--env` 切换（见 [[多环境配置与环境隔离]]）。
4. **公共 fixture 放错层**：session 级登录态 fixture 放到了某个子目录 conftest，导致只有该目录用例能登录。全局共享的 session fixture 应放根 conftest 或专门 `fixtures/` 目录。
5. **core 里混了断言逻辑导致重写失效**：自写 `my_assert()` 内部 `assert`，pytest 的 assert 重写只重写测试模块里的顶层 `assert`，封装函数内部的失败信息会丢。断言封装要注意保留上下文（见 [[测试框架日志与断言封装]]）。
6. **分层过细反而难维护**：7 层不是强制，小项目 3~4 层足够。判断标准不是层数，而是「一次需求变更改几处」——改一处能生效，分层就对了。
7. **数据层和用例层循环**：`data/` 为了读配置去 import `config`，而 `config` 又读 `data` 默认值，形成环。数据层应只做纯数据加载，环境差异交给 config。

## 面试怎么答

- **问：你框架分了几层，每层职责是什么？**
  答：一般 4~5 层——用例层（只写数据-业务-断言）、业务/接口层（接口封装与业务编排）、核心层（请求/驱动/断言封装）、配置层（多环境）、工具层（日志/DB 等最底层）。强调依赖单向、下层不认识上层，conftest 做横切。
- **问：怎么判断分层合不合理？**
  答：看「一次需求变更的改动范围」。接口路径变了只改 1 处、换环境跑不改代码、新人加用例只需懂用例层——满足这几点就是分对了；反之就层没分对或依赖反向了。
- **追问：为什么 utils 不能 import api？**
  答：会形成循环依赖，而且违反分层「下层不认识上层」的原则；utils 是最底层公共工具，必须零业务依赖，否则换项目都复用不了。
