# 测试用例设计方法：等价类与边界值

![[assets/equivalence-boundary.svg]]
*图示：等价类把无穷输入切成有限的「有效类 / 无效类」，边界值再在每条分界线上补「上点 / 离点 / 内点」——缺陷密度最高的地方正是这些分界线。*

> 用有限的用例覆盖无限的输入空间，并把用例数压到能在 CI 里跑完的量级。

## 概念

### 为什么需要「设计方法」

一个输入框接受 6–20 位用户名。穷举所有可能输入是 `(26+26+10)^20` 量级，宇宙热寂也跑不完。测试的本质约束是：

- **输入空间无限，测试预算有限**；
- 所以必须做**有理有据的抽样**，而不是「凭感觉多试几个」。

等价类与边界值就是这套抽样理论里最基础、投入产出比最高的两个方法。它们的地位类似排序算法里的快排——不是最花哨的，但 80% 场景够用。

### 等价类划分（Equivalence Partitioning）

**核心假设**：如果输入域中某一组数据，程序会用**同一条代码路径**处理它们，那么这组数据中任意一个能发现的缺陷，其它值也能发现；反之亦然。这一组数据就是一个**等价类**。

于是每个等价类只需要**取一个代表值**。

划分出两类：

- **有效等价类**：符合需求规格、程序应当正常处理的输入。用来验证「该work的work了」。
- **无效等价类**：不符合规格、程序应当拒绝的输入。用来验证「该拦的拦住了」。

一个容易被忽略的经验规则：

- **有效等价类可以在一条用例里合并多个**（多个字段各取有效值，一条用例覆盖）；
- **无效等价类必须一条用例只覆盖一个**。因为程序遇到第一个非法输入就会返回错误，后面的非法输入根本走不到校验代码，会产生**屏蔽效应**，导致你以为覆盖了其实没有。

### 边界值分析（Boundary Value Analysis）

**核心假设**：缺陷不是均匀分布在输入域里的，而是**扎堆在边界上**。原因非常朴素——边界处对应的是代码里的比较运算符：

```python
# 需求：长度 6-20 位
if len(username) > 6:        # bug：应该是 >= 6，长度正好 6 的合法用户被拒
    ...
if len(username) < 20:       # bug：应该是 <= 20，长度正好 20 的合法用户被拒
    ...
for i in range(len(items) - 1):   # bug：少处理最后一个元素
    ...
```

`>` 写成 `>=`、`<` 写成 `<=`、循环少一次多一次（off-by-one），是所有语言、所有程序员都会犯的错。边界值分析就是**专门针对这类错误设计的取值策略**。

标准取值（以区间 `[6, 20]` 为例）：

| 术语 | 含义 | 取值 |
|------|------|------|
| 上点 | 边界上的点 | 6、20 |
| 离点 | 边界外最近的点 | 5、21 |
| 内点 | 区间内的任意点 | 13 |

所以一条边界至少 3 个值，两条边界共 5 个值：`5, 6, 13, 20, 21`。相比在 6–20 里随机取 100 个值，这 5 个值的缺陷检出率高一个量级。

### 两者的关系：不是二选一，是叠加

标准工作流是：

1. **先划等价类**——决定「取值分几种类型」；
2. **再对每个类的边界补值**——决定「每种类型具体取哪几个数」。

单用等价类，会漏掉 off-by-one；单用边界值，会漏掉「非数字」「空值」「特殊字符」这类结构性的无效类。

## 用法

### 完整推导一个真实需求

需求（登录接口 `POST /api/login`）：

- `username`：6–20 位，仅字母数字，必填；
- `password`：8–16 位，必须含字母和数字，必填；
- 用户名不存在返回 `10001`，密码错误返回 `10002`，参数不合法返回 `400`。

**第一步：按字段列等价类表**

| 字段 | 类型 | 等价类描述 | 代表值 |
|------|------|-----------|--------|
| username | 有效 | 长度 6–20 且全字母数字 | `qa_user01`（注意下划线其实非法，见下） |
| username | 无效 | 长度 < 6 | `abc` |
| username | 无效 | 长度 > 20 | 21 个 `a` |
| username | 无效 | 含非字母数字 | `qa user`、`qa@user` |
| username | 无效 | 空 / 缺字段 | `""` / 不传 |
| password | 有效 | 8–16 位且含字母+数字 | `Passw0rd` |
| password | 无效 | 纯字母 | `Password` |
| password | 无效 | 纯数字 | `12345678` |
| password | 无效 | 长度不足 | `Pa0` |

> 上表第一行故意埋了个雷：`qa_user01` 含下划线，按规格是**无效**的。这类「自以为是有效值」的错误在评审时最常见，所以等价类表必须逐条对照规格文字，而不是凭感觉填。

**第二步：对长度类补边界值**

username 长度：`5`（离点）、`6`（上点）、`13`（内点）、`20`（上点）、`21`（离点）。

**第三步：转成 pytest 用例**

```python
import pytest
import requests

BASE = "https://api.example.com"


def login(username: str, password: str):
    return requests.post(f"{BASE}/api/login",
                         json={"username": username, "password": password},
                         timeout=10)


# 有效等价类 + 边界：可以合并多个有效值到一组数据里
@pytest.mark.parametrize("username", [
    pytest.param("a" * 6,  id="长度下边界6"),
    pytest.param("a" * 13, id="长度内点13"),
    pytest.param("a" * 20, id="长度上边界20"),
])
def test_login_username_length_valid(username, prepared_user):
    """长度合法的用户名应能通过参数校验（此处用已注册用户，断言登录成功）。"""
    resp = login(username, "Passw0rd")
    assert resp.status_code == 200
    assert resp.json()["code"] == 0


# 无效等价类：一条用例只违反一个规则，避免屏蔽效应
@pytest.mark.parametrize("username, reason", [
    pytest.param("a" * 5,  "长度离点5",   id="len-5"),
    pytest.param("a" * 21, "长度离点21",  id="len-21"),
    pytest.param("qa user", "含空格",     id="has-space"),
    pytest.param("qa@user", "含特殊字符", id="has-at"),
    pytest.param("",        "空字符串",   id="empty"),
])
def test_login_username_invalid(username, reason):
    resp = login(username, "Passw0rd")   # 密码保持合法，只让用户名违规
    assert resp.status_code == 400, f"{reason} 应被参数校验拦截"
```

注意 `test_login_username_invalid` 里**密码始终是合法值**——这就是「一次只违反一条规则」的落地方式。如果用户名和密码同时违规，接口先校验哪个字段是实现细节，用例就变得不可靠。

### 特殊输入的等价类清单（复用型 checklist）

除了业务规格给出的类，下面这组「结构性无效类」几乎对所有字符串输入都适用，可以固化成团队的检查表：

```text
空字符串 ""            前后空格 "  abc  "        纯空格 "   "
不传该字段              null / None              超长（1w 字符）
中文 / emoji            SQL 关键字 ' or 1=1--    HTML/JS <script>
大小写变体              全角字符１２３            换行符 \n \r\n
前导零 "007"            科学计数法 "1e3"         负号 "-1"
```

数值型输入再补一组：`0`、`-1`、最大值、最大值+1、小数、超长精度小数。

### 边界值的隐藏边界

面试里的加分点是能说出**规格没写、但真实存在的边界**：

- **数据类型边界**：`int32` 上限 2147483647，金额字段传 `2147483648` 会溢出；
- **存储边界**：MySQL `varchar(20)` 存中文时按字符还是字节，`utf8mb4` 下 emoji 占 4 字节；
- **分页边界**：`page=0`、`page=-1`、`page_size=0`、`page_size=10000`；
- **时间边界**：月末 31 号、闰年 2 月 29 日、跨年、时区切换、夏令时；
- **集合边界**：空列表、1 个元素、正好等于分页大小、超过一页。

这些是「等价类表画得再漂亮也覆盖不到」的部分，必须靠经验补。

## 踩坑

1. **无效等价类合并成一条用例，结果漏测**。曾经把「用户名太短 + 密码太短」写在一条用例里，断言 `status_code == 400` 通过了，上线后发现密码长度校验根本没写——因为服务端在用户名校验失败时就 `return` 了，密码校验代码从未执行。**规矩：无效值一次只放一个。**

2. **只测无效不测「无效的边界」**。测了 `len=3` 太短，没测 `len=5`。而 bug 恰好是 `if len < 5: reject`（写成 5 而非 6），`len=5` 时被错误放行。离点必须精确到边界外**第一个**值，不能随便取个远处的值。

3. **等价类划分依据用了实现而非规格**。看了后端代码发现它用正则 `^[a-z0-9]{6,20}$`，就按这个划分类，结果规格要求支持大写字母而代码没支持——用例和代码「一起错」，测了等于没测。**划分依据只能是需求规格。**

4. **边界值只测输入不测输出**。接口返回列表最多 100 条，测了请求参数 `page_size=100`，没验证响应里实际返回条数是否为 100（可能返回 99 或 101）。**输出域也有边界。**

5. **参数化数据里放了会互相污染的值**。等价类用例经常要用真实账号，如果多条用例共用同一个账号并修改其状态（比如连续输错密码触发锁定），后面的用例就会被前面的影响，表现为「单跑通过、全跑失败」。解法是每条用例通过 fixture 造独立账号。

6. **中文字符长度算错**。规格写「6–20 位」，前端按 `String.length` 校验（UTF-16 码元），后端按 `len()` 校验（Python 是字符数），数据库按字节数限制。同一个「20 位」在三处含义不同，emoji 用户名一测就崩。设计边界值时必须问清楚「位」的单位。

7. **正数边界忘了 0 和负数**。`price` 字段规格写「不超过 99999」，只测了 `99999/100000`，漏了 `0` 和 `-1`——结果下单金额可以传负数，账户余额不减反增。**只要是数值，`0` 和负数永远是必测的无效类。**

## 面试怎么答

**Q：说说等价类划分和边界值分析。**

A（30 秒骨架）：这两个是最基础的黑盒用例设计方法，解决的是「输入空间无限、测试预算有限」的矛盾。等价类划分是按「程序处理路径相同」把输入域切成若干组，每组取一个代表值，分有效等价类和无效等价类；边界值分析是在等价类的分界线上补取值，因为缺陷密集分布在边界——本质上是针对 `>` / `>=` 写反、off-by-one 这类错误。实际用的时候两者叠加：先划类确定「取几种」，再补边界确定「具体取哪几个」。取值规则是每条边界取上点、离点、内点。

**追问 1：为什么无效等价类要一条用例只覆盖一个？**

A：因为**屏蔽效应**。程序遇到第一个非法输入通常直接返回，后面的校验代码根本不执行。如果一条用例同时传了两个非法值，断言 400 会通过，但你并不知道第二个校验是否真的存在。我踩过这个坑：用户名和密码同时超短，用例一直绿，上线后发现密码长度校验压根没写。有效等价类反过来可以合并，因为它们都会被完整执行到。

**追问 2：边界值的「离点」怎么取？**

A：取边界外**最近**的那个值，而不是随便一个非法值。区间 `[6,20]` 的离点是 `5` 和 `21`，不能拿 `3` 和 `100` 代替。因为要检出的错误是「边界写偏了一位」，只有紧贴边界的值能暴露它。对开区间要注意方向：`(6,20)` 的上点是 6 和 20（此时它们本身是非法的），离点是 7 和 19。

**追问 3：除了规格写明的边界，还有哪些边界？**

A：数据类型边界（int32 溢出）、存储边界（varchar 字节数 vs 字符数）、分页边界（page=0、size=0、最后一页）、时间边界（月末、闰年、跨时区、夏令时）、集合边界（空集合、单元素、正好一页）。这些规格文档里通常不写，但真实缺陷很多。还有输出域边界——不只是输入要卡边界，返回的列表条数、金额精度同样要验。

**追问 4：这些方法怎么落到自动化里？**

A：等价类表的每一行天然就是 `@pytest.mark.parametrize` 的一条数据。我会把「代表值 + 期望结果 + 用例说明」三列写进 YAML 数据文件，用例代码只保留一份逻辑，通过 `ids` 把中文说明带进报告，失败时报告里直接显示「长度离点5 应被拦截」而不是 `test_login[param3]`。这样新增一个等价类只是加一行数据，不用改代码。
