# 测试用例设计方法：场景法与正交实验法

> 等价类解决「单字段取什么值」，场景法解决「多步骤怎么串」，正交实验法解决「多字段组合怎么砍」。

## 概念

### 单点覆盖不等于业务可用

等价类和边界值是**字段级**方法，它们能保证每个输入框都被验过，却回答不了两个更贵的问题：

1. 用户真实操作是一串动作（登录 → 搜索 → 加购 → 下单 → 支付 → 退款），**步骤之间的状态传递**对不对？
2. 系统有 5 个开关型配置，每个 3 种取值，**组合数 3⁵ = 243**，全测跑不完，测哪些？

前者用**场景法**，后者用**正交实验法**。

### 场景法（Scenario Testing）

场景法源自用例（Use Case）建模，核心概念只有两个：

- **基本流（basic flow）**：一切顺利时系统走的主路径。一个业务通常只有一条。
- **备选流（alternative flow）**：从基本流的某个节点岔出去的分支，包括异常、可选步骤、循环、回退。

设计方法：**画出流程图 → 基本流走 1 条 → 每条备选流各走 1 条（走完后可能回到基本流，也可能终止）**。

以「下单支付」为例：

```text
基本流:  选商品 → 加购物车 → 提交订单 → 选支付方式 → 支付成功 → 订单完成

备选流1: 提交订单时库存不足     → 提示并回到商品页
备选流2: 支付时余额不足         → 提示充值，订单保持待支付
备选流3: 支付超时未完成          → 订单自动取消，库存回滚
备选流4: 支付成功但回调丢失      → 定时任务补单，最终一致
备选流5: 用户主动取消订单        → 库存回滚，优惠券退回
备选流6: 使用优惠券支付          → 金额减免后走正常支付
```

场景法的价值在于：它检出的缺陷是**状态类缺陷**——库存扣了没回滚、优惠券用了没退、订单状态机走到了非法状态。这类 bug 单测和接口单点测试都发现不了，因为每一步单看都是对的。

### 正交实验法（Orthogonal Array Testing）

**问题**：搜索功能有 4 个筛选条件，每个 3 个取值，全组合 3⁴ = 81 条。测 81 条太贵，随便挑 5 条又心里没底。

**理论依据**：绝大多数由组合引起的缺陷是**两两交互（pairwise）**导致的，即「A 取某值 + B 取某值」就会触发，很少需要三个及以上因素同时特定取值。研究数据大致是：单因素缺陷约占 20–40%，两因素交互再覆盖 30–50%，两两组合合计能发现 70–90% 的组合缺陷。

**正交表**就是一张事先设计好的表，它保证：**任意两列中，所有可能的取值组合都至少出现一次**，同时行数远小于全组合。

正交表记法 `L_n(m^k)`：

- `n` = 实验次数（行数，即用例数）；
- `k` = 因素个数（列数，即字段数）；
- `m` = 每个因素的水平数（每个字段的取值个数）。

4 因素 3 水平用 `L9(3^4)`：**9 条用例覆盖 81 种组合的全部两两交互**，压缩比 9:1。

| 用例 | 类目 | 价格区间 | 排序 | 是否包邮 |
|------|------|---------|------|---------|
| 1 | 数码 | 0-100 | 综合 | 是 |
| 2 | 数码 | 100-500 | 销量 | 否 |
| 3 | 数码 | 500+ | 价格 | 不限 |
| 4 | 服饰 | 0-100 | 销量 | 不限 |
| 5 | 服饰 | 100-500 | 价格 | 是 |
| 6 | 服饰 | 500+ | 综合 | 否 |
| 7 | 食品 | 0-100 | 价格 | 否 |
| 8 | 食品 | 100-500 | 综合 | 不限 |
| 9 | 食品 | 500+ | 销量 | 是 |

竖着看任意两列，比如「类目 × 排序」：数码-综合、数码-销量、数码-价格、服饰-销量、服饰-价格、服饰-综合……9 种组合全在。这就是「正交」的含义。

### 三种方法的分工

| 方法 | 解决的问题 | 产物 | 适用阶段 |
|------|-----------|------|---------|
| 等价类 + 边界值 | 单字段取什么值 | 参数化数据行 | 接口/表单级 |
| 正交实验法 | 多字段组合怎么砍 | 组合矩阵 | 配置项、筛选器、多选表单 |
| 场景法 | 多步骤怎么串 | 端到端流程用例 | E2E、验收测试 |

实战顺序：先用等价类确定每个因素的**水平**（取值集合），再用正交表砍组合，最后用场景法把这些单点串成业务流。

## 用法

### 场景法落到 pytest

场景法用例天然是「有状态、多步骤」的，写法上要点是：**每一步的产物通过变量传给下一步，且失败点要能一眼看出在哪一步**。

```python
import allure
import pytest


@allure.epic("电商")
@allure.feature("下单支付")
class TestOrderPaymentScenario:
    """场景法：一个测试类 = 一个业务，一个测试方法 = 一条流。"""

    @allure.story("基本流：正常下单支付")
    def test_basic_flow(self, logged_in_client, sku_with_stock):
        with allure.step("1. 加入购物车"):
            cart = logged_in_client.add_to_cart(sku_with_stock.id, qty=1)
            assert cart["total_qty"] == 1

        with allure.step("2. 提交订单"):
            order = logged_in_client.create_order(cart["cart_id"])
            assert order["status"] == "WAIT_PAY"

        with allure.step("3. 支付"):
            pay = logged_in_client.pay(order["order_id"], channel="balance")
            assert pay["status"] == "SUCCESS"

        with allure.step("4. 校验订单终态与库存扣减"):
            detail = logged_in_client.get_order(order["order_id"])
            assert detail["status"] == "PAID"
            assert sku_with_stock.current_stock() == sku_with_stock.init_stock - 1

    @allure.story("备选流：支付超时订单自动取消，库存回滚")
    def test_alt_flow_pay_timeout(self, logged_in_client, sku_with_stock, clock):
        cart = logged_in_client.add_to_cart(sku_with_stock.id, qty=1)
        order = logged_in_client.create_order(cart["cart_id"])

        with allure.step("把系统时间推进到超时之后，触发定时任务"):
            clock.advance(minutes=31)
            logged_in_client.trigger_job("order_timeout_cancel")

        detail = logged_in_client.get_order(order["order_id"])
        assert detail["status"] == "CANCELLED"
        # 场景法的核心断言：状态回滚是否彻底
        assert sku_with_stock.current_stock() == sku_with_stock.init_stock
```

三个关键设计：

1. **`allure.step` 分步**——报告里能直接看出挂在第几步，不用读日志；
2. **每条备选流一个测试方法**，不要用 `if` 在一个方法里塞多条流；
3. **断言不止看最后一步的返回值，还要回查被影响的状态**（库存、优惠券、余额）——状态类缺陷全靠这一句。

### 正交表落到参数化

Python 生态里不用手抄正交表，用 `allpairspy`（两两组合，比严格正交表更灵活，允许各因素水平数不同）：

```python
# pip install allpairspy
from allpairspy import AllPairs
import pytest

FACTORS = [
    ["数码", "服饰", "食品"],           # 类目
    ["0-100", "100-500", "500+"],       # 价格区间
    ["综合", "销量", "价格"],           # 排序
    [True, False, None],                # 是否包邮（None=不限）
]

# 生成两两覆盖的组合，通常 9-12 条，远小于 81
PAIRS = [tuple(p) for p in AllPairs(FACTORS)]


@pytest.mark.parametrize(
    "category, price_range, sort_by, free_shipping",
    PAIRS,
    ids=[f"{c}-{p}-{s}-{f}" for c, p, s, f in PAIRS],
)
def test_search_filter_combination(api, category, price_range, sort_by, free_shipping):
    resp = api.search(category=category, price_range=price_range,
                      sort_by=sort_by, free_shipping=free_shipping)
    assert resp.status_code == 200
    items = resp.json()["items"]
    # 通用不变量断言：不管什么组合，结果都必须满足筛选条件
    for it in items:
        assert it["category"] == category
        if free_shipping is True:
            assert it["free_shipping"] is True
    # 排序正确性
    if sort_by == "价格":
        prices = [i["price"] for i in items]
        assert prices == sorted(prices)
```

跑一下看压缩效果：

```bash
pytest tests/test_search.py --collect-only -q | tail -3
# 收集到 11 条，而全组合是 81 条
```

**关键点**：组合用例的断言必须写成**不变量（invariant）**——「无论什么组合，结果都必须满足 X」，而不是给每个组合写死期望值。否则 11 条用例要维护 11 份期望，还不如全组合。

### 加约束条件

真实业务里某些组合是非法的（比如「食品」类目下没有「500+」价格区间），`allpairspy` 支持过滤：

```python
def is_valid(row):
    # row 是部分填充的组合，长度从 1 递增，需要判断长度
    if len(row) >= 2 and row[0] == "食品" and row[1] == "500+":
        return False
    return True


PAIRS = [tuple(p) for p in AllPairs(FACTORS, filter_func=is_valid)]
```

注意 `filter_func` 收到的 `row` 是**部分组合**（生成过程中逐列填充），所以必须先判断 `len(row)` 再取下标，否则 `IndexError`。这是这个库最容易踩的坑。

## 踩坑

1. **场景法写成了"一个方法跑完所有流"**。用 `if` 分支在一个测试方法里同时验基本流和三条备选流，结果第一条分支失败后面全不执行，报告里只显示 1 个失败，实际有 4 个场景没验证。**一条流一个测试方法**，代价是重复代码，用 fixture 抽公共前置解决。

2. **场景用例只断言最后一步**。下单支付流最后断言 `status == PAID` 通过了，但库存没扣、优惠券没核销。上线后出现「支付成功但库存对不上」的资损问题。**场景法的价值全在「状态是否彻底一致」的回查断言上**，只看接口返回值等于白做。

3. **备选流没验「回滚是否彻底」**。测了「支付超时订单取消」，只断言订单状态变 CANCELLED，没查库存是否回滚、优惠券是否退回、预扣的余额是否释放。这是场景法最高频的漏测点。

4. **正交表用错了「水平数不齐」的场景**。标准正交表要求各因素水平数相同（`L9(3^4)` 要求都是 3 水平）。实际业务里往往是「3 种类目 × 2 种排序 × 5 种价格」，硬套正交表要做「水平合并」很别扭。**直接用 pairwise 工具（allpairspy / PICT）**，它天然支持不等水平数。

5. **对组合用例写死期望值**。给 11 条组合各写一个期望的返回条数，需求一改数据全废。改成不变量断言（筛选条件必须被满足、排序必须有序）后，数据变化不影响用例。

6. **`allpairspy` 的 `filter_func` 忘了判断 `len(row)`**。生成过程中会用长度 1、2、3、4 的部分组合调用过滤函数，直接 `row[3]` 必然 `IndexError`，而且报错栈在库内部，第一次遇到会懵。

7. **认为 pairwise 能覆盖所有组合缺陷**。它只保证两两覆盖，三因素及以上交互触发的缺陷会漏。对**核心付费链路**上的关键组合，该穷举还是要穷举，或者用 `pytest.param` 手工补几条已知高风险组合。pairwise 是省钱手段，不是银弹。

8. **正交/pairwise 结果不稳定导致 nodeid 变化**。有些工具生成顺序不固定，导致每次运行 `test_x[数码-0-100-综合-True]` 这样的 id 集合变化，CI 上的历史趋势和失败重跑就对不上。**把生成结果固化成常量列表或 YAML 文件**，别在收集期动态生成。

## 面试怎么答

**Q：除了等价类和边界值，你还会用什么用例设计方法？**

A（30 秒骨架）：主要再用两个。一个是**场景法**，针对多步骤业务流，把系统行为分成基本流和备选流，基本流走一条、每条备选流各走一条，专门用来发现状态类缺陷——比如订单取消了库存没回滚。另一个是**正交实验法/pairwise**，针对多字段组合爆炸，理论依据是大部分组合缺陷由两两交互引起，所以只要保证任意两个因素的取值组合都出现过，就能用十几条用例覆盖几十上百种组合的绝大部分风险。实际项目里我用 `allpairspy` 生成组合再喂给 `parametrize`。

**追问 1：场景法怎么保证不漏场景？**

A：先画业务流程图或状态机图，把每个节点的分支都标出来，然后逐条枚举：正常路径 1 条，每个节点上的异常/可选/回退各 1 条。特别要覆盖的是**逆向操作**——取消、退款、退货、超时，这些路径涉及状态回滚，缺陷率最高。另外要覆盖**并发场景**，比如两个用户同时下单最后一件库存。我的检查方法是对着状态机看：每个状态转移箭头是否都有对应用例。

**追问 2：正交实验法和 pairwise 有什么区别？**

A：正交表是严格的数学构造，要求各因素水平数相同、行数是固定的（L9、L18 等），并且保证任意两列的组合出现**次数相同**（均衡性）。pairwise 只要求任意两列组合**至少出现一次**，不要求次数相同，因此支持不等水平数、支持约束条件、生成的用例数通常更少。软件测试里不需要正交表的均衡性（那是给方差分析用的），所以工程上基本都用 pairwise 工具，比如 allpairspy、微软的 PICT。

**追问 3：pairwise 覆盖不到的怎么办？**

A：pairwise 只保证两两覆盖，三因素以上的交互会漏。我的做法是分层处理：核心链路（下单、支付、鉴权）的高风险组合手工补进去，用 `pytest.param(..., id="已知风险组合")` 标出来；线上出过事故的组合固化成回归用例，永久保留。也就是「pairwise 打底 + 经验补刀」，而不是完全交给算法。

**追问 4：这些方法怎么和自动化结合？**

A：三种方法的产物都能映射成 pytest 结构——等价类/边界值 → `parametrize` 数据行；pairwise 组合 → 生成后固化成常量列表再 `parametrize`；场景法 → 一条流一个测试方法，用 `allure.step` 分步、用 fixture 管前置数据。组合用例的断言要写成不变量而不是硬编码期望；场景用例的断言要回查受影响的状态而不只看返回值。
