# 多环境配置与环境隔离

![[assets/env-config-resolution.svg]]
*图示：配置解析是「命令行 `--env` 优先级最高 → 覆盖项目默认 → 再回退到基础配置」；敏感信息走环境变量/密钥管理，不进仓库。*

> 一套脚本要在 test / staging / prod 跑，靠的不是改代码，而是**配置隔离 + 运行时切换**。环境隔离做不好，轻则跑错环境，重则把测试数据写进生产库。

## 概念

### 什么是环境隔离

环境隔离包含两层：

1. **配置隔离**：不同环境的 host、账号、数据库、开关分开存，切换不碰代码；
2. **数据隔离**：测试产生的脏数据不影响其他环境，尤其不能污染 prod。

核心机制是「**运行时选环境 → 加载对应配置 → 全局只有一个 settings 实例**」。

### 优先级：命令行 > 环境文件 > 默认值

`--env staging` 最高，其次是 `config/staging.yaml`，最后是 `config/base.yaml` 里的默认值。这样本地默认跑 test，CI 传 `--env` 决定跑哪。

## 用法

### 多环境 YAML

```yaml
# config/base.yaml
timeout: 10
retry: 2

# config/test.yaml
env: test
base_url: https://test.api.example.com
db:
  host: test-db.example.com

# config/prod.yaml
env: prod
base_url: https://api.example.com
db:
  host: ${DB_HOST}        # 敏感信息从环境变量取
```

### 加载器 + conftest 切换

```python
# config/settings.py
import os
import yaml


class Settings:
    def __init__(self, env: str):
        self.env = env
        base = yaml.safe_load(open("config/base.yaml", encoding="utf-8"))
        spec = yaml.safe_load(open(f"config/{env}.yaml", encoding="utf-8"))
        cfg = {**base, **spec}
        # 把 ${VAR} 替换成环境变量
        self.base_url = os.path.expandvars(cfg["base_url"])
        self.db = cfg["db"]


_settings = None


def get_settings(env="test"):
    global _settings
    if _settings is None:
        _settings = Settings(env)
    return _settings
```

```python
# conftest.py
def pytest_addoption(parser):
    parser.addoption("--env", action="store", default="test")


@pytest.fixture(scope="session")
def settings(request):
    return get_settings(request.config.getoption("--env"))
```

用例里只 `from config.settings import get_settings`，不关心当前是哪个环境。

## 踩坑

1. **配置硬编码进用例**：`BASE_URL = "https://test..."` 写死，换环境只能全局替换或改代码，CI 没法用同一份脚本跑多环境。所有环境相关值必须进 config。
2. **敏感信息入库**：prod 的账号密码、DB host 直接写进 yaml 提交到 Git，等于泄露凭证。正确做法是 yaml 里写 `${DB_HOST}` 这类占位符，运行时从环境变量或密钥管理（Vault/KMS）注入。
3. **settings 被并行跑串环境**：xdist 多个 worker 是独立进程，各自有 `_settings` 实例还好；但若用 `PYTEST_XDIST_WORKER` 共享内存或单例挂在全局可变对象上，可能发生 A worker 改成 prod、B worker 跟着变。环境实例应 per-process 隔离（见 [[pytest-xdist 并行执行]]）。
4. **默认环境选错导致跑生产**：本地忘了传 `--env`，默认竟然是 prod。默认值永远设成最安全的 test，prod 必须显式指定。
5. **不同环境数据结构不一致**：test 返回 `code`，prod 返回 `status`，用例断言写死一个字段名，换环境就挂。断言应基于「业务语义」而非「字段名」，或各环境在 config 里声明字段映射。
6. **yaml 占位符没展开**：写了 `${DB_HOST}` 但加载器没 `os.path.expandvars`/`os.environ` 替换，连地址都变成字面量。加载层必须做环境变量替换。
7. **测试数据污染生产**：用真实生产账号下单，产生真金白银的订单。环境隔离要配合「测试账号/影子库/数据清理 fixture」，测试数据必须可识别、可回滚。
8. **config 目录被收集成用例**：`testcases/` 之外放 `test_*.py` 导致 pytest 误收集。配置/工具模块命名避免 `test_` 前缀，或用 `python_files` 配置限定收集范围。

## 面试怎么答

- **问：一套脚本怎么在 test/prod 多环境跑？**
  答：配置外置到 `config/{env}.yaml`，conftest 加 `--env` 命令行参数，运行时加载对应配置生成全局唯一 settings 实例；敏感信息用 `${VAR}` 占位、从环境变量注入，不进仓库。
- **问：怎么保证不会误跑生产？**
  答：默认值设成最安全的 test 环境，prod 必须显式传 `--env`；同时配合测试账号和清理 fixture 保证即使跑 prod 也不会产生不可回滚的脏数据。
- **追问：xdist 并行下多环境配置会冲突吗？**
  答：每个 worker 是独立进程，各自持有自己的 settings 实例就不冲突；要避免的是把环境状态放在跨进程的共享可变对象上。
