# 分层测试模型与测试金字塔

![[assets/test-pyramid.svg]]
*图示：测试金字塔——越往上用例单价越高、执行越慢、越容易 flaky，所以数量必须越少；反模式「冰淇淋筒」把 UI 用例堆到最多，最终没人看红灯。*

> 决定「哪一层测什么、各层写多少」，这是自动化投入产出比的总开关。

## 概念

### 问题的起点：自动化为什么会烂尾

大多数团队的自动化死法是一样的：

1. 从 UI 层开始写，因为「看得见、像手工测试」；
2. 用例攒到几百条，一次回归跑 3 小时；
3. 每次跑挂 20 条，其中 15 条是元素没加载出来、环境抖动、测试数据被别人改了；
4. 排查失败比手工测一遍还慢；
5. 大家默认「红灯是正常的」，最后 CI 里把这个 job 设成 `allow_failure`；
6. 自动化名存实亡。

根因不是「Selenium 不稳定」，而是**把本该在下层验证的逻辑放到了上层**。金字塔模型就是对这件事的纠正。

### 测试金字塔的三层

Mike Cohn 提出的经典模型，从下往上：

| 层 | 验证对象 | 依赖 | 单条耗时 | 建议占比 |
|----|---------|------|---------|---------|
| 单元测试 | 单个函数/类的逻辑 | 无（外部依赖全 mock） | 毫秒级 | ~70% |
| 集成/接口测试 | 服务对外契约、组件协作 | 需服务和 DB | 百毫秒~秒级 | ~20% |
| UI / E2E 测试 | 端到端用户旅程 | 全套环境 + 浏览器 | 秒~分钟级 | ~10% |

比例数字不用死记（不同业务差别很大），要理解的是**为什么是这个形状**。三个支撑理由：

**1. 成本随层级指数上升。** 一条单元测试写完就能跑，一条 UI 用例要处理元素定位、等待、弹窗、登录态、测试数据准备，写的时间是 10 倍，维护成本是 20 倍。

**2. 稳定性随层级指数下降。** 假设每一层单点稳定性 99.9%，一条 UI 用例串联 30 个交互步骤，成功率就是 `0.999^30 ≈ 97%`。100 条用例每次跑就有 3 条随机失败——这就是 flaky 的数学来源，跟你代码写得好不好无关。

```python
# 直观感受 flaky 是怎么被「串联」放大的
step_reliability = 0.999
for steps in (1, 10, 30, 60):
    print(steps, round(step_reliability ** steps, 4))
# 1 0.999   10 0.9900   30 0.9704   60 0.9417
```

**3. 定位效率随层级下降。** 单元测试红了，直接指向某个函数；UI 用例红了，可能是前端 bug、后端 bug、环境问题、数据问题、脚本问题——先花 20 分钟判断「这是不是真 bug」。

### 反模式一：冰淇淋筒（Ice Cream Cone）

上宽下窄：UI 用例最多，接口用例少量，单元测试几乎没有。症状就是开头那段「烂尾流程」。

出现原因通常不是技术选择，而是组织结构：测试团队独立于开发团队，拿不到代码只能从界面测，于是所有验证都堆在 UI 层。

### 反模式二：纸杯蛋糕（Cupcake）

上下都宽、中间瘪：开发写了很多单测，测试写了很多 UI 用例，**中间的接口层没人负责**。结果是大量重复覆盖（同一条业务规则单测和 UI 各验一遍）加上关键缝隙漏测（服务间契约无人验证）。

接口层恰恰是投入产出比最高的一层：不依赖界面所以稳定，能覆盖绝大部分业务规则，执行速度接近单测。**测开的主战场应该在这一层。**

### 现代变体：奖杯模型与蜂巢模型

- **测试奖杯（Testing Trophy，Kent C. Dodds）**：底部是静态检查（TypeScript / ruff / mypy），中间最宽的是集成测试，上面是单测和少量 E2E。适用于前端和微服务——因为这类系统的 bug 更多出在「模块拼接」而不是「单个函数算错」。
- **蜂巢模型（Honeycomb，Spotify）**：微服务场景下，中间的「集成测试」最宽，两头细，理由同上。

这些变体和金字塔**不矛盾**，它们共享同一条原则：

> **能在更低成本、更快反馈的层次验证的逻辑，绝不要放到更高层去验。**

金字塔的形状只是这条原则在「传统单体应用」上的解。

### 各层职责边界怎么划

实践中最有用的一条判断规则是**「这个断言依赖什么」**：

- 只依赖纯函数逻辑（金额计算、状态机流转、参数校验规则）→ **单元测试**；
- 依赖服务的输入输出契约、DB 读写、跨服务调用 → **接口测试**；
- 依赖真实浏览器渲染、JS 交互、跨页面跳转、真实用户视角 → **UI 测试**。

反过来，UI 层**不该**做的事：

- 验证边界值（`price=-1` 应该报错）→ 接口层做，UI 只留一条代表性的；
- 验证所有错误码文案 → 接口层做；
- 验证排序/筛选的所有组合 → 接口层做，UI 只验「筛选后列表确实变了」。

UI 层**只留**：核心业务主流程（冒烟）、真实用户操作序列、纯前端交互（拖拽、富文本、跨页面状态保持）。

## 用法

### 用目录结构固化分层

```text
tests/
├── unit/                    # 无外部依赖，毫秒级，每次提交都跑
│   ├── test_price_calc.py
│   └── test_order_state_machine.py
├── api/                     # 需要服务 + DB，秒级，每次合并跑
│   ├── test_login_api.py
│   └── test_order_api.py
├── e2e/                     # 需要全套环境 + 浏览器，分钟级，每日跑
│   └── test_order_journey.py
└── conftest.py
```

### 用 marker 让分层可执行

```python
# pytest.ini 或 pyproject.toml 里先注册，避免 unknown mark 警告
# [pytest]
# markers =
#     unit: 单元测试，无外部依赖
#     api: 接口测试，需要服务与数据库
#     e2e: 端到端测试，需要浏览器
#     smoke: 冒烟用例，核心主流程

import pytest


@pytest.mark.unit
def test_discount_calc():
    assert calc_discount(100, "VIP") == 90


@pytest.mark.api
def test_create_order(api_client):
    resp = api_client.post("/orders", json={"sku": 1, "qty": 1})
    assert resp.status_code == 201


@pytest.mark.e2e
@pytest.mark.smoke
def test_order_journey(browser):
    ...
```

在 CI 里分阶段执行，让反馈按成本递进：

```yaml
# .github/workflows/ci.yml 片段
jobs:
  unit:
    steps:
      - run: pytest -m unit -q --maxfail=1        # 1 分钟内出结果
  api:
    needs: unit
    steps:
      - run: pytest -m api -n 4 --dist=loadfile   # 5 分钟
  e2e:
    needs: api
    steps:
      - run: pytest -m "e2e and smoke" -n 2       # 只跑冒烟，15 分钟
  nightly-e2e:
    # 定时任务里才跑全量 e2e
    steps:
      - run: pytest -m e2e -n 4
```

这套配置把金字塔从「口号」变成了「机制」：单测挂了就不浪费机器跑接口，接口挂了就不跑 E2E。

### 用数据量化你的金字塔

想说服团队调整比例，先把现状测出来：

```python
# conftest.py：统计各层用例数与耗时，跑完打印一张分布表
import collections
import pytest

_durations = collections.defaultdict(list)

LAYERS = ("unit", "api", "e2e")


def _layer_of(item):
    for m in LAYERS:
        if item.get_closest_marker(m):
            return m
    return "unmarked"


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when == "call":
        _durations[_layer_of(item)].append(report.duration)


def pytest_terminal_summary(terminalreporter):
    total_cnt = sum(len(v) for v in _durations.values()) or 1
    total_dur = sum(sum(v) for v in _durations.values()) or 1
    terminalreporter.write_sep("=", "分层分布")
    for layer, ds in sorted(_durations.items()):
        terminalreporter.write_line(
            f"{layer:<9} 用例 {len(ds):>4} 条 ({len(ds)/total_cnt:>5.1%})  "
            f"耗时 {sum(ds):>7.1f}s ({sum(ds)/total_dur:>5.1%})  "
            f"均值 {sum(ds)/len(ds):>5.2f}s"
        )
```

典型的「冰淇淋筒」输出长这样，一目了然：

```text
================================ 分层分布 =================================
api        用例   48 条 (14.9%)  耗时    62.3s (3.5%)  均值  1.30s
e2e        用例  260 条 (80.7%)  耗时  1704.5s (96.0%)  均值  6.56s
unit       用例   14 条 ( 4.3%)  耗时     8.4s (0.5%)  均值  0.60s
```

## 踩坑

1. **照搬 70/20/10 比例，忽略业务形态**。一个纯配置管理后台、逻辑几乎都在 CRUD，硬凑 70% 单测只能写出一堆测 getter/setter 的废用例。比例是结果不是目标，**真正的目标是「同一条逻辑只在最低可行层验一次」**。

2. **把「接口测试」写成「UI 测试的无头版」**。有的团队接口用例里串了 10 个接口模拟完整业务流，一挂就得看半天。接口层用例应当**尽量单接口 + 少量关键组合流**，长业务流留给 E2E 或专门的场景用例文件，并且明确标注。

3. **E2E 用例里做数据准备**。用 UI 点 20 步造出一个「已支付订单」再验退款，一半的执行时间和 90% 的失败概率都花在准备阶段。**准备走接口或直接写 DB，UI 只跑被验证的那几步**，这是 E2E 提速最有效的一招。

4. **单测大量 mock 导致「测了个寂寞」**。把被测函数所有依赖都 mock 掉，最后断言的其实是 mock 的行为。判断标准：**如果实现改成另一种等价写法，测试就挂了，那这条单测测的是实现不是行为**。

5. **没有分层 marker，CI 只能全量跑**。所有用例混在一个目录、没有 marker，导致「改一行代码要等 2 小时全量回归」。分层的第一步不是重写用例，而是**先把现有用例打上 marker**，成本极低、收益立竿见影。

6. **UI 用例挂了直接加重试掩盖**。`--reruns 3` 让红灯变绿灯，但 flaky 的根因（隐式等待不足、测试数据竞争）被埋起来，最终演变成「重试 3 次还是挂」。重试是**给不可控外部因素兜底**的，不是给脚本缺陷兜底的，且必须统计重试率并治理。

7. **误以为分层是「用例的物理位置」**。有人把 UI 用例挪到 `tests/api/` 目录就宣称完成分层。分层的实质是**验证对象和依赖范围**，不是目录名。判断依据永远是「这条用例断言的是什么、依赖了什么」。

## 面试怎么答

**Q：说说你对测试金字塔的理解。**

A（30 秒骨架）：金字塔描述的是各层自动化用例的合理数量关系——单元测试最多、接口测试居中、UI/E2E 最少。之所以是这个形状，是因为越往上单条用例的编写成本、执行耗时、维护成本、flaky 概率都指数上升，而定位效率下降。核心原则只有一句：**能在更低层用更低成本验证的逻辑，绝不放到高层去验**。对应的反模式是「冰淇淋筒」——UI 用例堆最多，一次回归几小时、天天红灯，最后没人看。

**追问 1：那具体每层测什么？**

A：我用「断言依赖什么」来划边界。只依赖纯逻辑（金额计算、状态流转、参数校验规则）放单测；依赖服务契约、DB、跨服务调用放接口层；依赖真实浏览器渲染和用户操作序列才放 UI 层。反过来说，边界值、错误码文案、筛选排序的所有组合，都不该在 UI 层验，UI 只留核心主流程和纯前端交互。接口层是测开的主战场——不依赖界面所以稳定，又能覆盖绝大部分业务规则。

**追问 2：微服务下金字塔还适用吗？**

A：形状会变。微服务的缺陷更多出在「服务拼接」而不是单函数，所以业界有 Spotify 的蜂巢模型和 Kent Dodds 的测试奖杯模型，都是**中间的集成测试最宽**。但底层原则没变，还是「在最低可行层验证」。另外微服务要补一块金字塔没画的东西——**契约测试**（Pact 之类），它用极低成本替代了大量跨服务集成用例，避免「联调环境永远有一个服务是坏的」。

**追问 3：现有项目是冰淇淋筒，你怎么改？**

A：分四步，且不停机改造。第一步先量化：给所有用例打分层 marker，用 `pytest_runtest_makereport` 统计各层用例数和耗时占比，拿数据说话。第二步分级 CI：单测→接口→冒烟 E2E 分阶段跑，先把「改一行等两小时」解决掉。第三步做下沉：挑失败率最高的 20 条 UI 用例，逐条问「这条验的规则能不能在接口层验」，能就下沉、UI 只留一条代表。第四步治理 flaky：统计重试率，重试率高的用例单独拉清单修根因，而不是靠 `--reruns` 掩盖。

**追问 4：单元测试是开发写还是测试写？**

A：应该是开发写，测开负责建标准和把关——覆盖率门禁、review 单测质量、提供测试工具库。原因很实际：单测要求了解内部实现，测试同学写不仅效率低，而且容易写成「测实现细节」的脆弱用例。测开更该把精力放在接口层和框架/效能建设上。如果团队现实是开发不写单测，那也别硬推，先把接口层做扎实，收益更快。
