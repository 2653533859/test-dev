# 管道与重定向

> 搞懂 fd 0/1/2 三条通道，才能把命令串成流水线、把日志和报错分别落到该去的地方，而不是每次都靠试。

![[assets/pipe-redirect.svg]]
*图示：进程自带 stdin/stdout/stderr 三个描述符；管道只把前一个进程的 fd1 接到后一个的 fd0，stderr 不进管道；`2>&1` 复制的是「写这句时」fd1 的指向，所以必须写在 `> file` 之后。*

## 概念

### 三个标准文件描述符

任何进程启动时，内核都会为它准备三个已打开的文件描述符（file descriptor，简称 fd）：

| fd | 名字 | 默认指向 | 用途 |
|----|------|----------|------|
| 0 | stdin | 终端键盘 | 读输入 |
| 1 | stdout | 终端屏幕 | 正常输出 |
| 2 | stderr | 终端屏幕 | 错误与诊断信息 |

**为什么要把 stdout 和 stderr 分成两条**？因为它们的消费者不同。stdout 是「程序的产出物」，要能被下一个程序继续加工；stderr 是「给人看的诊断」，即使 stdout 被重定向进文件或管道，报错也应该仍然能出现在屏幕上。这也是 stderr **默认不带缓冲**（立即输出）而 stdout 在非终端时是块缓冲的原因。

在 shell 里可以直接看到这三个：

```bash
ls -l /proc/self/fd
# 0 -> /dev/pts/0
# 1 -> /dev/pts/0
# 2 -> /dev/pts/0
```

### 重定向：换掉某个 fd 的指向

重定向是 **shell 在 fork 出子进程后、exec 目标程序之前**做的事：它调用 `open()` 打开目标文件，再用 `dup2()` 把这个新描述符复制到 fd 1（或 0、2）上。所以**程序本身完全不知道自己在被重定向**，它只管往 fd 1 写。

这就解释了两件事：一是任何程序都能被重定向，不需要程序做适配；二是重定向语法是**从左到右依次执行**的，顺序会改变结果。

### 管道：用内核缓冲区把两个进程接起来

`cmd1 | cmd2` 的执行过程：

1. shell 调用 `pipe()` 创建一对相连的 fd（读端、写端），这是一块内核内存缓冲区（Linux 上默认 64KB）。
2. fork 两个子进程，把 cmd1 的 fd1 换成管道写端，把 cmd2 的 fd0 换成管道读端。
3. **两个进程同时启动、并发运行**。cmd1 写满缓冲区就阻塞，等 cmd2 消费；cmd2 读空了就阻塞，等 cmd1 生产。

关键推论：

- 管道是**流式**的，不是「cmd1 全跑完再交给 cmd2」。所以 `tail -f app.log | grep ERROR` 能实时出结果，`cat 10G.log | head -3` 也能秒回（head 读够就退出，cat 收到 SIGPIPE 结束）。
- **只有 fd1 进管道，fd2 不进**。`make 2>&1 | tee build.log` 里的 `2>&1` 就是为了把错误也塞进管道。
- 管道两端的进程各自有独立的内存空间，**管道右侧的变量赋值在子 shell 里，出了管道就丢**（下面踩坑会讲）。

## 用法

### 输出重定向

```bash
cmd > out.log            # stdout 覆盖写入（文件会先被清空）
cmd >> out.log           # stdout 追加
cmd 2> err.log           # stderr 单独落一个文件
cmd > out.log 2> err.log # 分开落两个文件
cmd > all.log 2>&1       # 合并到一个文件（顺序不能反）
cmd &> all.log           # bash 简写，等价于上一行
cmd &>> all.log          # 追加版
cmd > /dev/null 2>&1     # 全部丢弃，只关心退出码时用
cmd 2>/dev/null          # 只屏蔽报错（find 扫全盘时常用）
```

`2>&1` 读作「把 fd2 也指向 fd1 当前指向的地方」。**它是复制指向，不是建立联动**，所以：

```bash
cmd > out.log 2>&1     # ✅ 先让 1 指向文件，2 再复制 → 都进文件
cmd 2>&1 > out.log     # ❌ 2 先复制了此刻的 1（屏幕），1 之后才改 → 错误还在屏幕
```

反过来利用这个特性，可以**只把错误送进管道**：

```bash
./deploy.sh 2>&1 >/dev/null | mail -s "部署报错" ops@example.com
```

### 输入重定向与 here-doc

```bash
mysql -uroot -p test < init.sql        # 从文件读 stdin
wc -l < access.log                     # 注意：输出里不含文件名，和 wc -l access.log 不同

# here-document：把一段内联文本喂给命令
mysql -uroot -p <<'EOF'
USE testdb;
SELECT COUNT(*) FROM orders WHERE status = 'PAID';
EOF

# here-string：单行输入
grep -o '[0-9]\+' <<< "订单号 20260731 金额 998"
```

`<<'EOF'`（引号）与 `<<EOF`（无引号）的区别很重要：**加引号则内容原样传递，不做变量替换**；不加引号会展开 `$VAR`、`` `cmd` ``。写 SQL、写包含 `$` 的配置模板时必须加引号。`<<-EOF` 则允许用 Tab 缩进结束符，脚本里更好看。

### 管道与常用配套命令

```bash
# 统计访问量前 10 的 IP —— Linux 面试的「Hello World」
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

# tee：分流，既落盘又继续往下传
./run_tests.sh 2>&1 | tee test.log | grep -E "FAILED|ERROR"
./deploy.sh | sudo tee -a /var/log/deploy.log     # tee 常用来解决 sudo 重定向问题

# xargs：把 stdin 转成命令行参数（很多命令不读 stdin，只认参数）
find . -name "*.pyc" -print0 | xargs -0 rm -f
cat hosts.txt | xargs -I{} -P4 ssh {} 'uptime'    # -P4 四路并发

# 常见的「过滤器」
sort -u        # 排序去重
uniq -c        # 统计相邻重复次数（必须先 sort）
wc -l          # 数行数
cut -d: -f1    # 按分隔符取列
tr -s ' '      # 压缩连续空格
column -t      # 对齐成表格
```

### 进程替换：把命令输出当成文件

```bash
diff <(sort a.txt) <(sort b.txt)              # 比较两个命令的输出
diff <(ssh host1 'md5sum /app/app.jar') <(ssh host2 'md5sum /app/app.jar')

# 解决「管道右侧变量丢失」的经典写法
while read -r line; do
    count=$((count + 1))
done < <(grep ERROR app.log)
echo "$count"      # 这里 count 有值
```

`<(cmd)` 会创建一个 `/dev/fd/63` 之类的临时 fd，让命令输出表现得像一个文件，是对付「只接受文件参数」的命令的利器。

### 常用组合速查

```bash
cmd > file 2>&1              # 合并落盘
cmd 2>&1 | tee -a log        # 合并 + 屏幕 + 追加落盘
nohup cmd > app.log 2>&1 &   # 后台运行且捕获全部输出
cmd < /dev/null              # 断开 stdin，防止后台任务因读输入而挂起
: > file                     # 清空文件但不改 inode（正在被写的日志用这招）
exec 3>&1                    # 把 fd1 备份到 fd3，之后可 exec 1>&3 还原
```

## 踩坑

1. **`2>&1` 写在 `> file` 前面，报错丢了**。CI 里最常见的「日志里啥都没有，任务却失败了」。记住口诀：**先定向 1，再把 2 复制过去**。

2. **`cmd > file` 会先清空文件，即使 cmd 失败**。shell 在启动命令**之前**就 `open(..., O_TRUNC)` 了。所以 `sort file > file` 会得到空文件——因为 file 在 sort 读之前已被清空。原地处理要用临时文件或 `sponge`（moreutils）：

   ```bash
   sort file > file.tmp && mv file.tmp file
   ```

3. **`sudo cmd > /root/x.log` 报 Permission denied**。重定向是**当前 shell**（普通用户）做的，`sudo` 只提升了 cmd 的权限。解法：`cmd | sudo tee /root/x.log > /dev/null`，或 `sudo bash -c 'cmd > /root/x.log'`。

4. **管道右侧的变量赋值消失**。

   ```bash
   count=0
   grep ERROR app.log | while read -r line; do count=$((count+1)); done
   echo "$count"      # 还是 0！
   ```

   因为管道每一段都在**子 shell** 里跑，子 shell 的变量不会回传父进程。解法：用进程替换 `done < <(grep ...)`，或开启 `shopt -s lastpipe`（需非交互模式），或干脆改用 `count=$(grep -c ERROR app.log)`。

5. **管道的退出码默认取最后一个命令**。`grep ERROR app.log | wc -l` 即使 grep 没匹配到（退出码 1），整条命令仍返回 0。CI 里要严格判断得加 `set -o pipefail`，或查 `${PIPESTATUS[@]}` 数组。

6. **`grep` 在管道里不实时输出**。程序检测到 stdout 不是终端时会切换成**块缓冲**（4KB 满了才吐），所以 `tail -f app.log | grep ERROR | tee out.log` 会一卡一卡的。解法：`grep --line-buffered`，或用 `stdbuf -oL cmd`，或 `unbuffer cmd`（expect 包）。

7. **`cat file | grep xxx` —— 无用的 cat（UUOC）**。多起一个进程、多一次拷贝，直接 `grep xxx file` 即可。不过在 `cat a b c | ...` 合并多文件、或想强调数据流方向时是可以接受的。

8. **`head` 提前退出导致上游报 `Broken pipe`**。`yes | head -3` 时 `yes` 会收到 SIGPIPE 而死掉，这是**正常机制**不是故障；但如果上游是自己写的 Python 脚本，可能会抛 `BrokenPipeError` 刷一屏 traceback，需要在脚本里处理 SIGPIPE。

9. **`>>` 与多进程并发追加**。多个进程同时 `>>` 同一个文件，小于 `PIPE_BUF`（4KB）的写入是原子的，超过就可能交错。多进程写日志应该各写各的文件，或走 syslog。

10. **`tee` 之后管道断了**。`cmd | tee log | grep X`，如果 grep 提前退出，tee 会收到 SIGPIPE 终止，log 可能不完整。要保完整日志就把 tee 放最后，或用 `tee log > >(grep X)`。

## 面试怎么答

**Q：`>` 和 `>>` 的区别？`2>&1` 是什么意思？**

A：`>` 是覆盖，shell 以 `O_TRUNC` 打开文件，会先清空；`>>` 是追加，以 `O_APPEND` 打开。`2>&1` 表示把文件描述符 2（stderr）指向当前 fd 1 指向的位置，实现错误与正常输出合流。关键是**顺序**：`> file 2>&1` 才对，因为 `2>&1` 复制的是执行到这一句时 fd1 的指向；写成 `2>&1 > file`，fd2 复制的还是屏幕，之后 fd1 才改到文件，结果错误信息没进日志。

**Q：管道是怎么工作的？`cat big.log | grep x` 会不会先把整个文件读进内存？**

A：`|` 让 shell 创建一个内核管道缓冲区（默认 64KB），把左边进程的 stdout 和右边进程的 stdin 分别接到管道两端，两个进程**并发执行**。数据是流式传递的：写满缓冲区就阻塞等消费，读空就阻塞等生产。所以不会把整个文件读进内存，`cat 10G.log | head -3` 也能立刻返回——head 拿够三行就退出，cat 因为写端没人读收到 SIGPIPE 而结束。

**Q：`ls | grep x` 里如果 ls 报错，错误信息会被 grep 过滤吗？**

A：不会。管道只连接 stdout（fd1），stderr（fd2）依然直连终端。想让错误也进管道要写 `ls 2>&1 | grep x`，bash 还可以简写成 `ls |& grep x`。这个设计是有意为之——即使输出被重定向走了，诊断信息也要能被人看到。

**Q：为什么 `while read` 循环里改的变量，出了循环就变回去了？**

A：因为管道的每一段都在**子 shell**（fork 出来的独立进程）里执行，子进程改的是自己那份内存里的变量，父 shell 看不到。解决办法有三个：一是用进程替换 `while read ...; done < <(cmd)`，让循环留在当前 shell；二是 bash 4.2+ 开 `shopt -s lastpipe`（且要关掉 job control）；三是避开循环，直接用 `$(cmd)` 命令替换或 `grep -c` 之类的命令拿结果。

**Q：CI 脚本里 `cmd1 | cmd2` 前面失败了，为什么流水线还是绿的？**

A：管道的退出码默认只取最后一个命令的。要让任意一段失败都能感知，脚本开头加 `set -euo pipefail`，`pipefail` 会让整条管道返回最后一个非零退出码；需要精确判断哪一段失败时，读 `${PIPESTATUS[@]}` 数组。
