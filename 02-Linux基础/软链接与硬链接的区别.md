# 软链接与硬链接的区别

> 用 `ln` / `ln -s` 做发版目录切换与文件复用，理解 inode 机制，看懂「删了文件磁盘却没释放」的本质。

![[assets/hardlink-symlink.svg]]
*图示：硬链接是「多个目录项 → 同一 inode」，删掉一个名字只减 nlink；软链接是「独立 inode，内容是一段目标路径字符串」，目标没了就变断链。*

## 概念

### 先讲清楚 inode

在 Linux 文件系统（ext4、xfs）里，一个文件被拆成三部分存储：

1. **目录项（dentry）**：存在于父目录中，保存「文件名 → inode 号」的映射。
2. **inode**：一个固定大小的结构体，保存文件的**全部元信息**——类型、权限、属主属组、大小、三个时间戳、链接数 `nlink`，以及**指向数据块的指针**。inode 里**唯独没有文件名**。
3. **数据块（data block）**：真正的内容。

推论：**文件名只是数据的一个「引用」**。这一个认知能解释后面所有现象。

```bash
ls -li app.log
# 131074 -rw-r--r-- 1 root root 1024 Jul 31 10:20 app.log
#  ↑ inode 号，同一文件系统内唯一
```

### 硬链接：给同一个 inode 加一个名字

```bash
ln source.txt hard.txt
```

内核只做一件事：在目录里加一条「hard.txt → inode 131074」的记录，并把该 inode 的 `nlink` 从 1 加到 2。**没有复制任何数据**，两个名字完全平等——没有「谁是原始文件」的说法。

删除文件的系统调用其实叫 `unlink()`，语义就是「删掉一个目录项、`nlink -= 1`」。只有当 `nlink == 0` **且没有任何进程持有该文件的打开句柄**时，内核才回收数据块。

硬链接的两条硬性限制，都源于实现：

- **不能跨文件系统**。inode 号只在单个文件系统内唯一，跨文件系统时目录项没法指向另一个文件系统的 inode。
- **普通用户不能给目录建硬链接**。目录的硬链接会在目录树里制造环，导致 `find`、`rm -r` 之类的遍历陷入无限循环，而且没有简单办法检测。（`.` 和 `..` 是内核自己维护的特例。）

### 软链接（符号链接）：一个存着路径字符串的特殊文件

```bash
ln -s /data/release-20260731 /app
```

软链接是**独立的文件**，有自己的 inode、自己的权限位（永远显示 `lrwxrwxrwx`，实际鉴权看目标），它的「内容」就是一串目标路径文本。访问 `/app/conf.yaml` 时，内核在路径解析阶段发现 `/app` 是软链接，就把它替换成 `/data/release-20260731` 继续解析。

因为存的是路径而不是 inode 号，所以软链接**可以跨文件系统、可以指向目录、可以指向根本不存在的路径**（断链）。

### 对照表

| 维度 | 硬链接 `ln` | 软链接 `ln -s` |
|------|-------------|----------------|
| 本质 | 同一 inode 的另一个目录项 | 独立 inode，内容是目标路径字符串 |
| 独立 inode | 否（inode 号相同） | 是（inode 号不同） |
| 跨文件系统 | 不可以 | 可以 |
| 指向目录 | 普通用户不可以 | 可以 |
| 目标删除后 | 仍可访问（数据还在） | 断链，访问报 `No such file or directory` |
| 占用空间 | 只多一条目录项 | 一个 inode + 路径字符串 |
| `ls -l` 显示 | 与普通文件无异，`nlink` > 1 | `lrwxrwxrwx ... link -> /target` |
| 典型用途 | 备份去重、日志切割保留句柄 | 发版目录切换、命令多版本管理 |

## 用法

### 建、看、删

```bash
# 硬链接
ln source.txt hard.txt
ls -li source.txt hard.txt        # inode 号相同，nlink 都是 2

# 软链接（顺序：ln -s 目标 链接名，记成「从哪来 到哪去」）
ln -s /data/release-20260731 /app
ls -l /app                        # lrwxrwxrwx 1 root root 24 Jul 31 10:20 /app -> /data/release-20260731

# 查看软链接指向
readlink /app                     # /data/release-20260731
readlink -f /app/conf.yaml        # 递归解析所有软链接得到最终真实路径

# 删除软链接（注意结尾不要带斜杠！）
rm /app                           # 正确：只删链接
rm -rf /app/                      # 危险：带斜杠会被当成目录，删的是目标目录里的内容
unlink /app                       # 更安全，unlink 不接受目录
```

### 蓝绿发版：软链接的经典用法

```bash
#!/usr/bin/env bash
set -euo pipefail

NEW_DIR="/data/release-$(date +%Y%m%d%H%M)"
mkdir -p "${NEW_DIR}"
tar -xzf app.tar.gz -C "${NEW_DIR}"

# 原子切换：ln -sfn 先建临时链接再 mv 覆盖，避免出现「链接暂时不存在」的空窗
ln -sfn "${NEW_DIR}" /app.tmp
mv -Tf /app.tmp /app

systemctl restart app
```

要点：

- `-f` 强制覆盖已有链接，`-n` 把已存在的软链接目录当普通文件处理（**不加 `-n` 会把新链接建到 `/app/` 目录里面去**，变成 `/app/release-xxx`，这是最经典的坑）。
- `mv -T` 保证覆盖是原子的（`rename` 系统调用），回滚时只需把链接指回旧目录，秒级完成。

### 日志切割：硬链接保留句柄

```bash
cd /var/log/app
ln access.log access.log.$(date +%F)   # 硬链接：同一份数据，两个名字
: > access.log                          # 清空原文件（截断，不改 inode，进程句柄仍有效）
```

用 `ln` + 截断而不是 `mv`，好处是**文件的 inode 从未变过**，正在写日志的进程句柄一直指向同一 inode，不需要发信号让它重开文件。（`mv` 之后进程会继续往改名后的文件写，新文件一直是空的。）

### 判断一个文件有没有硬链接

```bash
ls -l app.log                 # 第二列就是 nlink，大于 1 说明有硬链接
find / -xdev -inum 131074     # 按 inode 号反查所有名字
stat app.log                  # 完整元信息：inode、Links、三个时间戳
```

## 踩坑

1. **`ln -s` 用相对路径，移动后失效**。`ln -s ../data/x.conf link` 存的就是字面量 `../data/x.conf`，一旦 `link` 被移到别的目录，解析基准变了就断链。**创建软链接一律用绝对路径**，除非你明确要「跟着一起搬」的语义。

2. **`ln -sf` 少了 `-n`，链接建进目录里**。已有 `/app -> /data/v1`，执行 `ln -sf /data/v2 /app`，因为 `/app` 解析后是个目录，结果生成了 `/data/v1/v2` 这个链接，`/app` 依然指向 v1。发版脚本必须用 `ln -sfn`。

3. **`rm -rf /app/` 删的是目标目录的内容**。软链接名字后加斜杠会被当作目录访问，`rm -rf` 会进去清空真实数据。删链接**永远不带尾斜杠**，或者用 `unlink`。

4. **`cp` 软链接默认解引用**。`cp /app/conf.yaml /bak/` 复制的是目标文件内容而不是链接本身；要保留链接语义用 `cp -a` 或 `cp -P`（`--no-dereference`）。同理 `tar` 默认保留链接，而 `tar -h` 会解引用。

5. **`du` 统计硬链接只算一次，`ls` 每个名字都显示完整大小**。一个 1G 文件建了 3 个硬链接，`ls -lh` 三处都显示 1G，但 `du -sh` 只算 1G。看似「文件加起来比磁盘还大」，实际没有重复占用。

6. **删了大文件磁盘空间没释放**。`rm` 只是 `nlink -= 1`，如果还有进程打开着这个文件，inode 不会被回收。用 `lsof | grep deleted` 找到进程，重启它或用 `: > /proc/<pid>/fd/<n>` 截断。详见 [[Linux 磁盘空间排查：df 与 du]]。

7. **跨文件系统建硬链接报 `Invalid cross-device link`**。`df` 确认两个路径的挂载点，跨设备只能用软链接。Docker 容器里挂载卷时特别容易撞上。

8. **软链接的权限位是摆设**。`lrwxrwxrwx` 永远是 777，实际能不能读写完全取决于目标文件的权限。对软链接 `chmod` 会作用到目标上（Linux 行为）。

9. **循环软链接**。`ln -s /a /b && ln -s /b /a` 会让路径解析报 `Too many levels of symbolic links`（内核限制通常是 40 层）。`find -L` 遇到循环链接可能会卡很久。

## 面试怎么答

**Q：软链接和硬链接的区别？**

A：从 inode 讲最清楚。硬链接是给同一个 inode 再加一条目录项，两个名字完全平等，`inode` 号相同、`nlink` 加一；删掉其中一个只是 `nlink` 减一，数据还在。因为 inode 号只在单个文件系统内有效，所以硬链接不能跨文件系统，也不允许对目录建（会在目录树里制造环导致遍历死循环）。

软链接是一个独立的小文件，有自己的 inode，内容是一段目标路径字符串，内核在路径解析时替换。所以它能跨文件系统、能指向目录、能指向不存在的路径（断链）。实际工程里发版目录切换用 `ln -sfn`，因为它可以指向目录且切换是原子的。

**Q：为什么删除了大文件，`df` 显示的磁盘空间没有释放？**

A：`rm` 实际调用的是 `unlink`，只删目录项、把 `nlink` 减一。inode 和数据块的回收条件是 `nlink == 0` **并且**没有任何进程还打开着它。日志文件被应用进程持有句柄的情况下删掉，`df` 就不会减少，而 `du` 因为扫不到目录项已经统计不出来了——「`df` 和 `du` 对不上」就是这个信号。定位用 `lsof +L1` 或 `lsof | grep deleted`，处理办法是重启持有句柄的进程，或者应急用 `: > /proc/<pid>/fd/<fd号>` 把文件截断。

**Q：为什么不能给目录建硬链接？**

A：目录硬链接会让目录树从「有向无环图」变成「有环图」。`find`、`rm -r`、`du` 这类遍历都基于无环假设，出现环之后会无限递归，而且没有低成本的环检测手段；同时 `..` 的语义会变得不唯一（一个目录有两个父目录）。所以内核直接禁止普通用户创建，只有内核自己维护的 `.` 和 `..` 是例外——这也是为什么空目录的 `nlink` 是 2、每加一个子目录就加 1。

**Q：日志切割为什么推荐 `copytruncate` 或硬链接，而不是直接 `mv`？**

A：因为进程持有的是 inode 句柄不是文件名。`mv` 之后 inode 没变，进程继续往改名后的旧文件写，新建的同名文件永远是空的。解决方式有两种：一是 `mv` 后给进程发信号（Nginx 是 `kill -USR1`）让它重新 `open` 日志路径；二是用 `logrotate` 的 `copytruncate`（先复制再把原文件截断为 0，inode 不变），代价是复制期间的写入可能丢失。用硬链接 + 截断是 `copytruncate` 的等价手法，且避免了大文件复制。
