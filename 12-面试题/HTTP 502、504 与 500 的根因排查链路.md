# HTTP 502、504 与 500 的根因排查链路

> 在基于反向代理（如 Nginx）的典型微服务架构中，HTTP 500、502、504 分别代表不同网络层级与应用链路的异常。快速定位的核心在于区分**反向代理自身判定**还是**上游服务返回**，以及是**连接无法建立（502）**、**响应超时等待（504）**还是**业务代码内部抛出未捕获异常（500）**。

## 30 秒回答骨架

- **HTTP 500 (Internal Server Error - 应用层崩溃)**：上游应用服务器（如 Django / Spring Boot / Go）已经成功接收并开始处理请求，但在执行过程中发生了未捕获的运行时异常（如空指针、语法错误、数据库连接池耗尽抛出未处理异常），由应用框架自身构造并返回了 500 状态码给客户端。
- **HTTP 502 (Bad Gateway - 网关连不上/上游进程夭折)**：Nginx 作为网关，尝试向上游（Upstream）发起 TCP 连接或发送数据时，上游服务**连接被拒绝（Connection Refused / 服务进程挂了/未监听对应端口）**，或者上游服务在数据发送到一半时发生 OOM 崩溃导致**连接被异常重置（Connection reset by peer）**。
- **HTTP 504 (Gateway Timeout - 网关等待响应超时)**：Nginx 成功与上游服务器建立了 TCP 连接并将 HTTP 请求转发过去，但上游服务在 Nginx 配置的超时阈值内（如 `proxy_read_timeout 60s`）**未能返回任何响应数据**。根因通常为慢 SQL 阻塞、死锁、下游依赖服务长连接卡死或应用内部线程池打满。

## 展开

### 1. 架构拓扑与状态码产生节点

```text
[ 客户端 Client ]
       |
       | 1. HTTP Request
       v
+--------------+
| Nginx 网关   | <======== [ 若无法建立连接 / 进程崩溃，Nginx 自身吐出 502 Bad Gateway ]
+-------+------+ <======== [ 若超过 proxy_read_timeout，Nginx 自身吐出 504 Gateway Timeout ]
        |
        | 2. Upstream 连接 (TCP / Unix Socket)
        v
+-------------------------------+
| 上游服务 (Spring / Python / Go)| <======== [ 代码抛出未捕获异常 / Bug，应用返回 500 Internal Error ]
+-------------------------------+
```

### 2. 500 / 502 / 504 核心差异对比矩阵

| 状态码 | 含义 | 响应生成方 | 典型底层触发场景 | Nginx `error.log` 典型特征 |
| :--- | :--- | :--- | :--- | :--- |
| **500** | Internal Server Error | **上游应用代码** | 空指针异常（NPE）、SQL 语法错误、未捕获的业务逻辑异常 | Nginx 只记录 access.log `status: 500`，error.log 无错误 |
| **502** | Bad Gateway | **Nginx 代理层** | 上游服务宕机未启动、端口写错、JVM OOM 崩溃被杀、Keepalive 偶发断开 | `connect() failed (111: Connection refused)` 或 `recv() failed (104: Connection reset by peer)` |
| **504** | Gateway Timeout | **Nginx 代理层** | 业务执行过慢、慢 SQL、死锁、调用三方未设超时导致卡死 | `upstream timed out (110: Connection timed out) while reading response header from upstream` |

### 3. 系统性排查排障链路四步法

```text
[ 收到报警 / 接口报错 ]
          |
          v
1. 查 Nginx access.log 提取 $status, $upstream_status, $upstream_response_time
          |
          +---- status=500, upstream_status=500:
          |     直接下钻 -> 查应用业务日志 (Spring logback / Python logging) 搜 ERROR 堆栈
          |
          +---- status=502:
          |     查 Nginx error.log
          |     |-- "Connection refused": 检查应用服务进程是否存在 (systemctl/docker ps/ps aux)
          |     |-- "Connection reset by peer": 检查 dmesg -T 是否有 OOM Killer 杀掉进程
          |     +-- "no live upstreams": 检查上游集群健康检查与 DNS 解析
          |
          +---- status=504:
                查 Nginx error.log
                |-- 确认超时的 upstream_addr 节点
                +-- 查应用当前线程堆栈 (jstack / pprof)，定位是否在等待数据库锁或三方 HTTP 调用
```

#### Nginx 日志格式辅助配置（测开定位神器）

在排查反向代理问题时，标准的 Nginx 日志必须包含 upstream 追踪变量：

```nginx
log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                '$status $body_bytes_sent "$http_referer" '
                '"$http_user_agent" upstream_addr: $upstream_addr '
                'upstream_status: $upstream_status '
                'request_time: $request_time '
                'upstream_response_time: $upstream_response_time';
```

## 可能被追问的点

- **Nginx 报 502 时，出现 `104: Connection reset by peer` 最常见的三种情况？**
  1. 上游服务执行过程中触发了内存爆满，操作系统内核触发 OOM Killer 直接发送 `SIGKILL` 强杀上游进程；
  2. 上游服务框架（如 Go / Node.js）自身发生了 Fatal Panic / Crash，进程瞬间退出，未完成标准四次挥手；
  3. HTTP Keep-Alive 空闲超时冲突：上游服务端配置的 `keepalive_timeout`（如 60s）小于 Nginx 网关维持的存活时间，上游主动断开连接的同时网关恰好发起复用请求。
- **504 发生时，客户端虽然收到了 504 报错，但上游数据库里该笔订单真的没有创建吗？**
  - **不一定！** 504 仅仅表示网关在规定时间内没有拿到响应头。很可能此时上游服务器还在后台继续执行（或者实际上已经把订单写入数据库，只是返回给网关慢了）。
  - 这就是分布式系统的「状态未知（In-doubt State）」，此时客户端绝对不能简单盲目重发，否则会导致**重复扣款/重复下单**，必须依赖接口幂等性（Idempotency Key）设计。
- **如果只是盲目调大 Nginx 的 `proxy_read_timeout`（例如从 60s 改为 300s）来解决 504，会有什么灾难性后果？**
  - 掩盖了上游慢查询或死锁的真正 Bug；
  - 导致大量客户端连接长时间挂起不释放，迅速耗尽 Nginx 的 `worker_connections` 和上游服务的连接池/线程池，最终导致网关全线被拖垮，小故障演变为全局雪崩。

## 结合自己项目的例子

在一次自动化用例并发压测与大促演练中，测试套件针对商品详情页与下单结算链路高频请求时，监控大盘突然出现每分钟 300+ 笔 504 报警，伴随零星 502 报错。

- **排障全链路**：
  1. **解析 Nginx 日志**：`grep " 504 " access.log | awk '{print $NF, $(NF-1)}'`，发现 `request_time` 均卡死在 30.00 秒，且 `upstream_status: 504`，对应的 upstream 地址是订单结算集群节点；
  2. **下钻应用状态**：登录订单上游机，通过 `jstack <pid>` 抓取 JVM 线程堆栈，发现大量 `DubboServerHandler` 线程阻塞在等待 Redis 分布式锁 `RLock.lock()`；
  3. **定位死锁与 502 伴生因**：由于抢购并发过高，Redis 响应变慢，导致订单线程池被全部打满，后续新连接排队超过全连接队列后，操作系统直接丢包/回 RST，进而触发了外层 Nginx 的 502；同时存量排队超过 30s 的直接被 Nginx 掐断返回 504。
- **解决方案与验证**：
  1. 修复分布式锁代码中的非确定性自旋逻辑，改用 Redisson 带超时的 `tryLock(3, 5, TimeUnit.SECONDS)`，快速失败不积压；
  2. 针对高并发订单库存查询增加本地 Guava Cache 降级保护；
  3. 调整 Nginx upstream 配合熔断降级策略。
- **复测效果**：复测全链路压力提升至原指标 1.5 倍时，504 与 502 状态码归零，API P99 响应耗时收敛在 80ms 以内。
