# 字典底层哈希扩容与哈希冲突解决

> Python 3.6+ 的 dict 底层采用「稀疏哈希索引表 + 紧凑键值条目数组」的分离存储结构，冲突通过开放寻址法的微扰法（Perturbation）探测解决，装载因子阈值为 2/3（约 66.7%）时触发扩容。

## 30 秒回答骨架

- **底层数据结构**：自 Python 3.6 起（PEP 468/498 演化，PyPy 启发），CPython 将字典拆分为 `indices` 索引数组与 `entries` 条目数组。`indices` 是稀疏稀排数组存条目下标；`entries` 按插入顺序紧凑存放 `hash, key, value`。这使得内存占用减少 20%~25%，且天生保证了**插入有序性**。
- **哈希冲突解决**：采用**开放寻址法（Open Addressing）**中的**微扰法（Perturbation Probing）**，探测步长公式为 $j = ((5 \times j) + 1 + perturbation) \pmod{2^n}$，随着每轮循环 $perturbation = perturbation \gg 5$ 逐步衰减，高位哈希参与计算，有效打破二次探测常见的长程聚集（Clustering）。
- **扩容机制**：当已分配槽位与伪删除标记（Dummy/DKIX_DUMMY）合计达到当前容量的 **2/3** 时触发扩容；小字典以 4 倍扩容（$\le 50000$ 元素），大字典以 2 倍扩容，扩容时重建 `indices` 并剔除所有 Dummy 槽位。

## 展开

### 1. 传统哈希表 vs 紧凑哈希表（Compact Dict）

在 Python 3.5 之前，CPython 的字典底层是一个连续的 `PyDictKeyEntry` 数组，每个槽位（Slot）直接存储 `me_hash, me_key, me_value`：

```text
Python 3.5 之前的稀疏大数组（64位系统每个Entry占 24字节）：
entries = [
    [hash, key, value],   # 0
    [NULL, NULL, NULL],   # 1 空槽（浪费 24 字节）
    [NULL, NULL, NULL],   # 2 空槽（浪费 24 字节）
    [hash, key, value],   # 3
    ...
]
```
由于装载因子限制在 2/3 以下，数组中有 1/3 到 1/2 的槽位是空的，每个空槽都浪费 24 字节。

Python 3.6+ 采用紧凑存储重构（Compact Dict）：

```text
Python 3.6+ 分离结构：
indices = [-1,  0, -1,  1, -1, -1,  2, -1]  (根据容量选择 int8 / int16 / int32，极小内存)
                ↓       ↓           ↓
entries = [
    [hash0, key0, val0],  # 0 紧凑排列，无空隙
    [hash1, key1, val1],  # 1 按插入先后追加
    [hash2, key2, val2]   # 2
]
```

- `indices` 是哈希路由表：大小为 $2^n$（默认初始化为 8），值根据最大元素容量动态选择 `int8_t`（-128~127）、`int16_t` 等，未占用或冲突后探查不到记为 `-1`（`DKIX_EMPTY`）。
- `entries` 紧凑连续：只有实际插入的数据才会 push 到 `entries`，内存连续对 CPU L1/L2 缓存友好。
- **插入保序的本质**：遍历字典时只需要顺序遍历 `entries` 数组，因而默认保证了键的插入顺序。

### 2. 冲突解决：微扰法（Perturbation Probing）

开放寻址法如果单纯采用线性探测（$j = (j+1) \pmod N$）极易形成一次聚集；如果采用普通二次探测，哈希值的高位比特（High Bits）完全无法参与步长推导。CPython 在 `Objects/dictobject.c` 中设计了微扰算法：

```c
// 伪代码逻辑示意（来自 CPython dictobject.c）
size_t mask = dict->dk_size - 1;
size_t perturb = hash;
size_t i = hash & mask;

while (indices[i] != DKIX_EMPTY) {
    if (indices[i] >= 0) {
        PyDictKeyEntry *entry = &entries[indices[i]];
        if (entry->me_key == key || (entry->me_hash == hash && PyObject_RichCompareBool(entry->me_key, key, Py_EQ))) {
            return indices[i]; // 找到目标键
        }
    }
    // 冲突探测公式
    i = (5 * i + 1 + perturb) & mask;
    perturb >>= 5; // 微扰值右移5位衰减，逐步让高位特征影响探测轨迹
}
```

探测公式核心特点：
1. **全周期保证**：因为取模基数是 $2^n$，且乘数 5 与 $2^n$ 互质，加数 1 为奇数，微扰衰减为 0 后退化为仿同余线性发生器，数学上证明能够**不重复地遍历哈希表的所有槽位**。
2. **高位参与度**：初期的 `perturb` 携带完整的原始哈希高位信息，每次右移 5 位，使得具有相同低位哈希但高位不同的两个 Key，其探测序列完全不同，大幅降低碰撞堆积。

### 3. 删除标记与扩容流程

- **伪删除（Dummy）**：开放寻址法不能将删除项直接置为 EMPTY（-1），否则后续依赖该槽位探测的链式查询会中断。CPython 将 `indices[i]` 置为 `-2`（`DKIX_DUMMY`），查找时跳过继续探查，插入时允许覆写。
- **触发扩容条件**：`USABLE_FRACTION(dk_size) = (dk_size * 2) / 3`。当 `num_entries + num_dummies >= 2/3 * dk_size` 时，触发扩容。
- **扩容重构（Resize）**：
  - 新建更大容量的 `indices`（根据当前活跃元素数计算新尺寸，旧元素较少时 4 倍，较大时 2 倍）。
  - 将所有存活键值对重新哈希计算索引，**剔除所有 Dummy 槽位**，`entries` 被重新紧缩压缩。

## 可能被追问的点

- **为什么装载因子阈值选 2/3 而不是 Java HashMap 的 0.75？**
  - Java HashMap 采用拉链法（链表 + 红黑树），发生哈希冲突时只在对应桶的链表后追加，即便装载因子到 0.75，桶冲突代价相对可控。
  - Python dict 是**开放寻址法**，整个数组共享寻址空间，当装载率超过 70% 后，长探测链的概率呈指数上升，CPU Cache Miss 剧增。2/3 是时间性能（探测步长均值 $\le 2$）与内存利用率的最佳平衡点。
- **自定义对象作为 dict 的 key 时，为什么重写 `__eq__` 必须同时重写 `__hash__`？**
  - dict 寻址先拿对象的 `hash(obj)` 定位桶位；若定位到的槽位存在 Key，先比对内存地址 `entry->key == key`，若不等再比对 `hash` 是否相同，最后才调用 `__eq__`。
  - 如果只重写 `__eq__` 而不重写 `__hash__`，两个业务相等的对象由于基于 `id()` 的默认哈希值不同，根本落不到同一个寻址链上，导致 `d[A] = 1; d[B]` 抛出 `KeyError`。在 Python 中一旦重写了 `__eq__`，解释器会自动将 `__hash__` 置为 `None`，若不显式补上即变为 unhashable。
- **遍历字典过程中 `dict.pop()` 或增删 Key 报 `RuntimeError: dictionary changed size during iteration` 底层原理？**
  - 字典内部维护了一个 `dk_version`（版本变更序列计数器）。每次 `setitem`、`delitem` 触发 entries 增删或 resize 时，`dk_version` 递增。
  - 迭代器对象在创建时记录了当前版本号；每步 `__next__` 会校验当前版本号是否匹配，一旦失配立即抛出 `RuntimeError`，防止迭代器读取越界或悬空指针。

## 结合自己项目的例子

在微服务测试平台的自动化用例执行引擎中，我们需要在大批量并发压测中记录每个请求的 TraceContext 与上下文变量池（ContextStore），底层设计直接封装了多级 Python 字典。

在一次压测到 5 万级并发用例上下文调度时，监控发现 Python 工作进程内存暴涨 3 倍，且垃圾回收耗时显著增长。深入剖析发现：
1. 上下文变量在每条步骤执行后频繁使用 `del context[var_name]` 清理临时参数。
2. 频繁的增删导致 `indices` 中积累了海量的 `DKIX_DUMMY`（-2）伪删除占位符，触发了字典无谓的扩容与频繁微扰探测，平均单次 Key 查询哈希探测次数从 1.2 次劣化到了 7.8 次。
3. **改造方案**：将高频变更的执行期变量按执行生命周期分片，短生命周期的临时字典改用固定结构的 `dataclass` / `__slots__` 结构，跨步骤共享大字典则通过 `context.clear()` 批量释放并复用预分配对象池。
4. **效果**：工作节点字典操作内存开销下降 42%，高负载下上下文查找耗时 P99 从 3.4ms 压降到 0.4ms 以内。
