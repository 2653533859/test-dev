# TCP 三次握手为什么不能是两次

> 三次握手的本质是「双方各自确认对方的收发能力 + 同步初始序列号」，两次做不到，四次没必要。

## 30 秒回答骨架

握手要达成两个目的：**双向确认收发能力**、**双向同步初始序列号（ISN）**。

- 两次握手时，客户端知道「我能发、服务端能收能发」，但**服务端不知道自己的 SYN+ACK 客户端有没有收到**，也就无法确认「客户端的接收能力」和「自己 ISN 已被对方确认」。
- 更严重的是**历史重复连接**：网络中滞留的旧 SYN 迟到到达，两次握手下服务端会直接建连并分配资源，造成资源浪费与数据错乱；三次握手时客户端能在第三步发 RST 终止这个错误连接。
- 四次也可以，但服务端的 ACK 与 SYN 能合并成一个包，所以三次是**能达成目的的最小次数**。

## 展开

### 三次握手做了什么

```text
Client                                  Server
  |  SYN, seq=x                            |   → 客户端 ISN=x
  |--------------------------------------->|
  |  SYN+ACK, seq=y, ack=x+1               |   → 服务端 ISN=y，确认了 x
  |<---------------------------------------|
  |  ACK, seq=x+1, ack=y+1                 |   → 确认了 y
  |--------------------------------------->|
```

逐步看每一方获得了什么信息：

| 时刻 | 客户端确认了 | 服务端确认了 |
|------|-------------|-------------|
| 第 1 次后 | —— | 对方发送能力正常、自己接收能力正常 |
| 第 2 次后 | 双方收发能力都正常、对方已收到我的 ISN | 同上 |
| 第 3 次后 | 同上 | 自己发送能力正常、对方接收能力正常、自己的 ISN 已被确认 |

**只有到第三次，服务端才补齐了「自己能发」和「对方能收」这两条信息**。少一次，服务端就是在信息不完整的情况下把连接置为 ESTABLISHED。

### 两次握手的真实危害：历史重复连接

这是 RFC 793 里给出的首要理由，比「确认收发能力」更具体。

场景：客户端发出 SYN(seq=x1)，这个包在网络里因为路由抖动被延迟很久，客户端超时后重发 SYN(seq=x2) 并正常完成通信、关闭连接。此时那个滞留的 SYN(seq=x1) 才姗姗来迟。

- **两次握手**：服务端收到旧 SYN 就直接进入 ESTABLISHED，分配接收缓冲、TCB 等资源，还会按 x1 的序列号等数据。客户端根本不知情，这个连接就一直挂着，资源白白占用。
- **三次握手**：服务端回 SYN+ACK 后要等第三个 ACK。客户端发现这个 SYN+ACK 对应的是一个自己早已废弃的连接（序列号对不上当前状态），会回一个 **RST**，服务端立即释放资源。

**第三次握手本质上给了客户端一次「否决权」**，这是两次握手结构上给不了的。

### 同步初始序列号（ISN）

TCP 的可靠性建立在序列号之上：去重、排序、重传都靠它。双方各自维护一套发送序列号，所以 ISN 必须**双向同步且双向确认**。

ISN 不是从 0 开始，而是基于时钟和四元组哈希生成的随机值，目的有两个：避免不同「化身」（同一四元组的前后两个连接）的报文串台；提高攻击者猜测序列号做连接劫持的难度。

### 为什么不需要四次

如果严格按「每个方向独立握手」来算，应该是：SYN → ACK → SYN → ACK 四步。但服务端的 ACK（确认客户端的 SYN）和 SYN（发送自己的 ISN）**在同一时刻产生、可以合并到一个报文里**，于是压缩成三次。

对比四次挥手：挥手时服务端收到 FIN 后往往还有数据没发完，ACK 必须先发、FIN 得等数据发完再发，所以合并不了，才是四次。**能不能合并，取决于两个动作是不是同时就绪。**

## 可能被追问的点

- **第三次握手可以携带数据吗？** 可以。第三个 ACK 允许带数据（TCP Fast Open 更进一步，让第一个 SYN 就带数据）。第一次 SYN 通常不带数据，否则会放大 SYN Flood 的攻击成本。
- **SYN Flood 是什么，怎么防？** 攻击者伪造源 IP 大量发 SYN，服务端回 SYN+ACK 后等第三次 ACK，半连接队列被打满，正常连接进不来。防护手段：`net.ipv4.tcp_syncookies=1`（不占队列，用 cookie 编码状态）、调大 `tcp_max_syn_backlog`、减少 `tcp_synack_retries`。
- **半连接队列和全连接队列的区别？** 半连接（SYN queue）存收到 SYN 但还没收到第三次 ACK 的连接；全连接（accept queue）存握手完成、等待应用 `accept()` 的连接。全连接队列满了会丢 ACK 或回 RST，表现为客户端偶发连接超时，用 `ss -lnt` 看 `Send-Q`/`Recv-Q` 能发现。
- **四次挥手为什么要 TIME_WAIT，为什么是 2MSL？** 一是保证最后一个 ACK 丢了对方重发 FIN 时还能应答，二是让本次连接的残留报文在网络中消散，避免污染同四元组的新连接。2MSL = 一个报文最大生存时间的往返。
- **大量 CLOSE_WAIT 说明什么？** 说明本端收到了 FIN 但应用层没调用 `close()`，通常是代码里连接没关或异常分支漏关——是**应用 bug**，不是网络问题。

## 结合自己项目的例子

在商城中台的一次性能测试里，我压订单创建接口，TPS 冲到 800 左右就上不去了，错误率从 0 涨到 6%，JMeter 报的是 `Connection timed out`。

第一反应是应用性能瓶颈，但应用服务器 CPU 只有 40%，GC 也正常。于是我从网络层往下看：

```bash
# 在应用机上抓半连接/全连接溢出计数
netstat -s | grep -i listen
# 160 times the listen queue of a socket overflowed
# 160 SYNs to LISTEN sockets dropped

ss -lnt | grep 8080
# State   Recv-Q  Send-Q   Local Address:Port
# LISTEN  129     128      0.0.0.0:8080
```

`Recv-Q` 已经顶到 `Send-Q`（全连接队列长度 128），说明握手完成的连接堆在 accept 队列里没人取走，内核直接丢掉了第三次 ACK——客户端以为连接建好了，实际服务端并没有，超时就来自这里。

根因是 Tomcat 的 `acceptCount` 保持默认值 100，同时 `maxThreads` 偏小，业务线程被慢 SQL 拖住，来不及 `accept`。我们做了两件事：把慢 SQL 优化掉（订单列表缺了个联合索引），并把 `acceptCount` 与内核 `somaxconn` 一起调到 1024。复压之后 TPS 到 2100 才出现拐点，错误率回到 0。

这个案例我在面试里常拿来讲，因为它能自然带出三次握手的两个队列：**很多「偶发连接超时」根本不是网络丢包，而是全连接队列溢出，读懂握手过程才知道去哪看这个指标。**
