# 自动化框架的收益怎么量化

> 「提升了测试效率」是零分答案。要给出口径清晰、能追溯到数据源的指标。

## 30 秒回答骨架

从**四个维度**给数字，每个维度都要能说清计算口径和数据来源：

1. **效率**：回归耗时（2 人天 → 11 分钟）、人力释放（每次上线省 2 人 × 2 天）、反馈周期（从「上线前一天才知道」到「提交后 15 分钟知道」）。
2. **质量**：上线前缺陷拦截率（60% → 92%）、生产回归缺陷数（月均 4 → 0.3）、平均缺陷发现时长。
3. **成本**：投入的人力（我 1 人 6 周搭建 + 日常约 20% 精力维护）、算清 ROI，**敢说成本才可信**。
4. **协作**：用例可被非作者维护（60% 新增用例不是我写的）、其他团队复用（推广到 2 个业务组）。

**最重要的一条**：自动化真正的价值不是「跑得快」，而是**把回归成本降到足够低，从而让回归范围不再需要靠经验裁剪**。这句话能把讨论从工具层面拉到质量策略层面。

## 展开

### 每个指标的口径和数据源

含糊的数字会被当场问穿，所以每个指标都要准备「怎么算的 + 从哪来的」。

| 指标 | 计算口径 | 数据来源 |
|------|---------|---------|
| 回归耗时 | 全量回归从开始到出报告的墙钟时间 | 改造前：测试排期表里的人天记录；改造后：Jenkins 构建时长 |
| 缺陷拦截率 | 上线前发现数 /（上线前 + 上线后 30 天内暴露的同源缺陷数） | Jira 缺陷单的「发现阶段」字段 |
| 自动化发现缺陷数 | 由自动化用例首次发现、且被确认为有效的缺陷 | Jira 里打 `found-by:auto` 标签统计 |
| 用例通过率/稳定性 | 连续 30 次构建中「非产品原因失败」的用例占比 | Allure 历史趋势 + 失败原因分类记录 |
| 维护成本 | 每月花在修用例上的工时 | 自己记的工时表（这个数据最难拿，但最有说服力） |

**「敢报维护成本」是一个强信号**。所有自动化都有维护成本，主动说出来说明你在客观评估而不是推销。

### ROI 怎么算给面试官听

```text
投入：
  搭建   1 人 × 6 周            = 30 人日
  维护   每月约 4 人日 × 12 月   = 48 人日
  合计                          = 78 人日 / 年

节省：
  回归  每次省 2 人 × 2 天 = 4 人日
        每月上线 4 次      = 16 人日/月 → 192 人日/年
  生产缺陷减少 3.7 个/月，每个缺陷平均处理成本约 1 人日
        （含定位、修复、回归、发版）→ 44 人日/年

净收益 ≈ 192 + 44 - 78 ≈ 158 人日/年
```

这个算法不追求精确，追求的是**展示你有成本意识、会算账**。面试官不会去核对数字，但会判断你的思考方式。

如果被质疑「省下来的人日真的省了吗」，实话实说：**省下的时间没有变成人力缩减，而是转投到了探索式测试和专项测试上**——这恰恰是自动化的正确用法，机器做重复的，人做需要判断的。

### 别只说效率，说「策略变化」

效率数字容易被当成"工具改进"，但下面这类变化才是质变：

- **回归范围不再裁剪**：以前每次上线只能挑 30% 的用例回归（因为跑不完），挑哪些靠经验，漏的地方就在没挑中的部分。现在 810 条全跑只要 11 分钟，**回归范围从「经验决定」变成「全量」**，这是最本质的收益。
- **反馈左移**：从「测试阶段发现」变成「提交后 15 分钟发现」。缺陷修复成本随发现阶段指数上升，这一条的价值远大于省下的人日。
- **发布节奏解绑**：以前发版要预留 2 天回归窗口，只能双周发；现在能做到随时可发，业务侧的响应速度提上来了。
- **知识沉淀**：用例本身就是一份可执行的业务规则文档。新人接手时跑一遍用例比读三天文档快。

### 反面：哪些"收益"不要说

- **「写了 800 条用例」**——数量不是收益，是投入。
- **「覆盖率 90%」**——不说口径的覆盖率没有意义，且容易被追问到崩（是接口覆盖率？行覆盖率？需求覆盖率？）。
- **「解放了人力」**——太虚，必须落到具体多少人日、这些人日去做了什么。
- **「提高了代码质量」**——测试不直接提高代码质量，别抢开发的功劳。

## 可能被追问的点

- **「拦截率从 60% 到 92%，一定是自动化的功劳吗？同期有没有别的变化？」** 这是个很尖锐的好问题。诚实回答：同期还上线了代码评审规范，两者都有贡献。我能拆出来的部分是「由自动化用例首次发现的有效缺陷」这个指标——一年 137 个，这部分可以确定归因于自动化。**承认归因复杂性比强行邀功可信得多。**
- **「自动化发现的缺陷里，有多少是真正重要的？」** 说实话：大部分是回归类缺陷（改动引入的），严重级别以 P2/P3 为主，P0/P1 很少。**自动化的价值在于"防止倒退"而不是"发现新大陆"**，探索式测试才是发现深层缺陷的手段。这个认知本身是加分项。
- **「维护成本会不会随用例增长失控？」** 会，所以要做三件事控制：分层设计限制改动影响面、用例分级避免全量跑、定期清理长期不失败也不覆盖新逻辑的僵尸用例（我每季度清一次，去年清掉了 60 多条）。
- **「如果 ROI 算下来是负的，你还做吗？」** 分情况。如果是短生命周期的项目、需求还在剧烈变动，那就不该做自动化，用检查清单+手工更划算。**能说出「什么情况下不该做自动化」，说明你不是工具狂热者。**
- **「你怎么让老板认可这些数字？」** 关键是**在开始之前就把基线数据记下来**。我改造前专门花了两周记录人工回归的耗时和缺陷数据，否则事后拿不出对比。这个动作本身就是经验。

## 结合自己项目的例子

商城中台这套框架，我从第一天就在准备"怎么证明它有用"，这件事的过程比结果更值得讲。

**动作一：先立基线。** 在写第一行框架代码之前，我做了两周的数据收集：

- 让组里 6 个人在回归期间用共享表格记录实际工时，拿到「每次上线人工回归平均 3.8 人日」。
- 从 Jira 导出近 6 个月的缺陷单，按「发现阶段」分类，算出上线前拦截率 60.4%，生产回归类缺陷月均 4.2 个。

**没有基线，后面所有的收益都是自说自话。** 很多人做完自动化说不出收益，就是卡在这一步。

**动作二：把度量做进流水线，而不是靠手工统计。**

```groovy
// Jenkinsfile 片段：每次构建把关键指标写进 InfluxDB
post {
    always {
        script {
            def summary = readJSON file: 'allure-report/widgets/summary.json'
            def total  = summary.statistic.total
            def passed = summary.statistic.passed
            def durationMin = (summary.time.duration / 60000).round(1)
            influxDbPublisher(
                selectedTarget: 'qa-metrics',
                customData: [
                    total       : total,
                    passed      : passed,
                    pass_rate   : (passed * 100 / total).round(2),
                    duration_min: durationMin,
                ],
            )
        }
        allure includeProperties: false, results: [[path: 'allure-results']]
    }
}
```

Grafana 上做了一块「自动化健康度」看板：用例总数、通过率趋势、执行时长趋势、失败 Top10 用例。**趋势图比单点数字有说服力得多**——leader 每周会自己去看，我不需要专门汇报。

**动作三：区分「自动化发现的缺陷」。** 我在 Jira 里加了一个 `found-by` 字段，值有 `auto` / `manual` / `prod`。自动化用例失败并确认为真实缺陷时，提单必须打 `auto`。这样我随时能拉出「自动化一共拦住了多少个」。第一年是 137 个。

**踩过的坑**：早期我报过一个很漂亮但站不住的数字——「用例数 810 条，覆盖率 90%」。在一次汇报里被问「哪个 90%」，我答不上来（其实是我自己拍的）。那次之后我把所有对外的数字都建了一张口径表，写清计算公式和数据源，**报数字之前先问自己「如果被追问怎么算的，我答得上来吗」**。

现在我讲这套框架时的标准说法是：

> 一年下来自动化拦住 137 个缺陷，回归耗时从 3.8 人日降到 11 分钟，上线前拦截率从 60% 到 92%，生产回归缺陷从月均 4.2 降到 0.3。投入是 30 人日搭建加每月 4 人日维护。**但我认为最大的收益不在这些数字里——是回归范围不用再靠经验裁剪了，这让质量从依赖个人经验变成了依赖体系。**

最后那句是整段的落点。**数字证明你会做事，那句话证明你想清楚了为什么做。**
