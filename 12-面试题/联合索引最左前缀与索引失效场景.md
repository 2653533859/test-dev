# 联合索引最左前缀与索引失效场景

> 给定索引 `(a, b, c)`，哪些查询能用上、用到第几列、为什么会失效——用 B+ 树排序规则一次讲清。

## 30 秒回答骨架

一句话原理：**联合索引在 B+ 树里是按 (a, b, c) 的字典序排好的，只有前面的列确定了，后面的列才是有序的。**

由此推出三条结论：

1. **最左前缀**：查询条件必须从 `a` 开始连续使用，`a` / `a,b` / `a,b,c` 能走；跳过 `a` 直接查 `b` 或 `c` 走不了（除非能走覆盖索引扫描）。
2. **范围查询截断**：遇到 `>`、`<`、`between`、`like 'x%'` 之后的列**不能再用于索引定位**，只能在回表或索引条件下推时过滤。等值可以一直往后传。
3. **对索引列做运算就失效**：函数、表达式、隐式类型转换会让 B+ 树的有序性失效，退化成全表或全索引扫描。

判断到底用了几列，看 `EXPLAIN` 的 `key_len`，不要靠猜。

## 展开

### 为什么是「最左」：字典序

假设表 `t(a int, b int, c int)`，索引 `idx_abc(a, b, c)`。叶子节点上的键大致是这样排列的：

```text
(1,1,1) (1,1,5) (1,2,3) (1,2,9) (2,1,4) (2,3,1) (3,1,1) ...
```

观察这个序列：

- `a` 整体是**全局有序**的（1,1,1,1,2,2,3）。
- `b` 只在 **a 相同的分组内**有序（a=1 时 b 是 1,1,2,2）。
- `c` 只在 **a、b 都相同的分组内**有序。

所以 `WHERE b = 2` 无法用索引做二分定位：整棵树里 b 值是散落的。这就是最左前缀的全部原因——**不是 MySQL 规定的语法限制，是数据物理排列决定的**。

### 逐条对照：能走还是不能走

以 `idx_abc(a, b, c)`、三列都是 `int NOT NULL` 为例（`int` 占 4 字节，`key_len` 每列 +4）：

| 查询条件 | 能否用索引 | 用到几列 | key_len |
|----------|-----------|---------|---------|
| `a = 1` | 能 | a | 4 |
| `a = 1 AND b = 2` | 能 | a, b | 8 |
| `a = 1 AND b = 2 AND c = 3` | 能 | a, b, c | 12 |
| `b = 2` | 不能定位 | —— | —— |
| `b = 2 AND c = 3` | 不能定位 | —— | —— |
| `a = 1 AND c = 3` | 能，但只定位到 a | a | 4 |
| `a = 1 AND b > 2 AND c = 3` | 能，定位到 b 截断 | a, b | 8 |
| `a > 1 AND b = 2` | 能，定位到 a 截断 | a | 4 |
| `b = 2 AND a = 1` | 能 | a, b | 8 |

两个容易答错的地方：

- **顺序无关**：`WHERE b = 2 AND a = 1` 照样走，优化器会重排条件。最左前缀说的是**索引列的顺序**，不是 SQL 里书写的顺序。
- **`a = 1 AND c = 3`**：索引只能定位到 a，`c = 3` 无法用于查找。但 MySQL 5.6+ 的**索引条件下推（ICP）**会在存储引擎层用索引里已有的 c 值先过滤，减少回表次数，`Extra` 显示 `Using index condition`。所以「用不上索引」这个说法不严谨，准确说法是「不能用于定位，但能用于过滤」。

### 范围查询为什么截断

```sql
SELECT * FROM t WHERE a = 1 AND b > 2 AND c = 3;
```

`a = 1 AND b > 2` 在树上定位到一段连续区间 `(1,2,+∞) ... (1,+∞,*)`。这段区间里 b 各不相同，因此 c 是乱序的——无法再用二分。所以 c 只能逐行比对。

**推论：建联合索引时，等值列放前面、范围列放最后。** 如果高频 SQL 是 `WHERE status = 1 AND create_time > ?`，索引应该建 `(status, create_time)` 而不是 `(create_time, status)`。

`like 'abc%'` 属于范围（前缀匹配），`like '%abc'` 连范围都算不上，只能全扫。

### 索引失效的常见场景

```sql
-- 1. 对索引列做函数或运算：树上存的是 create_time，不是 DATE(create_time)
SELECT * FROM t_order WHERE DATE(create_time) = '2026-07-31';   -- 失效
SELECT * FROM t_order
 WHERE create_time >= '2026-07-31 00:00:00'
   AND create_time <  '2026-08-01 00:00:00';                    -- 改写后可用

-- 2. 隐式类型转换：phone 是 varchar，传数字会触发 CAST，等价于对列做函数
SELECT * FROM t_user WHERE phone = 13800138000;   -- 失效
SELECT * FROM t_user WHERE phone = '13800138000'; -- 可用

-- 3. 左模糊
SELECT * FROM t_user WHERE name LIKE '%三';        -- 失效

-- 4. OR 连接的列有一侧无索引：整体退化全表扫
SELECT * FROM t_user WHERE id = 1 OR remark = 'x'; -- remark 无索引则失效

-- 5. 不等于 / NOT IN 且选择性差：优化器算下来回表成本高于全扫，主动放弃
SELECT * FROM t_order WHERE status != 1;

-- 6. 字符集或排序规则不一致的 JOIN：等价于隐式转换，被驱动表索引用不上
```

第 5 条要强调：**这不是「失效」，是优化器基于成本的主动选择**。如果 `status != 1` 只命中 1% 的数据，索引照样会走。回答时说「优化器认为全表扫更便宜」比说「不等于会失效」更专业。

### 用 EXPLAIN 验证

```sql
EXPLAIN SELECT * FROM t WHERE a = 1 AND b > 2 AND c = 3;
```

重点看四列：

- `type`：`ref`（等值走索引）> `range`（范围）> `index`（全索引扫）> `ALL`（全表扫）。出现 `ALL` 或 `index` 就要警惕。
- `key`：实际用了哪个索引，`NULL` 表示没用。
- `key_len`：用到了索引的前几列。可空列 +1 字节，`varchar` 再 +2 字节存长度。
- `Extra`：`Using index` 是覆盖索引（不回表，最好）；`Using where` 表示回表后还要过滤；`Using filesort` / `Using temporary` 说明排序分组没走上索引。

## 可能被追问的点

- **`(a,b,c)` 能不能替代 `(a)` 和 `(a,b)` 两个索引？** 能。所以建索引要考虑「索引合并的可能」，别为每列都建单列索引，浪费空间还拖慢写入。
- **`ORDER BY` 能不能用上联合索引？** 能，但要满足最左前缀且方向一致。`WHERE a = 1 ORDER BY b` 可以走；`WHERE a = 1 ORDER BY c` 不行（b 未确定）；`ORDER BY b ASC, c DESC` 在 MySQL 8.0 之前也不行（8.0 支持降序索引）。
- **什么是覆盖索引？** 查询需要的所有列都在索引里，不用回表。`SELECT a, b FROM t WHERE a = 1` 走 `idx_abc` 就是覆盖索引，`Extra` 显示 `Using index`。这也是反对 `SELECT *` 的一个硬理由。
- **索引不是越多越好，代价是什么？** 每个二级索引都要占存储、每次 `INSERT`/`UPDATE`/`DELETE` 都要维护 B+ 树，写入变慢；索引过多还会干扰优化器选择。
- **区分度怎么影响索引？** 性别这种只有两个值的列建索引基本没用（区分度低，回表成本高于全扫）。可以用 `SELECT COUNT(DISTINCT col)/COUNT(*)` 评估。
- **强制走索引怎么写？** `FORCE INDEX(idx_abc)`，但这是应急手段，压测和线上尽量靠更新统计信息（`ANALYZE TABLE`）与改写 SQL 解决。

## 结合自己项目的例子

商城中台的订单列表接口，在一次性能测试中 P95 从 200ms 涨到 3.2s。我按「先看慢日志、再看执行计划」的顺序排查。

慢查询日志里捞出的语句是：

```sql
SELECT * FROM t_order
 WHERE merchant_id = 10086
   AND DATE(create_time) = '2026-07-30'
   AND status = 2
 ORDER BY create_time DESC LIMIT 20;
```

`EXPLAIN` 显示 `type=ALL`、`key=NULL`、`rows` 约 480 万，还有 `Using filesort`。表上已有索引 `idx_merchant_status(merchant_id, status)`，理论上应该能走。

定位到两个问题：

1. `DATE(create_time)` 对列做了函数，虽然不影响前两列，但这条 SQL 里更致命的是**第二个问题**——
2. `merchant_id` 在表里是 `varchar(32)`（历史设计，商户号可能带字母前缀），而 ORM 传进来的是 int，触发隐式类型转换，整个索引直接用不上。

改动分两步：

- 应用层把 `merchant_id` 统一按字符串传参，隐式转换消失，`type` 变成 `ref`。
- 把时间条件改写成左闭右开区间，并新建索引 `idx_m_s_ct(merchant_id, status, create_time)`——等值列在前、范围兼排序列在最后，这样 `ORDER BY create_time DESC` 也能直接用索引的有序性，`Using filesort` 消失。

改完 `key_len` 从 `NULL` 变成 132（`varchar(32)` utf8mb4 可空 + `int` + `datetime`），扫描行数从 480 万降到 21 行，P95 回到 45ms。

后来我把这件事沉淀成了两条规范并加进了 CI：一是 DAO 层禁止对索引列套函数（评审时人工卡），二是接入了一个慢 SQL 检查脚本，压测环境开 `long_query_time=0.5`，压测结束自动跑 `pt-query-digest` 出 Top10 慢 SQL 贴到报告里。**从「这次调好了」变成「下次能提前发现」，这才是面试官想听的落点。**
