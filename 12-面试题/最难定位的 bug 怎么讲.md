# 最难定位的 bug 怎么讲

> 考的不是 bug 有多难，是你的排查方法论：怎么收敛范围、怎么验证假设、怎么防复发。

## 30 秒回答骨架

讲一个**偶发、跨系统、表象具有误导性**的 bug，按五步讲：

1. **现象（20 秒）**：什么场景下出现、复现概率、表象是什么。
2. **难在哪（20 秒）**：为什么不好查——偶发、日志无异常、本地不复现、多系统交叉。
3. **收敛过程（90 秒，重点）**：怎么一步步把范围从「整条链路」缩小到「某一行代码」。**这段要体现二分、控制变量、假设-验证的思维。**
4. **根因（20 秒）**：一句话说清，越具体越好。
5. **防复发（20 秒）**：补了什么用例、加了什么监控、改了什么流程。**这一步区分「查出来了」和「测开」。**

选题原则：**不要挑「难在体力」的 bug（翻了 10 万行日志），要挑「难在思路」的 bug。**

## 展开

### 排查方法论的四个动作

面试官真正想看的是你有没有这套东西，讲案例时要让它自然浮现出来。

**一、先稳定复现，再谈定位。** 无法复现的问题只能靠猜。所以第一步永远是找规律：

- 记录每次出现的时间、环境、账号、数据、操作路径，找共同点。
- 提高触发频率：加大并发、缩短间隔、放大数据量、把随机因素固定住。
- 复现率从 5% 提到 80%，后面的定位成本会降一个数量级。

**二、二分收敛。** 把链路切成两半，判断问题在哪半边，再切。

- 链路二分：客户端 → 网关 → 应用 → 缓存 → 数据库，在每层加观测点看数据是从哪一层开始不对的。
- 版本二分：`git bisect` 在几百个提交里定位引入问题的那一次提交。
- 配置二分：逐项对齐两个环境的差异。

**三、控制变量。** 一次只改一个东西。这是最容易违反的一条——着急时容易同时改三处，然后好了也不知道是哪处起的作用。

**四、假设 - 验证 - 排除。** 每一步先明确写出「我猜是 X，如果是 X，那么应该能观察到 Y」，然后去验证 Y。**能被证伪的假设才是有效假设**，「可能是网络问题」这种不可证伪的猜测毫无价值。

### 常用的观测手段

| 层次 | 手段 |
|------|------|
| 应用 | 日志（关键路径打 traceId）、APM 链路追踪、`arthas` 在线诊断、远程 debug |
| JVM | `jstack` 看线程栈、`jmap` 看堆、GC 日志 |
| 数据库 | 慢查询日志、`SHOW ENGINE INNODB STATUS` 看锁与死锁、binlog 看数据实际变更 |
| 网络 | `tcpdump` + Wireshark、`ss`/`netstat` 看连接状态、抓包对比请求实际内容 |
| 系统 | `top`/`vmstat`/`iostat`、`strace` 跟系统调用、`dmesg` 看 OOM Killer |
| 客户端 | 浏览器 Network/Performance 面板、Charles/mitmproxy 改包重放 |

**能说出「什么现象该用什么工具」，比说「我会用 Wireshark」有用得多。**

### 讲的时候要避免的坑

- **不要讲成流水账**。「我看了日志，没发现问题，又看了代码，还是没发现，后来问了开发……」——听起来像是在盲试。要讲清每一步背后的判断依据。
- **不要把功劳全归自己**。如果最后是开发定位到的，就实话说，重点讲你怎么把范围缩小到那一块、怎么给出了关键线索。**诚实 + 清晰的贡献边界，比虚构的独立英雄更可信。**
- **不要选一个你其实没搞懂根因的 bug**。被追问两层就会露馅。

## 可能被追问的点

- **「为什么本地不复现？」** 常见原因要能列举：环境配置差异（JDK/依赖版本、时区、字符集）、数据量差异（本地 100 条、生产 500 万条，触发了不同的执行计划）、并发差异（本地单线程）、真实网络延迟、缓存状态不同、第三方依赖是 Mock 的。
- **「偶发问题怎么提高复现率？」** 加压（并发放大竞态）、缩短超时时间（放大边界）、注入延迟（在关键点 sleep 让竞态窗口变大）、固定随机种子、用真实数据快照替换构造数据。
- **「这个 bug 为什么之前的测试没发现？」** 这题在考自省。诚实分析用例设计的盲区（比如只测了单用户串行场景，没测并发），并说明后来怎么补的。**能承认测试策略有缺陷，是成熟度的体现。**
- **「如果一直定位不出来怎么办？」** 分层回答：先做业务止血（降级、限流、回滚、加开关），再补足观测手段（加日志、加埋点、开链路追踪）等待下次复现，同时评估影响面决定投入多少。**「先止血再定位」是很重要的线上思维。**
- **「你怎么和开发协作定位？」** 给出的信息要结构化：可复现步骤、traceId、请求响应报文、时间点、影响范围、我已排除的可能性。**「我已经排除了什么」这条最能提高协作效率**，也最能体现你不是甩锅。

## 结合自己项目的例子

我讲的是商城中台优惠券的一个**超卖问题**，它满足偶发、跨系统、表象误导三个特征。

**现象**：大促预热期间，运营配置了一张限量 1000 张的优惠券。活动结束后对账发现**实际发出了 1043 张**。超发比例约 4%，且只在开抢瞬间的高并发下出现，平时手工怎么点都不复现。

**难在哪**：

1. 应用日志里没有任何异常，每一次领取都是正常的成功日志。
2. 库存扣减的代码看起来是对的——先查剩余、再扣减，而且有 `WHERE remain > 0` 的条件。
3. 测试环境按正常流程测了 200 遍，一次都没复现。
4. 涉及三个系统：营销服务、库存服务、Redis 缓存，不知道问题出在哪一段。

**收敛过程**：

**第一步，先让它稳定复现。** 我判断这是并发问题，于是用 JMeter 构造了「1000 张券，2000 个用户在 1 秒内并发领取」的场景。第一次跑就发了 1037 张，**复现率 100%**。这一步是整个排查的转折点——从"偶发"变成"必现"，后面就好办了。

**第二步，确定问题出在哪一层。** 我在三个层面同时观测：

- 接口层：JMeter 统计成功响应数 = 1037，说明应用确实认为成功了 1037 次。
- 缓存层：Redis 里的 `coupon:stock:1001` 最终值是 `-37`，**说明扣减确实扣穿了**。
- 数据库层：`t_coupon_record` 表里 1037 条记录，与接口层一致。

结论：问题在**扣减库存这一步本身**，不是在下游的记录环节。范围从三个系统收敛到了一段代码。

**第三步，看代码验证假设。** 我的假设是「查询和扣减不是原子的」。翻代码看到的是：

```python
# 营销服务里的伪代码
remain = redis.get(f"coupon:stock:{cid}")     # 1. 查剩余
if int(remain) > 0:                            # 2. 判断
    redis.decr(f"coupon:stock:{cid}")          # 3. 扣减
    create_record(uid, cid)                    # 4. 落库
```

这是典型的 **check-then-act 竞态**：1000 个请求同时执行到第 1 步都读到 `remain = 1`，都通过了第 2 步的判断，然后一起扣。**这正好是我在 [[Python 并发编程]] 笔记里记过的「读—改—写」非原子问题，只是从进程内换到了分布式场景。**

**第四步，验证假设成立。** 我在第 1 步和第 3 步之间注入了 50ms 的延迟（把竞态窗口人为放大），超发量从 37 张暴涨到 400 多张——**假设被强验证**。

**根因一句话**：库存的「读取-判断-扣减」三步不是原子操作，在高并发下产生竞态，导致超卖。

**修复方案**（开发实现，我参与了方案评审）：把三步合成一个原子操作。Redis 的 `DECR` 本身是原子的，所以改成**先扣再判断，扣穿了再补回来**：

```python
remain = redis.decr(f"coupon:stock:{cid}")    # 原子扣减，返回扣后值
if remain < 0:
    redis.incr(f"coupon:stock:{cid}")          # 补回去
    raise CouponSoldOut()
create_record(uid, cid)
```

同时在数据库层加了兜底：`t_coupon_record` 上建 `(coupon_id, user_id)` 唯一索引，防止同一用户重复领；库存表扣减用 `UPDATE ... SET remain = remain - 1 WHERE id = ? AND remain > 0`，靠行锁保证原子性，`affected_rows = 0` 即为无库存。**缓存挡量、数据库兜底，两层都不能少。**

**防复发（这段我一定会讲）**：

其一，**把并发场景写进了用例体系**。原来的用例设计维度里根本没有「并发」这一档，我补了一条规范：**所有涉及「有限资源」的接口（库存、优惠券、秒杀名额、抽奖次数）必须有并发用例**，用 JMeter 或 pytest 多线程跑，断言最终发放量 == 限量。

其二，**做成了可复用的能力**。我在框架里封装了一个并发断言工具：

```python
def assert_no_oversell(func, concurrency: int, limit: int):
    """并发调用 func，断言成功次数不超过 limit"""
    with ThreadPoolExecutor(max_workers=concurrency) as ex:
        results = list(ex.map(lambda _: func(), range(concurrency)))
    success = sum(1 for r in results if r.get("code") == 0)
    assert success == limit, f"超卖: 限量 {limit}，实发 {success}"
```

现在写一条超卖用例只要三行。目前覆盖了 9 个有限资源类接口。

其三，**加了线上监控**：库存值出现负数时直接告警到钉钉，不用等对账。

**结果**：这一套补上之后，后续三次大促零超卖。而且那个并发工具在另外两个接口上又抓出过 2 个同类问题（一个是抽奖次数、一个是秒杀名额），**说明这不是孤例，是一类系统性的测试盲区。**

我讲这个案例的落点是：**定位出根因只是完成了一半，把「我们的用例设计里缺了并发这一维」这个更本质的问题补上，才是测开该交付的东西。**
