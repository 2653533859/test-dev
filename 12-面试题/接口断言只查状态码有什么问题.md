# 接口断言只查状态码有什么问题

> 「200 就算通过」是接口自动化最常见的假通过来源。答这题要给出分层断言体系。

## 30 秒回答骨架

只断言状态码的问题是**漏检率极高**，200 只能证明「请求被服务端受理了」，证明不了业务对不对：

- 业务失败但 HTTP 层成功：`200 {"code": 5001, "msg": "库存不足"}`，状态码照样是 200。
- 返回结构变了：字段改名、类型从 int 变 string、层级下沉，用例全绿但下游已经崩了。
- 值错了：下单成功了，但优惠金额算错、订单状态是错的。
- 只改了内存没落库：接口返回成功，数据库里根本没这条记录。

所以我的框架里断言分**五层**：协议层（状态码、响应时间、Content-Type）→ 结构层（JSON Schema）→ 业务码层 → 字段值层 → 数据/链路层（数据库、缓存、MQ、日志）。**前三层做成通用能力自动执行，后两层按用例配置。**

## 展开

### 五层断言各管什么

| 层 | 断言内容 | 能发现的问题 | 落地方式 |
|----|---------|-------------|---------|
| 协议层 | HTTP 状态码、响应时间、Content-Type、关键响应头 | 服务挂了、鉴权失效、超时、返回了 HTML 错误页 | 请求层统一做，无需用例声明 |
| 结构层 | 字段是否存在、类型、必填、枚举范围 | 字段改名/删除/类型漂移，前端会白屏的那类 | JSON Schema，Schema 文件与用例数据同目录 |
| 业务码层 | `code` / `success` 等业务状态字段 | HTTP 200 但业务失败 | 通用断言，默认断言成功码，异常用例显式指定 |
| 字段值层 | 关键字段的具体值、计算结果 | 金额算错、状态机流转错、分页数量不对 | 用例级配置，支持 JSONPath 取值 |
| 数据链路层 | 数据库落库、缓存写入、MQ 消息、日志埋点 | 接口"假成功"、异步链路断裂 | 用例按需调用 db/redis 校验方法 |

### 结构层：JSON Schema 而不是手写断言

手写 `assert "order_id" in resp` 这种断言，一个接口 20 个字段就要写 20 行，而且没人会写全。用 Schema 声明一次，全接口复用：

```python
from jsonschema import validate

ORDER_SCHEMA = {
    "type": "object",
    "required": ["code", "data"],
    "properties": {
        "code": {"type": "integer"},
        "data": {
            "type": "object",
            "required": ["order_id", "status", "pay_amount"],
            "properties": {
                "order_id": {"type": "string", "pattern": r"^ORD\d{16}$"},
                "status": {"type": "integer", "enum": [0, 1, 2, 3, 9]},
                "pay_amount": {"type": "number", "minimum": 0},
                "items": {
                    "type": "array",
                    "minItems": 1,
                    "items": {"$ref": "#/definitions/item"},
                },
            },
        },
    },
}

validate(instance=resp.json(), schema=ORDER_SCHEMA)
```

Schema 的价值不只是断言，它还是**一份可执行的接口契约**。开发改字段类型时，用例第一时间报错，而不是等到联调或线上。

### 字段值层：区分「精确断言」与「模式断言」

不是所有字段都能写死。订单号、创建时间每次都不一样，硬断言必然失败。分三类处理：

```python
# 1. 精确值：业务结果，必须写死
assert resp["data"]["status"] == 1
assert resp["data"]["pay_amount"] == 88.00

# 2. 模式/范围：动态值，断言格式或区间
assert re.match(r"^ORD\d{16}$", resp["data"]["order_id"])
assert abs(time.time() - resp["data"]["create_ts"]) < 60

# 3. 关系断言：字段之间的一致性，最容易漏但最值钱
items_total = sum(i["price"] * i["num"] for i in resp["data"]["items"])
assert resp["data"]["total_amount"] == items_total
assert resp["data"]["pay_amount"] == items_total - resp["data"]["discount"]
```

**第三类关系断言是接口测试的含金量所在**——它验证的是业务规则，而不只是「有没有返回」。

### 数据链路层：接口返回成功不代表业务完成

```python
def test_create_order(api_client, db):
    resp = api_client.post("/order", json=payload).json()
    oid = resp["data"]["order_id"]

    # 1. 落库校验
    row = db.query_one(
        "SELECT status, pay_amount, merchant_id FROM t_order WHERE order_id=%s", (oid,)
    )
    assert row is not None, f"接口返回成功但数据库无记录: {oid}"
    assert row["status"] == 1
    assert row["pay_amount"] == Decimal("88.00")

    # 2. 库存扣减（另一张表，验证事务完整性）
    stock = db.query_one("SELECT num FROM t_stock WHERE sku_id=%s", (SKU,))
    assert stock["num"] == origin_stock - 1

    # 3. 异步链路：轮询等待 MQ 消费完成，不要用 sleep
    assert wait_until(lambda: redis.exists(f"order:cache:{oid}"), timeout=5)
```

异步校验一定要用**轮询 + 超时**，不要 `time.sleep(3)`。sleep 短了偶发失败，长了拖慢全量。

### 断言封装：让失败信息自带上下文

```python
def assert_equal(actual, expect, msg=""):
    assert actual == expect, (
        f"{msg}\n期望: {expect!r}\n实际: {actual!r}"
    )
```

更进一步，在 `conftest.py` 里用 hook 把请求报文和响应报文挂到 Allure 附件上。**断言失败时能不能一眼看出原因，直接决定这套用例有没有人愿意维护。**

### 软断言：一次跑完所有校验

默认的 `assert` 遇到第一个失败就中断，后面的校验都看不到。对于「一个响应校验 15 个字段」的场景，软断言更高效：

```python
class SoftAssert:
    def __init__(self):
        self.errors = []

    def check(self, cond, msg):
        if not cond:
            self.errors.append(msg)

    def assert_all(self):
        assert not self.errors, "共 {} 处不符:\n{}".format(
            len(self.errors), "\n".join(self.errors)
        )
```

也可以直接用 `pytest-check` 插件，不用自己造。

## 可能被追问的点

- **那是不是所有字段都要断言？** 不是。断言过细会让用例极其脆弱（开发加个字段就红一片）。原则是：**契约级用 Schema 卡结构，业务级只断言与本用例意图相关的字段**。「这条用例在验证什么」决定断言什么。
- **响应结构变了导致大批用例失败，怎么降低维护成本？** 提取路径配置化（JSONPath 写在 YAML 里），响应解析集中在一个封装层，改一处即可；Schema 独立成文件，由接口负责人维护。
- **数据库断言会不会让用例变慢、变脆？** 会，所以只在**核心链路**用例上做（下单、支付、退款），普通参数校验用例不查库。另外查库要走只读账号，避免用例误改数据。
- **接口返回的是加密报文怎么断言？** 在响应层统一 decrypt 之后再进断言，用例层无感知；同时保留一条用例专门验证密文格式与签名本身。
- **怎么防止「用例写得跟实现一样错」？** 期望值来自需求文档或产品定义，不要从接口的实际返回反推（反向抄答案）。做法上是先写用例数据（含期望值）再联调。
- **断言失败与用例报错怎么区分？** `assert` 失败是 failed（业务不符），环境异常抛的是 error（如连接超时）。CI 上要分开统计，failed 才需要开发介入，error 通常是环境问题。

## 结合自己项目的例子

商城中台的优惠券核销接口出过一个线上问题，直接推动我把断言体系从「查状态码 + 查 code」升级到了五层。

事情是这样：营销侧改了满减规则的计算精度，把金额从 `BigDecimal` 换成了 `double`，`89.9 - 10` 算出来是 `79.89999999999999`。接口 HTTP 200、业务 `code=0`、`order_id` 也正常返回，我们那 60 条优惠券用例**全绿**。问题是在用户投诉「实付金额多了一分钱」之后才发现的。

复盘时我承认这就是断言层次太浅：用例只断言了 `code == 0` 和 `order_id` 非空。

改造分了三步：

1. **补结构层**：给 23 个核心接口写了 JSON Schema，`pay_amount` 这类金额字段限定 `"type": "number", "multipleOf": 0.01`。这一条本身就能拦住上面那个 bug。
2. **补关系断言**：在断言封装里加了 `assert_amount(actual, expect)`，内部统一转 `Decimal` 后比较，并封装了「商品总额 - 优惠 = 实付」这条规则的通用校验，所有下单类用例强制调用。
3. **补落库校验**：核心链路 8 个接口加了数据库断言，重点校验金额字段在库里的值与接口返回一致——顺带发现了另一个问题，退款单的 `refund_amount` 在库里存的是分、接口返回的是元，有个分支忘了换算。

上线三个月后的数据：接口用例数从 700 涨到 810（只多了 15%），但**捕获的缺陷数从月均 3 个涨到 11 个**，其中 6 个是原来断言不到的金额/状态类问题。我在复盘文档里写了一句话，面试时也常用：**用例数量不代表覆盖能力，断言深度才代表。**
