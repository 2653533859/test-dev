# Redis 缓存与 MySQL 双写一致性保障方案

> 在高并发读多写少架构中，Redis 缓存与 MySQL 数据库的双写一致性属于典型的分布式数据一致性难题。理论上 CAP 定理决定了无法同时保证高可用与强一致性；工程实践通常基于 Cache-Aside Pattern，采用「先更数据库再删缓存」为主体骨架，结合「延时双删」或「Canal 监听 Binlog 异步补偿」达成最终一致性（Eventual Consistency）。

## 30 秒回答骨架

- **核心原则与模式选型**：
  - **选用 Cache-Aside（旁路缓存）**：读时先读缓存，未命中则查库并回种缓存；写时更新数据库并**删除缓存**（不是更新缓存，更新缓存不仅容易引发写并发乱序覆盖，还会浪费无效计算）。
  - **为什么「先更新数据库，再删除缓存」优于「先删缓存，再更数据库」？**
    - 若先删缓存，写请求尚未写库完成时，并发的读请求会发现缓存为空，立即查库读取旧值并重新写入缓存，导致脏缓存长期驻留直至过期；
    - 先更数据库再删缓存，虽然理论上在“读未命中查出旧值但尚未写入缓存”与“写请求更库并删缓存”发生极罕见交错时仍有脏数据可能，但由于写库耗时远长于查库写缓存，发生概率极低。
- **一致性增强兜底策略**：
  1. **延时双删（Delayed Double Deletion）**：先删缓存 $\rightarrow$ 更库 $\rightarrow$ 休眠几百毫秒（覆盖主从复制延迟） $\rightarrow$ 再次删除缓存；
  2. **Canal 监听 MySQL Binlog 异步删除（最终一致性工业首选）**：业务代码只写 MySQL，由 Canal/Debezium 伪装为从库解析 Binlog 发往 MQ，由专门消费者负责幂等删除/更新 Redis。

## 展开

### 1. 为什么是“删除缓存”而不是“更新缓存”？

#### 并发写导致脏数据（更新缓存场景）
假设有两个写请求 A 和 B 并发操作：
1. 请求 A 更新数据库（值为 1）；
2. 请求 B 更新数据库（值为 2）；
3. 由于网络抖动，请求 B 先更新了 Redis 缓存（缓存值变为 2）；
4. 请求 A 紧接着更新了 Redis 缓存（缓存值变为 1）。

**最终结果**：数据库里的值是 2（最新），但 Redis 里的值却被请求 A 的旧数据覆写成了 1，产生**永久性脏数据**。而如果是**删除缓存**，写操作仅置空 Key，下次读请求会强行以数据库最终值重建。

### 2. 先更库再删缓存的极端并发边界与延时双删

#### 极端时序边界剖析（先更库再删缓存）

```text
时刻   线程 A (读请求)                  线程 B (写请求)
t1     查询 Redis (Cache Miss)
t2     查询 DB (得到旧值 val=1)
t3                                    更新 DB (新值 val=2)
t4                                    删除 Redis 缓存
t5     将旧值 val=1 写入 Redis (脏数据!)
```
要出现上述时序，必须满足条件：**步骤 t2 (读库) 在写库前开始，但步骤 t5 (写缓存) 却落在了写库并删缓存之后**。
因为内存写缓存（微秒级）通常远快于更新数据库并生成 binlog 落盘（毫秒级），所以现实中该概率极低。

#### 延时双删机制

针对必须先删缓存的业务或主从复制存在网络延迟的架构，使用延时双删：

```python
import time

def delayed_double_delete(key, new_value):
    # 1. 第一次删除缓存
    redis_client.delete(key)
    
    # 2. 更新数据库
    mysql_db.update_order(key, new_value)
    
    # 3. 延时等待（预估主从同步延迟 + 读请求网络耗时，通常 200ms ~ 500ms）
    time.sleep(0.3)
    
    # 4. 第二次删除缓存（清理在这段时间内可能被并发读载入的脏缓存）
    redis_client.delete(key)
```

### 3. 企业级终极方案：Canal 监听 Binlog + 消息队列重试

业务代码侵入性高、延时等待时间不好拿捏？大型互联网架构标准解法是将双写操作与业务解耦：

```text
[ 业务应用服务 ]
       |
       | 1. 只负责写入事务 (UPDATE/INSERT)
       v
+--------------+
| MySQL 主库   |
+-------+------+
        |
        | 2. 生成行级 binlog (ROW 模式)
        v
+--------------+
| Canal / DTS  | (伪装成 MySQL Slave 实时 dump binlog 解析数据变更)
+-------+------+
        |
        | 3. 发送数据变更事件消息 (Key, Type, NewVal)
        v
+--------------+
| Kafka / MQ   | (高吞吐、持久化、支持消息重试与 ACK)
+-------+------+
        |
        | 4. 消费者拉取事件
        v
+------------------------+
| 缓存刷新服务 (Consumer) | ---- 5. 执行 redis.delete(key) ----> [ Redis 集群 ]
+------------------------+      (若删除失败，走 MQ 阶梯重试机制，
                                 保证 100% 投递成功)
```

**方案收益**：
1. **彻底解耦**：业务代码只需聚焦保证 MySQL 本地事务的 ACID，无需关心 Redis 挂掉或网络异常；
2. **高可靠重试保障**：借助 MQ 的重试队列与死信队列，即使 Redis 短暂宕机，消息也不会丢失，恢复后消费继续保证最终一致；
3. **主从同步延迟天然友好**：Canal 挂在 MySQL 从库或直接基于主库 binlog 解析，从根源规避了读写分离导致主从读脏问题。

## 可能被追问的点

- **如果业务对一致性要求极高（如银行账户余额），缓存双写方案还能用吗？**
  - 如果必须绝对强一致性，应**直接读写数据库主库**并利用数据库行锁（`SELECT FOR UPDATE`），不宜引入缓存；
  - 或者使用**分布式锁（Redisson Lock）**在读写时将同一个 Key 的读写操作强行串行化，但这会严重牺牲系统并发吞吐量。
- **Redis 缓存击穿、穿透、雪崩对双写一致性有什么连锁反应？**
  - **缓存穿透**：查询必定不存在的 Key。应对方案：布隆过滤器（BloomFilter）或缓存空对象（设置短 TTL 1~2分钟）；
  - **缓存击穿**：热点 Key 正在双写被删除的瞬间，几十万并发同时打到 MySQL。应对方案：互斥锁（Mutex Lock / `SETNX`），仅允许一个读线程查库重构缓存，其余线程自旋等待；
  - **缓存雪崩**：大量 Key 设置了相同的过期时间，同一时间集中失效。应对方案：TTL 增加随机抖动范围（如 `base_ttl + randint(60, 300)`）。
- **采用 Canal 方案，binlog 消费存在秒级延迟，在这几百毫秒内用户看到旧数据怎么答复？**
  - 产品设计层面做妥协：C 端非强一致性页面通过前端 UI 状态乐观展示（更新后前端直接将状态置为“已提交”，不重新发起全量拉取）；
  - 核心对账与敏感变更走数据库直连校验。

## 结合自己项目的例子

在公司自动化测试平台的执行流水线配置模块中，平台将测试套件的配置策略（如重试次数、并行度、环境变量池）缓存在 Redis 中以承接海量 Worker 节点的秒级读取。

- **问题现象**：
  - 测试管理者修改了套件并发策略（从 4 并发改为 1 并发），点击保存后。随后启动的分布式任务依然以 4 并发在执行，偶发出现 10% 的几率读到了旧配置。
  - **排查**：原代码采用了“先删缓存，再更新数据库”。在写数据库因外键校验耗费 80ms 的瞬间，CI 系统的定时探活任务并发读取了该配置，因 Cache Miss 触发读库并回写了尚未提交的旧数据，导致脏数据常驻达 1 小时（原 TTL 为 3600 秒）。
- **落地改造**：
  1. **代码重构**：将配置变更调整为「先更新 DB 事务提交，再显式调用 `redis.delete`」；
  2. **引入动态 TTL 防护**：针对此高频变更的元数据，设置较短的兜底 TTL（5 分钟），并添加基础互斥锁重建机制；
  3. **架构升级为 Canal 同步**：接入公司中台 Canal 服务，将配置变更表 Binlog 推送至 Kafka，统一由 DataSync 消费组件驱动 Redis 键淘汰。
- **成效**：彻底根除了流水线偶发读脏配置导致的脏运行，配置变更缓存一致性达到 99.999% 的可观察稳定性。
