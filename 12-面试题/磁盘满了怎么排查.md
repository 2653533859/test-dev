# 磁盘满了怎么排查

> 「服务写日志报 No space left on device」，从分区定位到目录下钻再到隐藏占用的完整排查链。

## 30 秒回答骨架

三步走，外加两个「df 和 du 对不上」的特殊情况：

1. **`df -h` 先定位是哪个分区满了**，别一上来就 `du`——满的可能是 `/var` 而你在 `/home` 找了半天。
2. **`du -sh /* | sort -rh | head` 逐层下钻**，从根往下一层层缩小范围，直到找到具体的大文件或大目录。
3. **确认后再处理**：日志类先 `truncate` 或做轮转，临时文件直接删，业务数据先备份再动。

两个坑：`df` 显示满但 `du` 加起来对不上，通常是**文件已删除但进程句柄没释放**，用 `lsof +L1` 找；空间还剩很多却报磁盘满，是 **inode 耗尽**，用 `df -i` 看。

## 展开

### 第一步：df -h 定位分区

```bash
df -h
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/vda1        40G   38G     0 100% /
# /dev/vdb1       200G   12G  188G   7% /data
```

关键是看 `Use%` 和 `Mounted on`。上面这台机器根分区满了，而挂了 200G 的 `/data` 还很空——典型的「日志没写到数据盘」配置问题。

### 第二步：du 逐层下钻

不要直接 `du -sh /* `一把梭到底（大目录会跑很久），按层收敛：

```bash
# 第一层
du -sh /* 2>/dev/null | sort -rh | head -10
# 命中 /var 之后再下一层
du -sh /var/* 2>/dev/null | sort -rh | head -10
# 直到定位到 /var/log/app
du -sh /var/log/app/* | sort -rh | head -10
```

参数含义：`-s` 汇总不展开、`-h` 人类可读、`sort -rh` 按人类可读单位倒序（`-h` 让 `1.5G` 排在 `900M` 前面）。`2>/dev/null` 屏蔽 `/proc` 之类的权限报错。

也可以直接找大文件：

```bash
find / -xdev -type f -size +500M -exec ls -lh {} \; 2>/dev/null | sort -k5 -rh | head
```

`-xdev` 很重要，表示不跨越文件系统边界，避免顺着挂载点跑到别的盘上白找。

### 第三步：处理

日志文件**不要用 `rm`**。如果进程正持有这个 fd，`rm` 之后空间不会释放（见下文），而且日志直接断掉。正确做法是清空内容保留 inode：

```bash
# 清空但保留文件与 inode，进程继续往里写不受影响
truncate -s 0 /var/log/app/app.log
# 或
: > /var/log/app/app.log
```

长期方案是配 `logrotate`，按天或按大小切割并只保留 N 份。

### 特殊情况一：df 与 du 对不上（已删除文件被占用）

Linux 删除文件只是删掉目录项（硬链接数 -1）。只要还有进程持有该文件的 fd，inode 与数据块就不会回收，`du` 遍历目录树自然统计不到，但 `df` 读的是文件系统元数据，照样算它占着。

```bash
lsof +L1
# COMMAND  PID USER   FD   TYPE DEVICE SIZE/OFF NLINK NODE NAME
# java    2341 app    3w   REG  253,1  21474836     0  918 /var/log/app/app.log (deleted)
```

`NLINK` 为 0 且路径带 `(deleted)` 就是它。解法两种：重启（或 reload）持有它的进程；或者在不方便重启时，直接把那个 fd 清空：

```bash
: > /proc/2341/fd/3
```

### 特殊情况二：inode 耗尽

空间还剩几十 G，但创建文件报 `No space left on device`：

```bash
df -i
# Filesystem      Inodes   IUsed IFree IUse% Mounted on
# /dev/vda1      2621440 2621440     0  100% /
```

原因基本都是某个目录堆了海量小文件（session 文件、临时图片、未清理的用例产物）。找出小文件最多的目录：

```bash
for d in /var/*; do echo "$(find "$d" -xdev -type f 2>/dev/null | wc -l) $d"; done | sort -rn | head
```

删除时用 `find ... -delete` 或 `xargs -0 rm`，直接 `rm -rf dir/*` 在文件数太多时会因参数列表过长报 `Argument list too long`。

## 可能被追问的点

- **为什么 `rm` 了大日志空间没释放？** 上面「已删除文件被占用」那段就是答案，追问点在于能不能说出 inode 与硬链接计数的机制。
- **`du -sh` 和 `ls -l` 显示的大小为什么不一样？** `ls` 看的是文件逻辑大小，`du` 看的是实际占用的块数。稀疏文件（如预分配的数据库文件）逻辑大小远大于实际占用；反之极小的文件也会占满一个块（通常 4K）。
- **生产上能不能直接删日志？** 不能上来就删。先确认是否有采集程序还在读、是否属于需要留存的审计日志；优先 `truncate` + 补 `logrotate`。
- **怎么提前预防？** 监控加磁盘使用率告警（阈值 80%），日志强制轮转，把日志目录挂到独立数据盘，CI 产物目录定期清理。
- **容器里磁盘满怎么办？** 多半是镜像层与容器可写层堆积，`docker system df` 看分布，`docker system prune` 清理悬空镜像与停止的容器；也可能是容器内进程写了没挂卷的路径，撑爆宿主机的 `/var/lib/docker`。

## 结合自己项目的例子

在商城中台项目里，我维护的 Jenkins 构建机凌晨集体挂了，接口自动化任务全部 fail，报错是 `IOError: [Errno 28] No space left on device`。

我的排查过程：

1. `df -h` 看到根分区 100%，而挂载的 `/data` 只用了 7%。
2. `du -sh /var/* | sort -rh | head` 定位到 `/var/lib/jenkins/workspace` 占了 26G。
3. 再下钻发现是 UI 自动化任务每次失败都存截图和 Playwright trace，任务保留策略又设成了「保留 100 次构建」，累积了两个月。
4. 清理时先 `truncate` 了正在写的 `jenkins.log`，产物目录用 `find workspace -name "trace-*.zip" -mtime +7 -delete` 按时间清。

清完发现 `df` 只降到 88%，`du` 加起来对不上。`lsof +L1` 查出 Jenkins 主进程还持有一个 3.8G 的已删除日志文件（之前有同事直接 `rm` 过），reload 之后空间才真正回收。

后续我做了三件事收尾：

- 构建保留策略改成「保留 15 次构建 / 7 天」，产物只在失败时归档。
- `logrotate` 给 Jenkins 日志配了按 100M 切割、保留 5 份。
- 在流水线里加了一个 pre-check stage，磁盘使用率超过 85% 直接告警到钉钉群，不再等到构建失败才发现。

从那以后这类问题再没阻塞过夜间回归。这个例子我一般会强调最后一段——面试官想听的不是你会敲 `df`，而是你有没有把一次故障转成一条防线。
