# 自我介绍怎么讲

> 2 分钟，落点在测开能力而不是项目罗列。这段决定了面试官接下来往哪个方向挖。

## 30 秒回答骨架

自我介绍不是简历复述，它的真实作用是**给面试官递刀子**——你希望他往哪问，就在这里埋哪个钩子。

四段式结构，总时长控制在 **90~120 秒**：

1. **一句话定位（10 秒）**：几年经验 + 做什么方向 + 技术栈关键词。
2. **能力主线（40 秒）**：挑 2 个最能代表测开能力的事，带数字。不要罗列所有项目。
3. **技术栈（20 秒）**：分「熟练」和「了解」两档说，别把所有词都说成精通。
4. **求职动机与匹配（20 秒）**：为什么看这个岗位，我哪部分经历和它对得上。

**最忌讳的三件事**：从大学开始讲、把每个项目都过一遍、通篇形容词没有数字。

## 展开

### 参考稿（按我自己的经历写）

> 面试官好，我叫 XX，做测试开发 3 年，目前在一家电商 SaaS 公司负责商城中台的质量保障，主要覆盖订单和营销两条业务线。
>
> 这三年我主要做了两件事。**一是从零搭了一套接口自动化框架**，用 pytest 加 Allure，做了分层设计和数据驱动，现在有 810 条用例，接进 Jenkins 每天跑，全量回归从原来人工 2 天压到 11 分钟，上线前的回归缺陷拦截率从 60% 提到 92%。**二是治理 UI 自动化的稳定性**，接手时夜间跑批通过率只有 70%，我用 hook 把失败原因量化分类，发现 96% 是脚本问题不是产品问题，针对性改了等待策略和 Page Object，通过率提到 96.8%，单轮从 52 分钟降到 23 分钟。
>
> 技术栈上，**Python、pytest、requests 是我日常写代码用得最多的**；Selenium 和 Playwright 都做过项目落地；数据库能独立看执行计划做 SQL 优化；CI 这块 Jenkins 和 GitHub Actions 都配过完整流水线，Docker 用来固化测试环境。性能测试用 JMeter 做过大促压测，安全这块能做基础的 OWASP 冒烟。
>
> 我看贵司这个岗位提到要做**测试平台建设**，这正好是我下一步想深入的方向——我现在的框架已经到了「工具化」的天花板，再往上需要平台化才能让不写代码的同学也用起来。所以想过来做这件事。

念一遍大约 100 秒。

### 每一段的设计意图

**第一句定位**：给面试官一个「标签」，让他知道该按什么级别的问题问你。「3 年 + 电商 + 中台 + 订单营销」这几个词已经能让他判断业务复杂度。

**能力主线只讲两件事**：一件体现「从 0 到 1 的建设能力」（搭框架），一件体现「治理和优化能力」（稳定性治理）。这两类是测开岗最核心的两种能力。每件事都是「原来什么样 → 我做了什么 → 现在什么样」，全部带数字。

**数字是钩子**。说「92% 拦截率」，面试官大概率会追问「这个数怎么算的」；说「96% 是脚本问题」，他会问「你怎么统计的」。**这些追问你都提前准备过，等于把面试引导到了自己的主场。**

**技术栈分档说**。「日常用得最多」「都做过项目落地」「能做基础的」——三个层次清晰，避免了「我都会」带来的全面被挖风险。诚实分档反而显得可信。

**动机段要和 JD 对齐**。提前读 JD，挑一条你真的想做且有基础的，说清「为什么现在想做这件事」。这段的潜台词是「我不是海投，我认真看过你们」。

### 针对不同面试官调整重点

| 面试官 | 侧重 | 调整 |
|--------|------|------|
| HR 初面 | 稳定性、沟通、动机 | 弱化技术细节，强化「为什么离职」「为什么选这里」 |
| 技术一面 | 硬技能、代码能力 | 展开框架设计的取舍，主动提可以看代码/画架构 |
| 技术二面/主管 | 影响力、推动力、体系化 | 强调跨团队推动（推前端加 testid、推开发改规范）、团队收益 |
| 总监/交叉面 | 视野、业务理解 | 从「质量如何支撑业务目标」的角度讲，谈质量体系而非工具 |

**同一段经历，讲给不同的人要有不同的落点。** 搭框架这件事，对技术面讲「怎么分层、为什么这么分」，对主管面讲「怎么推动 6 个人都用起来、怎么衡量收益」。

### 应届/转岗怎么改

没有工作项目的话，把「能力主线」换成：

- **一个完整的自驱项目**：不要用教程里的 demo，要有自己的设计取舍。比如「我给某个开源项目写了接口自动化，覆盖了 40 个接口，发现并提了 3 个 issue，其中 1 个被合并」。
- **一次深度学习经历**：讲清「我为什么要弄懂这个」以及「弄懂之后解决了什么」。比如为了搞清楚一个偶发失败，把 Selenium 的等待机制源码读了一遍。

从手工测试转测开的，重点讲**「我用代码解决了自己工作中的什么重复劳动」**——这是最有说服力的转型证据，比「我学了 Python」强一百倍。

## 可能被追问的点

- **「你说的 92% 拦截率是怎么算的？」** 必须能答：上线前测试环境发现的缺陷数 /（上线前发现 + 上线后 1 个月内暴露的同类缺陷数）。数据来源是 Jira 的缺陷单，按「发现阶段」字段统计。**任何一个你说出口的数字，都要能说清口径和来源。**
- **「为什么从上家离职？」** 讲发展方向不匹配，不讲人和事的负面。比如「现在的框架已经做到工具化的上限，公司短期没有平台化的规划，我想在这个方向再走一步」。绝不吐槽前东家。
- **「你觉得自己最大的短板是什么？」** 说一个真实存在、但正在改进且不致命的短板。比如「大数据量的性能调优我只做到能定位、还不能深入到 JVM 参数级别的优化，最近在补 GC 相关的知识」。不要说「我太追求完美」这种假谦虚。
- **「介绍一下你最熟悉的一个项目」** 这其实是自我介绍的延伸，见 [[最有成就感的项目怎么讲]]。
- **「你平时怎么学习？」** 给具体载体：在维护一个知识库、跟哪几个源、最近在读什么。空说「我会看文档」没有说服力。

## 结合自己项目的例子

我准备自我介绍的过程本身可以讲一下，因为它体现了「怎么把经历结构化」的方法。

最早我的自我介绍是流水账：把商城中台、支付重构、App 上线三个项目各讲两句，讲完 3 分半钟，面试官面无表情，然后问「那你具体做了什么技术上的事？」——**说明我讲了一堆东西但没有一个记住的点。**

后来我做了三件事重写：

**第一步，把三年经历拆成事件清单。** 我按季度把做过的事列出来，一共 27 条，然后给每条打标签：是「从 0 到 1」还是「优化治理」还是「日常维护」。日常维护那类（写用例、跑回归）直接全部删掉——**那是职责不是亮点。**

**第二步，给剩下的事找数字。** 这一步最费劲。搭框架这件事我原来只会说「提升了效率」，为了找数字我翻了 Jenkins 的历史构建记录（拿到了耗时从 2 天到 11 分钟的对比）、翻了 Jira 导出的缺陷数据（算出了拦截率）。**过程中我发现有些自认为的"成果"根本拿不出数据，那些就不敢往简历上写了**，这本身也是一次筛选。

**第三步，按岗位准备两个版本。** 投「测试开发」岗的版本，能力主线放框架建设和稳定性治理；投「质量工程/测试架构」岗的版本，把第二件事换成「推动质量门禁落地，让 3 个业务组接入了统一的 CI 模板」——同样是真实的事，但落点从「我技术好」变成「我能影响一个组织」。

改完之后最直接的变化：**面试官开始顺着我给的数字往下问了**。有一次面试，前 20 分钟全在聊「96% 是脚本问题」这个统计是怎么做的、hook 怎么写的、分类维度怎么定的——那 20 分钟我答得极其顺，因为都是我真做过并且提前想清楚的。

我的结论是：**自我介绍的质量，取决于你有没有认真复盘过自己的经历，而不是取决于你的话术。** 话术只是把复盘结果组织出来。所以准备面试的正确顺序是：先复盘 → 再找数字 → 最后才是措辞。
