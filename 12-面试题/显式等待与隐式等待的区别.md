# 显式等待与隐式等待的区别

> Web 自动化必考题。能答出「混用会导致超时相乘」，就比背概念的人高一层。

## 30 秒回答骨架

三种等待的定位完全不同：

- **强制等待** `time.sleep(n)`：无条件死等 n 秒。元素早就出来了也要等满，网络慢了又不够用，**应该禁用**。
- **隐式等待** `driver.implicitly_wait(10)`：全局生效一次，作用于**所有 `find_element` 调用**。找不到元素时在超时内轮询重试，只能等「元素出现在 DOM 里」这一个条件。
- **显式等待** `WebDriverWait(driver, 10).until(EC.element_to_be_clickable(...))`：针对**特定条件**等待，条件可以是可见、可点击、文本出现、元素消失、alert 弹出等，也可以自定义。

结论：**显式等待是首选**，因为 UI 自动化的失败大多不是「元素不在 DOM 里」，而是「在 DOM 里但被遮挡 / 还没渲染 / 还没绑定事件」。**两者不要混用**，混用时超时时间可能相乘，一个本该 10 秒失败的用例会等 60 秒甚至更久。

## 展开

### 隐式等待的实际行为

```python
driver.implicitly_wait(10)      # 设置一次，整个 driver 生命周期有效
driver.find_element(By.ID, "kw")
```

实现在 **WebDriver 服务端**（浏览器驱动进程）：收到 `findElement` 命令后，如果没找到，驱动会以约 500ms 的间隔轮询 DOM，直到找到或超时抛 `NoSuchElementException`。

三个关键限制：

1. **只判断「元素存在于 DOM」**，不判断可见、不判断可点击。元素 `display:none` 时它照样返回成功，接着 `click()` 抛 `ElementNotInteractableException`。
2. **对 `find_elements`（复数）会等满全程**。因为返回空列表不算失败，所以「断言元素不存在」的场景会白等 10 秒。
3. **对元素状态变化无效**。等待「loading 遮罩消失」「按钮从灰变亮」这类需求，隐式等待完全帮不上。

### 显式等待的实际行为

```python
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

wait = WebDriverWait(driver, 10, poll_frequency=0.5,
                     ignored_exceptions=(StaleElementReferenceException,))
btn = wait.until(EC.element_to_be_clickable((By.CSS_SELECTOR, "[data-testid=submit]")))
btn.click()
```

实现在**客户端**：`until` 里是一个循环，每隔 `poll_frequency` 调一次传入的可调用对象，返回真值就退出并返回该值，超时抛 `TimeoutException`。`ignored_exceptions` 里的异常在轮询期间会被吞掉继续重试——这也是它能扛住 `StaleElementReferenceException` 的原因。

常用条件对照：

| 场景 | 条件 |
|------|------|
| 元素在 DOM 里 | `presence_of_element_located` |
| 元素可见（有尺寸、非 hidden） | `visibility_of_element_located` |
| 元素可点击（可见 + enabled） | `element_to_be_clickable` |
| loading 遮罩消失 | `invisibility_of_element_located` |
| 文案渲染完成 | `text_to_be_present_in_element` |
| 新窗口打开 | `number_of_windows_to_be(2)` |
| 弹窗出现 | `alert_is_present` |

条件不够用就自定义，任何「返回真值或 None」的可调用对象都行：

```python
def element_attribute_to_be(locator, attr, value):
    def _predicate(driver):
        el = driver.find_element(*locator)
        return el.get_attribute(attr) == value and el
    return _predicate

wait.until(element_attribute_to_be((By.ID, "status"), "data-state", "ready"))
```

### 为什么混用会「超时相乘」

隐式等待改变了 `find_element` 的行为：**它不再立即失败，而是先阻塞 10 秒**。而显式等待的每一轮轮询内部都要调 `find_element`。

于是发生这样的事：

```python
driver.implicitly_wait(10)
WebDriverWait(driver, 30, poll_frequency=0.5).until(
    EC.visibility_of_element_located((By.ID, "not-exist"))
)
```

- 显式等待第 1 轮：调 `find_element` → 隐式等待阻塞 10 秒 → 抛 `NoSuchElementException` → 被 `until` 吞掉 → 本该 0.5 秒的一轮实际花了 10 秒。
- 第 2 轮：又是 10 秒。
- 显式等待的 30 秒总超时是在**每轮开始前**检查的，所以实际耗时会在 30 秒边界上超出一整轮，接近 40 秒才抛 `TimeoutException`。

更糟的是这个行为在不同浏览器驱动、不同 Selenium 版本下表现不一致（有的实现里两者叠加得更离谱）。**官方文档明确写了不要混用。**

所以我的做法是：**在创建 driver 的 fixture 里就把隐式等待设为 0**，框架内统一走显式等待封装。

```python
@pytest.fixture
def driver():
    d = webdriver.Chrome(options=opts)
    d.implicitly_wait(0)        # 显式禁用，避免团队里有人偷偷开
    yield d
    d.quit()
```

### 封装到 BasePage 里

用例层不应该出现 `WebDriverWait`，都收到 BasePage：

```python
class BasePage:
    def __init__(self, driver, timeout=10):
        self.driver = driver
        self.wait = WebDriverWait(
            driver, timeout,
            ignored_exceptions=(StaleElementReferenceException,),
        )

    def click(self, locator):
        self.wait.until(EC.element_to_be_clickable(locator)).click()

    def type(self, locator, text):
        el = self.wait.until(EC.visibility_of_element_located(locator))
        el.clear()
        el.send_keys(text)

    def wait_loading_gone(self):
        self.wait.until(EC.invisibility_of_element_located(LOADING_MASK))
```

这样等待策略是框架层的统一决策，不是每个人写用例时的自由发挥。

### Playwright 的自动等待

Playwright 把等待做进了框架内核：每个操作前自动执行 **actionability 检查链**——元素 attached → visible → stable（位置不再变动）→ enabled → 可接收事件（未被遮挡）→ 才执行动作，默认超时 30 秒。

```python
page.get_by_role("button", name="提交").click()   # 不需要写任何等待
expect(page.get_by_text("提交成功")).to_be_visible()  # 断言自带重试
```

所以 Playwright 用例里几乎看不到等待代码。这也是选型时它相对 Selenium 最大的体验优势。要注意 `force=True` 会跳过这套检查——能让用例"通过"，但也就放弃了框架给的保护，**用它之前先想清楚是不是在掩盖真实的产品问题**。

## 可能被追问的点

- **为什么不能用 `sleep`？** 三个理由：等不够时偶发失败、等太久时拖慢全量（100 条用例每条多等 3 秒就是 5 分钟）、掩盖真实的性能问题。唯一勉强能用的场景是等一个没有任何 DOM 信号的动画结束，而这本身就说明前端缺少可测性标识。
- **元素时有时无怎么办？** 先分类：DOM 未渲染完 → 显式等待；元素被遮罩挡住 → 等遮罩消失；元素在 iframe 里 → 先 switch；元素被重新渲染 → `StaleElementReferenceException`，加进 `ignored_exceptions` 或改成每次重新定位；异步接口慢 → 等待具体的业务文案出现而不是等元素。
- **`StaleElementReferenceException` 的根因？** 元素引用指向的是一个已经从 DOM 树上被移除/替换的节点（Vue/React 重渲染极常见）。解法是**不要缓存 WebElement**，每次操作前重新定位；Playwright 的 Locator 天生惰性求值，不存在这个问题。
- **显式等待超时时间设多少合适？** 通用操作 10 秒，明确的慢操作（导出、支付回调）单独放大到 30~60 秒，不要全局调大——全局调大会让真正的 bug 也拖着不报错。
- **`presence` 和 `visibility` 选哪个？** 要交互就用 `visibility` 或 `clickable`；只是要读 `textContent` 或判断存在性，`presence` 更快。
- **页面加载本身怎么等？** `driver.set_page_load_timeout(30)`，配合 `pageLoadStrategy`（`normal`/`eager`/`none`）。SPA 应用 `load` 事件早就触发了但内容还没渲染，所以还是要靠显式等待具体元素。

## 结合自己项目的例子

商城中台的后台管理端有 120 条 UI 用例，接手时夜间跑批的通过率长期在 70% 左右，每天早上要花 1 小时人工确认哪些是真 bug、哪些是脚本飘。团队里当时的普遍做法是「失败了就加 `sleep(3)`」，代码里搜出来 87 处 sleep。

我做了一轮专项治理：

**第一步：量化失败原因。** 用 `pytest_runtest_makereport` 钩子把每次失败的异常类型、页面截图、当前 URL 落到一份 CSV 里，跑了一周攒了 214 条失败记录，分类统计：

| 异常类型 | 占比 | 主要成因 |
|---------|------|---------|
| `ElementClickInterceptedException` | 41% | 全局 loading 遮罩未消失就点击 |
| `StaleElementReferenceException` | 26% | 表格数据刷新后复用了旧引用 |
| `TimeoutException` | 18% | 部分是真慢，部分是等错了条件 |
| `NoSuchElementException` | 11% | 动态 class 定位不稳 |
| 真实产品 bug | 4% | —— |

**96% 的失败是脚本问题，这个数据本身就说服了 leader 给我时间做治理。**

**第二步：针对性改造。**

- 在 `BasePage.click()` 里内置「先等 loading 遮罩不可见，再等元素可点击」，一次性干掉 41% 的失败。
- `WebDriverWait` 统一加 `ignored_exceptions=(StaleElementReferenceException,)`，并把 PO 里所有缓存的 `self.xxx_element` 改成方法内重新定位，解决 26%。
- 删掉全部 87 处 `sleep`，替换成具体条件的显式等待。清理时发现有 3 处 sleep 掩盖的其实是真实性能问题——商品列表页在 5000 条数据下要 8 秒才渲染完，提了性能优化单。
- 定位不稳的部分推动前端加了 `data-testid`，先在改动最频繁的 12 个页面落地。

**第三步：兜底而非依赖兜底。** 加了 `pytest-rerunfailures --reruns 1`，但同时在 CI 上统计「重跑后才通过」的用例数并输出到报告——这个数字如果超过 5%，说明治理退化了，要重新看。**重跑是安全网，不是解决方案，这个态度面试时要明确表达出来。**

结果：通过率从 70% 提到 96.8%，单轮耗时从 52 分钟降到 23 分钟（删 sleep 贡献最大），早上的人工确认时间从 1 小时降到 10 分钟以内。
