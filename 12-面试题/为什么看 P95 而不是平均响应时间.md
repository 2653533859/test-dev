# 为什么看 P95 而不是平均响应时间

> 平均值会被长尾稀释，掩盖掉真正受影响的那批用户。这题答好了能顺势聊到整个指标体系。

## 30 秒回答骨架

**平均值不可靠的根本原因是响应时间的分布是长尾的、右偏的，不是正态分布。**

- 平均值会被大量快请求稀释：900 个请求 50ms、100 个请求 3000ms，平均只有 345ms，看起来还行，但**有 10% 的用户等了 3 秒**。
- 平均值无法反映最差体验，而用户感知的是「我这次点下去卡了」，不是「大家平均多快」。
- P95 的含义是「95% 的请求快于这个值」，它直接对应**服务质量承诺（SLA）**：我承诺 95% 的用户在 200ms 内拿到响应。

实践里我一般同时看 **P50（典型体验）、P95（SLA 基线）、P99（最差体验/长尾）、max（异常点）**，再配合 TPS 和错误率一起判断。只报平均值的性能报告在我这儿是不合格的。

## 展开

### 一组数据看穿平均值

假设 1000 个请求：

```text
900 个 →   50 ms
 90 个 →  800 ms
 10 个 → 5000 ms

平均值 = (900×50 + 90×800 + 10×5000) / 1000 = 167 ms   ← 看起来很好
P50   =   50 ms
P90   =   50 ms
P95   =  800 ms   ← 真相开始显现
P99   =  800 ms
P99.9 = 5000 ms   ← 有用户等了 5 秒
max   = 5000 ms
```

如果只汇报「平均响应时间 167ms，达标」，那 100 个体验糟糕的用户就被彻底藏起来了。而在真实业务里，这 10% 往往不是随机分布的——**可能全部集中在数据量最大的头部商户身上**，也就是最重要的那批客户。

### 各分位数分别说明什么

| 指标 | 含义 | 用途 |
|------|------|------|
| P50（中位数） | 一半用户比它快 | 典型体验；和平均值差距大说明分布严重偏斜 |
| P90 / P95 | SLA 常用基线 | 对外承诺、容量规划的依据 |
| P99 | 长尾 | 反映 GC 停顿、慢 SQL、缓存 miss、连接池等待 |
| P99.9 / max | 极端点 | 定位偶发问题；样本少时噪声大，别单独下结论 |
| 平均值 | 参考 | 只和历史平均值比趋势，不做绝对判断 |
| 标准差 | 离散度 | 越大越说明系统不稳定，比平均值本身更有信息量 |

**平均值和 P95 的比值是个好用的健康度信号**：正常系统 P95 大约是平均值的 2~3 倍，如果到了 10 倍以上，说明存在明显的长尾问题，应该去查 GC、锁竞争、慢查询、外部依赖超时。

### 长尾从哪来

排查 P99 高但 P50 正常时，按这几个方向查：

1. **JVM Full GC / STW**：GC 日志里看停顿时长与频率，`jstat -gcutil` 观察老年代增长。
2. **慢 SQL**：某些参数下走不到索引（比如大商户的数据量触发了全表扫），`long_query_time` 调到 0.5 秒抓。
3. **缓存 miss**：热点数据命中缓存 50ms，miss 掉库 800ms，miss 率就是长尾比例。
4. **连接池 / 线程池排队**：池子打满后请求排队，队列越长尾巴越长。看池的 active/wait 指标。
5. **外部依赖抖动**：下游服务或第三方接口偶发慢，超时时间设得太长会把长尾拉得很远。
6. **压力机自身瓶颈**：这是最容易误判的一类，见下文。

### 三个核心指标的关系

**并发用户数 × TPS × 响应时间**满足利特尔法则（Little's Law）：

```text
并发数 ≈ TPS × 响应时间(秒)
```

例：TPS 500、平均响应 0.2s，则系统内约有 100 个请求在处理中。

由此推出压测曲线的三个阶段：

1. **轻负载区**：并发增加，TPS 线性上升，响应时间基本不变。
2. **拐点（最佳并发数）**：TPS 达到峰值，响应时间开始明显上升。**这就是系统的最大处理能力，容量规划取这个点。**
3. **过载区**：并发继续增加，TPS 不升反降（资源争抢、上下文切换、超时重试放大），响应时间陡增，错误率上涨。

**性能测试的目标就是找到这个拐点，而不是「压到系统崩溃」。**

### 压力机自身是瓶颈的表现

这是常考的一个追问点，几个典型信号：

- 压力机 CPU 跑满（尤其 JMeter GUI 模式或开了大量监听器时）。
- 服务端 CPU/内存/IO 都很闲，但 TPS 就是上不去。
- 加压力机（分布式压测）后 TPS 明显上升 —— 最直接的验证方法。
- 压力机网卡带宽打满（`sar -n DEV 1` 看），或本地端口耗尽（大量 TIME_WAIT，`ss -s` 看）。
- JMeter 自身 GC 频繁，`jmeter.log` 里有 `OutOfMemory`。

规避：命令行模式跑（`jmeter -n -t plan.jmx -l result.jtl -e -o report`）、压测时关闭「察看结果树」和「用表格察看结果」这类监听器、`HEAP` 调到 `-Xms2g -Xmx2g` 以上、结果只写 jtl 不写 xml。

## 可能被追问的点

- **P95 怎么算的？** 把所有请求的响应时间升序排列，取第 95% 位置上的值。注意：**多台压力机的 P95 不能直接取平均**，必须把原始数据合并后重新计算——这是分布式压测出报告时最常见的错误。
- **TPS 和 QPS 的区别？** TPS 是每秒事务数，一个事务可能包含多个请求（如「下单」= 查库存 + 创建订单 + 扣减库存）；QPS 是每秒请求数。JMeter 里用「事务控制器」来定义事务边界，报告口径要和业务对齐。
- **目标 TPS 怎么推算？** 常用二八原则：日均业务量 × 80% / (24×3600 × 10%) = 峰值 TPS。比如日订单 100 万，峰值 TPS ≈ 100万×0.8/(86400×0.1) ≈ 93。再乘上 2~3 倍余量作为压测目标。
- **稳定性测试压多久，看什么？** 一般按峰值的 70%~80% 压 8~24 小时。重点看**趋势**而非绝对值：内存是否只涨不降（泄漏）、TPS 是否随时间下滑、连接数/线程数是否单调增长、GC 频率是否变高、磁盘是否被日志撑满。
- **响应时间变长、TPS 上不去，怎么一步步定位？** 按链路从外到内：压力机 → 网络（带宽、丢包） → 负载均衡 → 应用（CPU、GC、线程池、锁） → 中间件（连接池、MQ 堆积、缓存命中率） → 数据库（慢 SQL、锁等待、连接数）。每一层都有对应的观测手段，**关键是每次只改一个变量**。
- **think time 要不要加？** 要。不加 think time 压出来的是「系统极限」，不是「真实业务场景」。做容量规划时必须按真实用户行为节奏（浏览 3 秒、填表 10 秒）建模，否则算出来的并发用户数会严重偏低。

## 结合自己项目的例子

商城中台大促前做压测，商品详情页接口的目标是「峰值 3000 TPS，P95 < 200ms」。

第一轮压测结果：TPS 3200 达标，**平均响应时间 88ms**，看起来很漂亮。但我拉出分位数一看：

```text
P50 =  35 ms
P90 =  62 ms
P95 = 145 ms
P99 = 2400 ms   ← 这里有问题
max = 8900 ms
```

平均值 88ms 完全掩盖了 P99 的 2.4 秒。按 3000 TPS 算，**每秒有 30 个用户在等 2 秒以上**，大促几小时下来就是几十万次糟糕体验。

**定位过程**：

1. 先看是不是压力机的问题。压力机 CPU 45%、网卡 30%，加一台压力机后 TPS 和分位数都没变化，排除。
2. 看 Grafana 上的应用监控，发现 P99 的尖刺和 **Full GC 的时间点高度重合**，每 90 秒一次、每次 STW 约 1.8 秒。
3. `jmap -histo` 抓了一次堆，占用最大的是一个商品详情的 DTO 对象，`char[]` 巨大。翻代码发现详情接口把商品的**全量富文本描述**（有的商品图文详情有几百 KB）也塞进了列表响应里，即使前端根本不展示。
4. 3000 TPS × 平均 80KB 的对象，年轻代扛不住，大量对象直接晋升老年代，触发频繁 Full GC。

**优化与验证**：

- 详情接口按场景拆字段，列表场景不返回富文本（改动只有几行）。
- 富文本单独走一个懒加载接口 + CDN 缓存。
- 顺带把 JVM 从 CMS 换成 G1，`MaxGCPauseMillis=200`。

复压结果：

```text
TPS = 3600（还涨了）
P50 =  28 ms
P95 =  71 ms
P99 = 118 ms   ← 从 2400ms 降到 118ms
max = 890 ms
```

大促当天实际峰值 2700 TPS，P99 稳定在 130ms 以内，零性能故障。

我在性能报告的模板里也做了一个改动：**取消「平均响应时间」作为验收指标，改成 P95 + P99 双指标，并强制附上响应时间分布直方图。** 后来这个模板被推广到了整个测试组。面试讲这个案例时，我会强调最后这一步——**发现问题是能力，把发现问题的方式固化成团队标准，才是测开该做的事。**
