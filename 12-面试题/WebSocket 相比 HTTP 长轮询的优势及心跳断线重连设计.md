# WebSocket 相比 HTTP 长轮询的优势及心跳断线重连设计

> 30 秒回答骨架：
> HTTP 长轮询本质上仍是单向短连接，每次交互都要经历三次握手并附带冗余的请求头，且连接关闭后导致大量处于 TIME_WAIT 状态的端口堆积；而 WebSocket 通过一次 HTTP 101 升级建立全双工长连接，后续基于最小仅 2 字节开销的轻量二进制帧传输。
> 保持长连接稳定性必须依赖「双向心跳检测」消除 TCP 半开连接与 NAT 超时剔除；在断线重连时，必须采用「带随机抖动的指数退避算法」，并在重连成功后触发重新订阅与状态重同步，防止重连风暴击垮服务端网关。

## 展开

### 1. 架构与性能对比全景

| 评估维度 | HTTP 长轮询 (Long Polling) | WebSocket (RFC 6455) |
| :--- | :--- | :--- |
| **通信模式** | 伪全双工（客户端挂起等待，拿到一次响应即断开） | **真正的全双工双向直连**，随时相互推拉数据 |
| **单条数据帧开销**| 每次传输携带 1KB~2KB 冗长 Headers | 仅 2~10 字节轻量二进制帧头（高有效载荷比） |
| **延迟表现** | 存在断开重连的建立延迟与队头阻塞 | 毫秒级直达，事件产生即刻推流 |
| **服务端资源** | 高频创建/销毁 Socket，容易耗尽内核端口 | 稳定持有 Socket，但考验每个连接的内存开销与句柄数 |

### 2. 双向心跳保活机制（防假死与 NAT 剔除）

- **为什么 TCP Keep-Alive 不够用？**：TCP 默认的 Keep-Alive 探测周期过长（通常为 2 小时），无法应对移动端 30 秒无流量即被运营商 NAT 表项静默淘汰的场景；
- **Ping/Pong 状态机**：
  - 客户端或服务端每隔 20 秒发送一次 RFC 6455 `0x9` Ping 帧；
  - 对端底层必须在毫秒级内返回 `0xA` Pong 帧；
  - 连续 2~3 个周期未收到应答，判定连接为「TCP 半开假死状态」，主动触发 `close(1001)` 释放 Socket。

### 3. 断线重连与防雪崩设计

```text
网络闪断 (Disconnect)
       │
       ▼
计算重试延迟: Delay = min(30s, BaseDelay * 2^attempt) ± Jitter (随机抖动)
       │
       ▼ 避免全量客户端在同一时刻并发建连
发起新一轮 WebSocket 升级握手
       │
       ▼ 连接成功
触发业务重同步 (Re-sync)
  ├── 补发 Topic 订阅指令 (恢复会话状态)
  └── 携带 last_received_msg_id 补拉离线消息
```

## 可能被追问的点

1. **为什么客户端发给服务端的帧必须加掩码（Mask），而服务端推流不用？**
   - *标准答案*：这是为了防御「缓存投毒（Cache Poisoning）攻击」。早期网络存在大量透明代理缓存，若恶意脚本能通过浏览器向 WebSocket 发送精心构造的明文 HTTP GET 请求，老旧代理可能会将该报文误当成合法请求缓存起来并响应给其他用户。4 字节随机 Mask 异或混淆使得帧在传输链路上完全不可预测，彻底消除了缓存中间件的混淆风险。
2. **如果用户关掉浏览器标签页，服务端没有收到 Close 帧，这个连接如何释放？**
   - *标准答案*：通常由于直接杀进程或网络断开导致 Close 帧丢失，此时连接进入 TCP 半开状态。服务端的读超时或心跳超时检测机制在超出阈值（如 60 秒无心跳）后，底层内核调用会返回 `EPIPE` 或超时错误，应用层框架（如 Netty/Tornado）自动回调 `onClose` 并关闭连接，回收文件句柄与内存。
3. **在自动化测试中，怎么验证 WebSocket 接口没有发生内存泄漏？**
   - *标准答案*：在压测环境中通过 Python 脚本或 JMeter 模拟持续挂起 1 万个长连接并周期性发送心跳。利用 Linux `cat /proc/net/sockstat` 观察 TCP 在线连接数，同时结合 `jstat -gcutil` 连续观测服务端的老年代堆内存与 GC 频率。若每万连接带来的物理内存增长超过安全基线（通常单长连接应小于 20KB~50KB），或者 Full GC 后内存无法回落，则说明存在 Session 引用未释放导致的内存泄漏。

## 结合自己项目的例子

> 在我们主导的电商大促实时直播竞拍看板项目中，前端需要实时接收数万观众的竞价与弹幕推送。
> 早期系统采用 HTTP 长轮询，在大促高峰期服务端被大量瞬时建连压垮，网关大量抛出 504 Gateway Timeout，且客户端经常出现「出价延迟超过 3 秒」的体验投诉。
> 
> 我主导推动了长连接方案的全面重构：
> 1. **全链路迁移至 WebSocket**，并在 Nginx 层配置协议升级与 60s 读取超时保护；
> 2. **在自动化框架中落地高韧性事件流断言库**，引入谓词匹配与滑动窗口机制，消除了长连接测试中因心跳帧交错引发的偶发 Flaky 假报错；
> 3. **客户端实现带抖动的指数退避重连与断线补拉**，在服务端单节点发布重启时，成功避免了 3 万客户端同时并发重连造成的网关击穿，平稳支撑了全网大促零故障交付。
