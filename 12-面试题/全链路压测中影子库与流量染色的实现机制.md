# 全链路压测中影子库与流量染色的实现机制

> 高级测试开发与性能架构师必考题。考察候选人是否具备生产级超高并发压测实操经验，以及数据防污染的架构设计能力。

## 30 秒回答骨架

全链路压测为了在生产环境摸高且不污染业务数据，依靠两大核心技术：
1. **流量染色（Traffic Coloring）**：
   - 压测引擎发起请求时在 Header 中注入统一压测标（如 `x-pressure-test: true`），微服务网关认证后，基于分布式追踪上下文（TraceContext / ThreadLocal）在跨线程、跨 RPC（gRPC/Dubbo）与跨消息队列时向下透传；
2. **影子存储隔离（Shadow Storage）**：
   - 数据访问层中间件（如 ShardingSphere / 动态数据源切面）拦截 SQL 与 Redis 读写，识别到压测标后自动将写操作路由到结构相同但物理隔离的**影子库（Shadow DB）**或影子缓存，外部支付与短信调用由 Mock 挡板切断。

## 展开

### 1. 压测标透传全生命周期

```text
压测引擎 (JMeter)
   │ (Header: x-pressure-test: true)
   ▼
API 网关 (Spring Cloud Gateway / Nginx) ──> 校验鉴权白名单，写入请求分布式 TraceContext
   │
   ▼ RPC (Dubbo / gRPC 附加 Attachment 隐式传参)
用户/订单微服务 ──> 异步线程池通过 TransmittableThreadLocal 避免上下文丢失
   │
   ├─ 查写 DB   ──> 数据库中间件拦截 SQL，判定有压测标 ──> 路由至 shadow_db
   ├─ 读写 Redis ──> 客户端切面自动为 Key 增加 pt: 前缀
   └─ 外部支付   ──> HTTP 客户端过滤器识别压测标 ──> 自动路由至内部 Mock Server
```

### 2. 核心架构防护要点

- **只读场景与回表**：在影子库未预热基础商品数据时，读操作通常路由到生产库（走生产真实索引），而写操作必须严格路由到影子库；
- **MQ 隔离策略**：对于 RocketMQ / Kafka，若消费者未做改造，容易消费影子消息触发下游真实操作。最佳实践是创建同名的 `topic-shadow` 或在消费者监听器中加入切面：若消息体含有压测标，直接走影子逻辑或安全丢弃。

## 可能被追问的点

1. **压测标在线程池里断了怎么办？怎么提前发现？**
   - **答题关键**：采用阿里开源的 `TransmittableThreadLocal`（TTL）包装所有线程池，解决原生 `InheritableThreadLocal` 只能在线程创建时传递、而在线程池复用时上下文无法更新的问题。压测前必须执行**低并发全链路探针巡检**：以单并发打入染色请求，在 APM 系统（SkyWalking）中比对各下游节点的 Span Tags，发现断标节点自动报警并阻断大规模压测。
2. **压测结束后，影子库数据如何处理？**
   - **答题关键**：压测窗口关闭后，通过自动化运维脚本批量执行 `TRUNCATE TABLE` 或清理影子库分片；对于 Redis 影子 Key（`pt:*`），设置较短的全局 TTL，压测结束 24 小时内自动过期淘汰。

## 结合自己项目的例子

> “在我们电商平台的大促全链路压测中，首次试压时发现有一笔压测订单向真实商户发送了真实的短信通知。排查发现是订单履约服务在发送通知时，通过异步消息队列解耦，但发 MQ 的生产端没有把分布式上下文写入消息 Header。我们团队随后联合基础架构部对 MQ 客户端 SDK 进行了切面统一升级，强制实现消息头透明装载上下文，并为第三方短信接入了自动化 Mock 挡板，在后续数万 TPS 的生产全链路压测中实现了生产数据与外部服务 100% 隔离。”
