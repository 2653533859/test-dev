# 分布式链路追踪与自动化测试排障

> 在复杂的微服务拓扑中，告别「接口报错 500 只能找开发逐个服务翻日志」，通过在测试请求中自动注入并透传 W3C TraceContext，实现从失败用例到故障服务、异常堆栈或慢 SQL 的秒级下钻排障。

## 概念

### 微服务黑盒测试的排障泥潭

在单体架构时代，接口自动化测试遇到报错，查单机日志就能迅速定位。而在微服务架构下：

```text
自动化用例 ──> API 网关 ──> 订单服务 ──> 库存服务 ──> 优惠券服务 ──> 支付服务
    │                          │ (RPC)       │ (RPC)        │ (RPC)
    └── 收到 500 Internal ─────┴─────────────┴──────────────┴──── 抛出 NullPointerException
```

测试人员发起一次 `/api/v1/orders/create` 请求，背后可能穿透了 5~8 个微服务和数个中间件。一旦接口断言失败（如返回 500、超时或业务码异常）：

1. **信息孤岛**：外层 HTTP 响应通常被网关脱敏包装成 `{"code": 50000, "message": "系统繁忙"}`，根本看不出是哪一个下游子服务报的错；
2. **日志拼接困难**：测试去 ELK 查日志，由于高并发环境下多台机器日志混杂，在没有唯一链路串联标记的情况下，犹如大海捞针；
3. **性能瓶颈定位低效**：一个接口耗时 2 秒，无法直观判断到底是数据库锁等待、网络抖动，还是某个下级 RPC 方法出现了 **N+1 次循环查询**。

### W3C TraceContext 与 OpenTelemetry 规范

为了统一分布式调用的上下文传播，W3C 制定了标准规范 **Trace Context**，现代微服务观测体系（OpenTelemetry、SkyWalking、Jaeger）均遵循此标准：

`traceparent` 请求头格式（全长 55 字符十六进制）：

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └───────────────┬────────────────┘ └───────┬────────┘ └─┬─┘
           版本号         64-bit Trace ID              Parent Span ID    采样标记
           (固定00)    (全链路全局唯一标识符)         (当前调用节点ID)  (01表示必须采样)
```

- **Trace ID**：整条端到端调用链的全局唯一 ID。只要测试客户端生成该 ID 并注入请求头，后端微服务在跨 HTTP、gRPC、消息队列传递时，就会自动沿用该 ID，并将各环节日志以此 ID 串联；
- **Span ID**：代表调用链中的某一个特定操作片段（例如「订单服务调用数据库查询库存」是一个 Span）。

## 用法

### 1. 测试客户端实现自动链路注入（Python requests 拦截器）

在测试框架的底层 `HttpClient` 中，对每个出站请求自动生成符合 W3C 规范的 `traceparent`，并绑定到当前测试用例的上下文中：

```python
import os
import secrets
import time
import requests


class TracingSession(requests.Session):
    """自带全链路追踪上下文透传能力的测试会话对象"""

    def request(self, method, url, **kwargs):
        headers = kwargs.setdefault("headers", {})

        # 1. 优先复用当前用例的 TraceID，若无则自动生成（16 字节随机 hex）
        trace_id = getattr(self, "current_trace_id", None)
        if not trace_id:
            trace_id = secrets.token_hex(16)
            self.current_trace_id = trace_id

        parent_span_id = secrets.token_hex(8)
        # 01 标记强制要求后端服务采样（Trace Flags: Sampled）
        traceparent = f"00-{trace_id}-{parent_span_id}-01"
        headers["traceparent"] = traceparent
        headers["X-Test-Trace-Id"] = trace_id  # 兼顾部分自研网关

        start_time = time.time()
        try:
            response = super().request(method, url, **kwargs)
            return response
        finally:
            cost_ms = (time.time() - start_time) * 1000
            # 记录请求耗时与 TraceID 供日志和报告消费
            print(f"[{method}] {url} | TraceID: {trace_id} | 耗时: {cost_ms:.2f}ms")
```

### 2. 测试报告集成：失败用例一键直达 APM 链路视图

当断言失败时，在 Allure 报告中自动生成一条可点击的超链接，直接打开公司内部的 SkyWalking 或 Jaeger 大盘：

```python
# conftest.py
import pytest
import allure


@pytest.hookimpl(tryfirst=True, hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()

    if report.when == "call" and report.failed:
        client = getattr(item, "cls_client", None) or getattr(
            item, "func_client", None
        )
        if client and hasattr(client, "current_trace_id"):
            trace_id = client.current_trace_id

            # 拼装 SkyWalking 或 Jaeger 的链路详情 URL
            skywalking_url = f"https://apm.company.internal/trace/{trace_id}"

            # 挂载到 Allure 报告附件
            allure.attach(
                f'<a href="{skywalking_url}" target="_blank">🔗 点击排查全链路日志 (TraceID: {trace_id})</a>',
                name="APM 故障链路排查入口",
                attachment_type=allure.attachment_type.HTML,
            )
```

## 踩坑

1. **API 网关强制重写或过滤 `traceparent`**：
   - *现象*：测试客户端在请求头注入了 `trace_id = "a1b2..."`，但在日志系统搜该 ID 一无所获。
   - *根因*：生产/测试环境的 API 网关（如 Kong、Nginx）配置了默认行为：为防止外网用户恶意伪造 TraceID 污染链路，网关会无脑丢弃外网传入的 `traceparent` 并重新生成。
   - *解法*：与运维/网关团队对齐，在测试或沙箱环境中开启网关的「保留传入链路上下文（`preserve_trace_id`）」策略，或在 Header 中附加 `X-Client-Type: Automated-Test` 白名单标记予以放行。
2. **异步消息队列（RocketMQ / Kafka）丢失链路上下文**：
   - *现象*：主链路 HTTP 接口能查到 Trace，但后续消费者异步处理数据的日志无法串联。
   - *根因*：上游服务在向 MQ 发送消息体时，没有将当前的 `TraceContext` 序列化放入消息的属性（MQ Properties / Kafka Headers）中，消费者拿到消息后只能开启一条全新的空 Trace。
3. **采样率（Sampling Rate）导致高压下 Trace 查无此记录**：
   - *现象*：接口自动化执行时有 TraceID，但点开 Jaeger 却显示「Trace not found」。
   - *根因*：服务端为了降低存储成本配置了 10% 概率采样。
   - *解法*：测试请求头尾部的标志位必须显式置为 `01`（`00-{traceid}-{spanid}-01`），且在配置了自适应采样的系统中设置 `X-B3-Sampled: 1` 标识，强制告知服务端此为必须全量落盘的采样请求。

## 面试怎么答

**Q：微服务接口自动化测试跑出了 500 报错，你们是如何快速定位具体是哪个服务出问题的？**
> 1. **全链路上下文透传**：我们的自动化测试客户端（Session）底层遵循 W3C TraceContext 标准，在每次发送 HTTP/gRPC 请求前，由客户端自动生成唯一的 128 位 `TraceID` 并注入到 `traceparent` 请求头中，并配置强制采样标示 `01`。
> 2. **端到端串联追踪**：微服务内部通过 OpenTelemetry / SkyWalking Agent 自动拦截并将此 `TraceID` 沿调用链（网关 $\rightarrow$ 各微服务 $\rightarrow$ 异步 MQ $\rightarrow$ 数据库）向后传递，并自动打印到所有的业务 log4j/logback 日志行中。
> 3. **报告无缝联动排障**：一旦自动化测试断言失败，`conftest.py` 中的失败钩子会捕获当前的 `TraceID`，并在 Allure 测试报告中自动生成直达 APM 链路大屏的超链接。测试或研发点击链接即可直接看到整条调用拓扑瀑布流，秒级定位是哪个微服务抛了异常、哪条 SQL 耗时过长，无需在多台机器日志里人工搜寻。
