# 文件上传与下载接口测试

> 接口不只是「发 JSON 收 JSON」。文件类接口走 `multipart/form-data` 和流式传输，断言落点从「响应体」变成「落盘文件本身」。

![[assets/file-upload-download-flow.svg]]
*图示：上传走 multipart 分块、服务端存盘返 file_id；下载走 stream 分块写盘，再比对 md5 与大小。*

## 概念

### 上传不是把文件塞进 JSON

`requests` 的 `files=` 参数走的是 `multipart/form-data`，和 `json=` 是两套编码：

| 维度 | json= | files= |
|------|------|--------|
| Content-Type | `application/json` | `multipart/form-data; boundary=...` |
| body 形态 | 结构化字段 | 二进制分块 + 元信息 |
| 断言对象 | 响应里的字段 | file_id / 落盘路径 |

### 下载是「边收边写」

`stream=True` 时 `r.content` 不会一次性读入内存，而是按块迭代写入本地文件，适合大文件。

## 用法

### 上传一个文件

```python
with open('a.png', 'rb') as f:
    r = requests.post('/upload', files={'file': ('a.png', f, 'image/png')})
assert r.json()['file_id']  # 服务端返回可后续引用的 id
```

### 下载并落盘校验

```python
r = requests.get('/export/order.zip', stream=True)
r.raise_for_status()
with open('order.zip', 'wb') as f:
    for chunk in r.iter_content(1024):
        f.write(chunk)
import os
assert os.path.getsize('order.zip') == int(r.headers['Content-Length'])
```

## 踩坑

### ① files 元组第四个元素漏了 MIME

`files={'file': open('a.png','rb')}` 缺 MIME 类型时，部分服务端按文件名后缀推断，另一些严格校验 Content-Type，导致上传被拒。显式给三元组 `(name, fp, mime)` 最稳。

### ② stream=False 时大文件撑爆内存

不写 `stream=True`，`r.content` 会一次性把 2GB 文件读进内存，用例直接 OOM。流式是防 OOM 的唯一正解。

### ③ 下载没关文件句柄

`with open(...)` 漏写会让临时文件句柄残留，CI 跑多了报「too many open files」。务必上下文管理器包住。

### ④ file_id 没透传给下游

上传返回的 `file_id` 若不作为下游接口入参，文件就成「孤儿」。断言链里要 `assert downstream_req['file_id'] == upload_resp['file_id']`。

### ⑤ md5 比对顺序反了

先比 `md5` 再比大小容易误判（大小相同内容却不同）。先比内容一致性再比大小，才是真校验。

## 面试怎么答

「文件上传下载接口怎么测？」

- 上传走 `multipart`，`files=` 给三元组最稳；断言盯 `file_id` 能透传下游；
- 下载走 `stream=True` 防内存爆，按块写盘；
- 校验两层：落盘存在 + 大小/md5 一致；
- 坑点：MIME 漏写、句柄未关、md5 顺序反——都是 CI 稳定性杀手。
