# 接口断言三层体系

> 只断言 `status_code == 200` 的自动化，本质上是一套探活脚本。断言分层，才是接口自动化真正产生价值的地方。

![[assets/assertion-layers.svg]]
*图示：协议层 → 结构层 → 业务值层是每条用例的必做项，数据层与链路层按业务重要度选做。*

## 概念

### 为什么只看状态码不够

看两个真实场景：

```python
# 场景 1：HTTP 200，但业务失败
r = api.post("/api/v1/pay", json={"order_id": 100231, "amount": "19.90"})
assert r.status_code == 200      # 通过！
print(r.json())
# {"code": 200105, "msg": "余额不足", "data": null}
```

很多后端框架无论业务成败都返回 HTTP 200，用 body 里的 `code` 表达业务结果。只断言状态码，支付全失败你也发现不了。

```python
# 场景 2：结构变了，值也对，但前端会崩
# 上周: {"data": {"total": 100, "list": [...]}}
# 这周: {"data": {"total": "100", "list": null}}
assert r.json()["data"]["total"] == 100    # 失败，但至少发现了
assert r.json()["data"]["list"] is not None  # 如果没写这条，就漏了
```

`total` 从 int 变 string、空列表变 null，是后端重构时最常见的破坏性变更。这类问题**只有结构层断言能系统性拦住**。

### 五层的职责划分

| 层 | 断言对象 | 必做？ | 能拦住的问题 |
|----|----------|--------|--------------|
| 1 协议层 | status_code、响应头、耗时 | 是 | 服务挂了、路由错、网关超时、返回了 HTML 错误页 |
| 2 结构层 | JSON Schema：字段、类型、必填、枚举 | 是 | 字段被删/改名、类型漂移、null 代替空数组 |
| 3 业务值层 | 业务码、关键字段值、计算结果 | 是 | 优惠算错、状态没流转、分页数据不一致 |
| 4 数据层 | 数据库落库结果 | 按重要度 | 事务回滚、只写缓存没写库、精度截断 |
| 5 链路层 | 日志、MQ 消息、下游调用 | 按重要度 | 异步任务没触发、通知链路断了 |

**1～3 层是每条用例的基本盘**，成本很低（结构层用 Schema 复用，业务层就几行 assert）。4～5 层成本较高，只对核心链路做。

### 断言不是越多越好

反向的坑同样存在：把整个响应体做全量快照比对（`assert r.json() == expected_full_dict`）。后果是每次后端加个字段，几百条用例全红，最后大家习惯性地改期望值，断言就失去了意义。

原则：**断言那些「变了就是 bug」的东西，忽略那些「变了很正常」的东西**（时间戳、trace_id、自增 ID、排序不稳定的列表）。

## 用法

### 封装分层断言器

```python
import re
from typing import Any
import jsonschema
import requests


class ApiAssert:
    """链式断言器：失败信息里自动带上请求与响应上下文。"""

    def __init__(self, resp: requests.Response):
        self.r = resp
        self._ctx = (
            f"\n  请求: {resp.request.method} {resp.url}"
            f"\n  请求体: {str(resp.request.body)[:500]}"
            f"\n  响应: {resp.status_code} {resp.text[:800]}"
        )

    # ---------- 第 1 层：协议 ----------
    def status(self, expected: int = 200):
        assert self.r.status_code == expected, \
            f"状态码期望 {expected} 实际 {self.r.status_code}{self._ctx}"
        return self

    def content_type(self, expected: str = "application/json"):
        actual = self.r.headers.get("Content-Type", "")
        assert expected in actual, f"Content-Type 期望含 {expected} 实际 {actual}{self._ctx}"
        return self

    def elapsed_below(self, ms: int):
        actual = self.r.elapsed.total_seconds() * 1000
        assert actual < ms, f"响应耗时 {actual:.0f}ms 超过阈值 {ms}ms{self._ctx}"
        return self

    # ---------- 第 2 层：结构 ----------
    def schema(self, schema: dict):
        try:
            jsonschema.validate(self.r.json(), schema)
        except jsonschema.ValidationError as e:
            raise AssertionError(
                f"响应结构不符合 Schema：{e.message}\n"
                f"  出错路径: {'.'.join(str(p) for p in e.absolute_path) or '<root>'}"
                f"{self._ctx}"
            ) from None
        return self

    # ---------- 第 3 层：业务值 ----------
    def biz_code(self, expected: int = 0):
        actual = self.r.json().get("code")
        assert actual == expected, \
            f"业务码期望 {expected} 实际 {actual}，msg={self.r.json().get('msg')}{self._ctx}"
        return self

    def field(self, path: str, expected: Any):
        actual = self._get(path)
        assert actual == expected, f"字段 {path} 期望 {expected!r} 实际 {actual!r}{self._ctx}"
        return self

    def field_in(self, path: str, candidates):
        actual = self._get(path)
        assert actual in candidates, f"字段 {path} 值 {actual!r} 不在 {candidates}{self._ctx}"
        return self

    def has_field(self, path: str):
        self._get(path)     # 取不到就抛
        return self

    def _get(self, path: str):
        """支持 data.list.0.id 这种点号路径。"""
        node = self.r.json()
        for part in path.split("."):
            if isinstance(node, list):
                node = node[int(part)]
            elif isinstance(node, dict) and part in node:
                node = node[part]
            else:
                raise AssertionError(f"路径 {path} 在 {part} 处取不到值{self._ctx}")
        return node

    def not_contains_sensitive(self):
        patterns = [
            (re.compile(r"1[3-9]\d{9}"), "完整手机号"),
            (re.compile(r"\d{17}[\dXx]"), "身份证号"),
            (re.compile(r"\$2[aby]\$\d{2}\$"), "bcrypt 密码 hash"),
        ]
        for pattern, desc in patterns:
            m = pattern.search(self.r.text)
            assert not m, f"响应泄漏{desc}: {m.group()}{self._ctx}"
        return self
```

用起来是这样：

```python
ORDER_SCHEMA = {
    "type": "object",
    "required": ["code", "msg", "data"],
    "properties": {
        "code": {"type": "integer"},
        "msg": {"type": "string"},
        "data": {
            "type": "object",
            "required": ["order_id", "status", "amount"],
            "properties": {
                "order_id": {"type": "integer", "minimum": 1},
                "status": {"enum": ["UNPAID", "PAID", "CANCELLED", "REFUNDED"]},
                "amount": {"type": "string", "pattern": r"^\d+\.\d{2}$"},
            },
        },
    },
}

def test_create_order(api, sku):
    r = api.post("/api/v1/orders", json={"sku_id": sku, "quantity": 2})
    (ApiAssert(r)
        .status(200)                       # 第 1 层
        .content_type("application/json")
        .elapsed_below(1000)
        .schema(ORDER_SCHEMA)              # 第 2 层
        .biz_code(0)                       # 第 3 层
        .field("data.status", "UNPAID")
        .field("data.amount", "39.80")     # 19.90 × 2，验算钱
        .not_contains_sensitive())
```

**`amount` 断言的是算出来的值 `39.80` 而不是「有这个字段」**——这才是业务层断言的意义。

### 第 4 层：数据库落库校验

```python
# conftest.py
import pymysql
import pytest

@pytest.fixture(scope="session")
def db():
    conn = pymysql.connect(host="10.0.0.5", user="qa", password="***",
                           database="shop_test", cursorclass=pymysql.cursors.DictCursor,
                           autocommit=True)
    yield conn
    conn.close()

@pytest.fixture
def query_one(db):
    def _q(sql, *args):
        with db.cursor() as cur:
            cur.execute(sql, args)
            return cur.fetchone()
    return _q
```

```python
def test_create_order_persisted(api, sku, query_one):
    r = api.post("/api/v1/orders", json={"sku_id": sku, "quantity": 2})
    ApiAssert(r).status(200).biz_code(0)
    order_id = r.json()["data"]["order_id"]

    row = query_one("SELECT status, amount, sku_id, quantity FROM orders WHERE id=%s", order_id)
    assert row is not None, f"订单 {order_id} 接口返回成功但库里没有（事务回滚？）"
    assert row["status"] == "UNPAID"
    assert str(row["amount"]) == "39.80", f"金额精度被截断：库里是 {row['amount']}"
    assert row["quantity"] == 2

    # 顺带验证库存被正确扣减
    stock = query_one("SELECT stock FROM skus WHERE id=%s", sku)["stock"]
    assert stock == 98, f"库存未正确扣减，期望 98 实际 {stock}"
```

这一层能抓到的典型缺陷：接口返回成功但事务回滚、金额 `19.90` 入库变成 `19.9` 或 `19`、库存扣减和订单创建不在一个事务里。

> SQL 一律用参数化（`%s` 占位）而不是字符串拼接，即使是测试代码。参考 [[04-数据库]]。

### 第 5 层：日志与消息校验

```python
import time

def test_pay_triggers_notify(api, order, read_log):
    api.post("/api/v1/pay", json={"order_id": order["order_id"], "amount": order["amount"]})

    # 异步链路要轮询等待，不能 sleep 死等
    deadline = time.time() + 10
    keyword = f"notify sent for order={order['order_id']}"
    while time.time() < deadline:
        if keyword in read_log("/var/log/app/notify.log", tail=500):
            break
        time.sleep(0.5)
    else:
        raise AssertionError(f"10 秒内未在日志中找到通知记录：{keyword}")
```

也可以直接消费 MQ 校验消息投递：

```python
def test_pay_publishes_mq_message(api, order, mq_consumer):
    api.post("/api/v1/pay", json={"order_id": order["order_id"], "amount": order["amount"]})
    msg = mq_consumer.poll(topic="order.paid", timeout=10)
    assert msg is not None, "支付成功但未投递 order.paid 消息"
    assert msg["order_id"] == order["order_id"]
    assert msg["amount"] == order["amount"]
```

### 用 pytest 的软断言收集全部失败

默认断言一失败就中断，后面的检查点看不到。用 `pytest-check` 可以一次跑完所有断言：

```python
import pytest_check as check

def test_order_all_fields(api, sku):
    r = api.post("/api/v1/orders", json={"sku_id": sku, "quantity": 2})
    data = r.json()["data"]
    check.equal(r.status_code, 200, "状态码")
    check.equal(data["status"], "UNPAID", "订单状态")
    check.equal(data["amount"], "39.80", "订单金额")
    check.equal(data["quantity"], 2, "数量")
    # 全部执行完，一次性报告所有失败项
```

适合字段多的响应，一轮就能拿到完整的差异清单，不用「改一个跑一次」。

## 踩坑

1. **只断言 status_code**：HTTP 200 + `code: 500001` 的组合让自动化完全失效。业务码必须断言。
2. **全量快照比对**：`assert r.json() == expected`。后端加个字段就全线飘红，久而久之大家闭眼改期望值，断言退化成摆设。要断言的是「变了就是 bug」的字段。
3. **断言里包含动态值**：`created_at`、`trace_id`、自增 `order_id` 每次都不一样。Schema 里只校验类型和格式，不校验具体值。
4. **失败信息里没有响应体**：`AssertionError: assert 400 == 200`，排查时得回去手动复现。断言器必须把请求方法、URL、请求体、响应体片段都带上。
5. **浮点数直接比较金额**：`assert data["amount"] == 39.8` 在浮点误差下偶发失败。金额一律用字符串或 `Decimal` 比较。
6. **数据库断言用了主库/从库不一致的连接**：主从延迟下刚写的数据从库还没有，用例偶发失败。测试要连主库，或者加重试轮询。
7. **异步链路用 `sleep(10)` 死等**：既慢又不稳。用轮询 + 超时（上面的 `while time.time() < deadline`）。
8. **数据库断言不清理**：查询用的连接开着事务不提交，把测试库锁住。用 `autocommit=True` 或显式 commit。
9. **Schema 写得太松**：`{"type": "object"}` 等于没校验。至少要有 `required` 和每个字段的 `type`。见 [[JSON Schema 响应结构校验]]。
10. **断言分层混在一起写**：一个测试函数里 30 行裸 assert，看不出哪条是协议层哪条是业务层。用断言器封装，可读性和复用性都会好很多。

## 面试怎么答

**Q：只断言状态码有什么问题，你的断言分几层？**

A：只断言状态码基本等于探活。很多后端框架不管业务成败都返回 HTTP 200，业务结果放在 body 的 `code` 字段里，支付全部失败你也测不出来。我的断言分五层：第一层协议层，status_code、Content-Type、响应耗时；第二层结构层，用 JSON Schema 校验字段是否存在、类型对不对、枚举值合不合法，这一层能系统性拦住后端重构时删字段、int 变 string、空数组变 null 这类破坏性变更；第三层业务值层，断言业务码和关键字段的**计算结果**，比如单价 19.90 买 2 件订单金额必须是 39.80；第四层数据层，回查数据库确认真的落库了、金额精度没被截断、库存正确扣减；第五层链路层，查日志或消费 MQ 确认异步链路触发了。前三层每条用例都做，成本很低；后两层对核心链路做。

**Q：断言是不是越多越好？**

A：不是。我见过把整个响应体做全量快照比对的做法，后端加一个字段就几百条用例飘红，最后团队养成了「一红就改期望值」的习惯，断言就彻底失去意义了。判断标准是「这个东西变了是不是 bug」：`created_at`、`trace_id`、自增 ID 每次都不一样，变了很正常，Schema 里只校验类型和格式就够；而金额、状态、业务码变了一定是 bug，必须精确断言。另外断言失败信息一定要带上请求方法、URL、请求体和响应体片段，否则排查时还得手动复现一遍，这个成本比多写几条断言高多了。

**Q：怎么验证接口真的把数据写进去了？**

A：加数据库断言。接口返回成功不等于落库成功——事务可能回滚、可能只写了缓存、可能字段精度被截断。做法是准备一个 session 级的数据库连接 fixture，用例里在接口断言之后 `SELECT` 回查，比对关键字段。这一层能抓到几类接口层看不见的缺陷：一是接口 200 但库里没记录；二是金额 `19.90` 存进去变成 `19.9` 或被截成 `19`；三是订单创建了但关联的库存没扣，说明不在一个事务里。注意两点：SQL 要参数化不能拼字符串；有主从架构的话要连主库，否则主从延迟会导致偶发失败。
