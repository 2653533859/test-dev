# 接口串联与依赖参数提取传递

> 单接口用例全绿、业务流一跑就崩，是接口自动化最常见的假繁荣。串联的难点不在「怎么传参」，而在「上下文放哪、失败怎么归因、脏数据怎么清」。

![[assets/api-chain-param-flow.svg]]
*图示：登录取 token、下单取 order_id，参数经由运行时上下文在步骤间传递，清理动作放在 fixture 的 yield 之后。*

## 概念

### 什么是接口串联

真实业务不是单点调用，而是一条链：

```text
登录 → 加购物车 → 创建订单 → 支付 → 查询订单状态 → 申请退款
```

后一步依赖前一步的产出（`token`、`cart_id`、`order_id`、`trade_no`）。串联测试要验证的是**状态在多个接口间的正确流转**，这是单接口用例覆盖不到的：单独测「支付接口」时你用的是一个手工造的固定订单，测不出「刚创建的订单支付时状态不对」这类问题。

### 三种传参方式的取舍

| 方式 | 写法 | 问题 |
|------|------|------|
| 模块级全局变量 | `global TOKEN` | 用例无法单独重跑、并发串号、顺序依赖 |
| 用例间返回值传递 | `test_b(test_a_result)` | pytest 不支持，只能靠 fixture |
| **fixture 承载上下文** | `@pytest.fixture` 返回 ctx | 推荐 |

新手最常写第一种，问题是**用例失去了独立性**——CI 里 `-k test_pay` 单独重跑必然失败，`pytest-xdist` 并发时几个 worker 抢同一个全局变量。

正确做法：**依赖关系用 fixture 显式表达**。fixture 天然支持缓存（同 scope 只跑一次）、自动清理（yield 之后）、并发隔离。

### 前置步骤不是测试步骤

一条重要的心智模型：串联链上的步骤分两类。

- **造数据的（Arrange）**：登录、创建订单。它们失败了应该报「前置条件失败」，而不是「支付接口 bug」
- **被测的（Act + Assert）**：本条用例真正要验证的那一步

区分的好处是**失败归因**。如果登录挂了，一百条用例全红，报告里应该清晰显示「前置登录失败」，而不是一百个五花八门的业务断言错误让你逐个排查。

实现上就是：造数据放 fixture 并用 `pytest.fail` / `assert` 明确报错，被测步骤放测试函数里。

## 用法

### 用 fixture 链式表达依赖

```python
# conftest.py
import pytest

@pytest.fixture(scope="session")
def api(base_url):
    """已登录的客户端，token 由 AuthSession 内部管理。"""
    s = AuthSession(base_url, "qa01", "Pwd@123")
    yield s
    s.close()


@pytest.fixture
def sku(api):
    """准备一个有库存的可售商品。"""
    r = api.post("/api/v1/admin/skus", json={"name": "测试商品", "stock": 100, "price": "19.90"})
    assert r.status_code == 200, f"[前置失败] 创建 SKU: {r.status_code} {r.text[:300]}"
    sku_id = r.json()["data"]["sku_id"]
    yield sku_id
    api.delete(f"/api/v1/admin/skus/{sku_id}")


@pytest.fixture
def order(api, sku):
    """在 sku 基础上创建一笔待支付订单。"""
    r = api.post("/api/v1/orders", json={"sku_id": sku, "quantity": 1})
    assert r.status_code == 200, f"[前置失败] 创建订单: {r.status_code} {r.text[:300]}"
    data = r.json()["data"]
    yield data                      # {'order_id': ..., 'amount': ..., 'status': 'UNPAID'}
    api.delete(f"/api/v1/orders/{data['order_id']}")   # 断言失败也会执行
```

用例只声明它需要什么，pytest 自动按依赖图构建：

```python
# test_pay.py
def test_pay_order(api, order):
    r = api.post("/api/v1/pay", json={"order_id": order["order_id"],
                                      "amount": order["amount"]})
    assert r.status_code == 200
    assert r.json()["data"]["status"] == "PAID"


def test_query_after_pay(api, order):
    api.post("/api/v1/pay", json={"order_id": order["order_id"],
                                  "amount": order["amount"]})
    r = api.get(f"/api/v1/orders/{order['order_id']}")
    assert r.json()["data"]["status"] == "PAID"
```

**每条用例拿到的都是全新的订单**（fixture 默认 function 级），互不干扰，单独重跑也没问题。

### 显式上下文对象：适合长业务流

链路超过 4～5 步时，fixture 套 fixture 会变得难读。这时用一个显式的 `ctx`：

```python
import pytest
from typing import Any

class FlowContext(dict):
    """业务流上下文：带来源追踪的字典，取不到时报错更清晰。"""

    def set(self, key: str, value: Any, *, step: str = "") -> None:
        self[key] = value
        print(f"[ctx] {step} 写入 {key}={value!r}")

    def need(self, key: str) -> Any:
        if key not in self:
            raise KeyError(f"上下文缺少 {key!r}，当前已有: {list(self)}。"
                           f"检查前置步骤是否执行或提取表达式是否写错")
        return self[key]


@pytest.fixture
def ctx():
    return FlowContext()
```

```python
def test_order_full_flow(api, ctx, sku):
    # step 1 下单
    r = api.post("/api/v1/orders", json={"sku_id": sku, "quantity": 2})
    assert r.status_code == 200, f"[step1 下单失败] {r.text[:300]}"
    ctx.set("order_id", r.json()["data"]["order_id"], step="step1")
    ctx.set("amount", r.json()["data"]["amount"], step="step1")

    # step 2 支付
    r = api.post("/api/v1/pay", json={"order_id": ctx.need("order_id"),
                                      "amount": ctx.need("amount")})
    assert r.status_code == 200, f"[step2 支付失败] {r.text[:300]}"
    ctx.set("trade_no", r.json()["data"]["trade_no"], step="step2")

    # step 3 查询状态（真正的断言点）
    r = api.get(f"/api/v1/orders/{ctx.need('order_id')}")
    data = r.json()["data"]
    assert data["status"] == "PAID"
    assert data["trade_no"] == ctx.need("trade_no")
    assert data["paid_amount"] == ctx.need("amount")
```

`need()` 的价值在于错误信息：`KeyError: 'trade_no'` 什么都说明不了，而「上下文缺少 'trade_no'，当前已有 ['order_id', 'amount']」一眼就知道是 step2 的提取失败了。

### 用 JSONPath 配置化提取

硬编码 `r.json()["data"]["list"][0]["id"]` 的问题是：响应结构一变，全线用例挂掉，而且改起来要翻遍代码。用表达式配置化：

```python
from jsonpath_ng.ext import parse   # pip install jsonpath-ng

def extract(resp_json: dict, expr: str):
    matches = parse(expr).find(resp_json)
    if not matches:
        raise AssertionError(f"提取失败：表达式 {expr} 在响应中无匹配\n响应: {resp_json}")
    return matches[0].value

# 提取规则和用例数据放一起
EXTRACT_RULES = {
    "login":  {"token": "$.data.access_token"},
    "order":  {"order_id": "$.data.order_id", "amount": "$.data.amount"},
    "pay":    {"trade_no": "$.data.trade_no"},
}

def run_step(api, ctx, step_name, method, path, body=None):
    r = api.request(method, path, json=body)
    assert r.status_code == 200, f"[{step_name}] HTTP {r.status_code}: {r.text[:300]}"
    for key, expr in EXTRACT_RULES.get(step_name, {}).items():
        ctx.set(key, extract(r.json(), expr), step=step_name)
    return r
```

详见 [[JSONPath 与正则提取响应字段]]。

### 参数占位符替换

YAML 用例里写 `${order_id}`，运行时从 ctx 替换：

```python
import re

PLACEHOLDER = re.compile(r"\$\{(\w+)\}")

def render(obj, ctx: dict):
    """递归替换 dict/list/str 中的 ${var} 占位符。"""
    if isinstance(obj, str):
        # 整个字符串就是一个占位符 → 保留原类型（int 不会被转成 str）
        m = PLACEHOLDER.fullmatch(obj)
        if m:
            return ctx[m.group(1)]
        return PLACEHOLDER.sub(lambda x: str(ctx[x.group(1)]), obj)
    if isinstance(obj, dict):
        return {k: render(v, ctx) for k, v in obj.items()}
    if isinstance(obj, list):
        return [render(v, ctx) for v in obj]
    return obj

ctx = {"order_id": 100231, "token": "abc"}
print(render({"id": "${order_id}", "url": "/api/orders/${order_id}"}, ctx))
# {'id': 100231, 'url': '/api/orders/100231'}
```

**`fullmatch` 那个分支很关键**：如果整个值就是一个占位符，要返回原始类型。否则 `{"id": "${order_id}"}` 会被渲染成 `{"id": "100231"}`（字符串），后端严格校验类型时直接 400。

### 清理：必须放在 yield 之后

```python
@pytest.fixture
def order(api, sku):
    r = api.post("/api/v1/orders", json={"sku_id": sku, "quantity": 1})
    assert r.status_code == 200, f"[前置失败] {r.text[:300]}"
    order_id = r.json()["data"]["order_id"]
    yield order_id
    # 无论用例通过还是断言失败，这里都会执行
    resp = api.delete(f"/api/v1/orders/{order_id}")
    if resp.status_code not in (200, 204, 404):
        print(f"[warn] 清理订单 {order_id} 失败: {resp.status_code}")
```

清理失败**只 warn 不 assert**——清理阶段抛异常会把一条本来通过的用例变成 error，掩盖真实结果。脏数据的问题另外用定时任务兜底。

## 踩坑

1. **用全局变量传参**：`global TOKEN` / 模块级 `ORDER_ID`。后果：用例无法单独重跑（`pytest -k` 直接失败）、`pytest-xdist` 并发时不同 worker 互相覆盖、用例顺序一变全崩。一律改 fixture。
2. **依赖用例执行顺序**：靠 `test_01_login`、`test_02_order` 这种命名保证顺序。pytest 默认按文件内定义顺序执行，但加上 `-p no:randomly`、`--lf`、xdist 之后就不保证了。顺序依赖是设计缺陷，不是可以靠约定绕过的。
3. **前置步骤失败报错不清晰**：登录 fixture 里不 assert，后面报 `KeyError: 'data'`，得追三层才知道是登录挂了。**每个前置步骤都要 assert 并带上 status 和 body 片段**。
4. **提取失败静默返回 None**：`r.json().get("data", {}).get("order_id")` 拿到 `None`，后续请求 `/api/orders/None`，报 404，你以为是查询接口的 bug。提取一定要在失败时立刻抛错。
5. **占位符替换把 int 变成 str**：见上文 `fullmatch` 分支。表现为莫名其妙的 400 参数类型错误。
6. **清理放在 yield 之前或写在用例末尾**：用例断言失败时清理不执行，测试库越跑越脏。必须放 `yield` 后（或用 `request.addfinalizer`）。
7. **清理动作抛异常**：把通过的用例变成 error。清理只 warn。
8. **fixture scope 用错**：`scope="module"` 的订单 fixture 被多条用例共享，第一条把它支付了，第二条测「取消未支付订单」必然失败。**有状态变更的数据用 function 级**。
9. **串联链太长**：一条用例串了 10 个接口，中间任何一环挂了整条红，定位成本极高。超过 5 步就该拆，或者把稳定的前置步骤换成直接写库/调内部接口造数据。
10. **前置数据用生产数据或固定 ID**：`order_id = 100001` 这种硬编码，换个环境就没了，或者被别人改了状态。前置数据一定要自己造。

## 面试怎么答

**Q：接口之间有依赖，登录 token 和上游返回的 ID 怎么传递？**

A：用 pytest 的 fixture 承载，不用全局变量。登录做成 `scope="session"` 的 fixture，返回一个已经带好鉴权的客户端；创建订单做成 function 级 fixture，返回 order_id 并在 `yield` 之后清理。用例函数声明需要哪个 fixture，pytest 自动按依赖图构建，这样每条用例都能单独重跑，也支持 xdist 并发。链路特别长的时候我会额外用一个显式的 ctx 字典在步骤间传值，配合 JSONPath 表达式做提取——比如 `$.data.order_id`，把提取规则配置化，响应结构变了只改配置不改代码。

**Q：为什么不用全局变量？**

A：三个硬伤。第一，用例失去独立性，CI 里用 `-k` 单独重跑某条失败用例必然报错，因为全局变量还是空的，而单独重跑是排障时最常用的操作。第二，`pytest-xdist` 并发时多个进程/线程互相覆盖，出现偶发的串号问题，还极难复现。第三，隐式依赖执行顺序，一旦有人调整了用例位置或者用了随机执行插件，整批崩掉。fixture 把依赖关系**显式化**了，谁依赖谁一眼可见，而且自带缓存和清理机制。

**Q：串联用例中间某一步失败了怎么办？**

A：先要能**区分是前置失败还是被测点失败**。我把链路上的步骤分成两类：造数据的放 fixture，里面 assert 时带上 `[前置失败]` 前缀和完整的 status、body 片段；真正被测的那一步放测试函数里。这样报告里一眼能看出「是登录服务挂了导致一百条全红」还是「支付接口本身有问题」。另外清理动作一定放在 fixture 的 `yield` 之后，保证断言失败时也执行；清理本身失败只打 warning 不抛异常，否则会把测试结果污染成 error。最后，如果一条链超过五步，我会考虑把稳定的前置部分改成直接写数据库或调内部接口造数据，缩短链路降低脆弱性。
