# 加密与解密接口的处理

> 当请求/响应体本身是密文时，`requests` 默认拿到的 `r.text` 是一堆乱码——你得在请求层和响应层各插一道「解密闸」，用例才能读得懂、断言得了。

![[assets/api-encrypt-flow.svg]]
*图示：客户端 AES 加密报文，线上只传密文；服务端用 RSA 验签后解密。用例侧必须自己 decrypt 才能看到明文。*

## 概念

### 为什么接口要加密

不是所有接口都是「你发什么、服务端原样回什么」。金融、支付、政务类系统常要求**报文级加密**：

- **传输加密（TLS）≠ 内容加密**：TLS 防中间人窃听，但服务端日志、DB 里仍是明文；内容加密是「业务层再把字段 AES 一遍」，连服务端内部存储也是密文。
- **签名 vs 加密**：`[[接口签名鉴权与 sign 计算]]` 解决「是谁发的、有没有被改」；加密解决「即使被截获也看不懂」。两者常叠加：先用签名防篡改，再用加密防窥探。

### 一次加密调用的三要素

| 要素 | 说明 | 自动化关注点 |
|------|------|------|
| 对称密钥（AES） | 加解密同一把钥匙，快 | 密钥从哪来、怎么喂给用例 |
| 非对称信封（RSA） | 用公钥包住 AES 密钥，防密钥泄露 | 公钥/私钥如何注入 |
| 明文落点 | 加解密后的原始数据 | 用例断言盯的是哪一层 |

## 用法

### 在请求层统一加密（给 Session 加 hook）

```python
import json, base64
from Crypto.Cipher import AES
from Crypto.Util.Padding import pad
import requests

class EncryptSession(requests.Session):
    def __init__(self, key: bytes):
        super().__init__()
        self._aes_key = key  # 16/24/32 字节

    def request(self, method, url, data=None, json=None, **kw):
        if json is not None:
            raw = json.dumps(json).encode()
            cipher = AES.new(self._aes_key, AES.MODE_ECB)
            enc = base64.b64encode(cipher.encrypt(pad(raw, AES.block_size)))
            data = enc  # 覆写 body 为密文
        return super().request(method, url, data=data, **kw)
```

调用时「无感」：`s.post('/api/order', json={"sku": 1, "amt": 99})` 发出去的就是 AES 密文。

### 响应层解密

```python
s = EncryptSession(key)
r = s.post('/api/order', json={...})
body = r.content  # 密文
cipher = AES.new(key, AES.MODE_ECB)
plain = cipher.decrypt(body)  # 解出来才是可读 JSON
assert json.loads(plain.decode())["code"] == 0
```

## 踩坑

### ① ECB 模式的「幽灵块」

`AES.MODE_ECB` 无 IV，相同明文永远相同密文，容易在日志里被横向比对出规律。生产别用 ECB，至少上 `MODE_CBC` + 随机 IV，且 IV 要随请求一起传，否则解密端对不上。

### ② base64 不是加密

`b64encode` 只是编码，任何人拿到都能解。它和「加密」是两回事——别把它当安全机制。

### ③ 密钥写死进用例

把 `key = b'1234567890abcdef'` 提交到仓库，密钥就泄露了。正确做法是用环境变量或 KMS 注入，用例里只 `os.getenv("API_AES_KEY")`。

### ④ padding 长度不对报错

`pad(raw, AES.block_size)` 要求输入是 16 的倍数，裸 `str.encode()` 直接用会报 `ValueError: Data must be padded to 16 byte boundary`。先用 `json.dumps` 再 pad，别反了。

### ⑤ 解密失败却断言通过了

若没拦截异常，`decrypt` 抛错会让用例红，但有时会「静默返回空 dict」，导致后续 `assert code == 0` 拿空值误判。务必先确认 `r.status_code == 200` 再解密。

## 面试怎么答

「加密接口怎么做自动化？」

- 先分层：TLS 解决传输安全，业务层 AES/RSA 解决内容保密；
- 自动化侧用 `Session` 子类在 `request()` 里统一加密，对用例透明；
- 响应用同样的密钥解密后再断言；
- 密钥走环境变量注入，不落库；
- 踩坑点：`ECB` 别上生产、`base64` 不是加密、padding 长度要对齐、解密失败要先判状态码。

这样既不改业务代码，又能稳定跑通加密接口。
