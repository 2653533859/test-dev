# 接口用例设计维度

> 「你怎么设计接口用例」是面试必问题。只答「正常场景 + 异常场景」等于没答——这里给一套能当场背出来、也能落到实处的九维清单。

## 概念

### 接口用例和 UI 用例的根本差别

UI 测试隔着一层界面，很多输入组合根本构造不出来（前端做了校验）。接口测试**直接打后端**，所以：

- 前端校验绕过后，后端的校验是否还在？（这是接口层最有价值的一类用例）
- 界面上不可能出现的组合（负数金额、超长字符串、并发同一订单）都能构造
- 但也测不到前端的展示与交互逻辑

一句话：**接口用例的核心价值在于「测后端自己的健壮性」，而不是复现用户操作路径。**

### 九个设计维度

按这个顺序过一遍接口，覆盖度基本就够了：

| # | 维度 | 关注点 |
|---|------|--------|
| 1 | 正向功能 | 全部必填、必填+可选、多组合法组合 |
| 2 | 参数校验 | 必填缺失、类型错误、超长/超短、非法枚举、特殊字符 |
| 3 | 边界值 | 最小、最小+1、最大、最大-1、最大+1、0、空、null |
| 4 | 业务规则 | 状态机流转、库存/余额不足、优惠互斥、限购 |
| 5 | 鉴权与权限 | 未登录、token 过期/非法、水平越权、垂直越权 |
| 6 | 幂等与并发 | 重复提交、并发扣减、重试后数据是否重复 |
| 7 | 异常与容错 | 上游超时、依赖挂掉、大数据量、超长响应 |
| 8 | 数据一致性 | 响应与数据库、缓存与数据库、主从延迟 |
| 9 | 非功能 | 响应时间、返回体大小、敏感信息泄漏 |

前三维是「输入」，4～6 是「逻辑」，7～9 是「系统层面」。新手往往只做 1～3，而真正的高价值缺陷集中在 4～6。

### 空值的四种形态要分开测

这是接口层特有的、UI 层测不到的坑。同一个「空」，在 JSON 里有四种表达，后端处理往往不一致：

```python
{"name": "张三"}      # 键不存在
{"name": null}        # 键存在，值为 null
{"name": ""}          # 空字符串
{"name": "   "}       # 全空格
```

典型 bug：后端用 `if (name != null)` 判断，`""` 就通过了校验，最后库里存了个空名字。这四种必须**分别设计用例**，不能合并成一条「测空值」。

### 越权测试：接口层最容易出高危缺陷的地方

- **水平越权**：用 A 用户的 token 访问 B 用户的资源（`GET /api/orders/{B的order_id}`），应该 403 但返回 200
- **垂直越权**：普通用户调用管理员接口（`DELETE /api/admin/users/1`），应该 403

前端不会给普通用户显示管理员按钮，所以 UI 测试永远发现不了垂直越权。这是接口测试的独有价值。

## 用法

### 用清单驱动，而不是凭感觉

拿一个「创建订单」接口举例，把九个维度落成实际用例：

```yaml
# testcases/create_order.yaml
接口: POST /api/v1/orders
参数:
  sku_id: string, 必填
  quantity: int, 必填, 1~99
  coupon_id: string, 可选
  remark: string, 可选, 最大 200 字符

用例:
  # 1 正向
  - id: TC001
    desc: 仅必填字段创建成功
    body: {sku_id: "SKU001", quantity: 1}
    expect: {status: 200, code: 0, has_field: "data.order_id"}
  - id: TC002
    desc: 必填 + 全部可选字段
    body: {sku_id: "SKU001", quantity: 2, coupon_id: "CP001", remark: "加急"}
    expect: {status: 200, code: 0}

  # 2 参数校验
  - id: TC010
    desc: 缺失必填 sku_id
    body: {quantity: 1}
    expect: {status: 400, code: 100001}
  - id: TC011
    desc: quantity 传字符串
    body: {sku_id: "SKU001", quantity: "abc"}
    expect: {status: 400}
  - id: TC012
    desc: remark 传 null
    body: {sku_id: "SKU001", quantity: 1, remark: null}
    expect: {status: 200}      # 可选字段传 null 应视为不传
  - id: TC013
    desc: remark 超长 201 字符
    body: {sku_id: "SKU001", quantity: 1, remark: "__201chars__"}
    expect: {status: 400}
  - id: TC014
    desc: sku_id 含 SQL 注入特征字符
    body: {sku_id: "SKU001' OR '1'='1", quantity: 1}
    expect: {status: 400, not_contains: "SQLSyntaxError"}

  # 3 边界值
  - id: TC020
    desc: quantity 下边界 1
    body: {sku_id: "SKU001", quantity: 1}
    expect: {status: 200}
  - id: TC021
    desc: quantity 下边界外 0
    body: {sku_id: "SKU001", quantity: 0}
    expect: {status: 400}
  - id: TC022
    desc: quantity 上边界 99
    body: {sku_id: "SKU001", quantity: 99}
    expect: {status: 200}
  - id: TC023
    desc: quantity 上边界外 100
    body: {sku_id: "SKU001", quantity: 100}
    expect: {status: 400}
  - id: TC024
    desc: quantity 负数
    body: {sku_id: "SKU001", quantity: -1}
    expect: {status: 400}
  - id: TC025
    desc: quantity 超大整数（int 溢出探测）
    body: {sku_id: "SKU001", quantity: 2147483648}
    expect: {status: 400}

  # 4 业务规则
  - id: TC030
    desc: 库存不足
    setup: 把 SKU001 库存置为 0
    body: {sku_id: "SKU001", quantity: 1}
    expect: {status: 200, code: 200101, msg_contains: "库存"}
  - id: TC031
    desc: 已下架商品
    body: {sku_id: "SKU_OFFLINE", quantity: 1}
    expect: {code: 200102}
  - id: TC032
    desc: 优惠券不属于当前用户
    body: {sku_id: "SKU001", quantity: 1, coupon_id: "CP_OTHER_USER"}
    expect: {status: 403}

  # 5 鉴权
  - id: TC040
    desc: 未登录
    auth: none
    expect: {status: 401}
  - id: TC041
    desc: token 非法
    auth: invalid
    expect: {status: 401}

  # 6 幂等与并发
  - id: TC050
    desc: 相同幂等键重复提交，只产生一笔订单
    repeat: 2
    headers: {Idempotency-Key: "fixed-key-001"}
    expect: {same_order_id: true}
  - id: TC051
    desc: 库存 1 时并发下单 10 次，只有 1 单成功
    concurrent: 10
    expect: {success_count: 1}
```

用例编号留出间隔（TC001、TC010、TC020）是个小技巧：后面补用例时不用重排。

### 参数校验用 pytest 参数化批量覆盖

```python
import pytest

INVALID_QUANTITY = [
    pytest.param(0,          400, id="下边界外-0"),
    pytest.param(-1,         400, id="负数"),
    pytest.param(100,        400, id="上边界外-100"),
    pytest.param(2147483648, 400, id="int32溢出"),
    pytest.param("abc",      400, id="类型错误-字符串"),
    pytest.param(1.5,        400, id="类型错误-小数"),
    pytest.param(None,       400, id="null"),
]

@pytest.mark.parametrize("quantity,expected_status", INVALID_QUANTITY)
def test_create_order_invalid_quantity(api, quantity, expected_status):
    r = api.post("/api/v1/orders", json={"sku_id": "SKU001", "quantity": quantity})
    assert r.status_code == expected_status, \
        f"quantity={quantity!r} 期望 {expected_status}，实际 {r.status_code}: {r.text[:200]}"
```

`pytest.param(..., id=...)` 给每条用例起中文名，报告里一眼能看出失败的是哪个边界。

### 空值四形态的专项用例

```python
EMPTY_FORMS = [
    pytest.param({"sku_id": "SKU001", "quantity": 1},              id="键不存在"),
    pytest.param({"sku_id": "SKU001", "quantity": 1, "remark": None}, id="null"),
    pytest.param({"sku_id": "SKU001", "quantity": 1, "remark": ""},   id="空字符串"),
    pytest.param({"sku_id": "SKU001", "quantity": 1, "remark": "   "}, id="全空格"),
]

@pytest.mark.parametrize("body", EMPTY_FORMS)
def test_remark_empty_forms(api, db, body):
    r = api.post("/api/v1/orders", json=body)
    assert r.status_code == 200
    order_id = r.json()["data"]["order_id"]
    # 关键：落库后 remark 应统一为空串或 NULL，不能存进去几个空格
    remark = db.query_one("SELECT remark FROM orders WHERE id=%s", order_id)["remark"]
    assert remark in (None, ""), f"全空格未被 trim，实际存了 {remark!r}"
```

### 越权用例的写法

```python
@pytest.fixture
def user_a_order(api_a):
    r = api_a.post("/api/v1/orders", json={"sku_id": "SKU001", "quantity": 1})
    order_id = r.json()["data"]["order_id"]
    yield order_id
    api_a.delete(f"/api/v1/orders/{order_id}")

def test_horizontal_privilege_escalation(api_b, user_a_order):
    """B 用户不能查看 A 用户的订单。"""
    r = api_b.get(f"/api/v1/orders/{user_a_order}")
    assert r.status_code in (403, 404), \
        f"水平越权：B 能读到 A 的订单，返回 {r.status_code} {r.text[:300]}"

def test_vertical_privilege_escalation(api_normal_user):
    """普通用户不能调管理员接口。"""
    r = api_normal_user.delete("/api/v1/admin/users/1")
    assert r.status_code == 403
```

返回 404 也可以接受——「资源不存在」比「无权访问」泄漏的信息更少，是更安全的实现。

### 并发与幂等

```python
from concurrent.futures import ThreadPoolExecutor

def test_concurrent_deduct_stock(api_factory, reset_stock):
    """库存 1，并发下单 10 次，必须只有 1 单成功，不能超卖。"""
    reset_stock("SKU_LIMIT", 1)

    def place_order(_):
        client = api_factory()          # 每线程独立 Session
        return client.post("/api/v1/orders",
                           json={"sku_id": "SKU_LIMIT", "quantity": 1})

    with ThreadPoolExecutor(max_workers=10) as ex:
        results = list(ex.map(place_order, range(10)))

    success = [r for r in results if r.json().get("code") == 0]
    assert len(success) == 1, f"超卖：{len(success)} 单成功"
```

注意 `api_factory()` 每线程新建客户端——共用 Session 在并发下有竞态，见 [[requests Session 会话保持与 Cookie]]。

## 踩坑

1. **只测「有没有报错」，不测「报什么错」**：所有异常都断言 `status_code == 400` 是不够的，业务码和提示文案也要断言。否则「库存不足」被改成「参数错误」你也发现不了。
2. **参数化用例的 id 用默认值**：报告里显示 `test_xxx[0-400]`，失败了得回去数第几条。一律手写中文 `id=`。
3. **前置数据靠上一条用例产生**：TC030 依赖 TC001 创建的订单，单独重跑 TC030 必然失败，且用例顺序一变全崩。前置数据必须用 fixture 自己造。
4. **测完不清理**：跑几百轮之后测试库里几十万条脏订单，查询接口的分页用例开始超时。清理放在 fixture 的 `yield` 之后。
5. **边界值只测「等于边界」**：真正的 bug 在边界外那一格。最大 99，要测 99 和 100，只测 99 等于没测。
6. **忽略 int 溢出边界**：`2147483647`（int32 上界）和 `9223372036854775807`（int64 上界）是很好的探测值，能测出后端的类型选择问题。
7. **越权用例只在权限模块测一次**：越权是**每个涉及资源 ID 的接口**都要覆盖的，不是一个独立模块。至少对核心资源接口全覆盖。
8. **并发用例共用一个 Session**：CookieJar 竞态导致偶发失败，误以为是产品的并发 bug。
9. **响应里有敏感信息没人查**：手机号、身份证、密码 hash 明文返回。加一条通用断言扫全量响应体：

   ```python
   import re
   SENSITIVE = [
       (re.compile(r"1[3-9]\d{9}"), "疑似完整手机号"),
       (re.compile(r"\d{17}[\dXx]"), "疑似身份证号"),
       (re.compile(r"\$2[aby]\$\d{2}\$"), "疑似 bcrypt 密码 hash"),
   ]

   def assert_no_sensitive(resp_text: str):
       for pattern, desc in SENSITIVE:
           m = pattern.search(resp_text)
           assert not m, f"响应泄漏{desc}: {m.group()}"
   ```

10. **用例设计只覆盖单接口，没有业务流**：单接口全绿，下单→支付→退款串起来就崩。串联用例必须有，见 [[接口串联与依赖参数提取传递]]。

## 面试怎么答

**Q：接口测试你会设计哪些维度的用例？**

A：我按九个维度过：一是正向功能，只传必填、必填加可选、多组合法组合；二是参数校验，必填缺失、类型错误、超长、非法枚举、特殊字符；三是边界值，最小、最小减一、最大、最大加一，还有 0、空、null；四是业务规则，状态机流转、库存不足、优惠互斥这些；五是鉴权与权限，包括未登录、token 过期，以及水平越权和垂直越权；六是幂等与并发，重复提交和并发扣减；七是异常容错，上游超时、依赖挂掉；八是数据一致性，响应和数据库、缓存的比对；九是非功能，响应时间和敏感信息泄漏。前三维是输入层面，四到六是逻辑层面，七到九是系统层面。**实际项目里高价值缺陷主要集中在四到六**，只做前三维的自动化价值不大。

**Q：接口测试和 UI 测试的用例设计有什么不同？**

A：最大的不同是接口测试能绕过前端校验，直接打后端。前端限制了输入长度和类型，UI 上根本构造不出「负数金额」「超长字符串」这类输入，但接口可以，所以**后端自己有没有做校验**是接口层独有的测试点。更典型的是垂直越权：前端不给普通用户显示管理员按钮，UI 测试永远发现不了，但接口层直接调管理员接口就能测出来。反过来接口测不到渲染和交互，两层是互补而不是替代关系。

**Q：一个「创建订单」接口，你能想到多少条用例？**

A：粗算下来三四十条。正向 2～3 条；参数校验按字段数乘以校验类型，三个字段大概 12 条；边界值光 quantity 一个字段就有 0、1、99、100、-1、int 溢出 6 条；业务规则看状态机，库存不足、商品下架、优惠券不可用、超出限购至少 4 条；鉴权 4 条；幂等和并发 2 条；再加数据一致性校验和敏感信息扫描。这里面参数校验和边界值用 pytest 参数化批量生成，代码量并不大，真正花时间的是业务规则那部分——需要跟产品和开发确认状态机和边界规则，这也是最容易发现需求本身有漏洞的地方。
